Terraform

Declarative config for everything outside Docker — Cloudflare zones, Access apps, tunnel ingress, UniFi LAN DNS, and the GitHub webhook that drives push-to-deploy. Single TF root at cloudflare/, state in MinIO, runner is the ./tf wrapper.

Read the provider docs before editing Schemas drift between provider minor versions and our HCL has to match. The registry's resource pages are the source of truth — not Stack Overflow, blog posts, or older copies of this doc. Direct links in cloudflare/README.md.

State backend — MinIO

Terraform state lives in MinIO at s3://terraform-state/cloudflare.tfstate. The bucket has versioning enabled, so an accidental tf destroy leaves the previous state version recoverable from MinIO's web console at minio.pod.haus.

MinIO runs as a Komodo-managed single-node stack on bilby (minio/compose.yaml, data at /var/lib/minio, API on loopback 127.0.0.1:9000 + console via the tunnel). The S3 backend uses native lockfile-in-S3 (provider feature use_lockfile = true) — no DynamoDB sidecar needed; concurrent tf apply attempts block on a .tflock object with S3 conditional-put semantics. Verified during the foundation smoke test.

Backrest covers the bucket via the minio plan (backup/bilby/config.json.tmpl) — daily snapshot of /var/lib/minio, which the nightly rclone hook ships to OneDrive. Restore drill steps are in disaster recovery.

The tf runner

./tf at the repo root is a thin bash wrapper around docker run hashicorp/terraform:latest. It attaches the container to dockernet so the S3 backend at http://minio:9000 is reachable, mounts the current working directory at /workspace, and forwards the environment variables every provider needs.

Credentials are resolved at run time from 1Password via op run reading cloudflare/.env: 

cd cloudflare
op run --env-file=.env -- ../tf plan
op run --env-file=.env -- ../tf apply

.env contains only op:// references — nothing sensitive is on disk. See cloudflare/.env.example for the full list.

Per-service module

Every tunnel-routed pod.haus hostname is exposed via one module "<name>" block in cloudflare/services_pod_haus.tf. The module (cloudflare/modules/pod_haus_service/) owns three resources for one hostname:

  • A cloudflare_dns_record CNAME pointing at the tunnel target, proxied through Cloudflare.
  • A cloudflare_zero_trust_access_application scoped to that one hostname, with the locked-by-default policy chain attached.
  • A structured ingress_rule output that cloudflare/tunnel.tf aggregates into the single cloudflare_zero_trust_tunnel_cloudflared_config resource.

Default policy chain is Homelab service-token bypass at precedence 1, Family allow at precedence 2. Service-token-bearing requests skip Access entirely (programmatic clients); browser users land on the Cloudflare Access login and are gated by the Family group. Override with the access_policy_ids input for special cases — Syncthing (Nathan-only), Paperless (Paperless-iOS service token first), UniFi (single Bypass-everyone for UniFi's own login).

Adding a new service

module "myservice" {
  source = "./modules/pod_haus_service"

  account_id               = local.pod_haus_service_defaults.account_id
  zone_id                  = local.pod_haus_service_defaults.zone_id
  tunnel_target            = local.pod_haus_service_defaults.tunnel_target
  default_bypass_policy_id = local.pod_haus_service_defaults.default_bypass_policy_id
  default_allow_policy_id  = local.pod_haus_service_defaults.default_allow_policy_id

  hostname = "myservice"
  backend  = "http://myservice:8080"
}

Then add module.myservice.ingress_rule to the pod_haus_module_ingress list in tunnel.tf, op run --env-file=.env -- ../tf apply from cloudflare/, done. cloudflared picks up the new ingress rule from CF's API automatically on its next reconnect (no container restart).

Module-output type quirk Passing a module-output struct directly into a typed provider list confuses the Cloudflare provider's schema validator (you'll see "config.ingress[0].service required"). Wrap each entry in a for r in ... : { hostname = r.hostname, service = r.service, ... } comprehension — the explicit field-by-field reshape unifies the type cleanly. See tunnel.tf for the pattern.

Day-to-day workflow

  1. Read the provider docs for the resource you're about to touch. Schemas vary between minor versions.
  2. Edit the relevant cloudflare/*.tf file.
  3. cd cloudflare && op run --env-file=.env -- ../tf plan. Read the diff line-by-line; provider v5 sometimes wants in-place updates that look surprising at first glance (default-value normalisation, deprecated-attribute flips, etc.).
  4. op run --env-file=.env -- ../tf apply when you're happy.
  5. For service exposure changes, smoke-test from the host with curl -sI https://<hostname>.pod.haus. A 302 redirect to podhaus.cloudflareaccess.com means the new Access app is gating; a 2xx response with the Homelab service-token headers means the bypass works.

Disaster recovery

After a bilby rebuild, before any tf apply runs, the terraform-state bucket has to exist in MinIO with the current state objects. Order:

  1. Bring MinIO up via Komodo (./komodo-sync + deploy).
  2. Restore /var/lib/minio from the most recent Backrest snapshot via the Backrest UI. The bucket + objects come back intact.
  3. cd cloudflare && op run --env-file=.env -- ../tf init — TF finds the restored state.
  4. ../tf plan — should show zero drift if the rebuild matched the last-applied state.
