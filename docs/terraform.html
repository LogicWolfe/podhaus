Terraform

Declarative config for the public edge, DNS, identity integrations, cloud hosts, MinIO IAM, and the GitHub webhook that drives push-to-deploy. Single TF root at terraform/, state in MinIO via the public storage.pod.haus, run with stock terraform from any machine — no wrapper.

Read the provider docs before editing Schemas drift between provider minor versions and our HCL has to match. The registry's resource pages are the source of truth — not Stack Overflow, blog posts, or older copies of this doc. Direct links in each provider's required_providers block in terraform/backend.tf.

State backend — MinIO

Terraform state lives in MinIO at s3://terraform-state/podhaus.tfstate. The bucket has versioning enabled, so an accidental terraform destroy leaves the previous state version recoverable from MinIO's web console at minio.pod.haus. Terraform reaches the backend over the public https://storage.pod.haus (Numbat rathole → Caddy → MinIO; see the runner section for why it is DNS-only).

MinIO runs as a Komodo-managed single-node stack on bilby (minio/compose.yaml, data at /var/lib/minio, API on loopback 127.0.0.1:9000 + console via the tunnel). The S3 backend uses native lockfile-in-S3 (provider feature use_lockfile = true) — no DynamoDB sidecar needed; concurrent terraform apply attempts block on a .tflock object with S3 conditional-put semantics. Verified during the foundation smoke test.

Backrest covers the bucket via the minio plan (backup/bilby/config.json.tmpl) — daily snapshot of /var/lib/minio, which the nightly rclone hook ships to OneDrive. Restore drill steps are in disaster recovery.

The same MinIO provider has a pouch alias for the separate instance at https://pouch.pod.haus. Terraform generates its root credential in the standard-field Pouch MinIO Root 1Password login, then owns the private sky-backups bucket, scoped IAM service account, and the ready-to-use Sky Backups credential handoff. The endpoint still satisfies the from-any-machine rule: remote Terraform traffic traverses Numbat and LAN traffic reaches bilby's Caddy through split-horizon DNS.

Running Terraform (stock, from any machine)

There is no wrapper script. Run stock terraform directly: 

cd terraform
terraform init   # one-time per machine
terraform plan
terraform apply

Hard requirement: this works from any machine — clone podhaus + have the chezmoi hook and local Homelab service-account token ⇒ terraform runs. When a fish shell enters the podhaus tree, ~/.config/fish/conf.d/podhaus-tf.fish reads the token, runs op inject against its 1Password references, and exports the standard provider, backend, and TF_VAR_* variables. The hook unsets them when the shell leaves the tree. Stock Terraform therefore needs no wrapper or credential flags. Leave and re-enter the tree, or start a new shell inside it, after rotating a credential. The .terraform.lock.hcl is not committed; each machine self-locks within the ~> version constraints (no cross-platform hash drift, zero maintenance).

Tailscale policy, DNS, and auth keys live in this root terraform/tailscale.tf owns the whole imported tailnet ACL, DNS, and the rotating tag:podnet and tag:recovery auth keys via the tailscale/tailscale provider, drives an 80-day rotation via a time_rotating resource, and writes the key value back to the existing op://Homelab/Tailscale Auth Key 1P item via a terraform_data + local-exec provisioner invoking op item edit. The recovery key is a normal Terraform-managed 1Password login consumed only by host bootstraps. Provisioner is used for podnet because the 1P item is category API_CREDENTIAL, which the 1Password TF provider's onepassword_item resource does not manage. The key value is passed via env var, not the command line, so it never surfaces in TF's command-echo.
Credential split is intentional The PWD hook is authoritative for Terraform backend and provider credentials. The S3 backend must authenticate before Terraform can evaluate provider data sources. Existing Homelab provider items also use custom root fields with random IDs, so restructuring them would ripple to the hook's 1Password references and komodo-op variable names. The 1Password/onepassword provider remains for credentials it can read or manage cleanly, including Pocket ID, Pouch MinIO, Forgejo, and the Sky backup accounts.

The S3 state backend is the public https://storage.pod.haus — MinIO behind its own Caddy + Let's Encrypt wildcard, not Cloudflare-proxied. Cloudflare's HTTP proxy rewrites the SigV4-signed Accept-Encoding header and breaks aws-sdk-go (SignatureDoesNotMatch); its single-level Universal SSL also can't cover Publii's virtual-host buckets. For LAN clients, traffic reaches Caddy directly via the UniFi split-horizon DNS. For genuine external clients (Publii on a laptop, remote terraform), traffic arrives via the Numbat BinaryLane rathole relay: storage.pod.haus A → Numbat's Terraform-derived relay address → rathole reverse tunnel (bilby dials out, noise+token) → bilby Caddy → MinIO. The UDM Pro SE binds WAN:443 itself, so direct port-forward is a dead path — see Numbat and networking for the relay architecture. pouch.pod.haus reuses the same raw port 443 relay and Caddy, then proxies to kangaroo's MinIO over the LAN. The UniFi provider talks to https://unifi.pod.haus (not a LAN IP). Off-LAN that reaches Numbat; UniFi split DNS sends LAN callers through bilby Caddy, preserving the same valid certificate and from-anywhere provider contract.

Protected-service module

Each protected *.pod.haus service keeps one module block in terraform/services_pod_haus.tf. The module still owns its Cloudflare Tunnel ingress and Access application for rollback. When edge_ipv4 is set, its active DNS record is instead a DNS-only A record to Numbat.

Adding a protected service therefore has three parts: add the module block with Numbat's application address, add the route to pomerium/config.yaml, and add the matching private-origin host in caddy/Caddyfile. Run terraform apply for DNS and push the stack configuration through the normal Komodo procedure. Do not remove the module's Tunnel or Access resources until the retained rollback edge is deliberately retired.

Public site cache

terraform/cache.tf owns the host-scoped cache rules, Tiered Caching, Smart topology, and global shared-certificate Authenticated Origin Pulls for the three public sites. The rules use bypass_by_default, so a response is cached only when its origin sends an explicit CDN-Cache-Control policy. Route classes, tags, and deploy-time invalidation remain with each site stack. See Public site caching.

Day-to-day workflow

  1. Read the provider docs for the resource you're about to touch. Schemas vary between minor versions.
  2. Edit the relevant terraform/*.tf file.
  3. cd terraform && terraform plan. Read the diff line-by-line; provider v5 sometimes wants in-place updates that look surprising at first glance (default-value normalisation, deprecated-attribute flips, etc.).
  4. terraform apply when you're happy.
  5. For service exposure changes, smoke-test from the host with curl -sI https://<hostname>.pod.haus. A 302 redirect to podhaus.cloudflareaccess.com means the new Access app is gating; a 2xx response with the Homelab service-token headers means the bypass works.

Disaster recovery

After a bilby rebuild, before any tf apply runs, the terraform-state bucket has to exist in MinIO with the current state objects. Order:

  1. Bring MinIO up via Komodo (./komodo-sync + deploy).
  2. Restore /var/lib/minio from the most recent Backrest snapshot via the Backrest UI. The bucket + objects come back intact.
  3. cd terraform && terraform init — TF finds the restored state.
  4. terraform plan — should show zero drift if the rebuild matched the last-applied state.
