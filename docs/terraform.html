Terraform

Declarative config for the public edge, DNS, identity integrations, cloud hosts, RustFS IAM, and the GitHub Actions secret CI uses to start push-to-deploy. Single TF root at terraform/, state in RustFS via the public storage.pod.haus, run with stock terraform from any machine — no wrapper.

Read the provider docs before editing

Schemas drift between provider minor versions and our HCL has to match. The registry's resource pages are the source of truth — not Stack Overflow, blog posts, or older copies of this doc. Direct links in each provider's required_providers block in terraform/backend.tf.

State backend — RustFS

Terraform state lives in RustFS at s3://terraform-state/podhaus.tfstate. The bucket has versioning enabled, so an accidental terraform destroy leaves the previous state version recoverable from the RustFS web console at rustfs.pod.haus. Terraform reaches the backend over the public https://storage.pod.haus (Numbat wstunnel → Caddy → RustFS; see the runner section for why it is DNS-only).

RustFS runs as a Komodo-managed single-node stack on bandicoot (rustfs/compose.yaml, data at /var/lib/rustfs, API, console, and SFTP on LAN ports 9000, 9001, and 8022). The S3 backend uses native lockfile-in-S3 (provider feature use_lockfile = true) — no DynamoDB sidecar needed; concurrent terraform apply attempts block on a .tflock object with S3 conditional-put semantics.

Backrest covers the data root via the rustfs plan on bandicoot. Bilby copies every Bandicoot repository into its existing restic repository and its existing OneDrive mirror. Restore drill steps are in disaster recovery.

The hashicorp/aws provider, configured only for the RustFS S3 endpoints, owns the six buckets, three versioning settings, and three public-read policies. The native weinmann-emt/rustfs provider owns the twenty RustFS IAM resources. Both have a pouch alias for the separate instance at https://pouch.pod.haus. Terraform generates its root credential in the standard-field Pouch RustFS Root 1Password login, then owns the private sky-backups bucket, scoped IAM service account, and the ready-to-use Sky Backups credential handoff. The endpoint still satisfies the from-any-machine rule: remote Terraform traffic traverses Numbat and LAN traffic reaches bilby's Caddy through split-horizon DNS.

Restic and the native RustFS provider retain their upstream-maintained MinIO S3 library dependencies. Podhaus operates no MinIO server, command-line client or Terraform provider. The moved declarations preserve credential and SFTP-key identity across Terraform address changes; the existing pouch-minio-root username is an unchanged credential value.

Running Terraform (stock, from any machine)

There is no shell hook or Terraform wrapper. op-vault selects the machine's Podhaus service account and op run supplies credentials only to Terraform's process tree: 

op-vault dev -- op run --env-file=terraform/terraform.env.op -- \
  terraform -chdir=terraform init   # one-time per machine
op-vault dev -- op run --env-file=terraform/terraform.env.op -- \
  terraform -chdir=terraform plan
op-vault dev -- op run --env-file=terraform/terraform.env.op -- \
  terraform -chdir=terraform apply

Hard requirement: this works from any Podhaus operator. Clone Podhaus, enrol that machine's scoped dev service account with op-vault mint dev, and run the command above. The committed terraform/terraform.env.op contains only op:// references. Provider, backend, and TF_VAR_* values exist only in the child process. Bash and fish use the same command, and leaving the repository cannot leak an ambient credential environment. The .terraform.lock.hcl is not committed; each machine self-locks within the ~> version constraints (no cross-platform hash drift, zero maintenance).

Provider mirror

Providers the public registry can no longer serve install from LogicWolfe/terraform-providers on git.pod.haus instead. Chezmoi clones that repository on every Podhaus operator to ~/.local/share/terraform-providers, pulls it hourly, and its managed ~/.terraformrc sends only the listed providers to the clone's mirror/ directory as a filesystem mirror; every other provider still installs directly from the registry. The provider keeps its registry address, so state and configuration name it as before.

trozz/pocketid is the one mirrored provider. Its author moved the GitHub repository from Trozz/terraform-provider-pocketid to pocket-id/terraform-provider, releases included, and GitHub redirected the old name until a new fork was created there on 2026-11-10. The registry still downloads from the old name, so every version returns 404, while the signed releases are intact in the new repository. The registry cannot list the new repository as it stands, because registry providers must live in a repository named terraform-provider-<name>. Upstream issue pocket-id/terraform-provider#127 tracks the fix.

Retire the mirror when upstream lands one of the two fixes discussed there:

  • The fork at the old name is removed or renamed, so GitHub's redirect returns and trozz/pocketid installs from the registry again. Confirm that https://github.com/trozz/terraform-provider-pocketid/releases/download/v2.5.0/terraform-provider-pocketid_2.5.0_SHA256SUMS answers 200 rather than 404. Nothing in Podhaus changes; go straight to the clean-up below.
  • The repository is renamed to terraform-provider-pocketid and published under a new registry address, such as pocket-id/pocketid. Change the provider's source in terraform/backend.tf, run terraform state replace-provider registry.terraform.io/trozz/pocketid registry.terraform.io/<new address> once from any operator (the state is shared), then run terraform init on each operator and confirm the plan reports no changes.

Clean-up after either fix: in the dotfiles repository, return dot_terraformrc.tmpl's provider_installation block to a plain direct {} and remove the terraform-providers entries from .chezmoiexternal.toml and .chezmoiignore. In Podhaus, drop the "installed from the provider mirror" comment in terraform/backend.tf and this section. Remove the forgejo_repository.terraform_providers block's prevent_destroy and then the block itself; its archive_on_destroy archives the repository rather than deleting it.

To add a release, run ./mirror-release trozz/pocketid <version> pocket-id/terraform-provider in a checkout of the mirror repository and push. The script refuses a release whose checksum file lacks a valid signature from the key pinned in its keys/ directory, or whose archives do not match their checksums. A refusal after upstream changes its signing key needs the new public key, taken from the registry's signing_keys for the release, committed under keys/ once it is confirmed to belong to the provider's maintainers. Terraform reports mirrored packages as unauthenticated because a filesystem mirror carries no signature; that check happened when the release was mirrored. Raise the version pin only after operators have pulled the new release.

Tailscale policy, DNS, and auth keys live in this root

terraform/tailscale.tf owns the tailnet ACL, DNS, and the rotating tag:recovery auth key through the tailscale/tailscale provider. The key rotates every 80 days and is stored in a Terraform-managed 1Password login consumed only by tailscale-recovery-bootstrap. Recovery nodes expose local OpenSSH on TCP 22 only. They install no routes and receive no access to one another.

Credential split is intentional

The committed op run environment file is authoritative for Terraform backend and provider credentials. The S3 backend must authenticate before Terraform can evaluate provider data sources. Existing Homelab provider items also use custom root fields with random IDs, so restructuring them would ripple to the environment file's 1Password references and komodo-op variable names. The 1Password/onepassword provider remains for credentials it can read or manage cleanly, including Pocket ID, Pouch RustFS, Forgejo, and the Sky backup accounts. Before running this root, unset RUSTFS_ENDPOINT, RUSTFS_USER, and RUSTFS_SECRET: the native provider gives those environment variables precedence over both configured RustFS endpoints, including the Pouch alias.

The S3 state backend is the public https://storage.pod.haus — RustFS behind its own Caddy + Let's Encrypt wildcard, not Cloudflare-proxied. Cloudflare's HTTP proxy rewrites the SigV4-signed Accept-Encoding header and breaks aws-sdk-go (SignatureDoesNotMatch); its single-level Universal SSL also can't cover Publii's virtual-host buckets. For LAN clients, traffic reaches Caddy directly via the UniFi split-horizon DNS. For genuine external clients (Publii on a laptop, remote terraform), traffic arrives via the Numbat BinaryLane wstunnel relay: storage.pod.haus A → Numbat's Terraform-derived relay address → wstunnel reverse tunnel (bilby dials out, authenticated by its relay certificate) → bilby Caddy → RustFS on bandicoot. The UDM Pro SE binds WAN:443 itself, so direct port-forward is a dead path — see Numbat and networking for the relay architecture. pouch.pod.haus reuses the same raw port 443 relay and Caddy, then proxies to kangaroo's RustFS over the LAN. The UniFi provider talks to https://unifi.pod.haus (not a LAN IP). Off-LAN that reaches Numbat; UniFi split DNS sends LAN callers through bilby Caddy, preserving the same valid certificate and from-anywhere provider contract.

Protected-service DNS

terraform/services_pod_haus.tf maps each protected *.pod.haus name to Numbat's application or relay address and creates DNS-only A records. Pomerium and Caddy own authentication and route policy beside the active edge stack.

Adding a protected service has three parts: add its DNS map entry, add the route to pomerium/config.yaml, and add the matching private-origin host in caddy/Caddyfile. Run terraform apply for DNS and push the stack configuration through the normal Komodo procedure.

Public site cache

terraform/cache.tf owns the host-scoped cache rules, Tiered Caching, Smart topology, and global shared-certificate Authenticated Origin Pulls for the three public sites. The rules use bypass_by_default, so a response is cached only when its origin sends an explicit CDN-Cache-Control policy. Route classes, tags, and deploy-time invalidation remain with each site stack. See Public site caching.

Day-to-day workflow

  1. Read the provider docs for the resource you're about to touch. Schemas vary between minor versions.
  2. Edit the relevant terraform/*.tf file.
  3. cd terraform && terraform plan. Read the diff line-by-line; provider v5 sometimes wants in-place updates that look surprising at first glance (default-value normalisation, deprecated-attribute flips, etc.).
  4. terraform apply when you're happy.
  5. For protected service exposure changes, smoke-test from the host with curl -sI https://<hostname>.pod.haus. An unauthenticated request should redirect to authenticate.pod.haus; verify the backend through its internal Gatus check rather than treating the redirect as application health.

Disaster recovery

Terraform state is on Bandicoot's RustFS, so a Bilby rebuild does not restore or deploy that stack. If Bandicoot storage is lost, follow the tagged RustFS restore procedure in Disaster recovery before running Terraform. Then:

  1. cd terraform && terraform init — TF finds the restored state.
  2. terraform plan — inspect and resolve any drift before applying.
