Terraform

Declarative config for everything outside Docker — Cloudflare zones, Access apps, tunnel ingress, UniFi LAN DNS, and the GitHub webhook that drives push-to-deploy. Single TF root at terraform/, state in MinIO via the public storage.pod.haus, run with stock terraform from any machine — no wrapper.

Read the provider docs before editing Schemas drift between provider minor versions and our HCL has to match. The registry's resource pages are the source of truth — not Stack Overflow, blog posts, or older copies of this doc. Direct links in each provider's required_providers block in terraform/backend.tf.

State backend — MinIO

Terraform state lives in MinIO at s3://terraform-state/podhaus.tfstate. The bucket has versioning enabled, so an accidental terraform destroy leaves the previous state version recoverable from MinIO's web console at minio.pod.haus. Terraform reaches the backend over the public https://storage.pod.haus (Caddy → MinIO; see the runner section for why not Cloudflare-proxied).

MinIO runs as a Komodo-managed single-node stack on bilby (minio/compose.yaml, data at /var/lib/minio, API on loopback 127.0.0.1:9000 + console via the tunnel). The S3 backend uses native lockfile-in-S3 (provider feature use_lockfile = true) — no DynamoDB sidecar needed; concurrent terraform apply attempts block on a .tflock object with S3 conditional-put semantics. Verified during the foundation smoke test.

Backrest covers the bucket via the minio plan (backup/bilby/config.json.tmpl) — daily snapshot of /var/lib/minio, which the nightly rclone hook ships to OneDrive. Restore drill steps are in disaster recovery.

Running Terraform (stock, from any machine)

There is no wrapper script (the old ./tf docker runner was decommissioned). Run stock terraform directly: 

cd terraform
terraform init   # one-time per machine
terraform plan
terraform apply

Hard requirement: this works from any machine — clone podhaus + have chezmoi-provisioned creds ⇒ terraform runs. The provider/backend credentials are exported into every fish shell by the chezmoi-rendered ~/.config/fish/conf.d/podhaus-tf.fish (resolved from 1Password at chezmoi apply time), so they are simply present in the environment — nothing to invoke. The .terraform.lock.hcl is not committed; each machine self-locks within the ~> version constraints (no cross-platform hash drift, zero maintenance).

Tailscale auth-key rotation lives in this root terraform/tailscale.tf mints the tag:podnet tailnet auth key via the tailscale/tailscale provider, drives an 80-day rotation via a time_rotating resource, and writes the key value back to the existing op://Homelab/Tailscale Auth Key 1P item via a terraform_data + local-exec provisioner invoking op item edit. Provisioner is used here because the 1P item is category API_CREDENTIAL, which the 1Password TF provider's onepassword_item resource does not manage. The key value is passed via env var, not the command line, so it never surfaces in TF's command-echo.
onepassword TF provider declared, no data sources yet The consolidated root declares the 1Password/onepassword provider so future items can plug into data-source-driven credential resolution. None of the current chezmoi-rendered TF provider creds (CLOUDFLARE_API_TOKEN, UNIFI_API_KEY, GITHUB_TOKEN, DIGITALOCEAN_TOKEN, TAILSCALE_OAUTH_*, TF_VAR_minio_user/password, TF_VAR_komodo_webhook_secret) actually use it — the provider's v3.x data source only exposes root-level fields whose field ID matches a fixed switch (username, password, credential, …), and all the relevant Homelab items use random UUIDs as field IDs. Unblocking the swap means restructuring those 1P items (move each secret into a section, or recreate with a known field ID) which ripples to op read paths and komodo-op variable names. Deferred; the PWD-scoped env vars work fine.

The S3 state backend is the public https://storage.pod.haus — MinIO behind its own Caddy + Let's Encrypt wildcard, not Cloudflare-proxied. Cloudflare's HTTP proxy rewrites the SigV4-signed Accept-Encoding header and breaks aws-sdk-go (SignatureDoesNotMatch); its single-level Universal SSL also can't cover Publii's virtual-host buckets. For LAN clients, traffic reaches Caddy directly via the UniFi split-horizon DNS. For genuine external clients (Publii on a laptop, remote terraform), traffic arrives via the kookaburra DigitalOcean rathole relay: storage.pod.haus A → 170.64.241.136 (kookaburra reserved IP) → rathole reverse tunnel (bilby dials out, noise+token) → bilby Caddy → MinIO. The UDM Pro SE binds WAN:443 itself, so direct port-forward is a dead path — see kookaburra and networking for the relay architecture. The UniFi provider talks to https://unifi.pod.haus (not a LAN IP), so nothing here is host- or LAN-pinned.

Per-service module

Every tunnel-routed pod.haus hostname is exposed via one module "<name>" block in terraform/services_pod_haus.tf. The module (terraform/modules/pod_haus_service/) owns three resources for one hostname:

  • A cloudflare_dns_record CNAME pointing at the tunnel target, proxied through Cloudflare.
  • A cloudflare_zero_trust_access_application scoped to that one hostname, with the locked-by-default policy chain attached.
  • A structured ingress_rule output that terraform/tunnel.tf aggregates into the single cloudflare_zero_trust_tunnel_cloudflared_config resource.

Default policy chain is Homelab service-token bypass at precedence 1, Family allow at precedence 2. Service-token-bearing requests skip Access entirely (programmatic clients); browser users land on the Cloudflare Access login and are gated by the Family group. Override with the access_policy_ids input for special cases — Syncthing (Nathan-only), Paperless (Paperless-iOS service token first), UniFi (single Bypass-everyone for UniFi's own login).

Adding a new service

module "myservice" {
  source = "./modules/pod_haus_service"

  account_id               = local.pod_haus_service_defaults.account_id
  zone_id                  = local.pod_haus_service_defaults.zone_id
  tunnel_target            = local.pod_haus_service_defaults.tunnel_target
  default_bypass_policy_id = local.pod_haus_service_defaults.default_bypass_policy_id
  default_allow_policy_id  = local.pod_haus_service_defaults.default_allow_policy_id

  hostname = "myservice"
  backend  = "http://myservice:8080"
}

Then add module.myservice.ingress_rule to the pod_haus_module_ingress list in tunnel.tf, terraform apply from terraform/, done. cloudflared picks up the new ingress rule from CF's API automatically on its next reconnect (no container restart).

Module-output type quirk Passing a module-output struct directly into a typed provider list confuses the Cloudflare provider's schema validator (you'll see "config.ingress[0].service required"). Wrap each entry in a for r in ... : { hostname = r.hostname, service = r.service, ... } comprehension — the explicit field-by-field reshape unifies the type cleanly. See tunnel.tf for the pattern.

Day-to-day workflow

  1. Read the provider docs for the resource you're about to touch. Schemas vary between minor versions.
  2. Edit the relevant terraform/*.tf file.
  3. cd terraform && terraform plan. Read the diff line-by-line; provider v5 sometimes wants in-place updates that look surprising at first glance (default-value normalisation, deprecated-attribute flips, etc.).
  4. terraform apply when you're happy.
  5. For service exposure changes, smoke-test from the host with curl -sI https://<hostname>.pod.haus. A 302 redirect to podhaus.cloudflareaccess.com means the new Access app is gating; a 2xx response with the Homelab service-token headers means the bypass works.

Disaster recovery

After a bilby rebuild, before any tf apply runs, the terraform-state bucket has to exist in MinIO with the current state objects. Order:

  1. Bring MinIO up via Komodo (./komodo-sync + deploy).
  2. Restore /var/lib/minio from the most recent Backrest snapshot via the Backrest UI. The bucket + objects come back intact.
  3. cd terraform && terraform init — TF finds the restored state.
  4. terraform plan — should show zero drift if the rebuild matched the last-applied state.
