Local model service on fractal

Goal. fractal's RTX 5090 serves a local coding model to Nathan, on the machine and away from it, and to friends he lets in. It gets out of the way within seconds whenever a game starts, comes back unattended when the game ends, and records enough to answer what happened to any request and how well each handoff to a game went.

What this costs. One new stack on fractal (two long-running containers and a one-shot download job), one small service we write and own (the watcher, about 300 lines of Python plus tests), one protected hostname, one Ansible change to let containers use the GPU, and 10 GB more of the host's memory given to WSL. Nothing we write sits between a client and the model: the model server is stock llama.cpp, configured. Electricity is about 37 cents for a heavy day of agent coding.

What would stop it. Three things, each checked before the rest is built: the chosen server settings, run at full size under their real memory cap, do not behave as the smaller measurements predict; containers on this WSL guest cannot use the GPU or run more than 10% slower than a process on the host; or the game-detection thresholds do not generalise beyond the one game they were measured on. Each has a named fallback under Order of work and kill criteria.

Build progress, 3 October 2026

The service is live on fractal. Stack fractal-llm runs from llm/, the watcher loads and unloads the model unattended, the loopback address http://127.0.0.1:8085 serves both request formats, and llm.pod.haus refuses anyone who is not signed in. What is left needs Nathan in person: approving a device sign-in on a phone, launching a game, restarting WSL, and making the two dashboards. The runbook is docs/runbooks/local-llm.md.

Where the build departs from this plan

  • fractal joined the early out-of-memory role, which settles the decision that was open under Scope.
  • The watcher is about 960 lines of Python, not 300. The extra is the handling the reviews asked for: loads started by something else, a model that dies while serving, slot reads that go unanswered during a save, retries and giving up.
  • The server logs one level above its default. The default level omits prompt size, tokens kept, forced re-reads and conversation saves. The higher level adds lines that can quote a request, so Alloy stores a server log entry as printed only when it matches a known shape that carries no text, and reduces every other entry to its heading and "text removed".
  • A load is not abandoned when a game appears. The load's own GPU activity cannot be told from a game's. A game that starts during a load shares the GPU until the load ends (33 to 64 s as measured live), then the normal yield happens. The Yield button still cancels a load.
  • A button hold is not kept across a watcher restart.
  • Callers cannot load the model. The router honours a request-level autoload switch that overrides its no-autoload setting, so Caddy drops the query string and forces a JSON content type on the model paths, and the watcher unloads any load it did not start while it is keeping the model away. Caddy also removes the X-Conversation-Id header, which let one caller cancel another's reply.
  • The watcher has no autoheal label. Its unhealthy states are ones a restart would hide. It ends its own process when GPU sampling stalls, and Docker restarts it.
  • The model file's cache is dropped after every load and unload, not only at a yield. It frees about 8 GiB of guest memory and made saves faster.
  • The load timeout is 300 s. A reload from disk took 28 to 64 s live, but the first load after the download took 181 s and loads of 104 to 176 s were seen in the first hour after a WSL restart.
  • The VRAM alert level is 31,000 MiB of whole-GPU use, and means the card is full, not that a spill happened: the one spilled run read 31,126 MiB and a larger pool that did not spill read 31,048.
  • While the model is away a client gets HTTP 400 "model is not loaded" from the server. Whether Claude Code and pi show that clearly was not tested; Caddy answering for the model paths remains the fallback.
  • Join between a request's Caddy line and its server detail is by finish time, since the server prints no request id.

Open

  • The model process dies with "CUDA error: unknown error" on long prompt reads. Seen three times on 2 and 3 October, with the GPU at 520 to 577 W: twice on the trial build and once in the stock image run by hand. A 70 s read at up to 579 W on the live stack did not fault. The watcher reloads the model, but the request in flight fails and every saved conversation is lost. The cause is not known. Windows Event Viewer (System log, source nvlddmkm) at those times is the first thing to read, and a lower GPU power limit set from Windows is the first thing to try.
  • Slow saves and loads soon after a WSL restart, and possibly after a game hands memory back. Time a large save soon after a game ends.
  • Sign-in round trip, the signed-in remote checks, the first real game, the guest restart and the dashboards, as marked above.
  • A change to llm/tests or llm/client redeploys the stack and reloads the model, because the content hash covers the whole stack directory.

Scope

In scope: the model server, the watcher, ingress and sign-in, records and alerts, and a command that fetches the sign-in token. Out of scope: how Claude Code, pi or Fenwick are configured to use the service. Those are Nathan's to set up and tune. What was measured about them is kept under Clients so it is to hand later.

Decided during the build: fractal joined the early out-of-memory role the other development hosts run (bilby, bandicoot and voltaire), in the same playbook run that enabled the GPU in containers. It steps in when available memory and free swap are both down to 10%. chezmoi sets no kill-order scores on fractal, so the role follows the kernel's ranking there, and the model server's kill-first mark puts it at the top. The rules in Memory while building and testing still apply.

Settled and built into the rest of this plan: no gateway of our own; idle conversations saved to memory by the server itself; a 204,800-token pool with four slots and the drafter; memory sized for a main conversation of up to 150,000 tokens; WSL raised from 15 GB to 25 GB; 60 seconds of quiet before the model returns after a game, with any Windows use of the GPU counting, video included; coding sessions dropped freely for a game; sign-in by device link through Pocket ID and Pomerium, built and proven during the build, open to Pocket ID's family and friends groups; the server's known faults are worked around, not reported to llama.cpp.

Components and how a request reaches the model

Two terms first. The model server is llama.cpp's own server running in its router mode, where it holds no model until told to load one and frees the VRAM when told to unload. The watcher is the one service we write. It stands beside the request path, never in it: it watches the GPU, tells the model server to load or unload, serves the control page, and writes the records that the model server does not write itself.

One request, from sign-in to response

  1. A remote client calls https://llm.pod.haus/v1/... carrying its Pocket ID sign-in token as its API key. Pomerium checks the token and that the caller is in Pocket ID's family or friends group, then forwards through fractal's existing outbound tunnel to Caddy, adding the caller's email as a header. A client on fractal skips those hops and calls Caddy's loopback listener.
  2. Caddy forwards the request unchanged to the model server and writes one access-log line when it ends: caller, client program, Claude Code's session identifier if present, path, status and duration.
  3. The model server picks a slot, reuses whatever part of the prompt that slot already holds, reads the rest, and streams the answer. Its log records the token counts, the timings and why it chose that slot.
  4. If a game holds the GPU, no model is loaded and the model server itself answers with an error. What that error looks like to pi and Claude Code is one of the unproven assumptions.

No translation between request formats happens anywhere, because the model server speaks both natively.

What is fast and what is slow

How this service feels comes down to one thing: whether the conversation being continued is still held by the server. A conversation is warm while the server holds its working state, and its next turn starts in under a second. It is cold when nothing holds it and the whole conversation has to be read again, at 1,500 to 3,900 tokens a second. The bar used throughout: under a second is fine, 45 s is unusable, 120 s is a total failure.

Measured on fractal. A cold read crosses 45 s at about 106,000 tokens and 120 s at about 190,000, so a large conversation must never go cold in ordinary use.

Several conversations at once

A slot holds one conversation's working state in VRAM; there are four. All slots draw on one shared pool of 204,800 tokens. Left to itself with idle conversations kept in VRAM, the server makes room badly: a newcomer takes over an idle conversation's slot and the idle one goes cold (67 s measured for a 97,000-token conversation).

So the server is set to do what it does by default: whenever a request starts, it copies every idle conversation out of VRAM into the guest's memory, where it is a saved conversation, and copies it back when that conversation's next turn arrives. Saving a 100,000-token conversation takes about 2.5 s, paid by whichever request starts next; bringing it back takes about 1.1 s. Only conversations generating at the same moment occupy the pool. Up to 12 GiB of saved conversations are kept; when that is full, the oldest is discarded.

Times for a 150,000-token main conversation. Cases 1 and 2 were measured at 97,000 tokens (1.4 to 2.0 s extra on the main conversation) and scaled. Subagent working times are illustrative.

Agents that start many threads from one fixed opening

A chat agent whose every thread begins with the same system prompt and tools need not read that opening each time. The server can reuse it for a new thread whenever a rewind point sits at the end of the shared part. An ordinary first message leaves its rewind point just past that, so the next thread reads cold. One warm-up request, the opening followed by a one-character message and one token of output, puts the rewind point in the right place, and it then stays there from thread to thread. The warm-up is the client's job, since only the client knows its own opening, and so is not part of this build. Such a client also needs somewhere else to go while a game holds the GPU, so both belong to one small piece of client logic. Fenwick's chat is the case in view:

  1. While the local model answers, chat goes to it.
  2. When a request fails because no model is loaded, or does not start within a few seconds, that request and those after it go to Sonnet.
  3. When the local model answers again, the client sends one warm-up, then routes chat back. Nobody sees the cold read.
  4. If a reply ever shows the opening was not reused, which the server reports with every response, the client sends a warm-up in the background.

GPU handoff between the model and a game

To yield is to unload the model so a game has the whole GPU; to resume is to load it again. The watcher samples whole-GPU utilisation and the model server's slot report at least once a second. It counts a GPU sample only when no slot was busy at that sample or the one before, because during reading or generation the model's own load hides everything else. Any activity seen while the model is idle is Windows wanting the GPU, and Windows always wins. That is meant to include lighter uses than games: video playing in a browser is expected to cross the threshold, and yielding to it is the intended behaviour.

The button. A page at llm.pod.haus/control, served by the watcher and allowed for Nathan only, shows the current state with two buttons: Yield now, which also holds the model away for at least ten minutes so there is time to launch something, and Resume now. It works from the gaming PC's browser and from a phone. It is the answer to the watcher's one blind spot: a game launched while the model is busy is not seen until the next pause between requests.

Thresholds are configuration with evidence attached. The 3% line, the five-second window and the 60-second quiet period come from one session with one light game. Every handoff event therefore carries the raw samples from the 30 seconds before the decision, so the numbers can be corrected from real sessions without another trial.

Conversations do not survive a yield. Unloading ends the model process, and with it every slot and every saved conversation. The first turn after a game re-reads its conversation from nothing, which for a large one is the longest wait this service produces in ordinary use. That is accepted: a coding session may be dropped freely for a game and nothing is saved on its behalf. It is recorded as a slow start whose cause is a handoff. A client that cannot wait, such as a chat agent, switches to another model while the local one is away; see agents with a fixed opening.

A request's two records are matched by path and finish time. That is exact while only a few requests finish in any second, which is the expected load.

A slow start is a request whose prompt read took more than 20 s. The usage dashboard lists every one with its tokens read and reused, its slot, the server's stated reason, what else was running, and whether a handoff or a restart came just before. It is the measure of whether the simple design is good enough. The server names each cause in a warning of its own at its normal log level: a saved conversation too large for the memory set aside, the oldest saved conversation removed to make room, an idle slot purged because the pool was full, the pool exceeded with every slot busy, and a full re-read forced for want of a rewind point. The server's slot report does not say which conversation a slot holds or what is saved in memory, so those warnings are the only record of the saved conversations.

Logging rules

  • No prompt or response text is stored anywhere. The model server runs at the log level that prints counts and timings, not content. Caddy logs no request bodies, redacts the sign-in token, and keeps only the listed headers. Friends' conversations are theirs.
  • Both containers log to stdout and take the existing path: Docker logs, Alloy, ClickStack. Each gets one parsing module beside the existing ones, so levels and timestamps are normalised like every other service.
  • No traces. With nothing of ours in the request path there is nothing to emit a span; the two per-request records carry the same facts.
  • Alerts stay with Gatus and stay few: either container unhealthy, which includes a stalled watcher, a yield that does not release the GPU, and the model spilling out of VRAM (the watcher reports unhealthy when VRAM sits at the card's limit while Serving). Slow starts and failed requests are dashboard material, not pages.

Remote access

Remote use must work from a machine with no browser, and getting signed in must not take more than opening a link. The flow is the standard device sign-in, built from what already runs: Pocket ID issues the token and Pomerium checks it.

  1. A small token command, shipped with the service, asks Pocket ID to start a device sign-in and prints one link with the code already in it. On a machine with a browser it opens the link itself.
  2. The person opens the link on any device, a phone included, and approves with Pocket ID as for any other service.
  3. The command, which has been waiting on Pocket ID, receives the token, caches it and prints it. Nothing is pasted back.
  4. pi and Claude Code send the token as their API key, in the standard bearer header both already use. The route is set to treat a bearer token as a Pocket ID token, so Pomerium checks it and applies the route's policy: the caller must be in Pocket ID's family or friends group.
  5. Renewal is silent, using the refresh token Pocket ID issued, until the session ends.

Pocket ID at id.pod.haus advertises the device sign-in endpoint and grant. Pomerium's acceptance of an identity provider's token as a bearer key is documented for every provider since version 0.30 and can be set for one route. The round trip has not been run; it needs a client entry in Pocket ID and the route, and is the first thing the ingress step proves. Fallback: the client opens a tunnel to fractal over the existing Pomerium SSH sign-in, which already handles remote machines with a link. It covers Nathan's machines only, since it needs a registered SSH key.

Guest memory, and how the stated window follows from it

A saved conversation with two rewind points costs about 440 MiB plus 40.5 KiB per token, which matched seven measured sizes within 2%: 0.9 GiB at 12,000 tokens, 2.2 GiB at 45,000, 4.3 GiB at 100,000, 6.2 GiB at 150,000, 8.2 GiB at 200,000. The memory set aside has to hold the main conversation and everything saved after it. With 12 GiB, a 4.8 GiB burst and 0.8 GiB for a chat agent's opening, the main conversation can be 150,000 tokens. The pool does not bound the window; a larger pool only gives more room for conversations generating at the same moment, about 55,000 tokens beside a full main conversation at 204,800.

WSL memory. The host has 32 GB. The guest goes from 15 GB to 25 GB: 17 GiB for the model server, 6 to 7 GB for dev work, the rest for the kernel. That leaves Windows a guaranteed 7 GB, and games need the rest back whenever they start. Two kinds of memory have to be let go at a yield:

MemorySizeHow it is released
The model process: saved conversations and rewind pointsUp to 17 GiBFreed the moment the process ends at unload. The guest's kernel reports freed pages to Windows without help.
The model file held in the guest's file cacheUp to 19.7 GB, as much as fitsNot returned by itself. The watcher asks the guest to drop this one file's cache at each yield, which needs no special privilege (measured: the guest's file cache fell from 8.2 to 1.4 GiB). The next load then reads the file from disk: 25 s, against 23 s with the file cached.

Windows is assumed to take the memory back once the service has released it; no Windows-side test gates the build. Each yield event records guest memory before and after, so the release is visible in the handoff records. The limit lives in a Windows-side file Ansible cannot reach, so Nathan changes it by hand and it is recorded in the hosts page.

Memory while building and testing

The trial install's first build ran the guest out of memory. llama.cpp was compiling with 28 parallel jobs while the model file downloaded in the downloader's high-performance mode, on the 15 GB guest. A compiler asked for memory that was not there, the kernel killed the largest process (the downloader, holding 4.6 GB), and the working session was lost with it. The second attempt, six compile jobs and a plain download, finished.

Raising the guest to 25 GB does not remove the risk, for three reasons. Once the model server holds its 17 GiB, 6 to 7 GB is left for everything else, which is less than the trial build had. The processor has 32 threads, so a build tool left at its default starts 32 or more compilers. And fractal has no early out-of-memory protection: the kernel acts only when memory is gone, and every process carries the same kill priority, so it takes whatever is largest.

Order of work and kill criteria

Ordered by dependency. The first three items exist to fail early.

  1. Prove the chosen settings at full size. Nathan raises the WSL limit to 25 GB. Then, on the trial install under /opt/llm, run the server under its 17 GiB cap with the settings table above: a 150,000-token main conversation through a three-subagent burst, a second session, and a yield. This needs no new code. Kill criterion: if the main conversation is dropped in the ordinary one-session case, either the stated window comes down or the disk-saving fix is designed, argued from the measured failure, and put to Nathan before anything else is built.
  2. GPU inside a container on fractal. Ansible change, then the performance check. Kill criterion: if containers cannot use the GPU or run more than 10% slower than a process on the host, the model server becomes an Ansible-managed systemd unit on the host and the watcher reaches it across the Docker bridge. Everything else stands.
  3. Model server in router mode. Confirm that unloading through its API frees VRAM as quickly as stopping the process did, that the preset file accepts every chosen setting, that the stock image is as fast as the trial install's own build, and what it answers while no model is loaded. If the stock image is slower, the stack builds the image itself under the rules in Memory while building and testing.
  4. Ingress and sign-in. The Pocket ID client and the device sign-in round trip first, then DNS, the Pomerium route, the Caddy block and the token command. Kill criterion: if Pomerium will not accept the Pocket ID token on the route, remote use goes over the existing Pomerium SSH sign-in as a tunnel. Usable remotely at this point with no handoff behaviour.
  5. Watcher: handoff, control page, events. Kill criterion: if, across the first sessions with different games, the events show wrong calls that no threshold change fixes, detection moves to a small Windows-side watcher that knows which process is a game and calls the same control endpoint. The states, the button and the records stand.
  6. Telemetry and alerts. Alloy config, Gatus checks, two dashboards.
  7. Hand-over. The addresses, the token command and the client notes go into the runbook. Friends get in by being in Pocket ID's friends group; nothing in this stack names a person.
  8. Docs and teardown of the trial install.

Unproven assumptions

  • Docker on this WSL guest can hand the GPU to a container. The toolkit is not installed today.
  • The router's unload frees VRAM in about 2 s. The measurement stopped the whole process instead.
  • Utilisation can be sampled from inside a container, and faster than once a second.
  • What the model server answers while no model is loaded, and whether pi and Claude Code show that as a clear "in use, try later" or as a confusing failure. If it is confusing, Caddy can answer for the model's paths while the watcher reports Yielded.
  • The device sign-in works end to end with both tools: Pocket ID issues a token to a command-line client, that token carries the person's groups, Pomerium accepts it as a bearer key on this route and applies the friends policy to it, and renewal stays silent for about a month.
  • Streaming responses survive Pomerium, the tunnel and Caddy with long gaps before the first byte.
  • The model server's log at its normal level carries every field in the record table, and none of the prompt.
  • The thresholds hold for games other than the one measured.
  • The chosen settings at full size. The 17 GiB cap with 12 GiB for saved conversations has not been run; every measurement so far was under a 9 GiB cap. The 150,000-token window rests on the size formula and on two real three-subagent bursts; subagents that grow larger will push the main conversation out.
  • What happens after a pool overflow: whether Claude Code's retries settle or collide again.
  • That the server never restores the wrong conversation from memory. An open llama.cpp report describes this under concurrent load; it was not seen here, and not tested for.

Reporting the server's faults to llama.cppSeven faults were found and fixes in llama.cpp would remove most of the remaining failures at their source. Not pursued; the settings in this plan work around them.
A shared API key on a public routeWorks with no sign-in at all, but puts llama.cpp's own key check on the open internet and identifies nobody.
Keeping 128 rewind points, as one published setup recommendsEach costs about 150 MB plus 2 KB per token of host memory here, so 20 to 70 GB per slot.
An inference engine built for many usersSuch engines share identical prompt openings across conversations by design, which removes the slot problems. Whether one runs this model, in this compact form, with its drafter, inside 32 GiB is unknown. Worth its own trial if recorded use shows several simultaneous users.
Keep the trial install and add to itIt is a hand-built binary, a user systemd unit and shell functions outside every podhaus convention: no push-to-deploy, no log parsing, no recovery owner.
Stop and start the container to yieldA stopped container reads as a failure to Komodo and Gatus, and any deploy during a game would start it again. Unloading inside a running server keeps one honest health state.
Let the model server unload itself when idleAny forgotten agent session would reload the model mid-game, and a second owner of the load decision would fight the watcher.
Detect games from WindowsMore exact, and kept as the fallback. It needs a second component on a side of the machine podhaus does not manage and this guest is deliberately cut off from.
Trigger on VRAM or powerMeasured not to work. A light game added under 1 GiB of VRAM, and power rose on launch but stayed high after the game closed.
A different inference engine for the full 262K windowThe only route found is a community-patched build tested on bare Linux. Worth its own trial later; not part of this service.

Teardown of the trial install

The game-session recording and a sample of the model server's log lines are copied into llm/tests/ first, since tests depend on them. Then, once the service is live, these are removed from fractal. The claude-qwen and pi-qwen shell functions and pi's model entry are Nathan's and are left alone; they point at the trial install's port and will need the new address.

  • the /opt/llm tree: the hand-built server, the model copy, the launch script, the recordings and the measurement scratch files;
  • the user unit qwen-llama.service;
  • the compiler packages and the NVIDIA package repository added for the trial build. Any image build the stack does happens inside a container and needs none of them.
