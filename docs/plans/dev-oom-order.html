Dev-work out-of-memory order

Plan for bilby, bandicoot and voltaire. Dev work (agents, builds, tests, shells) may use all the memory a host has. When the host runs short, a build dies first, then agents and shells, then tmux, and real services last. The host stays responsive.

Goal

No fixed memory budget for dev work. When available memory drops to 10% and swap is nearly full, one process is killed within a second, chosen in the order above. There's no machine-wide lockup and no power cycle.

Why: what happened on 2026-09-17

Bilby froze twice and had five memory crunches in two hours. Every crunch had the same cause: cargo test linking its test binaries in parallel, five to seven linkers at 1.1 to 1.7 GiB each. That's 7 to 9 GiB on a 15 GiB host whose services already hold about 4 GiB of RAM and 3 GiB of swap.

What the logs show about the kernel's out-of-memory killer today:

  • It fires late. With 8 GiB of swap to shuffle, the kernel keeps finding a little memory and never gives up. The 10:17 freeze logged no kill before the journal stopped at 10:21, and bilby had to be power-cycled at 10:29. At 11:33 it fired only after about 80 s of lockup, with ping dropping packets and taking 2.9 s to answer.
  • It kills the wrong things. At 11:34:32 it killed, in order: the temporary logger and dbus-broker (both +200), then the user manager (+100), and only then the linker (0). Losing the user manager took down every tmux pane and every Claude session on the host.
  • This has happened before. 2026-08-08 was the same kill of the user manager. That incident added a restart override, which brought the manager back but left everything that ran under it dead.

Approach

One packaged daemon, one kernel mechanism, one systemd feature and one bash feature. There's no memory limit, no list of tools and no per-agent configuration. It covers Claude Code and Codex alike.

MechanismWhat it buys
earlyoom (Fedora package, 1.9.0), a small daemon that watches available memory and free swapKills before the machine stalls, where the kernel's own killer only acts after it has locked up. It picks the process with the highest out-of-memory score, the same score the kernel uses, so the order below holds for both. It sends SIGTERM first and SIGKILL if memory keeps falling.
Out-of-memory score adjustment (oom_score_adj, inherited by child processes, and a process may always raise its own)Sets the kill order. Each tier is 300 points apart, and 300 points counts as 30% of the host's RAM plus swap, so size only reorders processes within a tier. Within a tier, the largest process goes first, so a runaway compiler, linker, test runner or JVM is chosen whatever the language.
BASH_ENV, a file bash reads before running any non-interactive commandBoth agents run every command through bash: Claude Code and Codex both use bash -c, even when SHELL is fish. With BASH_ENV exported from fish, each agent command raises itself to +900 before it runs, and whatever it starts inherits that. The agent binary itself never reads the file, so it stays at +600.
tmux as a socket-activated user servicetmux gets its own score (+300), below every shell and agent, and stops living inside whichever SSH login happened to start it.
OOMPolicy=continue on tmux pane groupsIf the kernel's killer ever fires as a backstop, systemd no longer stops the whole pane. Today's default (stop) takes the agent down with its build.

Where every process lives afterwards

user.slice/user-1000.slice/ ├─ session-N.scope SSH and desktop logins; fish in them raises itself to +600 └─ user@1000.service user manager, +100 (unchanged), on earlyoom's avoid list ├─ app.slice user services start at +200 (the user manager's default) │ ├─ tmux.service tmux server, +300, refuses manual stop │ ├─ tmux-spawn-…scope one per pane, OOMPolicy=continue │ │ ├─ fish raises itself to +600, exports BASH_ENV │ │ └─ claude / codex +600 (inherited) │ │ └─ bash -c … raises itself to +900 via BASH_ENV, e.g. cargo → ld │ └─ tmux-spawn-…scope … └─ session.slice … dbus-broker and desktop plumbing (earlyoom avoid list) system.slice/ host services 0 or below; containers 0, a few set +200 (unchanged)

Kill order

+900
1. Commandsbuilds, tests, compilers, anything an agent or a bash script runs (largest first)
+600
2. Agents and shellsclaude, codex, fish, and what you type straight into fish (largest first)
+300
3. tmux serverlast of the dev work
0
Real servicesonly if a single container holds more than 30% of RAM plus swap would one outrank tmux

A survey of all three hosts on 2026-09-17 found nothing above +200 today: user services (ssh-agent, dbus-broker, the clipboard bridge, GNOME's session helpers) sit at +200, and so does one browser container on bandicoot. Everything else is at 0 or below. So +300 and up belongs to dev work alone.

The kernel scores a process by its share of RAM plus swap, as 0 to 1000, and adds the adjustment. (/proc/<pid>/oom_score shows that sum plus 1000, times two thirds, so an idle process at 0 reads 666.) On bilby (15.3 GiB RAM, 8 GiB swap), 300 points is 7 GiB, so a small command dies before a 2 GiB agent, and an agent dies before tmux unless tmux is 7 GiB bigger. The user manager (+100) and dbus-broker score below tmux and are also on earlyoom's avoid list, so the 11:34 teardown can't recur from dev work.

When earlyoom fires

earlyoom's own defaults: available memory at or under 10% and free swap at or under 10%, then SIGKILL at 5%. Fedora's packaged setting (4%, capped at 400 MiB) is too late: bilby's lowest sample before the 11:33 lockup was 437 MiB. With 10%, bilby would have fired at every crunch this morning:

Trade-offs and known gaps

  • Services get swapped out during a big build. Dev work may push service memory into swap before earlyoom fires, so services can be slow for a while after a crunch. This is the price of using all the memory. Ignoring swap (-s 100) is the lever if it bites.
  • A service holding over 30% of RAM plus swap (about 7 GiB on bilby and bandicoot, 12 GiB on voltaire) would outrank tmux. No service is near that today.
  • Containers started by dev work run as services at 0: voltaire's dev containers (hybrid-sim-postgres-dev and others) and anything testcontainers starts. They die after tmux.
  • Commands started without fish or bash keep the score of whatever started them. A future agent that runs commands directly or through /bin/sh leaves them at +600, where they compete with agents by size. Anything started by a bash command is covered.
  • systemd-oomd stays as Fedora's backstop. It acts only after 20 s at 80% stall across the user manager or system services, well past earlyoom's trigger, and it hasn't fired in the last 30 days on bandicoot or voltaire. If it ever does act first, it ignores the kill order and removes a whole group, such as a pane with its agent.
  • A very fast allocation can beat earlyoom. It checks memory up to ten times a second when low. If memory still runs out, the kernel's killer fires with the same order, and panes survive it.
  • tmux refuses systemctl --user stop. To restart it on purpose, run tmux kill-server; the next mux starts a fresh one.
  • Cutting over ends each host's current tmux sessions once. The running server owns the socket path. Voltaire's /tmp move also needs one restart.

Kill criterion

If earlyoom routinely kills ordinary agent work on a host, the host is too small for its agent load. The answer is fewer parallel agents or more RAM, not more out-of-memory machinery. If services are noticeably slow after crunches, try ignoring swap before adding anything.

Decided

  • When earlyoom fires: 10% available memory and 10% free swap, earlyoom's own defaults. Chosen on 2026-09-17 because it matches every crunch this morning while letting builds that only need swap finish.
  • systemd-oomd stays at Fedora's default on all three. earlyoom fires first, so systemd-oomd only matters in a stall that earlyoom misses. Keeping the default is less configuration than switching it off. Bilby is brought back to the default.
