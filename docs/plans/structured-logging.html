Structured logging across the fleet

What is left of the structured-logging work: decisions awaiting the owner, checks to run after the next push, and one change in another repository. The schema, the shipping paths and every approved line drop are described in Logging and Monitoring.

Decisions awaiting the owner

  • Alloy's HTTP API bound to loopback. logging/compose.shared.yaml runs every host's Alloy with --server.http.listen-addr=0.0.0.0:12345, so any container sharing a Docker network with Alloy can read its configuration and component state, the ClickStack ingestion key included, with no credential. Recommendation: 127.0.0.1:12345; the healthcheck already dials 127.0.0.1. Trade-off: Alloy's UI is then reachable only through docker exec or a port forward on the host, not from another container. awaiting owner
  • Successful logs-ingest.pod.haus deliveries in bilby's Caddy access log. Bilby's Caddy logs every request, so every exporter request from Numbat, voltaire and Pinelake is a row: about 34k, 44k and 43k a day, 121k in all, 5% of the fleet's 2.6M rows (each exporter's request count on 2026-10-05). Proposal: drop the 2xx rows for logs-ingest.pod.haus in Alloy and keep every failure; the exporters' own request metrics and the Gatus pipeline heartbeats already count successful deliveries. It would join the approved drops in Logging. Trade-off: about 121k rows a day against a per-request record of each successful delivery. awaiting owner
  • An alert for an Alloy restart loop. The healthcheck depends on the metric name http_client_request_duration_seconds and the exporter's component_id label. If an Alloy release renamed either, every Alloy's check would fail and autoheal would restart every Alloy every 5–6 minutes with no alert: delivery continues between restarts, so the heartbeats stay green, and no Alloy is unhealthy long enough for the Komodo stacks check. Each restart drops the queue and reads every stopped container's log again. logging/tests runs the check only in the image cached on the machine that commits, while hosts pull the current image on every deploy. Proposal: a Gatus ClickHouse check counting each host's Alloy starts over the last hour (Alloy's own startup line, which its Docker tailer ships), alerting above 3. Trade-off: one more query per host against a restart loop nobody sees. awaiting owner
  • Replica-suffixed service names. A compose service with no container_name gets Compose's generated name, so its service.name is that name less the host prefix: llm-llm-model-1 for fractal-llm-llm-model-1, whose compose service is llm-model. Using the compose service name for such containers gives short names that survive a replica count or project rename. It must be done in enrich.alloy, never by changing the tailer's service label, which keys read positions and the parsers. Trade-off: a cleaner service list, against a rename for anyone filtering on today's names and a rule that has to recognise a generated name. awaiting owner
  • The Ollama model runner's lines in lumen-ollama. With successful requests under 10 s dropped, about 69k rows a day remain (measured 2026-10-05 08:00–16:20 Perth), almost all from the llama.cpp runner inside Ollama on bilby and fractal: five to seven slot lines per embed batch (slot launch_slot_, slot operator(), slot release, slot get_availabl, srv update_slots: all slots are idle), about 53k a day, and about 16k a day of model-load lines (llama_model_loader, print_info, llama_context) each time the model reloads after its 5-minute keep-alive. Voltaire's Ollama prints almost none of these. Proposal: drop the slot and model-load lines in lumen-ollama.alloy, keeping the runner's level= lines. Trade-off: about 69k rows a day against the per-batch trail of what the embedder did. awaiting owner
  • The authentication trail outside ClickHouse. Pomerium's and Pocket ID's sign-in records reach ClickHouse, which keeps them 180 days. Should they also stay in Pomerium's and Pocket ID's own stores? Trade-off: a second copy and its retention to manage, against one store holding the only record. awaiting owner
  • An audit log for storage.pod.haus. Unanswered: whether RustFS can record who used storage.pod.haus and with which key, beyond what bilby's Caddy sees of each request. awaiting owner
