Structured logging across the fleet

One schema for every log row on every host, documented so the next service and the next agent fit it without asking. Every field a service emits arrives queryable, with a correct severity and time, under names that never collide. Today the pipeline can do all of that and, in a dozen places, has been configured not to.

The case

The log pipeline already ships structured data end to end: a JSON body that reaches the ClickStack collector is parsed and every field lands in the attributes map, which is how Caddy's access lines are queryable by caller and path. The defects are all upstream of that, in our own Alloy configs, and almost all are the same mistake repeated: a per-service parser rewrites the JSON body to a short string for readability and discards the fields. The fix removes code rather than adding it. Per-service parsers shrink to severity mapping, one shared rule does the structuring, and the pipeline stops depending on which service happens to have a parser.

Two findings cannot wait for the rest. Lumen's throwaway code-search containers ship their request stream, including source snippets from indexed repositories, into a store with 180-day retention, under random names, and twice. And the only authentication trail the fleet has, Pomerium's authorize lines and Pocket ID's request lines, is stripped of identity before it leaves numbat and bilby. Both are a few lines in two Alloy modules and go first.

Kill criterion. If the shared JSON step cannot reproduce the attribute names the collector produces today for Caddy access lines, so that existing saved searches break, stop and fall back to keeping JSON bodies whole in the two offending parsers. That smaller fix restores the audit trail on its own.

Where structure is lost

The schema every row follows

One shape for every service, host and source, so a reader can interpret any row without knowing which service wrote it, and a new service needs no pipeline work to fit. Pipeline facts live in namespaced names that no application field can collide with; application fields keep their own names.

What a new service must do to fit: write JSON lines to stdout with a level field and a message field. Nothing in the pipeline changes. A text-only service gets one small parser module that maps its level word, and nothing else.

Services that ship their own OTLP (fenwick, fenwick-web-agent, indy-service, the book services, and whatever the fenwick tracing work adds) never pass through Alloy, so the enrich step cannot stamp them. Today their rows carry the SDK's resource: service.name, a UUID in service.instance.id, no host, no namespace. To fit, each sets OTEL_RESOURCE_ATTRIBUTES in its compose file to the schema's host, service.namespace and service.instance.id: one line per service, in those repos, after the names below are settled. decision host or host.name. host is what every Gatus check and the enrich step use today; host.name is the OpenTelemetry name an SDK's resource detector emits on its own. Recommended: adopt host.name fleet-wide and rewrite the Gatus queries in the same commit, so SDK-shipped and Alloy-shipped rows agree without a mapping.

Where this is documented once it ships

A new system doc, docs/logging.md: the table above, the new-service contract, how to query by instance or host in HyperDX, the parser rules (severity only, never rewrite a body, never drop a field), and the volume and secret rules. docs/monitoring.html keeps the alerting and pipeline-health content and points at it. AGENTS.md gains a row in its required-reading table and a hard rule: a parser never drops a field. It is written with the implementation, not before, because docs/ states what is true.

Approach, by component

Badges: mechanical needs no decision; decision is Nathan's call and names its trade-off.

Shared JSON structuring in the enrich step

logging/alloy-modules/enrich.alloy already runs an OTTL transform on every host's logs. It gains one rule: when the body starts with a brace, parse it, merge the fields into the log attributes without overwriting any that exist, then set the body to the message field (msg, message or log_message, whichever is present). mechanical

  • No field is lost to a collision. The pipeline's own facts use the namespaced names under Service names and attributes, so a service's host or service field lands under its own name beside them.
  • Secrets are stripped first. Keys that are unambiguous secrets go: authorization, cookie, set-cookie, password, access_token, refresh_token, id_token. Pomerium's OAuth state blob is stripped in its own module, not globally: state is an ordinary field elsewhere (the model watcher reports its state in one).
  • Nested objects keep today's names. Caddy's request, pino's req and Mongo's attr are flattened to the key names the collector produces now, checked against one live Caddy row before the switch.
  • No time parsing here. Docker already stamps each line with its nanosecond receive time; see Timestamps.
  • Some modules stay. HyperDX's [COMP] {…} prefix, FerretDB's and Backrest's mixed text-plus-JSON lines still need their own small parsers.

Timestamps

Seven parsers overwrite Docker's nanosecond receive time with a parsed whole-second time, and five of them pin Australia/Perth. Pinelake's Syncthing runs in America/Edmonton, so its rows land fourteen hours in the past, and the pins break the promise that a service can move hosts with its parsing intact. Stop parsing timestamps for Docker sources altogether; keep it only for file sources whose lines carry no other time (Plex's server log, Flood's job logs, ClickHouse's error file). mechanical

Docker's receive time is only as good as the host's clock. Fractal has no time sync and runs about 1.8 s ahead; the fenwick tracing plan's clock section (~/repos/podhaus-tracing-clock, chrony in the WSL Ansible role) fixes that and is the prerequisite for comparing fractal's log times with any other host's. This plan does not touch that role.

Audit trail

  • Logins and privilege use are filtered out. journal.alloy collects priority 0–4 only; sshd's Accepted publickey, sudo's session lines and earlyoom's kills are priority 5–6. Add journal sources with no priority filter for sshd.service, sudo, earlyoom.service and docker.service. Alloy ANDs matches within one source, so each unit is its own source. mechanical
  • Bilby's front door logs nothing. caddy/Caddyfile has no log directive, so nothing records who reached storage.pod.haus, git.pod.haus or any public site. Turn on access logs per site with the request delete filter fractal already uses. Trade-off: volume on the public sites against having any record at all. decision
  • Pomerium runs at debug. Only ssh-auth-notify needs it, and it reads docker logs, not ClickStack. Drop DEBUG in Alloy except the keyboard-interactive line it needs. Trade-off: less to diagnose a Pomerium policy problem after the fact. decision

decision What fills ServiceName. Recommended: stripped (flood, host one filter away in service.instance.id): one saved search covers every host and splits by host; the service list and Service Map stay short. Or host-prefixed as today (pinelake-flood), made consistent by prefixing bilby's too: the host is visible in the service list without a filter, at the cost of seven entries for every fleet-wide service. Either way the other fact is an attribute, so nothing is lost; the trade is what the first-glance column shows. Saved searches keyed on the losing form are rewritten in the same pass.
