MinIO to RustFS

Goal

Both object stores run RustFS: the primary storage.pod.haus instance (Terraform state, three static sites, the pets art bucket, Indigo's SFTP publishing through RustFS's own SFTP server) now on bandicoot, and kangaroo's pouch.pod.haus instance (Sky's restic repository). S3 endpoint names and client credentials stay unchanged; the console and Indigo’s SFTP address get the names described below. Backrest covers the primary store and every existing Bandicoot plan through Bilby’s existing OneDrive destination. The stopped MinIO data roots, images, secret volumes, credentials and matching Terraform checkpoints remain available for rollback after validation. MinIO’s S3 client and Terraform bucket resources remain; older pets snapshots expire under their existing retention. Destructive cleanup is deferred until Nathan separately authorizes removing rollback.

The one constraint that shapes this plan. The official RustFS 1.0.0 image is built with the ftps + webdav feature set. SFTP is an opt-in compile-time feature it does not include: the 1.0.0 binary's own feature manifest reads "Default feature set: ftps + webdav" and lists SFTP only in the "full" bundle, and the SFTP documentation says to build with cargo build --release --features sftp. Blocs on Indigo's iPad speaks FTP and SFTP only. So the primary instance runs an image we build from the RustFS source at the release tag with the sftp feature on. Upstream ships the recipe (Dockerfile.source with a RUSTFS_BUILD_FEATURES build argument), so our Dockerfile is that recipe pinned to a tag, not a bespoke build. The Pouch instance needs no SFTP and runs rustfs/rustfs:latest; the rollout records and validates its resolved version (1.0.0 for this migration).

Operating tolerance. This is a home-lab migration. Temporary outages during build, cutover or repair are acceptable. Preserve all data present at the cutover boundary; Nathan accepts losing writes made afterward if rollback is needed. The original stopped MinIO directories remain untouched after the payload and restore checks pass, until Nathan separately authorizes cleanup. No full parallel rehearsal environment is required.

Placement and access

Where a service runs and how it is reached are separate decisions. Bilby's Caddy is the front door: every name resolves to it (on the LAN directly, off the LAN through Numbat), and it proxies to wherever the service lives, by container name on bilby or by LAN address elsewhere. It already does this for nine bandicoot services. It does it for HTTP only, and the store's SFTP listener is raw TCP, so this plan adds Caddy's layer-4 module: one more --with in caddy/Dockerfile and a layer4 block that forwards port 8022 to the store's host. After that, any TCP service can land on any host with the same one-line change as an HTTP one.

The primary store lands on bandicoot: 766 GB free against bilby's 29, ten cores, and the recurring source build of the image is exactly the CPU- and disk-heavy work the bandicoot migration designated for it. Moving it later is two Caddy upstream addresses, a Backrest bind and a data copy; nothing in DNS, Terraform or any client changes.

How it is backed up

  • Backrest plan minio (bilby) snapshots /var/lib/minio nightly at 05:15 into the podhaus restic repository on Jump (/mnt/jump/backups). 20 snapshots exist, about 1.29 GiB each. Retention 14 daily, 4 weekly, 6 monthly.
  • Backrest plan pets (bilby) binds /var/lib/minio/pets-alive-assets alongside the pets SQLite, hourly, so one snapshot holds a consistent database-plus-assets set. 64 snapshots.
  • Bilby's and kangaroo's restic repositories are each mirrored to OneDrive by an rclone sync hook, so a prune propagates on the next run. Bandicoot’s existing repository (/mnt/jump/backups-bandicoot) has no OneDrive mirror in the checked-in configuration. This migration feeds its snapshots into Bilby’s existing off-site destination; it provisions no new OneDrive destination or independent mirror.
  • These snapshots hold MinIO's internal on-disk layout (xl.meta plus part files). They restore only into a server that reads MinIO's format, which RustFS does.
  • Pouch MinIO is deliberately not backed up: it is itself the extra copy, and Sky's laptop is the rebuild source.

Decisions

DecisionChoice and whyRejected
How the data moves Copy, then switch. RustFS 1.0.0 reads a MinIO data directory in place (objects, versions, bucket metadata, versioning flags and the built-in IAM, provided it is started with the same root credentials). We use that format compatibility but never on the live directory: MinIO is stopped, its directory is copied to the new host's data root, RustFS starts on the copy. The original remains untouched for rollback, so rollback restores the cutover state, deliberately discarding later writes. Preserve every object version, including Terraform state and Indigo’s undo history. Recreate Terraform-managed IAM on the RustFS copy using the original credential values, as described below. The copy is 1.4 GB over the LAN for the primary and 241 GB within Pouch (13 TB free) for kangaroo. Re-upload with mc mirror: loses all object versions and needs the IAM rebuilt. Rename the directory in place (kangaroo): instant, but RustFS rewrites system metadata on first start, so rollback is no longer a rename back.
Preparation and validation Build the image, capture credentials and Terraform state, and inventory the source data before stopping MinIO. Use the production cutover for integration checks. A small isolated provider check may resolve a specific uncertainty, but duplicating Caddy, both stores and every client for rehearsal is unnecessary. The untouched source directories protect the data while failures are repaired. A mandatory full rehearsal delays this home-lab migration without changing its accepted outage tolerance.
SFTP RustFS's built-in SFTP server, from our own build of the release tag with the sftp feature. It authenticates with the IAM access key as username and the secret as password, exactly as MinIO's did, and serves /<bucket>/<key> paths. Indigo's username, password, path and the host key fingerprint all stay as they are; the address becomes storage.pod.haus:8022, the store's name rather than a host's, reached through the front door's layer-4 forward. An SFTP gateway beside RustFS (SFTPGo): a second credential store and a second upstream for one user. RustFS's built-in FTP: cleartext credentials plus a passive port range. A prebuilt "full" image: upstream publishes none. Port 22: it is every host's own sshd, and Numbat's relay 22 is Forgejo's; SFTP stays LAN-only on 8022, as today.
Front door forwards TCP Caddy gains github.com/mholt/caddy-l4 in its xcaddy build and a layer4 app block: listen :8022, proxy to {$BANDICOOT_LAN_IPV4}:8022. The caddy stack publishes 8022; the store's stack publishes it on bandicoot's LAN address. This is what makes placement independent of access for non-HTTP services, and it is reused unchanged if the store ever moves. A split-horizon record to bandicoot for a second SFTP name: works, but one service under two names. A second Caddy on bandicoot: two front doors.
Where the image is built On bandicoot, by Komodo, with the same content-hash mechanism every other build service uses: a rustfs/Dockerfile pinned to the release tag rebuilds only when that file changes. This is the search-indexer and indy-board precedent (both build Rust on a 16 GB host), with jobs capped so the compile stays inside memory: bandicoot had 9.7 GB available and 2.9 GB of swap in use on 2026-09-26. A registry pipeline (build on the Forgejo runner, push to git.pod.haus, pull on the host): a second deploy path to maintain for one image. Hand-carrying an image with docker save: not config-as-code.
Version reference The Dockerfile's ARG RUSTFS_VERSION and the Pouch stack's image tag name the same release (1.0.0 today). A source build must name a tag, so this is not a reproducibility pin; bumping is editing two lines, and the two instances move together.
Backup coverage Every host backing up to Jump must have an off-site route. Bilby and Kangaroo already do. Feed all Bandicoot snapshots, including the new RustFS plan, into Bilby’s existing podhaus restic repository with restic copy before its existing OneDrive sync. Keep onedrive:Backups/podhaus-restic and its current OAuth state. Preserve Bandicoot’s local repository and retention. The cost is another local copy on Jump, not another remote destination. A new remote mirror for Bandicoot; byte-copying one restic repository into another; unsynchronised rclone reads of Bandicoot’s live repository.
Pets backup consistency The assets bucket is snapshotted by bandicoot's rustfs plan and the pets SQLite by bilby's pets plan, so they are no longer one consistent snapshot. The bucket is write-once UUID-named PNGs that the app writes before the database references them, so the worst case is a restored database referencing an asset up to a nightly interval newer than the restored bucket. Accepted. Moving pets to bandicoot too: out of scope for this plan; it can follow the same front-door move any time.
Terraform IAM moves to weinmann-emt/rustfs using its native RustFS admin API; buckets, versioning and bucket policies stay on aminueza/minio’s S3 resources. This is an explicit choice to use the RustFS provider, not a claim that MinIO admin clients cannot work: RustFS 1.0.0 accepts MinIO admin routes and handles their encrypted payloads. The chosen provider’s v0.0.8 imports omit fields needed to preserve users and service-account parents, so managed IAM is recreated on the copy with the same credentials. Terraform continues owning it. Importing native IAM resources and hand-editing Terraform state to repair missing fields. Moving IAM management into an init script. Both are unnecessary when a brief authentication outage is acceptable.
Anonymous read on versioned buckets RustFS 1.0.0 denies GetObject on a versioned bucket unless the policy also grants s3:GetObjectVersion (issue 7989, closed as not planned). The three public site policies and their three deploy policies gain that action; the unversioned pets bucket does not need it. Cost: an anonymous client can fetch a noncurrent version by id if it already knows the id; nothing lists versions anonymously.
Admin tooling rc (rustfs/cli, arm64 binary) is installed on bandicoot for admin work. mcli stays on bilby for S3 work (mirror, ls, undo) against storage.pod.haus, as do the mc images inside nathanbaxter-deploy, search-indexer and the Gatus monitor: it is used here for S3 operations. The MinIO Terraform provider also remains for bucket resources.
Console hostname minio.pod.haus becomes rustfs.pod.haus (Pomerium family route, Caddy route to bandicoot's :9001, DNS map). Settled.
1Password item names Every item named for MinIO is renamed for RustFS so the komodo-op variable names stop saying MinIO. Terraform-owned items rename in Terraform. The five hand-made items rename with op-vault dev -- op item edit <id> --title "…" --vault Homelab: the Podhaus service account holds write_items on Homelab (verified 2026-09-26 with op vault list --permission write_items), so the item renames are scripted preparation before cutover. Rename Terraform-owned items in a preparatory apply while both MinIO endpoints still run. Wait for every new Komodo variable before deploying consumers. Credential values remain unchanged.

The RustFS plan runs at 03:30 AWST. Backrest stops RustFS before reading its data files and restarts it from the snapshot-end hook, including after a backup failure. Use Bilby’s existing off-site job

  1. Mount Bandicoot’s existing Jump repository into Bilby’s Backrest container at /repos/podhaus-bandicoot. Restic needs write access to its lock directory even when reading snapshots; validate both the Jump sentinel and the expected repository identity before touching either repository. Read the existing restic password from the rendered secret configuration without logging it; no new secret or OAuth token is needed.
  2. Extend Bilby’s existing backrest-state success hook into one synchronous operation: copy all committed Bandicoot snapshots with restic -r /repos/podhaus copy --from-repo /repos/podhaus-bandicoot, apply scoped retention to those copied snapshots, then run the existing rclone sync to onedrive:Backups/podhaus-restic. Run it on successful and unchanged backups. Do not initialise either repository or disable restic locking. A failed or stale Bandicoot copy still allows Bilby’s existing repository to upload; the combined operation then fails and withholds its success heartbeat.
  3. Keep the copy and upload in Bilby’s Backrest task queue, which runs tasks serially; its own backups and prune must not mutate the destination during the raw mirror. Source-side restic locks protect the snapshot copy against Bandicoot prune. Do not run an independent scheduler or manual destination mutation alongside this hook. Verify queue behaviour on the deployed Backrest version. The five-minute schedule offset is not a correctness mechanism.
  4. Copied snapshots retain created-by:bandicoot and plan:… tags. Bilby’s ordinary per-plan retention does not own them. Apply the source’s 14-daily/4-weekly/6-monthly policy to only created-by:bandicoot, grouping by host, paths and tags so the seven plans and RustFS remain separate. Bilby’s existing prune reclaims their expired packs. Validate the copied tags before enabling retention; never use an unfiltered forget command.
  5. Treat copy, retention, upload or freshness-check failures as fatal and withhold the success heartbeat. Check that every expected source plan has a recent successful or unchanged backup and that its selected snapshot is present at the destination; an old but readable source repository must not earn a green off-site status. Keep the existing Bandicoot local-backup heartbeat distinct from Bilby’s off-site completion signal.

Restic’s snapshot-copy command transfers snapshots between repositories and skips already copied snapshots. It reads and rewrites their data under the destination’s encryption; the repositories’ files cannot be merged with rclone. Initial copying consumes extra space on Jump and may deduplicate less effectively across the existing repositories.

Add a configuration check alongside backup/tests/test_heartbeat_contract.py that accounts for every Jump-backed repository and its off-site route. A future host must not gain a Jump backup without a destination and failure signal. Validate the live result by restoring a representative file from every Bandicoot plan from the existing OneDrive repository, plus the complete RustFS restore below. Also check Bilby and Kangaroo’s latest off-site snapshot inventories.

The image: rustfs/Dockerfile

A two-stage file that is upstream's Dockerfile.source at the release tag, reduced to what we need, plus the repo's content-hash contract.

  • Builder stage: rust:1.97.1-trixie (upstream's toolchain image for 1.0.0), the packages upstream installs (build-essential pkg-config libssl-dev lld protobuf-compiler flatbuffers-compiler git), git clone --depth 1 --branch 1.0.0 of rustfs/rustfs, upstream's scripts/static.sh and cargo run --bin gproto steps, then cargo build --release --locked --bin rustfs --features sftp for the native target. No cross-compilation: bandicoot builds arm64, which is what it runs.
  • Memory bound: CARGO_BUILD_JOBS=2, CARGO_PROFILE_RELEASE_LTO=false, CARGO_INCREMENTAL=0, debug info off, symbols stripped, and 16 code generation units for the RustFS package. The package override reduces peak memory without rebuilding all dependencies. BuildKit cache mounts for the cargo registry and target directory keep a version bump from starting cold.
  • Runtime stage: ubuntu:26.04 as upstream, ca-certificates and curl for the healthcheck, user rustfs uid 10001, the binary at /usr/local/bin/rustfs, upstream's entrypoint semantics reduced to ENTRYPOINT ["/usr/local/bin/rustfs"] since the stack passes everything by environment. ARG STACK_CONTENT_HASH / ENV STACK_CONTENT_HASH pair for the lint.
  • SFTP proof: the container healthcheck requires both S3 readiness and an SSH banner on port 8022. Rollout validation then authenticates with the original password, verifies the original host key, and uploads, reads and deletes a probe file.

Preparation while MinIO still runs

  1. Prepare the stack, Caddy, consumer and Terraform changes on a branch. Separate the preparatory Terraform configuration, primary cutover and Pouch cutover so each apply matches the server currently running. A branch push does not deploy: the webhook filters for main, and Komodo pulls origin/main.
  2. Build the RustFS image on bandicoot with the SFTP feature and memory limits; build Caddy with layer 4 and confirm the module is present. Enable info-level logging for the build’s SFTP smoke check so the listener message is visible. These finite builds and checks are performed during implementation, not as part of this document edit.
  3. Capture private Terraform state, the complete IAM inventory, current item titles and both stores’ bucket configuration. Adopt the existing managed secrets into the password resources and confirm a plan proposes no password regeneration. Retain that credential checkpoint with the rollback artifacts.
  4. Apply only the preparatory changes described above using the old IAM resources: Terraform-owned item retitles and the compatible policy widening. Rename the five hand-made items by their recorded IDs, update terraform.env.op, and verify every new Komodo variable, including OP__KOMODO__SFTP_HOST_KEY__PRIVATE_KEY_B64 and OP__KOMODO__POUCH_RUSTFS_ROOT__*, exists before a stack consumes it.
  5. Check for server-side encryption and unsupported storage features on the source. Capture the primary store’s object/version manifest, including delete markers, and plaintext SHA-256 hashes fetched through S3 for every retained version. Pause publishers and scheduled writers during this final inventory and the copy; temporary failures are acceptable. Read failures or unsupported encryption must be resolved before the original store is retired.

Primary-store cutover

Komodo deletion runs Compose down and removes the stopped containers, but leaves the bind-mounted source data and named secret volumes intact.   2. Merge the primary cutover into main and push main. The commit adds rustfs/, removes minio/, updates Caddy and the primary consumers, and changes backup bindings. Merge and push the pets endpoint/variable change to that repository’s main too. Await the deployment results and CI with ci-watch <branch> <head_sha>. Repair any startup failures with the originals retained; zero downtime is not a requirement.
  3. Verify RustFS starts with the original root credentials, serves the copied buckets, and the unchanged terraform user can read and write its backend. Compare the source manifest and payload hashes before allowing publishers to resume.
