# Remote copy/paste — Mac clipboard into Claude Code over SSH, fleet-wide

Goal: copy on the Mac, Ctrl+V into Claude Code running over SSH on any
remote dev machine (devboxes: **voltaire**, **fractal**; bilby carries
the legacy install), images included, tmux or not. This worked before
(Mac → bilby); the machinery is **cc-clip**
(<https://github.com/ShunmeiCho/cc-clip>) — adopted third-party tool,
not homegrown — and it was only ever enrolled for bilby. This plan
makes it a fleet property.

## How cc-clip works (recovered 2026-08-11)

- **Mac**: launchd daemon (`com.cc-clip.daemon`) serves the local
  clipboard over HTTP on `127.0.0.1:18339` (text and PNG; also a
  `/notify` endpoint, nonce-authed).
- **Tunnel**: `RemoteForward 18339 127.0.0.1:18339` re-publishes the
  daemon on the remote host's loopback for the life of the SSH
  session. No public listener anywhere.
- **Remote host** (`~/.local/bin`, generated by `cc-clip setup <host>`
  run from the Mac): an `xclip` shim that answers clipboard reads from
  the tunnel — for an image clipboard it hands Claude Code the data it
  expects; a `claude` wrapper (real binary kept as
  `claude.cc-clip-real`) so CC's clipboard probing finds the shim; and
  `cc-clip-hook`, which POSTs CC Stop/Notification events to the Mac
  daemon (your Mac pings when a remote Claude finishes).
- Why this shape is necessary: CC reads the clipboard of the machine
  it runs on (no OSC 52/5522 remote-clipboard support — upstream
  issue closed not-planned), and no terminal escape protocol carries
  image data. tmux is bypassed entirely — the image never rides the
  terminal — so tmux needs nothing beyond the existing config.

## Ownership (per docs/host-provisioning.md boundary)

Everything cc-clip touches on a remote host is `$HOME` user-state — no
sudo anywhere — so this is **chezmoi-side, not Ansible's**; the Mac
isn't in the Ansible inventory at all. Within that:

- **chezmoi owns**: the `RemoteForward` for the devbox hosts in the
  managed ssh fragment (done 2026-08-11 — moved out of the bilby-only
  block to `Host bilby.pod.haus fractal.pod.haus voltaire.pod.haus`);
  the guarded Claude Stop/Notification hooks (already fleet-wide,
  no-op where cc-clip is absent); and the write-once `~/.ssh/config`
  stub (the 2026-08-11 split), which absorbs any appends `cc-clip
  setup` makes without drift.
- **cc-clip owns its own artifacts** — daemon, shims, wrappers, nonce.
  Deliberately NOT vendored into chezmoi: upstream has an installer,
  `cc-clip update`, and a host registry (`cc-clip hosts list`), and
  the claude-wrapper dance has to track CC's installer layout;
  forking that into chezmoi means we maintain it.
- **Per-host enrolment is a deliberate human act** (the machine-key enrolment
  pattern): `cc-clip setup <host>` from the Mac, once
  per devbox — but chezmoi detects the gap: after a Mac
  `chezmoi-update`, `__ccclip_nudge` (added 2026-08-11) diffs the
  fleet.toml devbox list against `cc-clip hosts list` and prints the
  exact `cc-clip setup` commands for any missing host, staying silent
  otherwise. Adding a devbox to fleet.toml is the whole declaration;
  the next Mac shell says what to run.

## Text copy (OSC 52) — audited correct, keep for reference

Text copy out of tmux is a separate, terminal-native path and was
audited clean on voltaire (2026-08-11): tmux 3.7b, `set-clipboard on`,
`allow-passthrough on`, `Ms` in both `tmux-256color` and
`xterm-ghostty` terminfo, Ghostty client negotiates the `clipboard`
feature, no stale `DISPLAY`/`WAYLAND_DISPLAY` in session env. If text
copy misbehaves on a machine, audit in that order; the quick
end-to-end check is `tmux set-buffer -w -- test` then pasting locally.
