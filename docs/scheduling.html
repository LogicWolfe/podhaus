Scheduling

Ofelia handles all docker-side cron in podhaus. Schedules are declared as labels on target containers — ofelia discovers them via the Docker socket and runs jobs as docker exec against the labeled container. No central config file.

How ofelia works here

The ofelia/ stack runs mcuadros/ofelia:latest in daemon mode with --docker. On startup it reads labels from every running container and builds its job schedule. Two label flavors in use:

  • job-exec — runs a command inside the target container via docker exec.
  • job-run (rarely) — runs a one-shot ephemeral container from a given image.

Cron schedules are interpreted in the container's local time. The TZ env is set to Australia/Perth so labels like "0 4 * * *" mean 04:00 AWST.

04:00 dead-time window

Scheduled work defaults to starting at 04:00 AWST. If a job is expected to take more than 2 hours, walk it back from 06:00 instead so the whole nightly run finishes before peak hours. This rule applies to Backrest plans (see Backup & recovery) and to ofelia jobs.

Why ofelia restarts itself daily

Workaround for upstream label-reload bug ofelia 0.3.x in label-discovery mode reads container labels at startup and only partially tracks changes after that. In practice, label-value changes on existing containers (typical when redeploying a stack with an updated schedule) silently fail to take effect.

The workaround: ofelia has a job-exec label on itself that runs kill 1 at 04:00 every day. PID 1 is ofelia, so it exits, and restart: unless-stopped brings up a fresh instance that re-reads all labels — including any schedule changes deployed during the day.

Bounds the worst-case "stale schedule" window to ~24 hours instead of indefinite. Self-referential but reliable. Drop it when upstream PR #368 ships true Docker-event-driven hot reload of label changes.

Other ofelia quirk

ofelia exits if it starts with zero jobs If ofelia comes up before any target container has its labels, the scheduler has zero jobs and ofelia exits fatally (rather than idling). After a fresh bilby boot, ofelia sometimes needs to be restarted once the labeled containers are up. Documented during the plex-stats-cleanup bring-up.

Adding an ofelia job

  1. Decide which container the job should run inside. The target container must already have docker compose bring it up — ofelia can't schedule jobs in a not-yet-running container.
  2. Add labels to the target container's compose: 
    labels:
  ofelia.enabled: "true"
  ofelia.job-exec.<name>.schedule: "0 4 * * *"
  ofelia.job-exec.<name>.command: "/path/to/script.sh"
  3. Deploy the target stack. Restart ofelia once (docker restart ofelia) so it picks up the new labels — the daily-self-restart hack will catch them the next cycle if you forget.
  4. If the job is critical, add a Gatus push heartbeat — the script should POST success/failure to a bearer-token-protected push endpoint, and Gatus's dead-man's-switch interval (25h is the convention) catches missed pings. Pattern in flood/scripts/rar-backlog.sh.
