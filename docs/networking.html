Networking

Docker bridge networking, Numbat's Pomerium and wstunnel edge, Caddy origin separation, and Terraform-managed DNS.

dockernet bridge

Every UI-facing container joins an external bridge network called dockernet at 172.18.0.0/16. Within the bridge, containers reach each other by container name via Docker's embedded DNS — never by static IP. Static IPs are reserved for LAN devices (e.g. the UniFi gateway at 10.0.0.1) and host-network services.

Every pinned LAN address has exactly one definition: the checked-in config/lan-addresses.json catalog. Terraform reads it for DHCP reservations and split-horizon DNS. Ansible, Komodo startup commands and the QNAP bootstrap read that same file directly, so host provisioning does not depend on a running Komodo instance. tools/render-lan-addresses.py generates komodo/sync/lan-addresses.toml; ResourceSync publishes its LAN_* variables, which stack environment blocks pass into Compose. Edit the catalog and run python3 tools/render-lan-addresses.py before committing; the pre-commit gate rejects stale generated values. Addresses in prose on these pages are for the reader; the file above is the truth. Do not write an address into a compose file, Caddyfile, Gatus config, Alloy config, inventory entry, or script — read the variable instead. Each consuming stack includes the catalog directory in its content hash, so an address change redeploys those stacks after ResourceSync publishes the variables.

Each consumer compose file declares: 

networks:
  - dockernet

# at the bottom:
networks:
  dockernet:
    external: true

Host-network services

A few services need direct host network access:

  • Home Assistant — Bluetooth, mDNS, multicast device discovery.
  • Plex — Plex's own LAN discovery protocol, GDM/DLNA.
  • Syncthing (kangaroo-side) — LAN device discovery via UDP/21027 multicast.

These declare network_mode: host in their compose. Caddy reaches them via the dockernet bridge gateway IP 172.18.0.1, such as home.pod.haus → 172.18.0.1:8123.

Numbat edge

Numbat is the active public gateway. Bilby and other internal targets make outbound wstunnel connections to it, each limited to its own listeners; Numbat has no routed path into the home network (Tunnels).

Port 22 on both addresses carries a per-source nftables rate limit on new connections (10/minute, burst 20); established sessions are never touched, and over-limit sources are dropped before they reach Pomerium or the Forgejo tunnel.

Protected browser names resolve to the application address. Pomerium authenticates with Pocket ID, then reaches Caddy's private :4443 listener through a loopback-only tunnel listener. That listener also requires Pomerium's client certificate. The public TLS tunnel reaches Caddy :4444, which has no protected virtual hosts. Caddy writes one access line per request on all three listeners. Behind the relay it sees only the tunnel client as its peer (wstunnel's reverse tunnels carry no PROXY protocol), so a :4443 line names the client from Pomerium's X-Forwarded-For and the signed-in person by the email Pomerium passes or by its request ID, and a :4444 line for a site Cloudflare does not front has no client address at all (Logging).

The public listener serves RustFS S3, Pocket ID, UniFi, static sites, scoped Umami ingestion, paperless-api.pod.haus, Komodo's outbound connection, and mTLS log ingestion. Forgejo uses Pomerium for HTTPS and the application address on port 22 for ordinary git@git.pod.haus SSH. Managed devices use the canonical <host>.pod.haus name for host SSH. Chezmoi sends Bilby, Bandicoot, Quokka and Fractal directly through split DNS and Kangaroo directly to its active LAN address while preserving the canonical host-key identity. Fractal's split-horizon record resolves to the LAN address its WSL guest shares with the Windows host under mirrored networking (UniFi-reserved, both in Terraform) and is safe precisely because fractal.pod.haus serves no HTTPS — its HTTPS name fractal.docs.pod.haus is separate and stays on Pomerium — and it keeps fractal reachable from the LAN even when the Pomerium edge is down. Chezmoi sends all other cases through Pomerium at ssh.pod.haus:22. On an unmanaged device, connect as nathan@ssh.pod.haus and choose a route from Pomerium's portal. Routes are named bilby, fractal, numbat, voltaire, kangaroo, bandicoot, pinelake, and quokka. CA trust on Ansible-managed hosts comes from the sshd_pomerium_ca role; on kangaroo (which Ansible cannot reach — QTS has no Python) kangaroo_bootstrap installs a boot-persistent start.sh that re-applies the trust after QTS regenerates sshd_config. Every host's outbound tunnel is a Komodo-managed wstunnel container (tunnel/<host>); kangaroo's runs on host networking so that it reaches the QTS sshd on its own loopback. Kangaroo's canonical route maps to QTS's real UID 0 account, admin. Tailscale recovery keeps separate *-recovery names so its break-glass role stays explicit.

Tunnels

wstunnel carries every outbound connection into Numbat. A client on each origin host dials wss://relay.numbat.pod.haus:2334 and asks the server to open reverse tunnels: Numbat listens, and each connection arriving there travels back to an address on the client's own network. Numbat's side is the numbat-tunnel Komodo stack (tunnel/numbat, container numbat-tunnel-server) on host networking, so its listeners bind Numbat's own addresses. Each origin host runs a <host>-tunnel stack (tunnel/<host>) from the upstream ghcr.io/erebe/wstunnel:latest image, started through the shared launcher tunnel/launcher/run-wstunnel. The launcher writes the stack's certificates to files and resolves Numbat's two public addresses from DNS at container start, so the repository never carries them. Every tunnel stack lists ../launcher under x-podhaus-content-paths, so a change to the launcher redeploys them all.

Pomerium reaches the loopback listeners for its HTTP and SSH routes; public HTTPS and Forgejo SSH are served from the public listeners without Pomerium.

Authentication is mutual TLS against a relay CA that Terraform owns (terraform/tunnel.tf). Each client holds its own certificate, whose common name is its host name (the MacBook is nb-macbook-air). Numbat requires the certificate and accepts only the common name as the upgrade path the client uses, and tunnel/numbat/restrictions.yaml maps that name, one rule per host, to the exact listeners the host may open. Everything else is denied, including forward tunnels, so a stolen client certificate opens only its own host's listeners. Clients trust only the relay CA (the launcher points SSL_CERT_FILE at a file holding it alone) and verify Numbat's certificate against it, so they accept no other server. The certificates are published to the 1Password Homelab item Numbat Tunnel; leaf certificates last five years and any terraform apply in their last 90 days renews them, and the CA lasts ten years. A renewed certificate reaches a tunnel only when its stack is redeployed, since a changed secret redeploys nothing: after the renewing apply, redeploy numbat-tunnel and every <host>-tunnel stack. The MacBook's client picks its certificate up on its next chezmoi apply.

A new listener needs both the client's tunnel arguments and a line in restrictions.yaml; the contract tests in tunnel/tests fail when a client's requested listeners differ from its rule, a listener has two owners, or a loopback listener Pomerium names has none. A second test runs the real launcher and server in Docker to prove that a client gets the listener its rule grants, is refused one it does not, and never connects when either side trusts a different CA. The server renders restrictions.yaml with Numbat's addresses when it starts, so a change restarts it and every tunnel drops until the clients reconnect. The firewall opens 443 and 2334 on the relay address (numbat_edge); the bootstrap play starts the tunnel server before Periphery. Alloy labels tunnel logs tunnel on clients and tunnel-server on Numbat.

Nathan's MacBook runs its own client and docs origin as chezmoi-managed LaunchAgents (com.podhaus.docs-origin and com.podhaus.docs-tunnel in the dotfiles repo), publishing its docs at mac.docs.pod.haus through Numbat's 127.0.0.1:8449. While the laptop sleeps or is off the network, that route answers with Pomerium's upstream error. MacBook setup covers the laptop side.

SSH sign-in links over Signal

Pomerium's native SSH parks an unauthenticated connection and shows the browser sign-in URL only on the interactive terminal, so headless clients (agents, git, ansible) hang with no way to see it. The ssh-auth-notify sidecar in the pomerium/ stack closes this: it watches the databroker's SessionBindingRequest records over the loopback gRPC ingress (127.0.0.1:5443, HS256-JWT-signed with the shared secret) and forwards every state change to fenwick, which puts the tappable sign-in link on the key owner's Signal within seconds. Approving in the browser completes the original parked connection — nothing client-side is wrapped.

The record id is the user_code, so the sidecar reconstructs the sign-in URL directly. The target route is not in the record; it appears only in Pomerium's debug log line ssh keyboard-interactive auth request, so the stack runs log_level: debug (with proxy_log_level: info keeping envoy's volume at normal levels) and the sidecar joins log to record on the key fingerprint via the docker socket. Who gets notified is configuration, not code: the POMERIUM_SSH_KEY_OWNERS variable in pomerium/stack.toml maps fingerprints to {user, machine}.

Pocket ID is the gate; the key you hold decides how much that identity buys. Anyone completing an SSH handshake with any key reaches keyboard-interactive — Pomerium writes the binding record before evaluating policy — so nothing can suppress a sign-in prompt at the key layer. What the key decides is two things. First, whether the link is pushed to Signal at all: the sidecar drops in_flight events for fingerprints outside the owner map (logged, never forwarded), keeping the notification channel from becoming a spam channel that anyone on the internet can ring. Second, what an approved link is worth: each SSH route in pomerium/config.yaml carries two OR'd allow rules, so a registered key may assume any principal (including root — the hosts run PermitRootLogin without-password with no AuthorizedPrincipalsFile, accepted knowingly since the same person could sudo), while an unregistered key is confined to the host's own login account — nathan everywhere, admin on kangaroo.

So an unregistered key is never locked out, only less convenient and less privileged: copy the URL Pomerium prints on the terminal, approve it, connect as the host account. Resolutions for unknown keys still forward — an approval of an unregistered key is an anomaly fenwick flags to POMERIUM_SSH_AUTH_DEFAULT_USER. Registering a key means updating both lists — the owner map in pomerium/stack.toml (who gets the push) and the ssh_publickey list in pomerium/config.yaml (full authorized_keys form, whether any principal is mintable) — plus a fenwick account for a new person. The client side of that contract lives in chezmoi: a Match host ssh.pod.haus block pins IdentitiesOnly to the machine key and the personal key, so an agent holding several identities cannot present an unregistered one by accident.

Because Pomerium hands the sign-in URL to whoever is connecting, the remaining defence against a phished link is behavioural: a link that reaches you by any route other than fenwick is someone else's parked connection — never approve one you did not just cause.

Transport is the gateway-token pattern: fenwick-events.pod.haus (relay address, Caddy :4444) requires the fenwick_events gateway token, then relays to fenwick's token-authenticated /events/async injection transport with X-Fenwick-User routing. Delivery is at-most-once — event ids are fenwick-assigned, so the sidecar never retries; a missed notification is a loud sidecar log, never a duplicate Signal message. The fenwick half (deterministic in_flight delivery with no LLM in the path, guidance-gated resolutions) is documented in the fenwick repo's docs/ssh-auth.html. The databroker protos are vendored at v0.33.0 and unpinned by design: if a Pomerium upgrade shifts the internal contract, the sidecar restart-loops loudly and the protos get refreshed then. A candidate upstream PR — putting the route hostname in the record's Details — would drop both the log join and the debug log level.

Quokka's USB Ethernet reservation and split-horizon SSH name use 10.0.0.199. Its docs name stays on Pomerium, which reaches Quokka's Caddy through the tunnel listener at 127.0.0.1:8548 on Numbat. Its off-LAN SSH route uses 127.0.0.1:2307. Docs use the friends policy; SSH uses Nathan's existing policy.

Identity and machine exceptions

Pomerium's default policy allows members of Pocket ID's family group, which it reads from the groups claim of the sign-in token. Gatus, the shared docs site, Forgejo and the local model service also allow the friends group. Syncthing, Sonarr, bookshelf, the development service and the Pine Lake names are Nathan-only, matched on his email. Exact public exceptions exist for Forgejo LFS, Komodo's GitHub webhook, HyperDX MCP, the local model service's setup page, and the separate Paperless API hostname. HyperDX and Paperless each require a distinct X-Podhaus-Gateway-Token from the Pomerium Gateway Tokens 1Password item, followed by the application's own credential.

llm.pod.haus, the local model service on fractal, is the route for command-line clients. It treats a bearer token as a Pocket ID access token (bearer_token_format: idp_access_token): pi or Claude Code send the token that the setup page's llm-token command fetches through Pocket ID's device sign-in as their API key, and the friends policy applies to it. Pomerium checks each token with Pocket ID once, at first use, and honours it for 30 days. The /setup paths are a public route: the setup page there signs in through Pocket ID in the browser and shows the same kind of token, so Pocket ID's group limit on the client is its gate. The /control paths are a separate Nathan-only route, and fractal's Caddy checks the caller's email again before forwarding them. Pomerium passes that email to the origin as X-Pomerium-Claim-Email on every route that passes identity headers. On fractal itself, Caddy serves the same paths with no sign-in at 127.0.0.1:8085. Fenwick on bandicoot reaches the model paths alone across the LAN at fractal.pod.haus:8086, also with no sign-in. Caddy answers 403 to any address but bandicoot's (fractal's Windows-side settings).

Umami's per-site tracker hosts expose only /script.js and /api/send. Read-only views stay behind Pomerium at stats.pod.haus/share/BRudfaqCQRTlnGYa/nathanbaxter.com, stats.pod.haus/share/xc2sfWOKuH3EbeXy/pets.indigopod.au, and stats.pod.haus/share/akYfaxpJqfylsF7D/skycroeser.net.

Cloudflare scope

Cloudflare remains authoritative DNS and the CDN for public websites and their Umami ingestion paths. CDN zones use Full (Strict) TLS plus Authenticated Origin Pulls, so Caddy rejects direct requests that bypass Cloudflare. Protected services and raw protocols are DNS-only. The origin-directed cache contract and per-site invalidation paths are in Public site caching. Podhaus service traffic no longer uses Cloudflare Tunnel or Access. Pine Lake's home, torrent, and sync names all use the Numbat pattern.

Management and logs

Numbat Periphery dials wss://core-connect.pod.haus/ws/periphery through the public TLS relay; Caddy exposes that exact path and Komodo's Noise keys authenticate it. Numbat Alloy sends OTLP to https://logs-ingest.pod.haus; Caddy requires Numbat's client certificate and ClickStack requires its ingestion key. Neither path uses Tailscale or exposes an internal management listener. Separately, a host enrolled with tailscale-recovery-bootstrap runs host-native Tailscale in userspace mode as an SSH-only recovery plane, joining the tailnet as <host>-recovery with tag:recovery; the tailnet's devices carrying that tag are the current members. The tag:recovery ACL permits member devices to TCP 22 and no reverse reach; containers receive no socket, route, state, or network capability. Pine Lake uses hosted JetKVM for recovery and is not part of the Tailscale recovery plane.

DNS

All DNS is Terraform-managed under terraform/, state in RustFS at s3://terraform-state/podhaus.tfstate:

  • Cloudflare public zones: DNS-only A records to Numbat for protected and raw services; proxied A records to Numbat's relay address for the public CDN sites. Pine Lake's home, torrent, and sync records point to Numbat's application address.
  • UniFi LAN-side split-horizon. unifi.pod.haus and bilby.pod.haus resolve to Bilby at 10.0.0.119 (from local.bilby_ip; see LAN addresses). Kangaroo stays on public DNS so its browser path remains behind Pomerium.

Workflow: edit the relevant dns_<zone>.tf, run terraform plan from terraform/, then terraform apply (stock terraform, no wrapper, from any machine; creds are loaded by the PWD-scoped chezmoi fish hook through op inject). The S3 state backend is the public https://storage.pod.haus (Caddy → RustFS), not Cloudflare-proxied — see Terraform.

Provider docs (read before editing): cloudflare_dns_record, unifi_dns_record.
