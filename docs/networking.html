Networking

Docker bridge networking, Terraform-managed Cloudflare ingress, Access policy chains, public Cloudflare DNS, and LAN UniFi DNS. Cloudflared talks directly to most backends; Caddy handles the DNS-only relay services that need public TLS on bilby.

dockernet bridge

Every UI-facing container joins an external bridge network called dockernet at 172.18.0.0/16. Within the bridge, containers reach each other by container name via Docker's embedded DNS — never by static IP. Static IPs are reserved for LAN devices (e.g. the UniFi gateway at 10.0.0.1) and host-network services.

Each consumer compose file declares: 

networks:
  - dockernet

# at the bottom:
networks:
  dockernet:
    external: true

Host-network services

A few services need direct host network access:

  • Home Assistant — Bluetooth, mDNS, multicast device discovery.
  • Plex — Plex's own LAN discovery protocol, GDM/DLNA.
  • Syncthing (kangaroo-side) — LAN device discovery via UDP/21027 multicast.

These declare network_mode: host in their compose. Cloudflare Tunnel reaches them via the dockernet bridge gateway IP 172.18.0.1 from cloudflared's side of the bridge — same pattern as home.pod.haus → 172.18.0.1:8123.

Cloudflare Tunnel

Forgejo uses one DNS-only hostname with two raw relay paths. https://git.pod.haus reaches kookaburra :443, traverses rathole to bilby's Caddy, then proxies to Forgejo; Pocket ID is the application login. git.pod.haus:22 reaches rathole on the droplet's anchor address and forwards to Forgejo's embedded SSH server. Host administration remains on port 22 of kookaburra's ordinary public address because sshd binds only that address. This gives ordinary web and git@git.pod.haus:owner/repo.git URLs without Cloudflare Access, Tailscale, or custom client ports.

DNS-only S3 endpoints: storage.pod.haus and pouch.pod.haus The two public S3 endpoints are grey-cloud DNS A records to the kookaburra rathole relay (DigitalOcean droplet, public IP 170.64.241.136) → rathole reverse tunnel → Caddy on bilby (own LE certificates) → MinIO. storage.pod.haus terminates at bilby's primary MinIO; pouch.pod.haus crosses the LAN from Caddy to the dedicated Pouch-backed MinIO on kangaroo. The home network has NO inbound WAN port — bilby dials out to kookaburra. The S3 data path cannot traverse Cloudflare's HTTP proxy (rewrites the SigV4-signed Accept-Encoding; single-level cert can't cover Publii vhost buckets); the rathole tunnel is raw TCP passthrough so SigV4 + Host stay intact. Both hostnames share the existing rathole storage service on public port 443; Caddy selects the backend by Host. See hosts → kookaburra for the relay host details and Terraform for the backend configuration.
Management plane: Tailscale (tag:podnet) Inter-host management traffic (Kookaburra Periphery dialing Core and log ship-back from Kookaburra to bilby's ClickStack) rides a private Tailscale tailnet — bilby (bilby-podnet) and kookaburra (kookaburra-podnet). Kookaburra's Periphery dials ws://bilby-podnet.tail9ceb.ts.net:9120. The Kookaburra server entry has an empty address because Core expects the outbound connection; no port 8120 is exposed on the droplet. Resolution works because both bilby's and kookaburra's /etc/docker/daemon.json set "dns": ["100.100.100.100", "1.1.1.1"] — Docker's embedded resolver (127.0.0.11) forwards unknown names to Tailscale's MagicDNS first, then 1.1.1.1; service-name resolution (ferretdb, caddy, etc.) is still handled by the embedded resolver before forwarding. The same setup on kookaburra lets alloy reach bilby's ClickStack at http://bilby-podnet.tail9ceb.ts.net:4318 without hardcoding bilby's drifting tailnet IP. Per-host daemon.json is system-level on each box (not in this repo). bilby's was set up manually once; kookaburra's is materialised by kookaburra_bootstrap's idempotent docker-daemon.json step, so a terraform apply -replace droplet rebuild re-establishes MagicDNS forwarding automatically. ACL is asymmetric: your devices → podnet freely; podnet ↛ your devices (blast-radius containment — a popped relay can't pivot into your laptop). The rathole data tunnel is independent (public, noise+token, NOT on the tailnet — clients reaching storage.pod.haus never touch any private network).

Cross-host container reachability — what works today

Asked plainly: can a container on host A reach a container on host B? The answer depends entirely on whether both hosts have a podnet sidecar.

  • bilby ↔ kookaburra: ✓ Either side's dockernet containers can reach the other's containers by tailnet FQDN ({bilby,kookaburra}-podnet.tail9ceb.ts.net). Packet flow: container → host bridge → host kernel routes 100.64.0.0/10 to tailscale0 → WireGuard → destination host's tailscale0 → destination dockernet bridge. The "podnet sidecar" is a network_mode: host tailscale container — it doesn't proxy, it just installs tailscale0 on the host. Host kernel does the routing.
  • bilby ↔ kangaroo: LAN-direct only. Kangaroo has no podnet sidecar (QTS hosts a podnet container would be awkward), so cross-host traffic uses the 10.0.0.0/24 LAN — e.g. kangaroo alloy ships logs to bilby's ClickStack at 10.0.0.119:4318 (bilby's LAN IP). Fine as long as both stay on-LAN.
  • kookaburra ↔ kangaroo: ✗ No path today. Kookaburra is off-LAN; kangaroo isn't on the tailnet.
Subnet routing for non-podnet hosts (not configured — YAGNI) Tailscale supports promoting a podnet member to a subnet router so the rest of the tailnet can reach hosts on its LAN. For us that would mean tailscale up --advertise-routes=10.0.0.0/24 on bilby, an ACL rule {"src": ["tag:podnet"], "dst": ["10.0.0.0/24:*"]}, and route approval in the Tailscale admin (or via a Terraform-managed Tailscale ACL). After that, permitted tailnet nodes, including Kookaburra, your off-LAN laptop, future pinelake — could reach kangaroo at 10.0.0.25.

Not enabled because nothing needs it. Kangaroo's outbound traffic (alloy → ClickStack, backrest → bilby) is initiated from kangaroo and uses the LAN directly. If a future requirement flips that — kookaburra needing kangaroo, or remote admin into kangaroo without VPN — turn it on then. Documented here so the option is discoverable.

A single cloudflared container on bilby holds the pod.haus tunnel credential. It starts without --config and fetches ingress from Cloudflare. Terraform's cloudflare_zero_trust_tunnel_cloudflared_config.pod_haus resource in terraform/tunnel.tf is the source of truth. 

- hostname: gatus.pod.haus
  service: http://gatus:8080
- hostname: home.pod.haus
  service: http://172.18.0.1:8123

Anything not listed returns 404 at the tunnel edge. For a normal pod.haus service, add a module block in terraform/services_pod_haus.tf, append its ingress output to pod_haus_module_ingress, then run terraform apply from terraform/. Cloudflared receives the remote configuration without a stack deploy.

cloudflared is distroless No shell, no curl, no wget — the image only ships the cloudflared binary. In-container healthchecks against /ready on port 20241 are structurally impossible, so the stack has no healthcheck and no autoheal label. cloudflared handles its own reconnection; restart: unless-stopped catches outright crashes; external liveness is monitored by Gatus hitting the public hostnames.

Cloudflare Access

All Access applications, policies, groups, and service tokens are codified in terraform/access.tf (Terraform). A single Pod Haus wildcard Application covers *.pod.haus with a Family allow policy — any single-label hostname under pod.haus is gated by browser-side Cloudflare Access login automatically.

Identity providers. Two login methods are offered and the Access login page shows a chooser: GitHub (dashboard-managed) and Pocket ID — a self-hosted passkey OIDC provider at id.pod.haus, registered as a generic-OIDC IdP in access.tf. The IdP only authenticates; the Family group still decides who is allowed, and allowed_idps is left unset on every app so both methods stay available (no lockout). See the Pocket ID runbook.

Implication for hostname design: prefer single-label names like backup.pod.haus over multi-label like backup.kangaroo.pod.haus — the wildcard only covers one label. Host-distinguishing names use a hyphen prefix instead (kangaroo-backup.pod.haus).

Every tunnel-routed pod.haus hostname has its own Access app, created by an instance of the terraform/modules/pod_haus_service Terraform module (one block per service in terraform/services_pod_haus.tf). The default policy chain is "Homelab service-token bypass → Family allow" — locked by default, overridable per service.

Per-service policy overrides currently in use:

  • UniFi — single Bypass-everyone policy (UniFi has its own LAN login).
  • Pocket ID (id.pod.haus) — Bypass-everyone, so Cloudflare can fetch the IdP's OIDC token + JWKS endpoints server-side; Pocket ID's own passkey login guards the admin UI. See the runbook.
  • Syncthing — Homelab bypass + Nathan-only reusable policy (cross-household concern, household share is private).
  • Paperless — Paperless-iOS service-token bypass at precedence 1, then the default chain.
  • Pine Lake apps — Nathan-only reusable policy, separate from the Family group (cross-household).
  • Komodo webhook — path-scoped Bypass on the komodo.pod.haus/listener/github prefix (Komodo's per-stack webhook listeners all live under it) so GitHub webhook deliveries skip Access; Komodo HMAC-validates each delivery itself.

The *.pod.haus wildcard Access app stays as the default-deny safety net. Anything not covered by a more-specific app falls through to it; the wildcard denies unless you're in the Family group or carrying the Homelab service token.

Service tokens

Two service tokens for programmatic access. Send as CF-Access-Client-Id + CF-Access-Client-Secret headers:

  • Homelab service token (op://Homelab/Cloudflare Access — Homelab Service Token) — full bypass of the *.pod.haus surface plus every per-host override above. One token, everything. Treat as high-value; a leak grants access to all of pod.haus.
  • Paperless iOS (op://Homelab/Cloudflare Access — Paperless iOS Service Token) — bypass scoped to paperless.pod.haus only. Paste both header values into Swift Paperless > Settings > Connection > Extra Headers.

DNS

All DNS is Terraform-managed under terraform/, state in MinIO at s3://terraform-state/podhaus.tfstate:

  • Cloudflare public zones — per-zone dns_<zone>.tf files plus the per-service module's CNAME for each tunnel-routed pod.haus host.
  • UniFi LAN-side split-horizon — dns_unifi_split_horizon.tf declares the two A records (unifi.pod.haus → 10.0.0.1, bilby.pod.haus → 10.0.0.119) via the ubiquiti-community/unifi provider against the UniFi controller at 10.0.0.1.

Workflow: edit the relevant dns_<zone>.tf, run terraform plan from terraform/, then terraform apply (stock terraform, no wrapper, from any machine; creds are loaded by the PWD-scoped chezmoi fish hook through op inject). The S3 state backend is the public https://storage.pod.haus (Caddy → MinIO), not Cloudflare-proxied — see Terraform.

Provider docs (read before editing): cloudflare_dns_record, unifi_dns_record.
