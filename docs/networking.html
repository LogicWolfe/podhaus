Networking

Docker bridge networking, Numbat's Pomerium and rathole edge, Caddy origin separation, and Terraform-managed DNS.

dockernet bridge

Every UI-facing container joins an external bridge network called dockernet at 172.18.0.0/16. Within the bridge, containers reach each other by container name via Docker's embedded DNS — never by static IP. Static IPs are reserved for LAN devices (e.g. the UniFi gateway at 10.0.0.1) and host-network services.

Each consumer compose file declares: 

networks:
  - dockernet

# at the bottom:
networks:
  dockernet:
    external: true

Host-network services

A few services need direct host network access:

  • Home Assistant — Bluetooth, mDNS, multicast device discovery.
  • Plex — Plex's own LAN discovery protocol, GDM/DLNA.
  • Syncthing (kangaroo-side) — LAN device discovery via UDP/21027 multicast.

These declare network_mode: host in their compose. Caddy reaches them via the dockernet bridge gateway IP 172.18.0.1, such as home.pod.haus → 172.18.0.1:8123.

Numbat edge

Numbat is the active public gateway. Bilby and other internal targets make named outbound rathole connections to it; Numbat has no routed path into the home network.

Port 22 on both addresses carries a per-source nftables rate limit on new connections (10/minute, burst 20); established sessions are never touched, and over-limit sources are dropped before they reach Pomerium or the Forgejo relay.

Protected browser names resolve to the application address. Pomerium authenticates with Pocket ID, then reaches Caddy's private :4443 listener through a loopback-only rathole service. That listener also requires Pomerium's client certificate. The public rathole service reaches Caddy :4444, which has no protected virtual hosts.

The public listener serves MinIO S3, Pocket ID, UniFi, static sites, scoped Umami ingestion, paperless-api.pod.haus, Komodo's outbound connection, and mTLS log ingestion. Forgejo uses Pomerium for HTTPS and the application address on port 22 for ordinary git@git.pod.haus SSH. Managed devices use the canonical <host>.pod.haus name for host SSH. Chezmoi sends Bilby and Fractal directly through split DNS and Kangaroo directly to its active LAN address while preserving the canonical host-key identity. Fractal's split-horizon record resolves to the Windows host's :22 forward (UniFi-reserved, both in Terraform) and is safe precisely because fractal.pod.haus is SSH-only — its HTTPS name fractal.docs.pod.haus is separate and stays on Pomerium — and it keeps fractal reachable from the LAN even when the Pomerium edge is down. Chezmoi sends all other cases through Pomerium at ssh.pod.haus:22. On an unmanaged device, connect as nathan@ssh.pod.haus and choose a route from Pomerium's portal. Routes are named bilby, fractal, numbat, voltaire, and kangaroo. CA trust on Ansible-managed hosts comes from the sshd_pomerium_ca role; on kangaroo (which Ansible cannot reach — QTS has no Python) kangaroo_bootstrap installs a boot-persistent start.sh that re-applies the trust after QTS regenerates sshd_config. Every host's outbound tunnel is a Komodo-managed rathole container (relay/*); kangaroo's runs on host networking because QTS cannot run the current upstream x86_64 rathole binary in a systemd unit. Kangaroo's canonical route maps to QTS's real UID 0 account, admin. Tailscale recovery keeps separate *-recovery names so its break-glass role stays explicit.

SSH sign-in links over Signal

Pomerium's native SSH parks an unauthenticated connection and shows the browser sign-in URL only on the interactive terminal, so headless clients (agents, git, ansible) hang with no way to see it. The ssh-auth-notify sidecar in the pomerium/ stack closes this: it watches the databroker's SessionBindingRequest records over the loopback gRPC ingress (127.0.0.1:5443, HS256-JWT-signed with the shared secret) and forwards every state change to fenwick, which puts the tappable sign-in link on the key owner's Signal within seconds. Approving in the browser completes the original parked connection — nothing client-side is wrapped.

The record id is the user_code, so the sidecar reconstructs the sign-in URL directly. The target route is not in the record; it appears only in Pomerium's debug log line ssh keyboard-interactive auth request, so the stack runs log_level: debug (with proxy_log_level: info keeping envoy's volume at normal levels) and the sidecar joins log to record on the key fingerprint via the docker socket. Who gets notified is configuration, not code: the POMERIUM_SSH_KEY_OWNERS variable in pomerium/stack.toml maps fingerprints to {user, machine}.

Pocket ID is the gate; the key you hold decides how much that identity buys. Anyone completing an SSH handshake with any key reaches keyboard-interactive — Pomerium writes the binding record before evaluating policy — so nothing can suppress a sign-in prompt at the key layer. What the key decides is two things. First, whether the link is pushed to Signal at all: the sidecar drops in_flight events for fingerprints outside the owner map (logged, never forwarded), keeping the notification channel from becoming a spam channel that anyone on the internet can ring. Second, what an approved link is worth: each SSH route in pomerium/config.yaml carries two OR'd allow rules, so a registered key may assume any principal (including root — the hosts run PermitRootLogin without-password with no AuthorizedPrincipalsFile, accepted knowingly since the same person could sudo), while an unregistered key is confined to the host's own login account — nathan everywhere, admin on kangaroo.

So an unregistered key is never locked out, only less convenient and less privileged: copy the URL Pomerium prints on the terminal, approve it, connect as the host account. Resolutions for unknown keys still forward — an approval of an unregistered key is an anomaly fenwick flags to POMERIUM_SSH_AUTH_DEFAULT_USER. Registering a key means updating both lists — the owner map in pomerium/stack.toml (who gets the push) and the ssh_publickey list in pomerium/config.yaml (full authorized_keys form, whether any principal is mintable) — plus a fenwick account for a new person. The client side of that contract lives in chezmoi: a Match host ssh.pod.haus block pins IdentitiesOnly to the machine key and the personal key, so an agent holding several identities cannot present an unregistered one by accident.

Because Pomerium hands the sign-in URL to whoever is connecting, the remaining defence against a phished link is behavioural: a link that reaches you by any route other than fenwick is someone else's parked connection — never approve one you did not just cause.

Transport is the gateway-token pattern: fenwick-events.pod.haus (relay address, Caddy :4444) requires the fenwick_events gateway token, then relays to fenwick's token-authenticated /events/async injection transport with X-Fenwick-User routing. Delivery is at-most-once — event ids are fenwick-assigned, so the sidecar never retries; a missed notification is a loud sidecar log, never a duplicate Signal message. The fenwick half (deterministic in_flight delivery with no LLM in the path, guidance-gated resolutions) is documented in the fenwick repo's docs/ssh-auth.html. The databroker protos are vendored at v0.33.0 and unpinned by design: if a Pomerium upgrade shifts the internal contract, the sidecar restart-loops loudly and the protos get refreshed then. A candidate upstream PR — putting the route hostname in the record's Details — would drop both the log join and the debug log level.

Identity and machine exceptions

Pomerium's default policy allows the two family Pocket ID identities. Syncthing and the development service are Nathan-only. Exact public exceptions exist for Forgejo LFS, Komodo's GitHub webhook, HyperDX MCP, and the separate Paperless API hostname. HyperDX and Paperless each require a distinct X-Podhaus-Gateway-Token from the Pomerium Gateway Tokens 1Password item, followed by the application's own credential.

Umami's per-site tracker hosts expose only /script.js and /api/send. Read-only views stay behind Pomerium at stats.pod.haus/share/BRudfaqCQRTlnGYa/nathanbaxter.com, stats.pod.haus/share/xc2sfWOKuH3EbeXy/pets.indigopod.au, and stats.pod.haus/share/akYfaxpJqfylsF7D/skycroeser.net.

Cloudflare scope

Cloudflare remains authoritative DNS and the CDN for public websites and their Umami ingestion paths. CDN zones use Full (Strict) TLS plus Authenticated Origin Pulls, so Caddy rejects direct requests that bypass Cloudflare. Protected services and raw protocols are DNS-only. The origin-directed cache contract and per-site invalidation paths are in Public site caching. Podhaus no longer uses Cloudflare Tunnel or Access. Voltaire retains its independent tunnel, and Pine Lake retains its existing Tunnel and Access estate until that host migrates to the Numbat pattern.

Management and logs

Numbat Periphery dials wss://core-connect.pod.haus/ws/periphery through the public TLS relay; Caddy exposes that exact path and Komodo's Noise keys authenticate it. Numbat Alloy sends OTLP to https://logs-ingest.pod.haus; Caddy requires Numbat's client certificate and ClickStack requires its ingestion key. Neither path uses Tailscale or exposes an internal management listener. Separately, Bilby, Numbat, and Kangaroo run host-native Tailscale in userspace mode as an SSH-only recovery plane. The tag:recovery ACL permits member devices to TCP 22 and no reverse reach; containers receive no socket, route, state, or network capability. While Pine Lake is being admitted to the fleet, one explicitly addressed temporary exception permits Bilby's recovery node to reach Pine Lake's Tailscale address on TCP 22 only; it is removed after Pine Lake's outbound Numbat SSH route passes off-LAN and reboot validation.

DNS

All DNS is Terraform-managed under terraform/, state in MinIO at s3://terraform-state/podhaus.tfstate:

  • Cloudflare public zones: DNS-only A records to Numbat for protected and raw services; proxied A records to Numbat's relay address for the public CDN sites. Pine Lake retains its explicit tunnel records until it moves to the outbound Numbat contract.
  • UniFi LAN-side split-horizon. unifi.pod.haus and bilby.pod.haus resolve to Bilby at 10.0.0.119. Kangaroo stays on public DNS so its browser path remains behind Pomerium.

Workflow: edit the relevant dns_<zone>.tf, run terraform plan from terraform/, then terraform apply (stock terraform, no wrapper, from any machine; creds are loaded by the PWD-scoped chezmoi fish hook through op inject). The S3 state backend is the public https://storage.pod.haus (Caddy → MinIO), not Cloudflare-proxied — see Terraform.

Provider docs (read before editing): cloudflare_dns_record, unifi_dns_record.
