Monitoring

Gatus does endpoint monitoring and routes alerts to Fenwick (the Signal home-helper), which triages each alert with an agent turn and notifies over Signal under household guidance; the Fenwick-health checks fall back to Postmark email so the watcher of Fenwick never routes through Fenwick. ClickStack (ClickHouse + HyperDX) is the observability backend; Alloy on all active hosts ships container logs and Gatus metrics to it over OTLP. Autoheal restarts unhealthy containers locally on each host. What a log row carries and how to find it is in Logging; this page covers alerting and the health of the pipeline itself.

Gatus

Forgejo has four independent signals: an internal HTTP health check against forgejo:3000, a public Pomerium-edge check and a TCP check of git.pod.haus:443 and :22, and an external heartbeat from the quiesced Backrest plan. Together they distinguish an application failure, either public relay path failing, and a backup failure.

Config-as-code endpoint monitoring, defined entirely in gatus/conf/config.yaml. Monitors HTTP endpoints, pushed heartbeats, and downstream-service-state checks. Stores results in SQLite with a 90-day cap. Service alerts route to Fenwick (the default custom alerter); the Fenwick-health checks use Postmark email. Unchanged by the ClickStack migration.

Three monitor types in use:

  • HTTP — periodic GET against the service's internal endpoint: a dockernet container name + port (e.g. http://hyperdx:8080/, http://paperless:8000/), the dockernet bridge gateway at 172.18.0.1:<port> for host-network services on bilby (Plex, Home Assistant), or the LAN IP for off-host targets (the QNAP web UI at https://10.0.0.25/). External probes are reserved for paths that genuinely need full-path coverage (storage.pod.haus, numbat-probe.storage.pod.haus, nathanbaxter.com, voice.pod.haus) that are intentionally public. Probing protected public URLs is deliberately avoided: Pomerium returns a login 302 for unauthenticated requests, which the default [STATUS] < 400 condition accepts as healthy — masking backend failure. Bit us on 2026-05-30 (see postmortem).
  • Push (external endpoints) — bearer-token-protected URLs that jobs/scripts POST to with success=true|false&error=.... Used for Backrest nightly heartbeats, Sky cache invalidation, and the RAR-extraction backlog scan.
  • Komodo-API check — Gatus calls Komodo Core's /read API and asserts a downstream state. Periphery checks cover every Komodo host through GetServerState. Remote-container checks use InspectDockerContainer and require both running state and healthy Docker health; this covers kangaroo services, the Fractal/Voltaire docs instances, the two local model containers, and bandicoot's Backrest, Radarr, bookcard and bookbinder. Bilby's docs health is probed directly over dockernet. The Komodo Alerts check asserts no unresolved CRITICAL alert, which in Komodo 2.3 means server health only (unreachable, CPU, memory, disk). Komodo never stores a failed procedure, action or build as an alert, so deploys are watched through Komodo's summary counts instead (below).

Failed deploys. Every push deploy, podhaus's and each service repo's, is a Komodo procedure. The Komodo procedures check reads GetProceduresSummary every minute and fails while any procedure's last run failed; Komodo stacks reads GetStacksSummary and fails while any stack is unhealthy, restarting, dead, created or removing. After three failed checks Gatus sends a service_alert to Fenwick, which tells Nathan on Signal, and a resolution notice follows two passing checks later. Both checks also fail if the API key can see no procedures or stacks. The limits come from the counts: the alert says that a procedure failed or a stack is unhealthy, never which one, so the next step is komodo.pod.haus. A failed procedure stays failed until it next succeeds, so the check stays red until then, and a second failure during that time raises no new alert. A failed Fenwick deploy also reports through Fenwick; if it leaves Fenwick down, the Fenwick-health email checks are the backstop.

Local model service. Two InspectDockerContainer checks in the group Local model read llm-server and llm-watcher on fractal every minute and require running state and healthy Docker health, with the default three-failure alert. The server's health probe is the router's /health, which passes with no model loaded, so a model yielded to a game never trips it; the check means the server process is down or hung. The watcher's own health check is where the service's real failure states surface: a yield that did not release the GPU, a model spilled out of video memory, loads given up, a hung model server. Its alert text names each reason and the log line to read, and a watcher that keeps ending itself (GPU sampling stalled, or the router unreachable, as during every llm-server restart) reads as restarting. The watcher has no autoheal label, so a restart cannot clear and hide those states. See the local model runbook.

Live monitors today cover every podhaus service plus the Backrest, RAR-extraction (cron safety-net), and kangaroo-backrest heartbeats. gatus.pod.haus shows the live status page.

Alerting is wired into the shared *defaults anchor: every endpoint that spreads <<: *defaults inherits alerts: *alerts (which is just [{type: custom}], picking up failure-threshold: 3 / send-on-resolved: true from alerting.custom.default-alert). The custom alerter now POSTs each alert to Fenwick (fenwick:8088/events/async) as a service_alert event; Fenwick's agent decides how to notify. The Fenwick-health checks deliberately opt out of the anchor with alerts: [{type: email}] (Postmark SMTP) — a check must never route through the thing it watches. Non-anchor endpoints declare their alerts: list explicitly. Adding a new monitor without alerts is a deliberate act, not the default.

Gatus metrics

gatus/conf/config.yaml sets metrics: true, exposing a Prometheus /metrics endpoint on Gatus's existing :8080 (the same port as the UI; /metrics remains Pomerium-protected). bilby's Alloy prometheus.scrapes it at a ~60s cadence and bridges Prometheus → OTLP through the same authenticated exporter as the logs. The series land in ClickHouse's otel_metrics_* tables and are queryable and dashboardable in HyperDX. Gatus's own endpoint/heartbeat monitoring and the alert chain (Gatus → Fenwick, with the Postmark backstop) are unaffected by this.

ESPHome device metrics

IoT devices under iot/esphome/ enable ESPHome's prometheus: component, exposing every entity as OpenMetrics on the device's own web server. bilby's Alloy scrapes each device at 60 s and bridges it through the same authenticated exporter, landing under service.name = esphome with instance separating devices. This is the only telemetry path off these devices — ESPHome has no syslog output, and the MQTT route would mean a broker plus a bridge process to carry log lines that are worth less than the entity state. Targets are scraped by IP, since Docker's resolver has no mDNS, so each device needs a UniFi DHCP reservation in terraform/unifi.tf; without one a lease change ends the scrape with no error anywhere. Kept deliberately narrow — roughly ten series per device — because bilby's ClickHouse runs under a 4 GB cap, which is also why scraping Home Assistant's /api/prometheus for every entity in the house is not a like-for-like alternative. See BLE remotes.

Local model metrics and logs

fractal's Alloy scrapes llm-watcher:8081/metrics and llm-server:8080/metrics every 15 s and bridges them through the same exporter, landing under service.name = llm-watcher and llm-server with host.name = fractal. The watcher's series are its state (llm_watcher_state, one series per state), GPU use, memory, power and temperature, the guest's memory and the slot pool. The server's are llama.cpp's request and token counters; the router forwards the scrape to the model process, so it names the model and sets autoload=false, and with no model loaded the scrape fails, which is a yielded signal that llm_watcher_state confirms. Their logs follow the logging schema: every field of the watcher's JSON events is an attribute, the event name among them as event, and the server's lines pass an allow-list that stores a line as printed only when it carries no prompt or reply text. Dashboards over these are not defined in the repository; they are created by hand in HyperDX. See the local model runbook.

Adding a Gatus monitor

Edit gatus/conf/config.yaml — YAML anchors at the top define common defaults (interval, alert config, conditions). Set the endpoint's group: to the service it belongs to (Komodo, Backup, Observability, Torrents, Plex, Storage, …) — grouping is service-primary, so a check lands with its service regardless of which host runs it. Note that for push (external) endpoints the group is part of the push key (<group>_<name>, lowercased, spaces→hyphens), so the sender's target URL must match. Save. Gatus reloads config automatically on file change — no restart.

A push (external) endpoint also needs a token: — the bearer the sender presents (Authorization: Bearer <token>). These tokens are not per-service: the endpoint key in the push URL is what routes a heartbeat to the right check, so a new heartbeat should reuse the general-purpose ${GATUS_HEARTBEAT_PUSH_TOKEN} (1Password Homelab item Gatus Heartbeat Push Token) rather than minting another. The older per-service tokens (GATUS_BACKREST_PUSH_TOKEN, GATUS_OFELIA_PUSH_TOKEN, GATUS_BACKREST_KANGAROO_PUSH_TOKEN) are kept as-is — no migration. The brinno site-time-lapse downloader's timelapse_brinno heartbeat (group Timelapse, 48h staleness window) is the reference example: it pushes to gatus:8080/api/v1/endpoints/timelapse_brinno/external?success=true with that bearer.

Sky's backup check is storage-driven. The hourly sky-backups-monitor job lists encrypted snapshot objects under sky-backups/personal-laptop/snapshots/ in Pouch RustFS and reports whether the newest object was committed within seven days. The job pushes its result to Gatus over dockernet; the laptop has no Gatus token or callback. Its Backup / Sky Restic Repository endpoint has a two-hour heartbeat window so a stopped monitor also becomes unhealthy. Before the first snapshot, the repository's config object supplies the seven-day initialization grace period.

Ingest-staleness alerts

Monitor for the absence of expected telemetry, not just service up/down. A process can be healthy while delivering no data: Alloy's own healthcheck stays green while the path to the collector is down, on purpose, so its queue survives, and a dead cross-LAN path is invisible to an ordinary up/down check. This is the guard for the recurring kangaroo cross-LAN exporter failure class.

Implemented as Gatus endpoints that POST a ClickHouse query and assert recent telemetry per host. Gatus runs on bilby and reaches ClickHouse across the LAN at bandicoot's published port, http://${BANDICOOT_LAN_IPV4}:8123/, with headers X-ClickHouse-User: default and X-ClickHouse-Key: ${CLICKHOUSE_PASSWORD}. Conditions: [STATUS] == 200 and [BODY] == 1. Use count() > 0 over an explicitly time-windowed scan, not max(Timestamp) > now() - INTERVAL N over an unbounded one — the Map predicate (...['host.name']=…) defeats primary-key pruning, so without the time filter the query scans every active part and times out at gatus's 10 s budget: 

SELECT toUInt8(count() > 0) FROM default.otel_logs
WHERE Timestamp > now() - INTERVAL <N> MINUTE AND ResourceAttributes['host.name']='<host>'

Six live endpoints in gatus/conf/config.yaml, of two kinds: heartbeats (assert a fresh Alloy self-metric reached ClickHouse, i.e. the host's whole telemetry ship-path Alloy → collector → ClickHouse is alive) and a log-volume check (counts otel_logs rows). Named for what they measure:

  • Five <Host> Telemetry Pipeline heartbeats, for kangaroo, Numbat, pinelake, bandicoot and voltaire. Each host's Alloy scrapes its own self-metrics every 60 s and ships them through the same exporter as the logs, so the query asserts a fresh per-host Alloy metric in a 15-minute window (otel_metrics_gauge where ResourceAttributes['host.name']='<host>'; the host.name attribute is stamped by the host_name transform in the ship module, logging/alloy-modules/ship.alloy, from the host name each host's config.alloy gives it). A wedged exporter, whose requests never return, is healed before the window empties: Alloy's healthcheck makes the container unhealthy 5–6 minutes after the exporter's last request completed, autoheal restarts it within 30 seconds, and the restarted Alloy delivers its first self-metric within about 90 seconds, so metrics resume within about 8 minutes of the last one and no check fails (exporter-stall healthcheck). A path to the collector that is down never restarts Alloy, which keeps its queue and delivers it once the path is back. A path down for longer than the window, or a wedge the restart does not cure, alerts 20–25 minutes after the last metric arrived: the window must first empty (15 minutes), the check runs every 5 minutes, and it alerts on the second failure in a row. Fractal deliberately has none: the existing Docs (fractal, via Komodo) check is the one alert wanted for fractal, and no further fractal alert is added.
  • Pipeline Log Ingest (bilby / total) is a 10-minute count() check that detects total collector, ClickHouse, or Alloy failure. A healed wedge of bilby's own exporter leaves a gap of at most about 8 minutes in its logs, inside the window. The heartbeats cover the other hosts' complete shipping paths without assuming a minimum log volume.

These are service checks, so their alerts ride the default Gatus → Fenwick chain. CLICKHOUSE_PASSWORD must be available to gatus — set in both the gatus/stack.toml env block and the gatus/compose.yaml service environment: (see the secrets doc's stack.toml↔compose env rule). To add another source, copy an endpoint block and change the host.name filter and window.

ClickStack

ClickStack is the observability backend on bandicoot (moved from bilby on 2026-09-09: 21 GB of growing local state and the fleet's one sustained CPU load belong on the host with the NVMe and the cores). It is the clickstack/ stack and bundles four containers:

  • ClickHouse (clickstack-clickhouse) — columnar store for telemetry. mem_limit: 4g plus a config.d drop-in (clickhouse-conf/config.d/podhaus.xml) that caps max_server_memory_usage, sets listen_host to 0.0.0.0, enables async_load_databases, and bounds the internal log.
  • HyperDX (hyperdx) — the query/dashboard/alert UI at https://watch.pod.haus. Also hosts the OpAMP server the collector talks to.
  • OTel collector (clickstack-otel) — the bundled OpenTelemetry collector. Bandicoot's Alloy reaches it by container name on dockernet. Its OTLP/HTTP port 4318 is published on the LAN: bilby's, kangaroo's and fractal's Alloy ship to it directly, and bilby's Caddy forwards logs-ingest.pod.haus to it for Numbat, voltaire and pinelake after checking the client certificate. HyperDX's 8080 (for watch.pod.haus, which still terminates on bilby) and ClickHouse's 8123 (for Gatus's pipeline heartbeats) are the other two LAN-published ports; the front doors stay on bilby, on the moved-service pattern.
  • Mongo (clickstack-mongo) — HyperDX app-state only: dashboards, alerts, users, source definitions, the ingestion key. Tiny but irreplaceable.

Alloy log collection

Alloy runs on all seven active hosts as the multi-host logging service: logging on bilby, bandicoot-logging on bandicoot, kangaroo-logging on kangaroo, numbat-logging on Numbat, fractal-logging on fractal, voltaire-logging on voltaire, and pinelake-logging on pinelake. They share logging/compose.shared.yaml and the module directory logging/alloy-modules/; each host's logging/<host>/alloy-conf/config.alloy is a short list of which source modules to run, that host's own scrapes, and its values for the ship module. Alloy tails each host's Docker socket (and the files and journal listed in Logging), and the parser chain hands every line to the ship module, logging/alloy-modules/ship.alloy, which is the same on every host: it bridges Loki-format input to OTLP (otelcol.receiver.loki → enrich → batch → otelcol.exporter.otlphttp), scrapes Alloy's own metrics, and ships to the ClickStack collector at the address each host gives it:

  • bandicoot — the collector's own host: plaintext to http://clickstack-otel:4318 by container name on dockernet.
  • bilby, kangaroo and fractal — cross-LAN to port 4318 at bandicoot's address from config/lan-addresses.json (plaintext, home LAN only), which reaches each stack as BANDICOOT_LAN_IPV4.
  • Numbat: HTTPS to logs-ingest.pod.haus through rathole and Caddy, with a dedicated client certificate.
  • voltaire: the same HTTPS ingress with its own client certificate.
  • pinelake: the same HTTPS ingress with its own client certificate.

Every host opens a new connection for each request (disable_keep_alives). Bilby, kangaroo and fractal need it: they reach the collector at bandicoot's published port, where Docker's NAT keeps a kept-alive connection mapped to the old collector container after a recreate, and the next request hangs with no error (the 2026-06-19 exporter wedge under Known issues). Bandicoot reaches the collector by container name, and the hosts that ship through logs-ingest.pod.haus reach bilby's Caddy, which opens its own connections to the collector; they share the setting because a new connection per request costs little at their volume.

Every request carries a HyperDX ingestion API key in the authorization header. The key lives in 1Password as clickstack-ingestion-key, is synced by komodo-op to a Komodo Variable, injected via each host's logging stack.toml and the shared compose file, and read by the ship module as sys.env("CLICKSTACK_INGESTION_KEY"). An empty/wrong key means a hard 401 and no data in HyperDX — a loud, visible failure with no silent fallback to the old sink.

Which containers, files and journal entries are collected, how each service is named, the parser rules and the schema every row follows are in Logging. tools/lint-alloy-config.py, run by tools/pre-commit, checks that every host config and module is formatted as alloy fmt prints it, that the modules pass alloy validate, and that each host config starts in Alloy against the modules it imports.

Every host's exporter retries a failed batch for at most 30 minutes (retry_on_failure in the ship module), then drops that batch and its queue worker takes the next. The budget is checked only when an attempt returns, so a request that never returns holds its worker whatever the budget; once every worker is held the exporter sends nothing, and the healthcheck below restarts it.

The exporter's queue is held in memory, so a recreate or reboot during a collector or path outage drops whatever is queued. A disk-backed queue (otelcol.storage.file in the alloy-data volume) would keep it, but is not restart-safe in the collector release Alloy carries: on a graceful shutdown while the destination is down, exporterhelper v0.161.0 drains the persisted queue with one attempt per request and deletes every request that fails (opentelemetry-collector issue 15677), and the storage component is public preview.

Exporter-stall healthcheck

An Alloy whose exporter has wedged is restarted, and nothing alerts unless the restart fails to bring delivery back. A wedged exporter is one whose requests never return: each such request holds one of the exporter's queue workers whatever the retry budget, and once every worker is held nothing more is sent. Both recorded wedges had that shape: no log line, no completed request, and a listening port (fractal's Alloy kept its port open through 2h41m of sending nothing, 2026-08-08).

The healthcheck in logging/compose.shared.yaml reads, from Alloy's own :12345/metrics, how many HTTP requests the clickstack exporter has completed: http_client_request_duration_seconds_count for component_id="otelcol.exporter.otlphttp.clickstack", summed over every status code, error type and HTTP version. The exporter sits in the ship module, so its metrics also carry component_path="/podhaus.ship.run"; the check matches the component_id alone. It fails when that count has not risen since the previous check, a minute earlier. Every host scrapes Alloy's own metrics every 60 seconds through the same exporter, so a working exporter completes a request every minute however quiet the host's logs are.

The count is of completed requests, not delivered ones. While the collector or the path to it is down, every request still ends, refused, unresolvable or cut off by the exporter's 30-second timeout, so the count keeps rising and Alloy is not restarted: it keeps its in-memory queue and the 30-minute retry delivers it once the path is back. A restart would drop that queue. An outage that outlasts the heartbeat window alerts through the heartbeats above.

Five failed checks a minute apart make the container unhealthy, 5–6 minutes after the last request completed depending on where the wedge falls between checks, and autoheal, which runs on every host and acts on the alloy container's autoheal label, restarts it within 30 seconds. A pause under 5 minutes never trips it. The Komodo stacks check, which counts unhealthy stacks, alerts only after three failures a minute apart, longer than the 30 seconds at most that an Alloy stays unhealthy. The image has no curl, wget or nc, so the check speaks HTTP through bash's /dev/tcp. It keeps the previous count in a tmpfs that every start empties, so a restarted Alloy, whose counters begin again at zero, is never compared with the process it replaced, and a check that cannot write that state fails. docker inspect alloy --format '{{json .State.Health}}' shows the counts the last five checks read. A restart drops what the wedged exporter had queued, which it was not sending anyway, and ships some lines twice (Logging).

Known risk: a renamed metric restarts every Alloy silently. The check depends on the metric's name and the exporter's component_id label. If an Alloy release changed either, every check would fail and every Alloy would restart every 5–6 minutes with no alert: delivery continues between restarts, so the heartbeats stay green, and no Alloy stays unhealthy long enough for the Komodo stacks check. Each restart drops the queue and reads every stopped container's log again. logging/tests/test_alloy_health.py, run by tools/pre-commit, runs the exact command from the compose file against a delivering, a refusing, a stopping and a never-answering collector, but in the grafana/alloy image cached on the machine that commits, which changes only when someone pulls it, while hosts pull the current image on every deploy. A rename can therefore reach the hosts before any test sees it; an alert on repeated Alloy restarts is a decision in the structured-logging plan.

Storage

ClickStack data lives on bandicoot's local NVMe, not Jump: /var/lib/clickstack/{clickhouse,clickhouse-logs,mongo,mongo-dumps}. ClickHouse and Mongo chown their data dirs to their own uid at startup; the NFS Jump all-squash blocks that, so local disk is mandatory here. Steady-state footprint is ~1.3 GB RAM, bounded by mem_limit on every container plus the ClickHouse config.d memory caps — this is the one memory-risky stack on a shared 15 GB machine.

Backup

ClickHouse telemetry is deliberately not backed up — it's regenerable and large. The MongoDB app-state is backed up: an ofelia job at 03:50 runs mongodump into /var/lib/clickstack/mongo-dumps (keeping the latest ~14 archives), and the Backrest clickstack plan picks that directory up at 05:05 into the existing restic + OneDrive chain.

Known issues

  • kangaroo Alloy log ingest can go stale — two distinct causes, two different fixes. The Kangaroo Telemetry Pipeline (heartbeat) Gatus check fires for both — since 2026-06-20 it's a 60 s self-metric heartbeat (above), which rides the same exporter as the logs, so either, left unrepaired, alerts about 20–25 minutes after the last metric arrived. A wedge stops the exporter's requests completing, so the exporter-stall healthcheck fails and autoheal restarts alloy; the heartbeat alerts only when the restart has not brought delivery back. A lost network fails every request at once, so the healthcheck stays green (a restart would not fix it) and the heartbeat is the alert. Read the alloy log to tell them apart — GetContainerLog kangaroo alloy:
    • Exporter wedge (root cause fixed 2026-06-19) — the exporter would stop shipping silently (no errors, just silence) and not recover without a restart. Root cause: kangaroo/kookaburra push cross-network to a fixed endpoint behind the collector host's published :4318 + NAT; when the clickstack-otel collector container recreates (e.g. on any clickstack/ edit, via the content hash), the old keepalive TCP connection stays mapped through conntrack to the dead container, so the next send blackholes and hangs silently — and retry_on_failure max_elapsed_time = "0s" (retry forever) made it permanent. Fixed by disable_keep_alives = true + a bounded 30m retry, which every host's exporter takes from the ship module: a fresh connection per batch always reaches the current collector. (A host that ships in-network by container name — DNS re-resolves — never hits this; since the move to bandicoot, bilby's exporter is cross-network too and carries disable_keep_alives and the same bounded retry.) Validated by recreating the collector and confirming kangaroo shipped straight across it. A wedge that recurs is cleared by the healthcheck's restart before the heartbeat can alert.
    • dockernet detach / phantom network — the log shows dial tcp <bandicoot>:4318: connect: network is unreachable. alloy has lost its dockernet attachment (NetworkSettings.Networks empty), usually because dockernet went phantom after Container Station churn: the libnetwork record survives (network inspect passes) but the bridge datapath is gone, so attaches fail with network <id> does not exist. Neither autoheal's restarts nor a RestartStack fix this — the container restarts and still has no usable network. Repair over SSH (admin@10.0.0.25; DK=/share/CACHEDEV2_DATA/.qpkg/container-station/usr/bin/docker): 
      $DK network disconnect -f dockernet alloy backrest   # clear dangling refs
$DK network rm dockernet                             # drop the phantom record
$DK network create dockernet                          # recreate a live bridge
$DK restart alloy backrest                           # reattach by name + rebuild the exporter
      The final restart is mandatory, not conditional. network connect on a running alloy gives it a working interface (an egress TCP test to the collector's :4318 will pass) but leaves its OTLP exporter wedged on the old connection state — it then goes silent and ships nothing, a green-but-dead trap that bit this repair on 2026-06-18. restart reattaches by network name and rebuilds the process. Verify with the data, not the container: rerun the log-rows query (SELECT count() FROM default.otel_logs WHERE Timestamp > now() - INTERVAL 5 MINUTE AND ResourceAttributes['host.name']='kangaroo' on clickstack-clickhouse) and confirm rows resume — a passing egress test or a healthy container is not proof of ingest. The kangaroo autorun.sh reconcile heals both the phantom network and running-but-detached containers (via restart) at boot, but a mid-life detach (no reboot) still needs this manual repair — the Kangaroo Telemetry Pipeline (heartbeat) check is the detection net for that case (its 60 s self-metric rides the same exporter, so a detach alerts about 20–25 minutes after the last metric arrived). See the firmware-reboot postmortem.
  • ClickHouse MergeTree part explosion. The collector's frequent small inserts create a large number of MergeTree parts. async_load_databases decouples ClickHouse startup from part count so a slow start no longer trips autoheal, but the underlying insert batching still needs tuning. The remaining work is tracked in the deferred platform debt plan.

HyperDX MCP server

HyperDX ships a built-in MCP (Model Context Protocol) server, served by the existing hyperdx container at path /api/mcp — no new service or container. Transport is Streamable HTTP; it is reachable through Numbat at https://watch.pod.haus/api/mcp. Verified working on HyperDX 2.25.0-beta. It gives an agent access to logs, exceptions, traces, and metrics for review.

Tools exposed (approximately): hyperdx_query, hyperdx_query_tile, hyperdx_list_sources, hyperdx_get_dashboard, hyperdx_save_dashboard, hyperdx_delete_dashboard — query logs/metrics/traces (builder / search / raw SQL) plus manage dashboards, saved searches, and alerts.

Auth is two layers, both passed as HTTP headers, both required:

  1. Numbat gateway: send X-Podhaus-Gateway-Token using field hyperdx_mcp from the Pomerium Gateway Tokens 1Password item. The public Pomerium route is limited to /api/mcp, and Caddy checks the token before HyperDX. Development machines receive this client credential through the Podhaus HyperDX item in the Dev vault. Komodo keeps its Homelab copy because the runtime secret sync has no Dev-vault grant.
  2. HyperDX Personal API Access Key as Authorization: Bearer <key> — the per-user accessKey (HyperDX Team Settings → API Keys). It is stored as credential in the Dev-vault Podhaus HyperDX item and persisted in Mongo (hyperdx db, users.accessKey) and captured by the nightly mongodump → Backrest backup.

Register the client (Claude Code) at user scope so it's available in all projects: 

claude mcp add --scope user --transport http hyperdx \
  https://watch.pod.haus/api/mcp \
  --header "X-Podhaus-Gateway-Token: <gateway-token>" \
  --header "Authorization: Bearer <key>"

On development machines the client config (~/.claude.json) is chezmoi-managed — the hyperdx MCP block and the key (templated from the Dev-vault Podhaus HyperDX item) live in the chezmoi source, not hand-edited into ~/.claude.json (chezmoi regenerates and would clobber a manual claude mcp add). The same command works from any machine through Numbat, with no LAN dependency.

pi gets the same server from the same chezmoi definition, written to ~/.pi/agent/mcp.json. It takes pi's default codemode exposure: the model reaches the tools from codemode scripts, named mcp__hyperdx__clickstack_*, rather than having each one declared. pi mcp list shows the connection.

Autoheal

Each host runs its own autoheal container (willfarrell/autoheal) — bilby's autoheal can't see kangaroo's Docker daemon, so each Periphery host needs one. Autoheal watches the local Docker daemon and restarts any container whose healthcheck reports unhealthy for ~3 consecutive checks, provided the container has the autoheal: "true" label. Unchanged by the ClickStack migration.

Standard pattern on every healthy stack: 

services:
  my-service:
    ...
    labels:
      autoheal: "true"
    healthcheck:
      test: ["CMD-SHELL", "..."]
      interval: 60s
      timeout: 10s
      retries: 3
      start_period: 30s

Docs-server is the deliberate exception. Its healthcheck represents the complete configured source catalog, so one unavailable repository source makes the container unhealthy while the process continues serving other sources. It has no autoheal label: restarting cannot restore a checkout and would turn a controlled degraded state into a restart loop. Gatus alerts on the red health state; Docker's unless-stopped policy still handles process exit.

Alloy's healthcheck checks that its exporter's requests are completing rather than that its port is open, with five retries, so autoheal restarts an Alloy whose exporter has wedged and leaves one whose collector is unreachable running with its queue (exporter-stall healthcheck).

Alerting flow

Alerting is owned by Gatus; ClickStack/HyperDX is for query and dashboards, not the alert path. Service alerts route to Fenwick (Signal); the Fenwick-health checks fall back to Postmark email.

  1. Endpoint check fails (HTTP non-2xx, body assertion fails, push missing, etc.).
  2. After failure-threshold consecutive failures (typically 3), Gatus fires the alert.
  3. Service checks (the default custom alerter): Gatus POSTs a service_alert to fenwick:8088/events/async with a bearer token + X-Fenwick-User: Nathan. Fenwick runs an agent turn and notifies over Signal under guidance — so notification behaviour (notify, dedup, aggregate) is shaped by guidance, not config.
  4. Fenwick-health checks (the Fenwick group: liveness + the 24h Signal-delivery check): the email alerter sends from uptime@nathanbaxter.com via Postmark SMTP. This path is deliberately independent of Fenwick, so a Fenwick/signal-cli outage still reaches you.
  5. Recovery (per success-threshold) sends a resolution notice on the same channel.
