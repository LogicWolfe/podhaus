Monitoring

Gatus does endpoint monitoring and pushes alerts to Postmark email. ClickStack (ClickHouse + HyperDX) is the observability backend; Alloy on both hosts ships container logs and Gatus metrics to it over OTLP. Autoheal restarts unhealthy containers locally on each host.

Gatus

Config-as-code endpoint monitoring, defined entirely in gatus/conf/config.yaml. Monitors HTTP endpoints, pushed heartbeats, and downstream-service-state checks. Stores results in SQLite with a 90-day cap. Alerts via Postmark webhook. Unchanged by the ClickStack migration.

Three monitor types in use:

  • HTTP — periodic GET on each *.pod.haus endpoint with status + body conditions.
  • Push (external endpoints) — bearer-token-protected URLs that jobs/scripts POST to with success=true|false&error=.... Used for Backrest nightly heartbeats and the RAR-extraction backlog scan.
  • Komodo-API check — Gatus calls Komodo Core's /read API and asserts that kangaroo's Periphery state is Ok. Surfaces "Komodo Core can't reach kangaroo Periphery" as a normal Gatus alert.

Live monitors today cover every public hostname plus the Backrest, RAR-extraction (cron safety-net), and kangaroo-backrest heartbeats. gatus.pod.haus shows the live status page.

Gatus metrics

gatus/conf/config.yaml sets metrics: true, exposing a Prometheus /metrics endpoint on Gatus's existing :8080 (the same port as the UI; /metrics is not added to the tunnel ingress, so it stays LAN-internal behind Access). bilby's Alloy prometheus.scrapes it at a ~60s cadence and bridges Prometheus → OTLP through the same authenticated exporter as the logs. The series land in ClickHouse's otel_metrics_* tables and are queryable and dashboardable in HyperDX. Gatus's own endpoint/heartbeat monitoring and the Postmark alert chain are unaffected by this.

Adding a Gatus monitor

Edit gatus/conf/config.yaml — YAML anchors at the top define common defaults (interval, alert config, conditions). Append a new endpoint to the appropriate group (services / heartbeats / docker). Save. Gatus reloads config automatically on file change — no restart.

Ingest-staleness alerts

Monitor for the absence of expected telemetry, not just service up/down. A process can be "healthy" (port open) while delivering no data — a wedged Alloy exporter, a dead cross-LAN path — invisible to an ordinary up/down check. This is the guard for the recurring kangaroo cross-LAN exporter failure class.

Implemented as Gatus endpoints that POST a ClickHouse query and assert the newest log row per host is recent. Gatus is on dockernet, so it reaches ClickHouse directly at http://clickstack-clickhouse:8123/ with headers X-ClickHouse-User: default and X-ClickHouse-Key: ${CLICKHOUSE_PASSWORD}. Conditions: [STATUS] == 200 and [BODY] == 1. The body query: 

SELECT toUInt8(max(Timestamp) > now() - INTERVAL <N> MINUTE)
FROM default.otel_logs
WHERE LogAttributes['host']='<host>'

Two live endpoints in gatus/conf/config.yaml:

  • Kangaroo Log Ingest (staleness) — 20-minute window, covering kangaroo's recurring cross-LAN exporter risk.
  • Pipeline Log Ingest (bilby / total) — 10-minute window, detecting total pipeline failure (collector / ClickHouse / Alloy down).

Alerts ride the existing Postmark chain. CLICKHOUSE_PASSWORD must be available to gatus — set in both the gatus/stack.toml env block and the gatus/compose.yaml service environment: (see the secrets doc's stack.toml↔compose env rule). To add another source, copy an endpoint block and change the host= filter and window.

ClickStack

ClickStack is the observability backend (bilby-only, as VictoriaLogs was). It is the clickstack/ stack and bundles four containers:

  • ClickHouse (clickstack-clickhouse) — columnar store for telemetry. mem_limit: 4g plus a config.d drop-in (clickhouse-conf/config.d/podhaus.xml) that caps max_server_memory_usage, sets listen_host to 0.0.0.0, enables async_load_databases, and bounds the internal log.
  • HyperDX (hyperdx) — the query/dashboard/alert UI at https://watch.pod.haus. Also hosts the OpAMP server the collector talks to.
  • OTel collector (clickstack-otel) — the bundled OpenTelemetry collector. Its OTLP/HTTP port 4318 is the only published port on the stack (kangaroo ships to it cross-LAN; bilby reaches it by container name).
  • Mongo (clickstack-mongo) — HyperDX app-state only: dashboards, alerts, users, source definitions, the ingestion key. Tiny but irreplaceable.

Alloy log collection

Alloy still runs on both hosts as the multi-host logging stack — logging on bilby, kangaroo-logging on kangaroo, both sharing logging/compose.shared.yaml. It scrapes container logs from each host's Docker socket. Instead of pushing to VictoriaLogs over the Loki API, it now bridges to OTLP (otelcol.receiver.loki → batch → otelcol.exporter.otlphttp) and ships to the ClickStack collector:

  • bilby — in-network to clickstack-otel:4318 by container name.
  • kangaroo — cross-LAN to http://10.0.0.119:4318 (plaintext, LAN-only — same trust posture as the old cross-LAN VL push).

Every request carries a HyperDX ingestion API key in the authorization header. The key lives in 1Password as clickstack-ingestion-key, is synced by komodo-op to a Komodo Variable, injected via each host's logging stack.toml, and read by config.alloy as sys.env("CLICKSTACK_INGESTION_KEY"). An empty/wrong key means a hard 401 and no data in HyperDX — a loud, visible failure with no silent fallback to the old sink.

Per-service log parsing

Log parsing is config-as-code. Each parsed service has a module at logging/<host>/alloy-conf/parsers/<service>.alloy — one Alloy declare module per service, imported via import.file and composed into an explicit chain in config.alloy. Each module:

  • parses that service's real event timestamp into the log entry,
  • normalizes the level to a detected_level attribute,
  • reduces the Body down to the message.

After the chain, an OTTL transform.enrich block sets service.name from the container name and maps detected_level → OTLP severity. That mapping is authoritative; for lines with no parsed level there's a body-keyword severity fallback (anchored to the first ~60 chars so e.g. "Total errors encountered: 0" isn't mislabelled ERROR). Services without a parser — rtorrent-cleanup, fenwick, docs-server, ofelia, signal-cli-rest-api — still flow with the generic fallback. Roughly 20 bilby services are parsed; kangaroo parses alloy, syncthing, backrest, komodo-periphery, and autoheal.

To parse a new service: add logging/<host>/alloy-conf/parsers/<service>.alloy and insert one link into the parser chain in that host's config.alloy. Anything not in the chain still ships, just with the generic fallback.

Retention

Retention is enforced as ClickHouse table TTL, applied post-bootstrap via ALTER TABLE … MODIFY TTL (the collector's default was 30d / 720h):

TableTTL
otel_logs180 days
otel_metrics_*90 days
otel_traces, hyperdx_sessions30 days

Storage

ClickStack data lives on bilby's local NVMe, not Jump: /var/lib/clickstack/{clickhouse,clickhouse-logs,mongo,mongo-dumps}. ClickHouse and Mongo chown their data dirs to their own uid at startup; the NFS Jump all-squash blocks that, so local disk is mandatory here. Steady-state footprint is ~1.3 GB RAM, bounded by mem_limit on every container plus the ClickHouse config.d memory caps — this is the one memory-risky stack on the shared 15 GB M1.

Backup

ClickHouse telemetry is deliberately not backed up — it's regenerable and large. The MongoDB app-state is backed up: an ofelia job at 03:50 runs mongodump into /var/lib/clickstack/mongo-dumps (keeping the latest ~14 archives), and the Backrest clickstack plan picks that directory up at 05:05 into the existing restic + OneDrive chain.

Access

watch.pod.haus sits behind the existing *.pod.haus Cloudflare Access wildcard (Family identity policy) and HyperDX's own login. There is a single HyperDX account, nathan@nathanbaxter.com; credentials are in 1Password as clickstack-hyperdx.

Known issues

  • kangaroo Alloy OTLP exporter can stall silently. The cross-LAN exporter on kangaroo-logging can stop shipping and not self-recover. The port-only container healthcheck can't detect this (the socket stays open). The current workaround is RestartStack kangaroo-logging. A real guard — metrics-based healthcheck/autoheal, exporter retry-queue tuning, or a scheduled restart — is an open follow-up.
  • ClickHouse MergeTree part explosion. The collector's frequent small inserts create a large number of MergeTree parts. async_load_databases decouples ClickHouse startup from part count so a slow start no longer trips autoheal, but the underlying insert batching still needs tuning — an open follow-up.

HyperDX MCP server

HyperDX ships a built-in MCP (Model Context Protocol) server, served by the existing hyperdx container at path /api/mcp — no new service or container. Transport is Streamable HTTP; it's reachable through the tunnel at https://watch.pod.haus/api/mcp. Verified working on HyperDX 2.25.0-beta. It gives an agent access to logs, exceptions, traces, and metrics for review.

Tools exposed (approximately): hyperdx_query, hyperdx_query_tile, hyperdx_list_sources, hyperdx_get_dashboard, hyperdx_save_dashboard, hyperdx_delete_dashboard — query logs/metrics/traces (builder / search / raw SQL) plus manage dashboards, saved searches, and alerts.

Auth is two layers, both passed as HTTP headers, both required:

  1. Cloudflare Access on *.pod.haus — pass the Homelab service token to bypass interactive login: headers CF-Access-Client-Id and CF-Access-Client-Secret. Credentials in the 1Password item Cloudflare Access — Homelab Service Token (field username = Client ID, field credential = Client Secret).
  2. HyperDX Personal API Access Key as Authorization: Bearer <key> — the per-user accessKey (HyperDX Team Settings → API Keys). Stored in 1Password as clickstack-hyperdx-mcp-key; also persisted in Mongo (hyperdx db, users.accessKey) and captured by the nightly mongodump → Backrest backup.

Register the client (Claude Code) at user scope so it's available in all projects: 

claude mcp add --scope user --transport http hyperdx \
  https://watch.pod.haus/api/mcp \
  --header "CF-Access-Client-Id: <id>" \
  --header "CF-Access-Client-Secret: <secret>" \
  --header "Authorization: Bearer <key>"

On bilby the client config (~/.claude.json) is chezmoi-managed — the hyperdx MCP block and the key (templated from 1Password clickstack-hyperdx-mcp-key) live in the chezmoi source, not hand-edited into ~/.claude.json (chezmoi regenerates and would clobber a manual claude mcp add). The same command works from any machine — it goes via the public tunnel + Access service token, with no LAN dependency.

Autoheal

Each host runs its own autoheal container (willfarrell/autoheal) — bilby's autoheal can't see kangaroo's Docker daemon, so each Periphery host needs one. Autoheal watches the local Docker daemon and restarts any container whose healthcheck reports unhealthy for ~3 consecutive checks, provided the container has the autoheal: "true" label. Unchanged by the ClickStack migration.

Standard pattern on every healthy stack: 

services:
  my-service:
    ...
    labels:
      autoheal: "true"
    healthcheck:
      test: ["CMD-SHELL", "..."]
      interval: 60s
      timeout: 10s
      retries: 3
      start_period: 30s

Alerting flow

Alerting is owned entirely by Gatus and Postmark — ClickStack/HyperDX is for query and dashboards, not the email alert path.

  1. Endpoint check fails (HTTP non-2xx, body assertion fails, push missing, etc.).
  2. After failure-threshold consecutive failures (typically 3), Gatus fires the alert chain.
  3. Postmark webhook sends email from alerts@pod.haus with the rich body.
  4. Recovery (3 consecutive successes) sends a resolution email.
