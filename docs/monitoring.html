Monitoring

Gatus does endpoint monitoring and routes alerts to Fenwick (the Signal home-helper), which triages each alert with an agent turn and notifies over Signal under household guidance; the Fenwick-health checks fall back to Postmark email so the watcher of Fenwick never routes through Fenwick. ClickStack (ClickHouse + HyperDX) is the observability backend; Alloy on all active hosts ships container logs and Gatus metrics to it over OTLP. Autoheal restarts unhealthy containers locally on each host.

Gatus

Forgejo has four independent signals: an internal HTTP health check against forgejo:3000, a public Pomerium-edge check and a TCP check of git.pod.haus:443 and :22, and an external heartbeat from the quiesced Backrest plan. Together they distinguish an application failure, either public relay path failing, and a backup failure.

Config-as-code endpoint monitoring, defined entirely in gatus/conf/config.yaml. Monitors HTTP endpoints, pushed heartbeats, and downstream-service-state checks. Stores results in SQLite with a 90-day cap. Service alerts route to Fenwick (the default custom alerter); the Fenwick-health checks use Postmark email. Unchanged by the ClickStack migration.

Three monitor types in use:

  • HTTP — periodic GET against the service's internal endpoint: a dockernet container name + port (e.g. http://hyperdx:8080/, http://paperless:8000/), the dockernet bridge gateway at 172.18.0.1:<port> for host-network services on bilby (Plex, Home Assistant), or the LAN IP for off-host targets (the QNAP web UI at https://10.0.0.25/). External probes are reserved for paths that genuinely need full-path coverage (storage.pod.haus, numbat-probe.storage.pod.haus, nathanbaxter.com, voice.pod.haus) that are intentionally public. Probing protected public URLs is deliberately avoided: Pomerium returns a login 302 for unauthenticated requests, which the default [STATUS] < 400 condition accepts as healthy — masking backend failure. Bit us on 2026-05-30 (see postmortem).
  • Push (external endpoints) — bearer-token-protected URLs that jobs/scripts POST to with success=true|false&error=.... Used for Backrest nightly heartbeats, Sky cache invalidation, and the RAR-extraction backlog scan.
  • Komodo-API check — Gatus calls Komodo Core's /read API and asserts a downstream state. Used for both Periphery reachability (GetServerState → assert status == Ok) and for containers gatus can't reach directly because they live on kangaroo (InspectDockerContainer → assert State.Status == running; covers backrest and syncthing on kangaroo).

Live monitors today cover every podhaus service plus the Backrest, RAR-extraction (cron safety-net), and kangaroo-backrest heartbeats. gatus.pod.haus shows the live status page.

Alerting is wired into the shared *defaults anchor: every endpoint that spreads <<: *defaults inherits alerts: *alerts (which is just [{type: custom}], picking up failure-threshold: 3 / send-on-resolved: true from alerting.custom.default-alert). The custom alerter now POSTs each alert to Fenwick (fenwick:8088/events/async) as a service_alert event; Fenwick's agent decides how to notify. The Fenwick-health checks deliberately opt out of the anchor with alerts: [{type: email}] (Postmark SMTP) — a check must never route through the thing it watches. Non-anchor endpoints declare their alerts: list explicitly. Adding a new monitor without alerts is a deliberate act, not the default.

Gatus metrics

gatus/conf/config.yaml sets metrics: true, exposing a Prometheus /metrics endpoint on Gatus's existing :8080 (the same port as the UI; /metrics remains Pomerium-protected). bilby's Alloy prometheus.scrapes it at a ~60s cadence and bridges Prometheus → OTLP through the same authenticated exporter as the logs. The series land in ClickHouse's otel_metrics_* tables and are queryable and dashboardable in HyperDX. Gatus's own endpoint/heartbeat monitoring and the alert chain (Gatus → Fenwick, with the Postmark backstop) are unaffected by this.

Adding a Gatus monitor

Edit gatus/conf/config.yaml — YAML anchors at the top define common defaults (interval, alert config, conditions). Set the endpoint's group: to the service it belongs to (Komodo, Backup, Observability, Torrents, Plex, Storage, …) — grouping is service-primary, so a check lands with its service regardless of which host runs it. Note that for push (external) endpoints the group is part of the push key (<group>_<name>, lowercased, spaces→hyphens), so the sender's target URL must match. Save. Gatus reloads config automatically on file change — no restart.

A push (external) endpoint also needs a token: — the bearer the sender presents (Authorization: Bearer <token>). These tokens are not per-service: the endpoint key in the push URL is what routes a heartbeat to the right check, so a new heartbeat should reuse the general-purpose ${GATUS_HEARTBEAT_PUSH_TOKEN} (1Password Homelab item Gatus Heartbeat Push Token) rather than minting another. The older per-service tokens (GATUS_BACKREST_PUSH_TOKEN, GATUS_OFELIA_PUSH_TOKEN, GATUS_BACKREST_KANGAROO_PUSH_TOKEN) are kept as-is — no migration. The brinno site-time-lapse downloader's timelapse_brinno heartbeat (group Timelapse, 48h staleness window) is the reference example: it pushes to gatus:8080/api/v1/endpoints/timelapse_brinno/external?success=true with that bearer.

Sky's backup check is storage-driven. The hourly sky-backups-monitor job lists encrypted snapshot objects under sky-backups/personal-laptop/snapshots/ in Pouch MinIO and reports whether the newest object was committed within seven days. The job pushes its result to Gatus over dockernet; the laptop has no Gatus token or callback. Its Backup / Sky Restic Repository endpoint has a two-hour heartbeat window so a stopped monitor also becomes unhealthy. Before the first snapshot, the repository's config object supplies the seven-day initialization grace period.

Ingest-staleness alerts

Monitor for the absence of expected telemetry, not just service up/down. A process can be "healthy" (port open) while delivering no data — a wedged Alloy exporter, a dead cross-LAN path — invisible to an ordinary up/down check. This is the guard for the recurring kangaroo cross-LAN exporter failure class.

Implemented as Gatus endpoints that POST a ClickHouse query and assert recent telemetry per host. Gatus is on dockernet, so it reaches ClickHouse directly at http://clickstack-clickhouse:8123/ with headers X-ClickHouse-User: default and X-ClickHouse-Key: ${CLICKHOUSE_PASSWORD}. Conditions: [STATUS] == 200 and [BODY] == 1. Use count() > 0 over an explicitly time-windowed scan, not max(Timestamp) > now() - INTERVAL N over an unbounded one — the Map predicate (...['host']=…) defeats primary-key pruning, so without the time filter the query scans every active part and times out at gatus's 10 s budget: 

SELECT toUInt8(count() > 0) FROM default.otel_logs
WHERE Timestamp > now() - INTERVAL <N> MINUTE AND LogAttributes['host']='<host>'

Three live endpoints in gatus/conf/config.yaml, of two kinds: heartbeats (assert a fresh Alloy self-metric reached ClickHouse, i.e. the host's whole telemetry ship-path Alloy → collector → ClickHouse is alive) and log-volume checks (count otel_logs rows). Named for what they measure:

  • Kangaroo Telemetry Pipeline and Numbat Telemetry Pipeline are heartbeats. Each host's Alloy scrapes its own self-metrics every 60 s and ships them through the same exporter as the logs, so the query asserts a fresh per-host Alloy metric in a 15-minute window (otel_metrics_gauge where ResourceAttributes['host']='<host>'; the host attribute is stamped by the svc_alloy transform in each host's config.alloy). A fixed 60 s cadence means a genuine stall alerts in ~10 min.
  • Pipeline Log Ingest (bilby / total) is a 10-minute count() check that detects total collector, ClickHouse, or Alloy failure. The remote-host heartbeats cover their complete shipping paths without assuming a minimum log volume.

These are service checks, so their alerts ride the default Gatus → Fenwick chain. CLICKHOUSE_PASSWORD must be available to gatus — set in both the gatus/stack.toml env block and the gatus/compose.yaml service environment: (see the secrets doc's stack.toml↔compose env rule). To add another source, copy an endpoint block and change the host= filter and window.

ClickStack

ClickStack is the observability backend on bilby. It is the clickstack/ stack and bundles four containers:

  • ClickHouse (clickstack-clickhouse) — columnar store for telemetry. mem_limit: 4g plus a config.d drop-in (clickhouse-conf/config.d/podhaus.xml) that caps max_server_memory_usage, sets listen_host to 0.0.0.0, enables async_load_databases, and bounds the internal log.
  • HyperDX (hyperdx) — the query/dashboard/alert UI at https://watch.pod.haus. Also hosts the OpAMP server the collector talks to.
  • OTel collector (clickstack-otel) — the bundled OpenTelemetry collector. Its OTLP/HTTP port 4318 is the only published port on the stack (kangaroo ships to it cross-LAN; bilby reaches it by container name).
  • Mongo (clickstack-mongo) — HyperDX app-state only: dashboards, alerts, users, source definitions, the ingestion key. Tiny but irreplaceable.

Alloy log collection

Alloy runs on all four active hosts as the multi-host logging service: logging on bilby, kangaroo-logging on kangaroo, numbat-logging on Numbat, and fractal-logging on fractal. They share logging/compose.shared.yaml. Alloy scrapes each host's Docker socket, bridges Loki-format input to OTLP (otelcol.receiver.loki → batch → otelcol.exporter.otlphttp) and ships to the ClickStack collector:

  • bilby — in-network to clickstack-otel:4318 by container name.
  • kangaroo — cross-LAN to http://10.0.0.119:4318 (plaintext, LAN-only).
  • Numbat: HTTPS to logs-ingest.pod.haus through rathole and Caddy, with a dedicated client certificate.
  • fractal: the same HTTPS ingress with its own client certificate.

Every request carries a HyperDX ingestion API key in the authorization header. The key lives in 1Password as clickstack-ingestion-key, is synced by komodo-op to a Komodo Variable, injected via each host's logging stack.toml, and read by config.alloy as sys.env("CLICKSTACK_INGESTION_KEY"). An empty/wrong key means a hard 401 and no data in HyperDX — a loud, visible failure with no silent fallback to the old sink.

Per-service log parsing

Log parsing is config-as-code. Each parsed service has a module at logging/<host>/alloy-conf/parsers/<service>.alloy — one Alloy declare module per service, imported via import.file and composed into an explicit chain in config.alloy. Each module:

  • parses that service's real event timestamp into the log entry,
  • normalizes the level to a detected_level attribute,
  • reduces the Body down to the message.

After the chain, an OTTL transform.enrich block sets service.name from the container name and maps detected_level → OTLP severity. That mapping is authoritative; for lines with no parsed level there's a body-keyword severity fallback (anchored to the first ~60 chars so e.g. "Total errors encountered: 0" isn't mislabelled ERROR). Services without a parser — rtorrent-cleanup, fenwick, docs-server, ofelia, signal-cli-rest-api — still flow with the generic fallback. Roughly 20 bilby services are parsed; kangaroo parses alloy, syncthing, backrest, komodo-periphery, and autoheal.

To parse a new service: add logging/<host>/alloy-conf/parsers/<service>.alloy and insert one link into the parser chain in that host's config.alloy. Anything not in the chain still ships, just with the generic fallback.

Retention

Retention is enforced as ClickHouse table TTL, applied post-bootstrap via ALTER TABLE … MODIFY TTL (the collector's default was 30d / 720h):

otel_logs180 days

Storage

ClickStack data lives on bilby's local NVMe, not Jump: /var/lib/clickstack/{clickhouse,clickhouse-logs,mongo,mongo-dumps}. ClickHouse and Mongo chown their data dirs to their own uid at startup; the NFS Jump all-squash blocks that, so local disk is mandatory here. Steady-state footprint is ~1.3 GB RAM, bounded by mem_limit on every container plus the ClickHouse config.d memory caps — this is the one memory-risky stack on the shared 15 GB M1.

Backup

ClickHouse telemetry is deliberately not backed up — it's regenerable and large. The MongoDB app-state is backed up: an ofelia job at 03:50 runs mongodump into /var/lib/clickstack/mongo-dumps (keeping the latest ~14 archives), and the Backrest clickstack plan picks that directory up at 05:05 into the existing restic + OneDrive chain.

Known issues

  • kangaroo Alloy log ingest can go stale — two distinct causes, two different fixes. The Kangaroo Telemetry Pipeline (heartbeat) Gatus check fires for both — since 2026-06-20 it's a 60 s self-metric heartbeat (above), which rides the same exporter as the logs, so a stall in either fails it within ~10 min. The port-only container healthcheck detects neither (the socket stays open, so the container reads healthy and autoheal ignores it). Read the alloy log to tell them apart — GetContainerLog kangaroo alloy:
    • Exporter wedge (root cause fixed 2026-06-19) — the exporter would stop shipping silently (no errors, just silence) and not recover without a restart. Root cause: kangaroo/kookaburra push cross-network to a fixed endpoint behind bilby's published :4318 + NAT; when the clickstack-otel collector container recreates (e.g. on any clickstack/ edit, via the content hash), the old keepalive TCP connection stays mapped through conntrack to the dead container, so the next send blackholes and hangs silently — and retry_on_failure max_elapsed_time = "0s" (retry forever) made it permanent. Fixed by disable_keep_alives = true + a bounded 30m retry on both cross-network exporters' config.alloy: a fresh connection per batch always reaches the current collector. (bilby ships in-network by container name — DNS re-resolves — and never hit this.) Validated by recreating the collector and confirming kangaroo shipped straight across it. If a wedge somehow recurs despite this, RestartStack kangaroo-logging remains the fallback.
    • dockernet detach / phantom network — the log shows dial tcp 10.0.0.119:4318: connect: network is unreachable. alloy has lost its dockernet attachment (NetworkSettings.Networks empty), usually because dockernet went phantom after Container Station churn: the libnetwork record survives (network inspect passes) but the bridge datapath is gone, so attaches fail with network <id> does not exist. A RestartStack does not fix this — the container restarts and still has no usable network. Repair over SSH (admin@10.0.0.25; DK=/share/CACHEDEV2_DATA/.qpkg/container-station/usr/bin/docker): 
      $DK network disconnect -f dockernet alloy backrest   # clear dangling refs
$DK network rm dockernet                             # drop the phantom record
$DK network create dockernet                          # recreate a live bridge
$DK restart alloy backrest                           # reattach by name + rebuild the exporter
      The final restart is mandatory, not conditional. network connect on a running alloy gives it a working interface (an egress TCP test to 10.0.0.119:4318 will pass) but leaves its OTLP exporter wedged on the old connection state — it then goes silent and ships nothing, a green-but-dead trap that bit this repair on 2026-06-18. restart reattaches by network name and rebuilds the process. Verify with the data, not the container: rerun the log-rows query (SELECT count() FROM default.otel_logs WHERE Timestamp > now() - INTERVAL 5 MINUTE AND LogAttributes['host']='kangaroo' on clickstack-clickhouse) and confirm rows resume — a passing egress test or a healthy container is not proof of ingest. The kangaroo autorun.sh reconcile heals both the phantom network and running-but-detached containers (via restart) at boot, but a mid-life detach (no reboot) still needs this manual repair — the Kangaroo Telemetry Pipeline (heartbeat) check is the detection net for that case (its 60 s self-metric rides the same exporter, so a detach trips it within ~15 min). See the firmware-reboot postmortem.
  • ClickHouse MergeTree part explosion. The collector's frequent small inserts create a large number of MergeTree parts. async_load_databases decouples ClickHouse startup from part count so a slow start no longer trips autoheal, but the underlying insert batching still needs tuning. The remaining work is tracked in the deferred platform debt plan.

HyperDX MCP server

HyperDX ships a built-in MCP (Model Context Protocol) server, served by the existing hyperdx container at path /api/mcp — no new service or container. Transport is Streamable HTTP; it is reachable through Numbat at https://watch.pod.haus/api/mcp. Verified working on HyperDX 2.25.0-beta. It gives an agent access to logs, exceptions, traces, and metrics for review.

Tools exposed (approximately): hyperdx_query, hyperdx_query_tile, hyperdx_list_sources, hyperdx_get_dashboard, hyperdx_save_dashboard, hyperdx_delete_dashboard — query logs/metrics/traces (builder / search / raw SQL) plus manage dashboards, saved searches, and alerts.

Auth is two layers, both passed as HTTP headers, both required:

  1. Numbat gateway: send X-Podhaus-Gateway-Token using field hyperdx_mcp from the Pomerium Gateway Tokens 1Password item. The public Pomerium route is limited to /api/mcp, and Caddy checks the token before HyperDX.
  2. HyperDX Personal API Access Key as Authorization: Bearer <key> — the per-user accessKey (HyperDX Team Settings → API Keys). Stored in 1Password as clickstack-hyperdx-mcp-key; also persisted in Mongo (hyperdx db, users.accessKey) and captured by the nightly mongodump → Backrest backup.

Register the client (Claude Code) at user scope so it's available in all projects: 

claude mcp add --scope user --transport http hyperdx \
  https://watch.pod.haus/api/mcp \
  --header "X-Podhaus-Gateway-Token: <gateway-token>" \
  --header "Authorization: Bearer <key>"

On bilby the client config (~/.claude.json) is chezmoi-managed — the hyperdx MCP block and the key (templated from 1Password clickstack-hyperdx-mcp-key and Pomerium Gateway Tokens) live in the chezmoi source, not hand-edited into ~/.claude.json (chezmoi regenerates and would clobber a manual claude mcp add). The same command works from any machine through Numbat, with no LAN dependency.

Autoheal

Each host runs its own autoheal container (willfarrell/autoheal) — bilby's autoheal can't see kangaroo's Docker daemon, so each Periphery host needs one. Autoheal watches the local Docker daemon and restarts any container whose healthcheck reports unhealthy for ~3 consecutive checks, provided the container has the autoheal: "true" label. Unchanged by the ClickStack migration.

Standard pattern on every healthy stack: 

services:
  my-service:
    ...
    labels:
      autoheal: "true"
    healthcheck:
      test: ["CMD-SHELL", "..."]
      interval: 60s
      timeout: 10s
      retries: 3
      start_period: 30s

Alerting flow

Alerting is owned by Gatus; ClickStack/HyperDX is for query and dashboards, not the alert path. Service alerts route to Fenwick (Signal); the Fenwick-health checks fall back to Postmark email.

  1. Endpoint check fails (HTTP non-2xx, body assertion fails, push missing, etc.).
  2. After failure-threshold consecutive failures (typically 3), Gatus fires the alert.
  3. Service checks (the default custom alerter): Gatus POSTs a service_alert to fenwick:8088/events/async with a bearer token + X-Fenwick-User: Nathan. Fenwick runs an agent turn and notifies over Signal under guidance — so notification behaviour (notify, dedup, aggregate) is shaped by guidance, not config.
  4. Fenwick-health checks (the Fenwick group: liveness + the 24h Signal-delivery check): the email alerter sends from uptime@nathanbaxter.com via Postmark SMTP. This path is deliberately independent of Fenwick, so a Fenwick/signal-cli outage still reaches you.
  5. Recovery (per success-threshold) sends a resolution notice on the same channel.
