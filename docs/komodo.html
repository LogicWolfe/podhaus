Komodo

Komodo is the orchestrator. One Core runs on bilby (with its own Periphery for the local host). Kangaroo runs a second Periphery, registered to the same Core. Every stack is a Docker Compose project plus a stack.toml file declaring server assignment and environment.

Components

Komodo Core itself runs as four containers in the komodo/ stack:

  • komodo-core — the API + web UI on port 9120.
  • komodo-periphery — bilby's local agent (the daemon Core actually talks to in order to run docker compose).
  • komodo-ferretdb — MongoDB-compatible API; Komodo's metadata store.
  • komodo-postgres — backing store for FerretDB.

Kangaroo runs its own komodo-periphery container — see Hosts → kangaroo. Both Peripheries are registered as Server resources in Komodo via komodo/sync/servers.toml.

Core ↔ Periphery auth (v2 PKI noise handshake)

Komodo v2 dropped the v1 KOMODO_PASSKEY shared secret for X25519 noise-handshake mutual auth. Each endpoint holds its own private key; the trust list lives as a set of public-key files.

  • bilby: Core and bilby Periphery share a host bind (/opt/komodo/keys → /config/keys), so each picks up the other's .pub from the same directory. Bilby is also where the master copies of all four keypairs live; the pubkeys are committed to komodo/keys/*.pub in the repo for reference + rebuild.
  • kangaroo, kookaburra, numbat: Each host has its own keys directory (bootstrap-managed bind, separate from etc-komodo). The bootstrap script SCPs that host's periphery.key + Core's core.pub from bilby's /opt/komodo/keys/ into the remote keys dir. Privkeys never live outside the host they belong to.
  • Trust list on Core: KOMODO_PERIPHERY_PUBLIC_KEYS (in komodo/compose.env) is a comma-separated list of file: paths under /config/keys/ — one .pub per known Periphery. Adding a new host = drop its .pub into the keys volume + extend that env list + restart Core.

Connection direction

v2 supports both Core → Periphery (inbound, like v1) and Periphery → Core (outbound). The choice is per-Server, set by the address field in servers.toml: a populated address = Core dials; empty = Periphery dials.

  • bilby: inbound. Core dials https://periphery:8120 via dockernet (same compose).
  • kangaroo: outbound. Periphery dials ws://10.0.0.119:9120 (bilby LAN). No inbound :8120 listener exposed on kangaroo.
  • kookaburra: outbound. Periphery dials ws://bilby-podnet.tail9ceb.ts.net:9120 over the tailnet (kookaburra Periphery on dockernet; daemon.json forwards MagicDNS via 100.100.100.100). No inbound listener.
  • numbat: outbound. Periphery dials wss://core-connect.pod.haus through the public TLS rathole path. Komodo Noise keys authenticate the connection; no inbound listener is exposed.

Off-host Peripheries use outbound on attack-surface grounds: their Periphery REST/WS surface isn't reachable from anywhere — nothing inbound to gate at all. The noise handshake is the sole auth on the outbound dial.

Two operating models

Each Periphery host picks one of two ways to read the repo. The current setup uses both:

bilbykangaroo
Operating model files_on_host = true Linked Repo (linked_repo = "podhaus" for kangaroo, podhaus-kookaburra for kookaburra, and podhaus-numbat for Numbat; Repo resources are per-Periphery, each host's clone is independent state)
How the repo gets there Cloned manually + bind-mounted into Core and Periphery Komodo clones via HTTPS + a GitHub PAT, stored at /etc/komodo/repos/<repo-name>/ inside the Periphery container
Deploy workflow Commit + push → the single webhook runs the podhaus-push-deploy procedure. Stage 1 stamps content hashes and directly reconciles stale running stacks when committed config or build context changed without a compose-text change. Stage 2's BatchDeployStackIfChanged "*" handles compose-text changes and new stacks. For local iteration: save + ./komodo-sync invokes the same procedure (out-of-procedure pre-sync first, then RunProcedure). Same workflow and the same Stage 1 / Stage 2. Hashes are computed from bilby's view of the repo and compared with the labels on containers running at the target host, so linked-repo config-only and build-context edits do not rely on an env diff. New linked-repo hosts inherit the behaviour automatically; no Stage 2 entries to maintain, no <host>- name prefix required. Convention still useful: the <host>- prefix on a stack name signals "lives on this remote host" at a glance (kookaburra-tailscale, kangaroo-backup), but it's a readability convention now, not a deploy-routing contract.
Best for Active development on the primary host Remote hosts where the source of truth must be the git remote

Three linked-repo hosts exist today: kangaroo (QNAP NAS, repo podhaus), kookaburra (retained DigitalOcean rollback, repo podhaus-kookaburra), and Numbat (active BinaryLane gateway, repo podhaus-numbat). Future deploy targets (e.g. pinelake) should follow the same pattern. Bilby stays on files_on_host because tight save-and-deploy beats the commit-roundtrip when the editor is on the same host.

Linked Repo deploys: what actually pulls DeployStack = pulls; RestartStack = no pull. DeployStack (manual or webhook-triggered) runs git pull --rebase --force origin <branch> on the Periphery clone before composing. RestartStack only docker compose restarts.

Komodo's native DeployStackIfChanged only considers compose text. It does not see a changed value behind a ${STACK_CONTENT_HASH} or ${BUILD_HASH_*} reference. The push procedure closes that gap via Stage 1's RunAction "podhaus-inject-content-hashes": the Action computes (a) a content hash of each stack directory and (b) per-service hashes for every build: context, both from bilby's view of the repo, and stamps STACK_CONTENT_HASH=<hash> + BUILD_HASH_<UPPER_SERVICE>=<hash> into the stack's stored env. The Action then compares the expected hashes with each running container's podhaus.* labels. If the labels are stale and compose text is unchanged, it runs a direct DeployStack. Stage 2 deliberately owns the disjoint cases: compose-text changes and brand-new stacks. A linked repo is pulled on deploy as part of that normal flow.

Always confirm a deploy via a config-level signal — the pulled-to commit hash or a metric — never "container healthy."

stack.toml structure

Every Komodo-managed stack has a stack.toml alongside its compose.yaml. Minimum shape (bilby-side): 

[[stack]]
name = "gatus"
description = "Config-as-code endpoint monitoring"
tags = ["podhaus"]

[stack.config]
server = "podhaus"
files_on_host = true
run_directory = "/etc/komodo/repo/gatus"

environment = """
TZ=[[TZ]]
POSTMARK_SERVER_TOKEN=[[OP__KOMODO__POSTMARK_SMTP__CREDENTIAL]]
"""

Key fields:

  • server — "podhaus" for bilby, "kangaroo" for kangaroo. Komodo dispatches the stack to that host's Periphery.
  • files_on_host vs linked_repo — picks operating model.
  • run_directory — where Periphery runs docker compose from. For bilby it's always /etc/komodo/repo/<stack>; for kangaroo it's relative to the Linked Repo clone.
  • environment — multi-line string of KEY=VALUE pairs. [[VAR]] entries are interpolated from Komodo Variables (see Secrets).

ResourceSync

Stack definitions, Server entries, Repo declarations, and any other Komodo resources are declared in TOML under komodo/sync/. Komodo reads these via a ResourceSync resource (created by komodo-start on first boot, recreated by ./komodo-sync on demand).

Files in the sync directory today:

  • komodo/sync/servers.toml — bilby and kangaroo Server entries.
  • komodo/sync/repos.toml — the podhaus Linked Repo for kangaroo.
  • komodo/sync/variables.toml — global non-secret variable declarations (TZ, MEDIA_DIR). Authoritative — the podhaus sync runs with include_variables = true, so a RunSync applies these. Stack-private vars (e.g. FENWICK_*) live as inline [[variable]] blocks in the relevant <stack>/stack.toml instead.
  • komodo/sync/procedures.toml — the podhaus-push-deploy procedure (the single push-to-deploy fan-out; see the Auto-deploy note below).
  • komodo/sync/actions.toml — Komodo Actions referenced by procedures. podhaus-inject-content-hashes is Stage 1 of the podhaus push procedure. It walks every stack at Komodo Core's /syncs/podhaus mount, hashes each committed stack directory plus every build context, stamps the hashes into stored env, and directly deploys running stacks whose hash labels are stale while compose text is unchanged. The deploy-written .env is the intentional exclusion. podhaus-purge-stack-cache reads a deployed stack's podhaus.cloudflare-cache-* labels and purges those tags after its deployment stage. See Public site caching.
  • komodo/sync/syncs.toml — child ResourceSyncs for the separate-repo services (fenwick, pets, docs), each a [[resource_sync]] block with its own linked_repo + dedicated push-deploy procedure. The podhaus sync picks them up via its resource_path scan.
Declare a ResourceSync with [[resource_sync]], never [[sync]] The synced-TOML key for a ResourceSync is [[resource_sync]] / [resource_sync.config] — Komodo's ResourcesToml field is resource_syncs (alias resource_sync); there is no sync alias in any version. Serde silently drops unknown top-level keys, so a [[sync]] block parses without error but creates nothing — the sync never appears. It bites opaquely: a correctly-keyed [[procedure]] (which does get created) that RunSyncs the missing sync makes the reconcile loop bail with procedure sync loop exited after max iterations and fail the whole RunSync — and Komodo discards the underlying error on that path, so the message is misleading. The fenwick/pets [[sync]] blocks had been inert the whole time (their syncs existed only from earlier manual creation); all three were migrated to [[resource_sync]] on 2026-06-26.
Auto-deploy on push (one webhook → one procedure) Komodo's webhook contract is per-resource: https://<host>/listener/<auth>/<resource_type>/<id>/<seg>. podhaus uses one webhook per repo, not per stack: GitHub hard-caps a repo at 20 push webhooks, and the procedure-level fan-out scales past that ceiling. terraform/github.tf creates one webhook → komodo.pod.haus/listener/github/procedure/podhaus-push-deploy/main (resource_type procedure; the trailing /main is the branch filter, not a verb — Komodo router.rs "/procedure/{id}/{branch}"). Access bypass is path-scoped to /listener/github; Komodo HMAC-validates with KOMODO_WEBHOOK_SECRET (the procedure's webhook_secret is empty → the global secret applies).

The procedure (komodo/sync/procedures.toml) fans out across four stages: Stage 0 RunSync "podhaus" — reconcile stack definitions + TOML-declared variables from disk to Komodo's stored resource state. Without this, a push that adds a new environment line to a stack.toml reached the deploy via the on-disk file but Komodo's DeployStack used the stored (pre-sync) resource def, so the var resolved empty. Stage 0 is config-reconcile-only — Komodo's built-in Sync Deploy sub-stage (which would auto-deploy any stack whose stored config diverges from deployed) no-ops because every podhaus stack.toml omits deploy = true; Stage 1 and Stage 2 below are the deploy authorities. Stage 1 RunAction "podhaus-inject-content-hashes" — walks every stack visible at Core's /syncs/podhaus mount, computes a deterministic content hash of each stack directory (including bind-mounted runtime paths) and per-service build-context hashes for any service with build:, and stamps STACK_CONTENT_HASH=<hash> + BUILD_HASH_<UPPER_SERVICE>=<hash> into the stored env. The Action compares those hashes to each running container's labels and directly deploys a stale stack when its compose text is unchanged. This is the trigger for config-only and build-context edits, and it works uniformly for files_on_host and linked_repo stacks. Stage 2 BatchDeployStackIfChanged "*": deploy compose-text changes and brand-new stacks. Stage 1 skips those cases, so the two paths do not recreate the same stack twice; unchanged stacks no-op. Stage 3 RestartStack "ofelia" — re-read container labels so cron schedule / command edits propagate (the released ofelia image reads labels only at startup; see Scheduling). The "*" pattern means new stacks auto-deploy on the next push with no github.tf edit and no per-stack registration. Stages run sequentially so each completes before the next fires (deterministic, vs the asynchronous polling of managed: true). ./komodo-sync invokes the same procedure (after a pre-sync round-trip to handle procedure-stage edits — see the komodo-sync row in the scripts table below). Single point of failure: a broken procedure breaks all push-deploys — komodo-sync is the fallback.
