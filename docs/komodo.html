Komodo

Komodo is the orchestrator. One Core runs on bilby (with its own Periphery for the local host). Kangaroo runs a second Periphery, registered to the same Core. Every stack is a Docker Compose project plus a stack.toml file declaring server assignment and environment.

Components

Komodo Core itself runs as four containers in the komodo/ stack:

  • komodo-core — the API + web UI on port 9120.
  • komodo-periphery — bilby's local agent (the daemon Core actually talks to in order to run docker compose).
  • komodo-ferretdb — MongoDB-compatible API; Komodo's metadata store.
  • komodo-postgres — backing store for FerretDB.

Kangaroo runs its own komodo-periphery container — see Hosts → kangaroo. Both Peripheries are registered as Server resources in Komodo via komodo/sync/servers.toml.

Two operating models

Each Periphery host picks one of two ways to read the repo. The current setup uses both:

bilbykangaroo
Operating model files_on_host = true Linked Repo (linked_repo = "podhaus" for kangaroo, linked_repo = "podhaus-kookaburra" for kookaburra — Repo resources are per-Periphery, each host's clone is independent state)
How the repo gets there Cloned manually + bind-mounted into Core and Periphery Komodo clones via HTTPS + a GitHub PAT, stored at /etc/komodo/repos/<repo-name>/ inside the Periphery container
Deploy workflow Commit + push → the single webhook runs the podhaus-push-deploy procedure; Stage 1 BatchDeployStackIfChanged "*" redeploys only the bilby stacks whose files changed or save + ./komodo-sync (force-redeploys any stack whose deployed_hash diverges from HEAD) Commit + push → same procedure; Stage 2 runs BatchDeployStack "kangaroo-*" AND BatchDeployStack "kookaburra-*", each a full DeployStack (git pull the clone + compose) unconditionally. No per-stack flag, no UI click. Adding a new linked-repo host = name its stacks <host>-* and add a matching execution. Naming convention: bare stack name (no prefix) = bilby (the primary, files_on_host host); the <host>- prefix is reserved for linked-repo hosts where Stage 2's BatchDeployStack "<host>-*" glob is the contract. So tailscale = bilby, kookaburra-tailscale = kookaburra.
Best for Active development on the primary host Remote hosts where the source of truth must be the git remote

Two linked-repo hosts exist today: kangaroo (QNAP NAS, repo podhaus) and kookaburra (DigitalOcean relay, repo podhaus-kookaburra). Future deploy targets (e.g. pinelake) should follow the same pattern. Bilby stays on files_on_host because tight save-and-deploy beats the commit-roundtrip when the editor is on the same host.

Linked Repo deploys: what actually pulls (verified, Komodo 1.19.5 source) Long-standing field belief was "manual DeployStack on a Linked Repo host doesn't pull." The Komodo source disproves it: DeployStack (manual or webhook-triggered) runs git pull --rebase --force origin <branch> on the Periphery clone before composing. It is RestartStack that does not pull — it only docker compose restarts. So the corrected rule is: RestartStack = no pull; DeployStack = pulls.

The real trap is subtler. DeployStackIfChanged's change-check compares against the Periphery clone — which only advances during a deploy. On a linked_repo stack that is a deadlock: it no-ops forever because the stale clone always looks "unchanged." This is resolved structurally by the push procedure, not per-stack: Stage 1 (BatchDeployStackIfChanged "*") no-ops harmlessly on kangaroo and kookaburra, then Stage 2 runs BatchDeployStack "kangaroo-*" AND BatchDeployStack "kookaburra-*", each an unconditional full DeployStack (pull + compose). So linked_repo stacks set no webhook_force_deploy — there are no per-stack webhooks; the <host>-* name patterns are the contract. bilby files_on_host stacks ride Stage 1 and self-skip when genuinely unchanged (free no-churn).

Historical compounding bugs (both fixed): the GitHub webhook once pointed at a non-existent path (every delivery 405, fixed 2026-05-16); and per-stack webhooks hit GitHub's hard 20-hook ceiling, replaced 2026-05-17 by the single procedure webhook (see the Auto-deploy note below). RunSync re-imports stack.toml config from bilby's bind-mount (no git) but does not pull a linked clone. Always confirm a deploy via a config-level signal — the pulled-to commit hash or a metric — never "container healthy."

stack.toml structure

Every Komodo-managed stack has a stack.toml alongside its compose.yaml. Minimum shape (bilby-side): 

[[stack]]
name = "gatus"
description = "Config-as-code endpoint monitoring"
tags = ["podhaus"]
deploy = true

[stack.config]
server = "podhaus"
files_on_host = true
run_directory = "/etc/komodo/repo/gatus"

environment = """
TZ=[[TZ]]
POSTMARK_SERVER_TOKEN=[[OP__KOMODO__POSTMARK_SMTP__CREDENTIAL]]
"""

Key fields:

  • server — "podhaus" for bilby, "kangaroo" for kangaroo. Komodo dispatches the stack to that host's Periphery.
  • files_on_host vs linked_repo — picks operating model.
  • run_directory — where Periphery runs docker compose from. For bilby it's always /etc/komodo/repo/<stack>; for kangaroo it's relative to the Linked Repo clone.
  • environment — multi-line string of KEY=VALUE pairs. [[VAR]] entries are interpolated from Komodo Variables (see Secrets).

ResourceSync

Stack definitions, Server entries, Repo declarations, and any other Komodo resources are declared in TOML under komodo/sync/. Komodo reads these via a ResourceSync resource (created by komodo-start on first boot, recreated by ./komodo-sync on demand).

Files in the sync directory today:

  • komodo/sync/servers.toml — bilby and kangaroo Server entries.
  • komodo/sync/repos.toml — the podhaus Linked Repo for kangaroo.
  • komodo/sync/variables.toml — non-secret variable declarations. Not the authoritative source — see Secrets → non-secret variables.
  • komodo/sync/procedures.toml — the podhaus-push-deploy procedure (the single push-to-deploy fan-out; see the Auto-deploy note below).
Auto-deploy on push (one webhook → one procedure) Komodo's webhook contract is per-resource: https://<host>/listener/<auth>/<resource_type>/<id>/<seg>. We do not use one webhook per stack: GitHub hard-caps a repo at 20 push webhooks and the fleet outgrew it (2026-05-17). Instead cloudflare/github.tf creates one webhook → komodo.pod.haus/listener/github/procedure/podhaus-push-deploy/main (resource_type procedure; the trailing /main is the branch filter, not a verb — Komodo 1.19.5 router.rs "/procedure/{id}/{branch}"). Access bypass is path-scoped to /listener/github; Komodo HMAC-validates with KOMODO_WEBHOOK_SECRET (the procedure's webhook_secret is empty → the global secret applies).

The procedure (komodo/sync/procedures.toml) fans out: Stage 1 BatchDeployStackIfChanged "*" — every stack, deploy only if its files changed (bilby diffs the live bind-mount → unchanged stacks self-skip, zero churn; kangaroo and kookaburra no-op here harmlessly because their stale clones look unchanged). Stage 2 runs two executions: BatchDeployStack "kangaroo-*" and BatchDeployStack "kookaburra-*" — the linked_repo stacks, each a full DeployStack (pull + compose) unconditionally. The "*" pattern means new stacks auto-deploy on the next push with no github.tf edit, no list, no 20-cap, ever. ./komodo-sync remains the manual force-redeploy / new-stack-registration equivalent. Single point of failure: a broken procedure breaks all push-deploys (vs. one stack's hook) — it is trivial config-as-code and komodo-sync is the fallback.

komodo-* scripts at the repo root

ScriptPurpose
komodo-startFirst-boot or post-recovery: starts the Komodo Core stack, seeds chicken-and-egg variables from 1Password, creates the ResourceSync resource, triggers the first sync. Idempotent — safe to re-run.
komodo-stopStops the Komodo Core stack (everything else stays running, since Komodo's job is just orchestration; the running containers are managed by Docker directly).
komodo-statusShows the Komodo Core container status.
komodo-syncTriggers the existing ResourceSync without a full restart of Komodo Core. Use after editing any TOML under komodo/sync/ or any stack.toml.
komodo-upgradePulls latest Komodo images, restarts the Core stack.
kangaroo_bootstrapOne-time bring-up for kangaroo. Renders Periphery .env from 1Password, ships compose + config to the QNAP via SSH, installs an @reboot crontab entry, idempotently appends the kangaroo Server to servers.toml.
