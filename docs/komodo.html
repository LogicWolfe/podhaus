Komodo

Komodo is the orchestrator. One Core runs on bilby (with its own Periphery for the local host). Kangaroo runs a second Periphery, registered to the same Core. Every stack is a Docker Compose project plus a stack.toml file declaring server assignment and environment.

Components

Komodo Core itself runs as four containers in the komodo/ stack:

  • komodo-core — the API + web UI on port 9120.
  • komodo-periphery — bilby's local agent (the daemon Core actually talks to in order to run docker compose).
  • komodo-ferretdb — MongoDB-compatible API; Komodo's metadata store.
  • komodo-postgres — backing store for FerretDB.

Kangaroo runs its own komodo-periphery container — see Hosts → kangaroo. Both Peripheries are registered as Server resources in Komodo via komodo/sync/servers.toml.

Core ↔ Periphery auth (v2 PKI noise handshake)

Komodo v2 dropped the v1 KOMODO_PASSKEY shared secret for X25519 noise-handshake mutual auth. Each endpoint holds its own private key; the trust list lives as a set of public-key files.

  • bilby: Core and bilby Periphery share a host bind (/opt/komodo/keys → /config/keys), so each picks up the other's .pub from the same directory. Bilby is also where the master copies of all four keypairs live; the pubkeys are committed to komodo/keys/*.pub in the repo for reference + rebuild.
  • kangaroo, numbat, fractal: Each host has its own keys directory (bootstrap-managed bind, separate from etc-komodo). The bootstrap script SCPs that host's periphery.key + Core's core.pub from bilby's /opt/komodo/keys/ into the remote keys dir. Privkeys never live outside the host they belong to.
  • Trust list on Core: KOMODO_PERIPHERY_PUBLIC_KEYS (in komodo/compose.env) is a comma-separated list of file: paths under /config/keys/ — one .pub per known Periphery. Adding a new host = drop its .pub into the keys volume + extend that env list + restart Core.

Connection direction

v2 supports both Core → Periphery (inbound, like v1) and Periphery → Core (outbound). The choice is per-Server, set by the address field in servers.toml: a populated address = Core dials; empty = Periphery dials.

  • bilby: inbound. Core dials https://periphery:8120 via dockernet (same compose).
  • kangaroo: outbound. Periphery dials ws://10.0.0.119:9120 (bilby LAN). No inbound :8120 listener exposed on kangaroo.
  • numbat: outbound. Periphery dials wss://core-connect.pod.haus through the public TLS rathole path. Komodo Noise keys authenticate the connection; no inbound listener is exposed.
  • fractal: outbound. Periphery dials the same public wss://core-connect.pod.haus endpoint.

Off-host Peripheries use outbound on attack-surface grounds: their Periphery REST/WS surface isn't reachable from anywhere — nothing inbound to gate at all. The noise handshake is the sole auth on the outbound dial.

Two operating models

Each Periphery host picks one of two ways to read the repo. The current setup uses both:

bilbykangaroo
Operating model files_on_host = true Linked Repo (linked_repo = "podhaus" for kangaroo, podhaus-numbat for Numbat, and podhaus-fractal for fractal; Repo resources are per-Periphery, each host's clone is independent state)
How the repo gets there A Komodo-managed clone — the deploy tree (Repo resource podhaus-deploy) — bind-mounted into Core and Periphery. bilby's own working checkout (~/repos/podhaus) is never read by the pipeline; the deploy tree is fed by the push webhook's pull stage or by komodo-sync's local-checkout overlay. Komodo clones via HTTPS + a GitHub PAT, stored at /etc/komodo/repos/<repo-name>/ inside the Periphery container
Deploy workflow Commit + push → the single webhook runs podhaus-push-deploy, which force-pulls the deploy tree to origin/main and then runs the internal podhaus-deploy procedure. Its Stage 1 stamps content hashes and directly reconciles stale running stacks when committed config or build context changed without a compose-text change. Stage 2's BatchDeployStackIfChanged "*" handles compose-text changes and new stacks. For local iteration: ./komodo-sync overlays the deploy tree with the working checkout's current state and invokes podhaus-deploy directly — deliberately skipping the pull stage. The two feeders are last-writer-wins: a push after a WIP komodo-sync reverts the fleet to main, and a komodo-sync after a push overlays local state again. Same workflow and the same Stage 1 / Stage 2. Hashes are computed from the deploy tree's current state and compared with the labels on containers running at the target host, so linked-repo config-only and build-context edits do not rely on an env diff. New linked-repo hosts inherit the behaviour automatically; no Stage 2 entries to maintain, no <host>- name prefix required. Convention still useful: the <host>- prefix on a stack name signals "lives on this remote host" at a glance (numbat-pomerium, kangaroo-backup), but it's a readability convention now, not a deploy-routing contract.
Best for Active development on the primary host Remote hosts where the source of truth must be the git remote

Three linked-repo hosts exist today: kangaroo (QNAP NAS, repo podhaus), Numbat (active BinaryLane gateway, repo podhaus-numbat), and fractal (remote development host, repo podhaus-fractal). Future deploy targets (e.g. pinelake) should follow the same pattern. Bilby stays on files_on_host because tight save-and-deploy beats the commit-roundtrip when the editor is on the same host.

Linked Repo deploys: what actually pulls

DeployStack = pulls; RestartStack = no pull. DeployStack (manual or webhook-triggered) runs git pull --rebase --force origin <branch> on the Periphery clone before composing. RestartStack only docker compose restarts.

Komodo's native DeployStackIfChanged only considers compose text. It does not see a changed value behind a ${STACK_CONTENT_HASH} or ${BUILD_HASH_*} reference. The internal podhaus-deploy procedure — invoked by podhaus-push-deploy after pulling the deploy tree to origin/main, and directly by komodo-sync after overlaying it with the local checkout — closes that gap via its Stage 1's RunAction "podhaus-inject-content-hashes": the Action computes (a) a content hash of each stack directory and (b) per-service hashes for every build: context, both from the deploy tree's current state, and stamps STACK_CONTENT_HASH=<hash> + BUILD_HASH_<UPPER_SERVICE>=<hash> into the stack's stored env. The Action then compares the expected hashes with each running container's podhaus.* labels. If the labels are stale and compose text is unchanged, it runs a direct DeployStack. Stage 2 deliberately owns the disjoint cases: compose-text changes and brand-new stacks. A linked repo is pulled on deploy as part of that normal flow.

Always confirm a deploy via a config-level signal — the pulled-to commit hash or a metric — never "container healthy."

stack.toml structure

Every Komodo-managed stack has a stack.toml alongside its compose.yaml. Minimum shape (bilby-side): 

[[stack]]
name = "gatus"
description = "Config-as-code endpoint monitoring"
tags = ["podhaus"]

[stack.config]
server = "podhaus"
files_on_host = true
run_directory = "/etc/komodo/repo/gatus"

environment = """
TZ=[[TZ]]
POSTMARK_SERVER_TOKEN=[[OP__KOMODO__POSTMARK_SMTP__CREDENTIAL]]
"""

Key fields:

  • server — "podhaus" for bilby, "kangaroo" for kangaroo. Komodo dispatches the stack to that host's Periphery.
  • files_on_host vs linked_repo — picks operating model.
  • run_directory — where Periphery runs docker compose from. For bilby it's always /etc/komodo/repo/<stack>; for kangaroo it's relative to the Linked Repo clone.
  • environment — multi-line string of KEY=VALUE pairs. [[VAR]] entries are interpolated from Komodo Variables (see Secrets).

ResourceSync

Stack definitions, Server entries, Repo declarations, and any other Komodo resources are declared in TOML under komodo/sync/. Komodo reads these via a ResourceSync resource (created by komodo-start on first boot, recreated by ./komodo-sync on demand).

Files in the sync directory today:

  • komodo/sync/servers.toml — bilby and kangaroo Server entries.
  • komodo/sync/repos.toml — the podhaus Linked Repo for kangaroo, plus the podhaus-deploy Repo resource: bilby's own Komodo-managed deploy tree (/etc/komodo/repos/podhaus-deploy), the single tree every deploy decision reads. It's fed two ways: the push webhook force-pulls it to origin/main (on_pull runs git clean -fd to clear untracked strays without touching gitignored files like the deploy-written .env), and komodo-sync overlays it with bilby's working checkout via the podhaus-load-local-tree action.
  • komodo/sync/variables.toml — global non-secret variable declarations (TZ, MEDIA_DIR, and PODHAUS_REPO — the deploy tree's fixed path). Authoritative — the podhaus sync runs with include_variables = true, so a RunSync applies these. Stack-private vars (e.g. FENWICK_*) live as inline [[variable]] blocks in the relevant <stack>/stack.toml instead.
  • komodo/sync/procedures.toml — two procedures: podhaus-push-deploy, the GitHub webhook entrypoint (pulls the deploy tree to origin/main, then runs the procedure below), and the internal podhaus-deploy, which carries the four-stage fan-out and deploys whatever the deploy tree currently holds — see the Auto-deploy note below.
  • komodo/sync/actions.toml — Komodo Actions referenced by procedures and by komodo-sync. podhaus-load-local-tree is komodo-sync's first step: mirrors bilby's working checkout (read-only at /syncs/podhaus-local) into the deploy tree at /syncs/podhaus via git ls-files enumeration on both sides. podhaus-inject-content-hashes is Stage 1 of the internal podhaus-deploy procedure. It walks every stack at Komodo Core's /syncs/podhaus mount (the deploy tree), hashes each committed stack directory plus every build context, stamps the hashes into stored env, and directly deploys running stacks whose hash labels are stale while compose text is unchanged. The deploy-written .env is the intentional exclusion. podhaus-purge-stack-cache reads a deployed stack's podhaus.cloudflare-cache-* labels and purges those tags after its deployment stage. See Public site caching.
  • komodo/sync/syncs.toml — child ResourceSyncs for the separate-repo services (fenwick, pets, docs), each a [[resource_sync]] block with its own linked_repo + dedicated push-deploy procedure. The podhaus sync picks them up via its resource_path scan.

Declare a ResourceSync with [[resource_sync]], never [[sync]]

The synced-TOML key for a ResourceSync is [[resource_sync]] / [resource_sync.config] — Komodo's ResourcesToml field is resource_syncs (alias resource_sync); there is no sync alias in any version. Serde silently drops unknown top-level keys, so a [[sync]] block parses without error but creates nothing — the sync never appears. It bites opaquely: a correctly-keyed [[procedure]] (which does get created) that RunSyncs the missing sync makes the reconcile loop bail with procedure sync loop exited after max iterations and fail the whole RunSync — and Komodo discards the underlying error on that path, so the message is misleading. The fenwick/pets [[sync]] blocks had been inert the whole time (their syncs existed only from earlier manual creation); all three were migrated to [[resource_sync]] on 2026-06-26.

Separate-repo stacks: push podhaus first

A stack defined in a separate repo still depends on podhaus for two things: the docs-server-<host> / equivalent Repo resource it names via linked_repo (komodo/sync/repos.toml), and its stack name in the deploy pattern of the matching push-deploy procedure (komodo/sync/procedures.toml). Both live in podhaus, so podhaus must land before the separate repo whenever a change adds a new instance.

Push them the other way and the failure is quiet: Stage 0's RunSync cannot resolve the linked repo, so the stack is never created, and Stage 1 would not deploy it anyway because the pattern still lacks the name. Nothing in the request path reports an error — the host's Caddy comes up healthy and reverse-proxies to a container that does not exist, which surfaces as a bodyless 502, i.e. a blank white page behind working authentication. Adding voltaire-docs hit this on 2026-08-09. Recovery is to land podhaus and re-run the separate repo's push-deploy procedure; no state needs unwinding.

Auto-deploy on push (one webhook → one procedure)

Komodo's webhook contract is per-resource: https://<host>/listener/<auth>/<resource_type>/<id>/<seg>. podhaus uses one webhook per repo, not per stack: GitHub hard-caps a repo at 20 push webhooks, and the procedure-level fan-out scales past that ceiling. terraform/github.tf creates one webhook → komodo.pod.haus/listener/github/procedure/podhaus-push-deploy/main (resource_type procedure; the trailing /main is the branch filter, not a verb — Komodo router.rs "/procedure/{id}/{branch}"). Access bypass is path-scoped to /listener/github; Komodo HMAC-validates with KOMODO_WEBHOOK_SECRET (the procedure's webhook_secret is empty → the global secret applies).

podhaus-push-deploy itself is two thin stages: Stage 0 PullRepo "podhaus-deploy" force-pulls bilby's Komodo-managed deploy tree (/etc/komodo/repos/podhaus-deploy) to origin/main, then Stage 1 RunProcedure "podhaus-deploy" runs the internal procedure below. bilby's own working checkout (~/repos/podhaus) is never touched by this path.

The internal podhaus-deploy procedure (komodo/sync/procedures.toml) deploys whatever the deploy tree currently holds — source-agnostic, so the same four stages serve both a fresh pull and, via komodo-sync, a local-checkout overlay: Stage 0 RunSync "podhaus" — reconcile stack definitions + TOML-declared variables from disk to Komodo's stored resource state. Without this, a push that adds a new environment line to a stack.toml reached the deploy via the on-disk file but Komodo's DeployStack used the stored (pre-sync) resource def, so the var resolved empty. Stage 0 is config-reconcile-only — Komodo's built-in Sync Deploy sub-stage (which would auto-deploy any stack whose stored config diverges from deployed) no-ops because every podhaus stack.toml omits deploy = true; Stage 1 and Stage 2 below are the deploy authorities. Stage 1 RunAction "podhaus-inject-content-hashes" — walks every stack visible at Core's /syncs/podhaus mount (the deploy tree), computes a deterministic content hash of each stack directory (including bind-mounted runtime paths) and per-service build-context hashes for any service with build:, and stamps STACK_CONTENT_HASH=<hash> + BUILD_HASH_<UPPER_SERVICE>=<hash> into the stored env. The Action compares those hashes to each running container's labels and directly deploys a stale stack when its compose text is unchanged. This is the trigger for config-only and build-context edits, and it works uniformly for files_on_host and linked_repo stacks. Stage 2 BatchDeployStackIfChanged "*": deploy compose-text changes and brand-new stacks. Stage 1 skips those cases, so the two paths do not recreate the same stack twice; unchanged stacks no-op. Stage 3 RestartStack "ofelia" — re-read container labels so cron schedule / command edits propagate (the released ofelia image reads labels only at startup; see Scheduling). The "*" pattern means new stacks auto-deploy on the next push with no github.tf edit and no per-stack registration. Stages run sequentially so each completes before the next fires (deterministic, vs the asynchronous polling of managed: true). ./komodo-sync runs a first step, RunAction "podhaus-load-local-tree", which overlays the deploy tree with bilby's working checkout's current state (tracked + untracked-unignored files), then invokes podhaus-deploy directly — deliberately not podhaus-push-deploy, whose pull stage would clobber that overlay — after the same out-of-procedure pre-sync round-trip to handle procedure-stage edits (see the komodo-sync row in the scripts table below). Single point of failure: a broken procedure breaks all push-deploys — komodo-sync is the fallback.
