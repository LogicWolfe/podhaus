Hosts

Four active hosts and one planned. Bilby's Komodo Core manages bilby, kangaroo, Numbat, and fractal.

bilby

Apple M1 Mac mini, 8 cores, 15 GB RAM, aarch64, Fedora Asahi Linux. Primary host. Runs Komodo Core (Postgres + FerretDB + Core + Periphery), the primary podhaus stacks, and the 1Password Connect API. LAN IP 10.0.0.119.

Filesystem highlights:

  • Local NVMe — hot operational state for every stack. See Storage for the per-stack layout.
  • /mnt/pouch: NFS mount of the QNAP HDD array. Plex media and Flood downloads.
  • /mnt/jump: NFS mount of the QNAP SSD array. Restic repositories, Paperless documents, Forgejo data, and Plex BIF thumbnails.
SELinux on Fedora Asahi Most container bind mounts need security_opt: label:disable or the :z volume flag. Pattern documented in Stack conventions.

Host CLI tools

For ad-hoc debugging and one-shot administration of containerized services, install the service's client CLI on bilby rather than spinning up a throwaway container or docker exec-ing into the running stack. Host-installed clients give you tab completion, persistent history, scriptable composition, and don't depend on whether the target container has the right tooling shipped inside.

The container approach still wins for two narrow cases: (a) one-time bootstrap of a stack you don't expect to interact with again, and (b) reaching a service whose protocol isn't routable from the host (rare — most run on dockernet, reachable from the host via the bridge gateway at 172.18.0.1). Everything else: install locally.

Firewall (firewalld)

bilby runs firewalld. The source of truth is the firewalld Ansible role — ansible/roles/firewalld/files/zones/public.xml (the LAN-facing end0 zone) plus files/services/*.xml (custom port groups). The role installs the service XML first, then the zone, runs firewall-cmd --check-config, and only then reloads. To change the firewall: edit the XML under ansible/roles/firewalld/files/ and run ansible-playbook playbooks/bilby.yml --tags firewall from ansible/.

Never edit the firewall imperatively Do not use firewall-cmd --add-port/--add-service (even --permanent). That writes straight to /etc/firewalld/ and diverges from the role's files; the next playbook run silently overwrites and reverts it. Change the XML, re-run the play.

The public zone allows ssh, mdns, dhcpv6-client, plex, and music-assistant, plus a rich rule that trusts the entire home LAN (10.0.0.0/24 → accept). Two patterns follow from that:

  • LAN-only service → no explicit rule. Anything reached only by devices on 10.0.0.0/24 is already covered by the LAN trust rule. Example: Home Assistant's HomeKit bridge on tcp/21063, reached only by the LAN Apple hubs (its advertise_ip is pinned to the IPv4 LAN address). Adding an explicit service for it would needlessly expose the port to the tailnet and dockernet.
  • Service needing non-LAN reach → explicit service XML. plex and music-assistant get their own XML because Caddy reaches them via the dockernet gateway (172.18.0.1, not in 10.0.0.0/24). That inbound flow isn't covered by the LAN rule, so the port must be named explicitly.

kangaroo

QNAP NAS, AMD GX-420MC, 16 GB RAM, QTS 5.x with Container Station, ext4. Secondary host. Runs a Komodo Periphery agent + Syncthing + a second Backrest + autoheal + a logging Alloy collector + the Pouch-backed MinIO instance. The active 10GbE LAN IP is 10.0.0.25; 10.0.0.232 is the spare 1GbE path.

Filesystem highlights:

  • /share/CACHEDEV1_DATA/Pouch — the bulk HDD volume. Same content bilby sees as /mnt/pouch. The dedicated MinIO data root is /share/CACHEDEV1_DATA/Pouch/minio.
  • /share/CACHEDEV2_DATA/Jump — the SSD volume. Kangaroo's Backrest restic repo lives at /share/CACHEDEV2_DATA/Jump/backups-kangaroo — a separate repo from bilby's to avoid restic two-client coordination.
  • /share/CACHEDEV2_DATA/Container/komodo-periphery/etc-komodo/ — Periphery state.
No Container Station GUI involvement The bootstrap uses SSH to install and start Periphery. After that, Periphery deploys stacks through the QNAP Docker socket. Container Station's REST API only accepts built-in template names, and its GUI flow blocks the docker.sock mount Periphery needs. Survival across CS/QTS upgrades is handled by the QNAP boot-DOM autorun.sh installed from kangaroo/host-autorun/. It starts Container Station's user Docker engine and reconciles exited or detached containers. See disaster recovery.

numbat

BinaryLane Perth, Rocky Linux 10, 1 vCPU, 1 GB RAM, 20 GB NVMe. Numbat is the active public gateway. Terraform owns the VM, both IPv4 address roles, DNS, Pocket ID configuration, PKI, and 1Password handoffs.

  • app.numbat.pod.haus: Forgejo SSH on port 22, Pomerium redirect and ACME on 80, Pomerium HTTPS on 443.
  • relay.numbat.pod.haus: Pomerium native SSH on port 22, public TLS rathole on 443, and rathole control on 2333.
  • Ansible-managed: host nftables, loopback-only sshd, a first-boot-only key-pinned sshd on application port 2222, outbound Periphery, and the SSH-only Tailscale recovery daemon. ansible-playbook playbooks/numbat-bootstrap.yml (fresh VM, from bilby) starts the relay before Periphery, installs the final firewall, then closes port 2222; playbooks/numbat.yml is the steady state, reached through Pomerium.
  • Komodo-managed: numbat-pomerium, numbat-relay, numbat-logging, and numbat-autoheal through linked repo podhaus-numbat.

Periphery returns through core-connect.pod.haus with Komodo Noise auth. Alloy returns through logs-ingest.pod.haus with per-host mTLS. There is no routed path into either home network. Its userspace Tailscale daemon publishes only loopback sshd to tag:recovery; it installs no host route. The BinaryLane console remains the final break-glass path.

fractal

Fedora 44 under WSL2 on a Windows desktop. Ryzen 9 9950X3D, 32 vCPU / 15 GB RAM, 1 TB ext4 root plus a LUKS /home. It is two things at once: Nathan's remote development machine and an ordinary podhaus host. The first host provisioned entirely by Ansible — it has no bootstrap script and never had one.

Everything in and out is a connection fractal makes. Its LAN address 10.0.0.70 is the Windows host, which forwards only :22 into the guest; the guest itself sits behind WSL's NAT on a subnet that changes across reboots. So there is no inbound path to depend on, and none is used.

  • Ansible-managed (root state): hostname via /etc/wsl.conf, timezone, Docker CE + dockernet, the developer toolchain, the Pomerium SSH user-CA trust, and Komodo Periphery. Run ansible/playbooks/fractal.yml.
  • chezmoi-managed (user state): everything under $HOME — shell, dotfiles, the machine SSH key. Applied by Nathan as himself; Ansible never invokes it.
  • Komodo-managed: fractal-relay (rathole client), fractal-caddy (mTLS origin), fractal-logging (Alloy), and fractal-docs (the docs-server over ~/repos) through linked repos podhaus-fractal and docs-server-fractal.
  • Bootstrap-managed: Komodo Periphery only — Core reaches this host solely through the connection Periphery makes, so a Komodo-driven redeploy of it would sever the path it runs on. Same reasoning as kangaroo. Ansible owns it instead of a script.

Ingress is an outbound rathole client to numbat, following the same pattern as bilby: fractal.docs.pod.haus lands on Pomerium, which forwards to 127.0.0.1:8444 on numbat, through the tunnel to fractal's Caddy on :4443 (mTLS origin), and on to the docs container. SSH takes the same route via 127.0.0.1:2204 and the ssh://fractal Pomerium route; ssh fractal.pod.haus resolves through a chezmoi Match originalhost rule, not a DNS record.

fractal has no backup stack. Everything Ansible and chezmoi put there is reproducible from the repos, and its Periphery private key also exists on bilby under /opt/komodo/keys/. The one category that is not covered is uncommitted work in ~/repos — that is a developer-discipline boundary today, not a backed-up one. Revisit if anything else lands on the host.

There is no TPM and no USB passthrough under WSL, so fractal cannot hold a hardware-resident machine key the way voltaire (TPM) and bilby (YubiKey PIV) do. Its machine key is a soft ed25519 key on the LUKS /home. A YubiKey was considered and rejected: usbipd attach is manual and does not survive a reboot, which forfeits the unattended-agent property the key exists for and deepens exactly the Windows coupling the outbound-only design avoids.

Adding another host

Any host that can run Python: use Ansible. fractal is the worked example — see Host provisioning for the role layout and the chezmoi boundary. In outline:

  1. Add the host to ansible/inventory/hosts.yml and give it an inventory/host_vars/<host>.yml. Put it in the role groups it belongs to (docker_hosts, komodo_periphery_hosts, devboxes).
  2. Generate its X25519 Periphery keypair on bilby, drop the pubkey at komodo/keys/<host>-periphery.pub, and append file:/config/keys/<host>-periphery.pub to KOMODO_PERIPHERY_PUBLIC_KEYS in komodo/compose.env. Never commit the private half.
  3. Declare the Server in komodo/sync/servers.toml with address = "" (new Peripheries dial Core outbound) and a Linked Repo in komodo/sync/repos.toml. Use files_on_host only if the repo will live directly on the host, bilby-style.
  4. Write <host>/periphery/compose.yaml and run the playbook. The komodo_periphery role ships the keys, brings the container up, and blocks until Core reports the Server Ok.
  5. Add the host's per-host overlays to backup/, autoheal/, logging/ following the existing pattern.

kangaroo is the exception and stays script-provisioned: QTS ships no Python at all, so it can never be an Ansible target. kangaroo_bootstrap remains its runbook.
