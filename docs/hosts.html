Hosts

Two physical hosts today, a third planned. Both are registered with the same Komodo Core on bilby; stack deploys for either host go through the same UI.

bilby

Apple M1 Mac mini, 8 cores, 15 GB RAM, aarch64, Fedora Asahi Linux. Primary host. Runs Komodo Core (Postgres + FerretDB + Core + Periphery), every original podhaus stack, the Cloudflare Tunnel, and the 1Password Connect API. LAN IP 10.0.0.119.

Filesystem highlights:

  • Local NVMe — hot operational state for every stack. See Storage for the per-stack layout.
  • /mnt/pouch — NFS mount of the QNAP HDD array. Plex media, BIFs, paperless documents, flood downloads.
  • /mnt/jump — NFS mount of the QNAP SSD array. Restic repo storage.
SELinux on Fedora Asahi Most container bind mounts need security_opt: label:disable or the :z volume flag. Pattern documented in Stack conventions.

Host CLI tools

For ad-hoc debugging and one-shot administration of containerized services, install the service's client CLI on bilby rather than spinning up a throwaway container or docker exec-ing into the running stack. Host-installed clients give you tab completion, persistent history, scriptable composition, and don't depend on whether the target container has the right tooling shipped inside.

The container approach still wins for two narrow cases: (a) one-time bootstrap of a stack you don't expect to interact with again, and (b) reaching a service whose protocol isn't routable from the host (rare — most run on dockernet, reachable from the host via the bridge gateway at 172.18.0.1). Everything else: install locally.

kangaroo

QNAP NAS, AMD GX-420MC, 16 GB RAM, QTS 5.x with Container Station, ext4. Secondary host. Runs a Komodo Periphery agent + Syncthing + a second Backrest + autoheal + a logging Alloy collector. LAN IP 10.0.0.232.

Filesystem highlights:

  • /share/CACHEDEV1_DATA/Pouch — the bulk HDD volume. Same content bilby sees as /mnt/pouch.
  • /share/CACHEDEV2_DATA/Jump — the SSD volume. Kangaroo's Backrest restic repo lives at /share/CACHEDEV2_DATA/Jump/backups-kangaroo — a separate repo from bilby's to avoid restic two-client coordination.
  • /share/CACHEDEV1_DATA/Container/komodo-periphery/etc-komodo/ — Periphery state.
No Container Station GUI involvement Periphery deploys via SSH + docker compose up -d against the QNAP host's Docker daemon directly. Container Station's REST API only accepts built-in template names, and its GUI flow blocks the docker.sock mount Periphery needs. Survival across CS/QTS upgrades is handled by a @reboot line in /etc/config/crontab — see disaster recovery.

kookaburra

DigitalOcean droplet, syd1 region, 1 vCPU / 1 GB RAM, 10 GB disk, Fedora 43 x86_64. Off-LAN public-ingress relay host — its sole job is terminating TCP for storage.pod.haus on its public reserved IP 170.64.241.136 and passing the bytes through a rathole reverse tunnel to bilby's Caddy. TLS terminates on bilby (LE wildcard), so this droplet only ever sees ciphertext — no MinIO data, no certs, no creds. Stateless by design (see the AGENTS hard rule).

Why it exists: the UDM Pro SE binds WAN tcp/443 with UniFi OS itself and shadows any direct WAN port-forward, so genuine external clients never reached bilby's Caddy via the home WAN IP. The relay sidesteps the UDM entirely: bilby dials out to kookaburra, no home inbound.

  • Public surface: :443 (rathole data) and :2333 (rathole control, noise+token). Nothing else inbound from the internet (DO firewall). Public SSH on :22 is kept open as a recovery path; the host's nftables ruleset rate-limits non-trusted sources and auto-allowlists any IP that successfully authenticates (no banning — agents fumbling keys aren't punished). All persisted in kookaburra/ssh-hardening/apply.sh so it survives any rebuild.
  • Management plane: Tailscale (tag:podnet); kookaburra appears as kookaburra-podnet. Komodo Periphery dials Core outbound at ws://bilby-podnet.tail9ceb.ts.net:9120 (Komodo v2 PKI, X25519 noise handshake — no inbound :8120 listener on kookaburra). The MagicDNS FQDN resolves to whatever tailnet IP bilby-podnet currently holds; both the Periphery (dockernet) and dockernet itself forward DNS through MagicDNS via the host /etc/docker/daemon.json.
  • Bootstrap-launched services (run before Komodo can manage them because Komodo→Periphery depends on Periphery being reachable): kookaburra-podnet (tailscale) and komodo-periphery. Brought up by kookaburra_bootstrap via SSH + docker compose; reboot-persistent via restart: unless-stopped. The tailscale container is subsequently adopted by the kookaburra-tailscale Komodo stack (same compose project name + container name + state volume) — Komodo manages it steady-state. Periphery stays bootstrap-managed.
  • Komodo-managed stacks: kookaburra-tailscale (adopts the bootstrap-launched tailscale; ships a tailscale-cleanup init that deletes stale tailnet ghosts so the bare hostname is reclaimable on rebuild), kookaburra-relay (rathole server), and kookaburra-logging (alloy → bilby ClickStack cross-tailnet). Linked-repo clone (podhaus-kookaburra) at /opt/komodo-periphery/etc-komodo/repos/podhaus-kookaburra/; force-deployed on every push via the kookaburra-* pattern in Stage 2 of podhaus-push-deploy.

Disaster recovery: terraform apply -replace=digitalocean_droplet.kookaburra in terraform/ rebuilds the droplet (reserved IP survives the reassignment), ./kookaburra_bootstrap reinstalls SSH hardening + dockernet bridge + tailscale + Periphery, push-deploy fans the rest out. The droplet is intentionally excluded from backups; if meaningful state ever lands on it, that hard rule (AGENTS.md) is voided — reopen the backup decision then.

Adding another host

The kangaroo bring-up doubled as the runbook for "add a host to the existing Komodo Core". The same path applies for pinelake:

  1. Bring up a Periphery agent on the new host (template at kangaroo/periphery/compose.yaml).
  2. Use the kangaroo_bootstrap script as a model — it's idempotent and covers .env rendering from 1Password, crontab survival, and idempotently appending the new server entry to komodo/sync/servers.toml.
  3. Declare a Linked Repo for the host in komodo/sync/repos.toml (kangaroo uses one — push-to-deploy via git clone) or use files_on_host if the repo is going to live directly on the host (bilby-style — save-and-deploy).
  4. Add the host's per-host overlays to backup/, autoheal/, logging/ following the existing kangaroo/bilby pattern.
