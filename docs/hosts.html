Hosts

Four active hosts and one planned. Bilby's Komodo Core manages bilby, kangaroo, Numbat, and the retained Kookaburra rollback host.

bilby

Apple M1 Mac mini, 8 cores, 15 GB RAM, aarch64, Fedora Asahi Linux. Primary host. Runs Komodo Core (Postgres + FerretDB + Core + Periphery), the primary podhaus stacks, the the retained Cloudflare Tunnel, and the 1Password Connect API. LAN IP 10.0.0.119.

Filesystem highlights:

  • Local NVMe — hot operational state for every stack. See Storage for the per-stack layout.
  • /mnt/pouch: NFS mount of the QNAP HDD array. Plex media and Flood downloads.
  • /mnt/jump: NFS mount of the QNAP SSD array. Restic repositories, Paperless documents, Forgejo data, and Plex BIF thumbnails.
SELinux on Fedora Asahi Most container bind mounts need security_opt: label:disable or the :z volume flag. Pattern documented in Stack conventions.

Host CLI tools

For ad-hoc debugging and one-shot administration of containerized services, install the service's client CLI on bilby rather than spinning up a throwaway container or docker exec-ing into the running stack. Host-installed clients give you tab completion, persistent history, scriptable composition, and don't depend on whether the target container has the right tooling shipped inside.

The container approach still wins for two narrow cases: (a) one-time bootstrap of a stack you don't expect to interact with again, and (b) reaching a service whose protocol isn't routable from the host (rare — most run on dockernet, reachable from the host via the bridge gateway at 172.18.0.1). Everything else: install locally.

Firewall (firewalld)

bilby runs firewalld. The source of truth is bilby/firewalld/ in the repo — zones/public.xml (the LAN-facing end0 zone) plus services/*.xml (custom port groups). It is staged onto the host by bilby/host-systemd/install.sh, which installs the service XML first, then the zone, runs firewall-cmd --check-config, and only then reloads. To change the firewall: edit the XML under bilby/firewalld/ and run sudo ./bilby/host-systemd/install.sh.

Never edit the firewall imperatively Do not use firewall-cmd --add-port/--add-service (even --permanent). That writes straight to /etc/firewalld/ and diverges from bilby/firewalld/; the next install.sh silently overwrites and reverts it. Change the XML, re-run install.sh.

The public zone allows ssh, mdns, dhcpv6-client, plex, and music-assistant, plus a rich rule that trusts the entire home LAN (10.0.0.0/24 → accept). Two patterns follow from that:

  • LAN-only service → no explicit rule. Anything reached only by devices on 10.0.0.0/24 is already covered by the LAN trust rule. Example: Home Assistant's HomeKit bridge on tcp/21063, reached only by the LAN Apple hubs (its advertise_ip is pinned to the IPv4 LAN address). Adding an explicit service for it would needlessly expose the port to the tailnet and dockernet.
  • Service needing non-LAN reach → explicit service XML. plex and music-assistant get their own XML because Caddy reaches them via the dockernet gateway (172.18.0.1, not in 10.0.0.0/24). That inbound flow isn't covered by the LAN rule, so the port must be named explicitly.

kangaroo

QNAP NAS, AMD GX-420MC, 16 GB RAM, QTS 5.x with Container Station, ext4. Secondary host. Runs a Komodo Periphery agent + Syncthing + a second Backrest + autoheal + a logging Alloy collector + the Pouch-backed MinIO instance. The active 10GbE LAN IP is 10.0.0.25; 10.0.0.232 is the spare 1GbE path.

Filesystem highlights:

  • /share/CACHEDEV1_DATA/Pouch — the bulk HDD volume. Same content bilby sees as /mnt/pouch. The dedicated MinIO data root is /share/CACHEDEV1_DATA/Pouch/minio.
  • /share/CACHEDEV2_DATA/Jump — the SSD volume. Kangaroo's Backrest restic repo lives at /share/CACHEDEV2_DATA/Jump/backups-kangaroo — a separate repo from bilby's to avoid restic two-client coordination.
  • /share/CACHEDEV2_DATA/Container/komodo-periphery/etc-komodo/ — Periphery state.
No Container Station GUI involvement The bootstrap uses SSH to install and start Periphery. After that, Periphery deploys stacks through the QNAP Docker socket. Container Station's REST API only accepts built-in template names, and its GUI flow blocks the docker.sock mount Periphery needs. Survival across CS/QTS upgrades is handled by the QNAP boot-DOM autorun.sh installed from kangaroo/host-autorun/. It starts Container Station's user Docker engine and reconciles exited or detached containers. See disaster recovery.

numbat

BinaryLane Perth, Rocky Linux 10, 1 vCPU, 1 GB RAM, 20 GB NVMe. Numbat is the active public gateway. Terraform owns the VM, both IPv4 address roles, DNS, Pocket ID configuration, PKI, and 1Password handoffs.

  • app.numbat.pod.haus: Forgejo SSH on port 22, Pomerium redirect and ACME on 80, Pomerium HTTPS on 443.
  • relay.numbat.pod.haus: Pomerium native SSH on port 22, public TLS rathole on 443, and rathole control on 2333.
  • Bootstrap-managed: host nftables, loopback-only sshd, a first-boot-only key-pinned sshd on application port 2222, outbound Periphery, and the SSH-only Tailscale recovery daemon. ./numbat_bootstrap starts the relay before Periphery, installs the final firewall, then closes port 2222.
  • Komodo-managed: numbat-pomerium, numbat-relay, numbat-pomerium, numbat-logging, and numbat-autoheal through linked repo podhaus-numbat.

Periphery returns through core-connect.pod.haus with Komodo Noise auth. Alloy returns through logs-ingest.pod.haus with per-host mTLS. There is no routed path into either home network. Its userspace Tailscale daemon publishes only loopback sshd to tag:recovery; it installs no host route. The BinaryLane console remains the final break-glass path.

kookaburra

DigitalOcean droplet, syd1 region, 1 vCPU / 1 GB RAM, Fedora 43 x86_64. Retained rollback gateway. Before Numbat it terminated raw TCP for storage.pod.haus, pouch.pod.haus, and git.pod.haus on its public reserved IP 170.64.241.136, then passed the bytes through rathole to bilby. HTTPS terminates at Caddy on bilby; the droplet only sees ciphertext. Forgejo SSH terminates in Forgejo itself. Migrated DNS no longer targets it, but nothing has been shut down. Stateless by design (see the AGENTS hard rule).

Why it exists: the UDM Pro SE binds WAN tcp/443 with UniFi OS itself and shadows any direct WAN port-forward, so genuine external clients never reached bilby's Caddy via the home WAN IP. The relay sidesteps the UDM entirely: bilby dials out to kookaburra, no home inbound.

  • Public surface: :443 on the Reserved IP for storage + Forgejo HTTPS, :22 on the Reserved IP's anchor interface for Forgejo SSH, and :2333 (rathole control, noise+token). Nothing else inbound from the internet (DO firewall). Public SSH on :22 is kept open as a recovery path; the host's nftables ruleset rate-limits non-trusted sources and auto-allowlists any IP that successfully authenticates (no banning — agents fumbling keys aren't punished). All persisted in kookaburra/ssh-hardening/apply.sh so it survives any rebuild. Host sshd listens on :22 only at the droplet's ordinary public address; rathole owns :22 only at the anchor address, so both protocols retain the standard port.
  • Management plane: Tailscale (tag:podnet); kookaburra appears as kookaburra-podnet. Komodo Periphery dials Core outbound at ws://bilby-podnet.tail9ceb.ts.net:9120 (Komodo v2 PKI, X25519 noise handshake; port 8120 is not published on kookaburra). The MagicDNS FQDN resolves to whatever tailnet IP bilby-podnet currently holds; containers on dockernet forward unknown names through MagicDNS via the host /etc/docker/daemon.json.
  • Bootstrap-launched services (run before Komodo can manage them because Komodo→Periphery depends on Periphery being reachable): kookaburra-podnet (tailscale) and komodo-periphery. Brought up by kookaburra_bootstrap via SSH + docker compose; reboot-persistent via restart: unless-stopped. The tailscale container is subsequently adopted by the kookaburra-tailscale Komodo stack (same compose project name + container name + state volume) — Komodo manages it steady-state. Periphery stays bootstrap-managed.
  • Komodo-managed stacks: kookaburra-tailscale (adopts the bootstrap-launched tailscale; ships a tailscale-cleanup init that deletes stale tailnet ghosts so the bare hostname is reclaimable on rebuild), kookaburra-relay (rathole server), and kookaburra-logging (alloy → bilby ClickStack cross-tailnet). Linked-repo clone (podhaus-kookaburra) at /opt/komodo-periphery/etc-komodo/repos/podhaus-kookaburra/. The normal content-hash reconcile and deploy-if-changed stages cover these stacks on each push.

Disaster recovery: terraform apply -replace=digitalocean_droplet.kookaburra in terraform/ rebuilds the droplet (reserved IP survives the reassignment), ./kookaburra_bootstrap reinstalls SSH hardening + dockernet bridge + tailscale + Periphery, push-deploy fans the rest out. The droplet is intentionally excluded from backups; if meaningful state ever lands on it, that hard rule (AGENTS.md) is voided — reopen the backup decision then.

pinelake (planned)

A second household's primary host, paralleling bilby's role for that environment. Designed to drop into the existing layout: a new entry in komodo/sync/servers.toml, its own row in the multi-host shared services (backup/, autoheal/, logging/), and per-stack deploys through the same Komodo Core. pinelake.haus already has Cloudflare DNS and Access scaffolding in terraform/; no server or stack definitions have landed yet.

Adding another host

The kangaroo bring-up doubled as the runbook for "add a host to the existing Komodo Core". The same path applies for pinelake:

  1. Bring up a Periphery agent on the new host (template at kangaroo/periphery/compose.yaml).
  2. Use kangaroo_bootstrap or numbat_bootstrap as the model that matches the host's connectivity.
    3. New Peripheries use v2 keypair authentication and dial Core outbound. Host-native boot integration keeps the Docker engine and bootstrap-managed Periphery alive.
  3. Declare a Linked Repo for the host in komodo/sync/repos.toml (kangaroo uses one — push-to-deploy via git clone) or use files_on_host if the repo is going to live directly on the host (bilby-style — save-and-deploy).
  4. Add the host's per-host overlays to backup/, autoheal/, logging/ following the existing kangaroo/bilby pattern.
