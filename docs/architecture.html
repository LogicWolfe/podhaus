Architecture

Two hosts, one Komodo Core, one git repo. All services run as Docker Compose stacks whose configs are committed; secrets are templated in at deploy time from 1Password.

Topology

bilby (Apple M1 Mac mini, 15 GB RAM, Asahi Linux) is the primary host. It runs Komodo Core, the Periphery agent for itself, and every original podhaus stack (Plex, Paperless, Home Assistant, Flood, etc.).

kangaroo (QNAP NAS, QTS, ext4) runs a second Periphery agent registered to the same Komodo Core, plus Syncthing, a second Backrest instance, an autoheal, and a logging Alloy collector. Kangaroo is a managed deploy target — its stacks live in the same git repo and are deployed through the same Komodo UI.

pinelake is a planned third host (same role as bilby — primary services for a second household). When it lands, it slots into the existing pattern with no further architectural work.

Repo layout

  • Single-host services live in a top-level directory with compose.yaml and stack.toml — e.g. plex/, paperless/, gatus/.
  • Multi-host shared services use the <service>/{compose.shared.yaml, <host>/...} layout. Each host's compose.yaml does include: [../compose.shared.yaml] and overlays host-specific bits. Applies to backup/, autoheal/, logging/.
  • Komodo's own infrastructure lives in komodo/ (ferretdb.compose.yaml, ResourceSync TOML files).
  • Bootstrap scripts (komodo-start, komodo-sync, kangaroo_bootstrap, kookaburra_bootstrap) sit at the repo root.
  • terraform/ is the ONE consolidated Terraform root for everything outside Docker — Cloudflare zones + Access apps + tunnel ingress, UniFi LAN DNS, the GitHub webhook that drives Komodo auto-deploy, DigitalOcean (the kookaburra relay droplet), Tailscale auth-key rotation, and MinIO IAM/bucket policies for Publii tenants. State at s3://terraform-state/podhaus.tfstate in MinIO (backend via https://storage.pod.haus). Stock terraform runs from any machine — no wrapper. See Terraform.

The repo is bind-mounted into bilby's Komodo Core (for ResourceSync) and bilby's Periphery (for stack compose files). Kangaroo's and kookaburra's Peripheries clone the repo themselves via Komodo's Linked Repo resource (different Repo names per host since each clone is independent state) — see Komodo → operating models.

Design principles

These four principles trump local convenience whenever they conflict:

Config-as-code

Any config that can live in the repo, should. Container-volume-only state is not an acceptable substitute — those files get lost on rebuild. Secrets live in 1Password and are templated in at deploy time; everything else is plain files committed alongside the compose definitions.

Local state by default

Bilby's NVMe is the canonical home for container state. NFS volumes carry bulk content (Plex media, paperless documents, BIFs) but not operational state. Backrest → Jump SSD → OneDrive is the durability mechanism. The original "stateless bilby on NFS" idea was abandoned during the Phase 6 architecture pivot — SQLite on NFS under contention is fragile.

Storage tier rule

Three tiers, chosen by what you'd hate to lose rather than by size alone:

  • Local NVMe — hot operational state, <5 GB per stack, backed up nightly.
  • Jump (NAS SSD, RAID5, ~280 GB free) — durable storage we'd hate to lose: restic repo.
  • Pouch (NAS HDD, RAID5, ~5 TB free) — bulk content where capacity matters more than per-drive resilience.

See Storage for mount details and the NAS-squash quirk.

Secrets from 1Password, never from the UI

Komodo Variables come from 1Password via komodo-op, never created manually through the Komodo UI. When a stack needs a secret, the workflow is:

  1. Add the item to the Homelab 1Password vault.
  2. komodo-op auto-syncs it as OP__KOMODO__<ITEM>__<FIELD>.
  3. Reference that synced name in the stack's environment block in stack.toml.

Manual UI variables don't survive a fresh Komodo bootstrap and silently break the disaster-recovery path. The only direct-seeded variables (in komodo-start) are chicken-and-egg credentials (the four ONEPASSWORD_* that komodo-op itself needs to talk to 1Password) plus host-discovered PODHAUS_REPO. Everything else — global non-secret vars (TZ, MEDIA_DIR) and stack-private ones (FENWICK_*, etc.) — lives in TOML and applies via the ResourceSync's include_variables = true config. See Secrets & variables for the full flow.

Ingress

Browser-facing service traffic enters through a single Cloudflare Tunnel running on bilby. Ingress rules live in cloudflare-tunnel/config.yml — adding a service that needs a hostname means adding one rule there plus a CNAME in dns/dnsconfig.js. Cloudflare Access enforces a *.pod.haus wildcard policy so every admin surface is gated on a "Family" identity group without needing a per-service Access app. DNS-only relay services are the explicit exceptions: MinIO TLS and both Forgejo protocols reach bilby through kookaburra's rathole relay. Forgejo uses one hostname, git.pod.haus: :443 terminates at bilby's Caddy and :22 reaches Forgejo's embedded SSH server. Pocket ID is the web authentication boundary.

See Networking for dockernet, host-network services, and DNS detail.

Stack lifecycle

Day-to-day, the loop is:

  1. Edit a stack's compose.yaml or stack.toml.
  2. Commit (optional — bilby uses files_on_host, so changes are read straight from the working tree).
  3. Run ./komodo-sync — Komodo Core picks up the updated stack definition.
  4. Deploy the stack from the Komodo UI (or accept the auto-pulled change).
Known gap komodo-sync updates stack definitions in Komodo's database but doesn't currently auto-redeploy changed stacks. Manual Deploy in the UI is the step that actually recreates containers. Tracked as a follow-up.
