Architecture

Six active hosts, one Komodo Core, one git repo. Services run as Docker Compose stacks whose configs are committed; secrets are templated in at deploy time from 1Password.

Topology

bilby (Apple M1 Mac mini, 15 GB RAM, Asahi Linux) is the primary host. It runs Komodo Core, the Periphery agent for itself, and the primary podhaus stacks (Plex, Paperless, Home Assistant, Flood, etc.).

kangaroo (QNAP NAS, QTS, ext4) runs a second Periphery agent registered to the same Komodo Core, plus Syncthing, a second Backrest instance, an autoheal, and a logging Alloy collector. Kangaroo is a managed deploy target — its stacks live in the same git repo and are deployed through the same Komodo UI.

numbat is a Rocky Linux BinaryLane VM in Perth. It is the active public gateway: Pomerium authenticates browser and host-SSH traffic, rathole accepts named outbound connections, Periphery dials Komodo Core, and Alloy ships logs back to bilby. It has no routed access to the home network.

fractal is a Fedora WSL2 development machine and an ordinary managed host. It reaches Komodo, logging, browser ingress, and SSH by making narrow outbound connections through Numbat; it has no general inbound path.

voltaire is a Fedora Workstation development machine on a foreign LAN. It has no inbound network path and reaches the fleet through outbound Periphery, rathole, and Alloy connections to Numbat.

pinelake is an Apple M1 Mac mini media appliance in the second household. OrbStack runs its Komodo-managed Plex, Flood, Syncthing, backup, ingress, logging, scheduling, and Autoheal stacks. It reaches the fleet through outbound Periphery, rathole, and Alloy connections to Numbat.

Repo layout

  • Single-host services live in a top-level directory with compose.yaml and stack.toml — e.g. plex/, paperless/, gatus/.
  • Multi-host shared services use the <service>/{compose.shared.yaml, <host>/...} layout. Each host's stack.toml lists the shared and host-specific compose files in file_paths. Applies to backup/, autoheal/, and logging/.
  • Komodo's own infrastructure lives in komodo/ (ferretdb.compose.yaml, ResourceSync TOML files).
  • Bootstrap scripts (komodo-start, komodo-sync, kangaroo_bootstrap) sit at the repo root; every host except kangaroo is provisioned from ansible/ instead.
  • terraform/ is the ONE consolidated Terraform root for everything outside Docker: BinaryLane and Numbat edge material, Cloudflare DNS, CDN, AOP, and Pine Lake DNS, UniFi LAN DNS, the GitHub webhook that drives Komodo auto-deploy, Tailscale recovery auth-key rotation, and MinIO IAM for Publii tenants. State at s3://terraform-state/podhaus.tfstate in MinIO (backend via https://storage.pod.haus). Stock terraform runs from any machine — no wrapper. See Terraform.

The repo is bind-mounted into bilby's Komodo Core (for ResourceSync) and bilby's Periphery (for stack compose files). Every other deploy target's Periphery clones the repo through Komodo's Linked Repo resource (different Repo names per host since each clone is independent state) — see Komodo → operating models.

Design principles

These four principles trump local convenience whenever they conflict:

Config-as-code

Any config that can live in the repo, should. Container-volume-only state is not an acceptable substitute — those files get lost on rebuild. Secrets live in 1Password and are templated in at deploy time; everything else is plain files committed alongside the compose definitions.

Local state by default

Bilby's NVMe is the canonical home for container state. NFS volumes carry bulk content (Plex media, paperless documents, BIFs) but not operational state. Backrest → Jump SSD → OneDrive is the durability mechanism. SQLite stays off NFS because contention there is fragile.

Storage tier rule

Three tiers, chosen by what you'd hate to lose rather than by size alone:

  • Local NVMe — hot operational state, <5 GB per stack, backed up nightly.
  • Jump (NAS SSD) holds durable storage we'd hate to lose, including restic repositories.
  • Pouch (NAS HDD RAID5) holds bulk content where capacity matters more than latency, including the dedicated sky-backups restic target served by MinIO on kangaroo.

See Storage for mount details and the NAS-squash quirk.

Secrets from 1Password, never from the UI

Komodo Variables come from 1Password via komodo-op, never created manually through the Komodo UI. When a stack needs a secret, the workflow is:

  1. Add the item to the Homelab 1Password vault.
  2. komodo-op auto-syncs it as OP__KOMODO__<ITEM>__<FIELD>.
  3. Reference that synced name in the stack's environment block in stack.toml.

Manual UI variables don't survive a fresh Komodo bootstrap and silently break the disaster-recovery path. The only direct-seeded variables (in komodo-start) are chicken-and-egg credentials (the four ONEPASSWORD_* that komodo-op itself needs to talk to 1Password) plus host-discovered PODHAUS_CHECKOUT (consumed only by Home Assistant's live UI-editable config bind). Everything else — global-default non-secret vars (TZ, MEDIA_DIR) and stack-private ones (FENWICK_*, etc.) — lives in TOML and applies via the ResourceSync's include_variables = true config. Pinelake's stack environments set TZ=America/Edmonton explicitly instead of consuming the Perth default. See Secrets & variables for the full flow.

Ingress

Protected browser names resolve to Numbat's application address. Pomerium authenticates with Pocket ID, then uses a loopback-bound rathole service and mTLS to reach bilby's private Caddy listener. Raw and public endpoints use Numbat's second address and a separate rathole service to Caddy's public-only listener. Forgejo HTTPS is protected; git.pod.haus:22 remains ordinary key-authenticated SSH. Cloudflare stays in front of public websites as a CDN and remains authoritative DNS. See Networking for the exact address and exception map, and Public site caching for the origin-directed cache model.

Pine Lake follows the outbound Numbat contract completely: home.pinelake.haus is its canonical native-SSH name, and torrent.pinelake.haus, sync.pinelake.haus and plex.pinelake.haus are Pomerium-protected browser routes. Plex streams never traverse Numbat; only the web UI does. Hosted JetKVM is its independent recovery path.

See Networking for dockernet, host-network services, and DNS detail.

Stack lifecycle

Day-to-day, the loop is:

  1. Edit the stack, its committed config, or its build context.
  2. Commit and push. The GitHub webhook starts podhaus-push-deploy.
  3. Stage 0 reconciles definitions and TOML variables. Stage 1 stamps content hashes and recreates running stacks whose committed content is stale.
  4. Stage 2 deploys compose-text changes and new stacks. Ofelia follows the resulting Docker events and reloads job labels itself.

For local iteration without a push, run ./komodo-sync. It performs an out-of-procedure sync first, then invokes the same deployment procedures. This is also the recovery path after editing komodo/sync/procedures.toml.
