Storage

Three storage tiers, chosen by what you'd hate to lose rather than by raw size. The tier decides where a stack's data lives.

The three tiers

Local NVMe (bilby internal)

Hot operational state for every stack — Plex DB, paperless pgdata, flood session, Home Assistant config, Komodo state. Typically <5 GB per stack. The default destination for any new container's data volume.

Backed up nightly by Backrest (see Backup & recovery). If a container needs to crash-restart, this is the disk that has to survive. SQLite files belong here, never on NFS.

Jump (NAS SSD)

QNAP SSD array (CACHEDEV2). Durable storage that we'd really rather not lose. Live consumers:

  • Restic repo at /mnt/jump/backups/ (bilby view) or /share/CACHEDEV2_DATA/Jump/backups/ (kangaroo view) — primary on-prem backup target.
  • Kangaroo's restic repo at /mnt/jump/backups-kangaroo/ — separate from bilby's to avoid two-client coordination.
  • Forgejo repositories at /mnt/jump/forgejo/, including Git repositories, LFS objects, attachments, and generated repository archives. Forgejo's SQLite database and config stay on bilby's local NVMe; Backrest stops the service while snapshotting both tiers together.
  • Paperless media at /mnt/jump/paperless/ — small, random-read, must-not-lose.
  • Plex BIF thumbnails at /mnt/jump/plex-video-thumbnails/ — regenerable, moved off Pouch 2026-06.
  • Kangaroo container state at /share/CACHEDEV2_DATA/Container/ — see the placement rule below.

ClickStack telemetry is not a Jump consumer — ClickHouse and MongoDB live on local NVMe at /var/lib/clickstack/ because the NFS all-squash on Jump blocks their startup chown. See the NAS-squash quirk below.

Bilby mounts Jump over NFS at /mnt/jump via x-systemd.automount in /etc/fstab (added 2026-05-23 after a post-reboot incident — see 2026-05-23 postmortem); kangaroo accesses it directly. Either-direction off-site sync to OneDrive runs out of bilby's Backrest container via the existing rclone hook.

Pouch (NAS HDD)

QNAP HDD array, RAID5 across 4 drives (static volume, rebuilt 2026-06), ~21.8 TB usable. Bulk content where capacity matters more than per-drive resilience: Plex media, flood downloads, Syncthing-replicated folders, and Sky's encrypted restic repository.

Bilby mounts Pouch over NFS at /mnt/pouch; kangaroo accesses it at /share/CACHEDEV1_DATA/Pouch. Same backing data.

The dedicated pouch-minio stack runs on kangaroo and writes directly to /share/CACHEDEV1_DATA/Pouch/minio. Its private sky-backups bucket is an additional backup copy of data that remains on Sky's source device. It is not copied to Jump or OneDrive.

Why these aren't backed up the same way Plex media and paperless documents are large and redundant (we have the originals). Backrest backs up the small operational state (Plex DB, Paperless pgdata) — not the bulk content.

Sizing rule

When a new stack lands, pick a tier by this rule of thumb:

  • <5 GB, hot, must-survive-restart: local NVMe on bilby.
  • 5–50 GB or "we'd hate to lose this": ask. Probably Jump.
  • >50 GB, bulk, regenerable: Pouch.
kangaroo's ordinary container state goes on CACHEDEV2 (Jump) Every kangaroo-resident stack's state dir lives under /share/CACHEDEV2_DATA/Container/, the backed-up SSD volume — Container Station itself installs there too (it follows the QTS default volume, which is CACHEDEV2). CACHEDEV1 (Pouch) holds bulk media, Syncthing's synced data, and the deliberate pouch-minio backup-target exception. MinIO's system metadata stays beside its objects because the server requires one exclusive data root; Terraform and 1Password can reconstruct its configuration. The 2026-06 Pouch RAID failure wiped Container Station and every stack whose state had defaulted onto CACHEDEV1; state survived only because backrest copied it cross-volume. Placement on the backed-up volume remains the model for every ordinary stack. The MinIO exception is safe only because Pouch itself is the requested secondary copy.

NFS quirks

Squash on Jump Kangaroo's /Jump export squashes all writes to uid 1000:gid 100 and denies chown. Container images that chown their data dir on startup will fail to deploy against Docker NFS volumes — this hit ghcr.io/ferretdb/postgres-documentdb, postgres:16, and 1password/connect-api during bring-up. The carve-out is permanent now: any state that would have lived on Jump moved to local NVMe instead.
NFS recovery + bare-stub defence

Both NAS mounts use x-systemd.automount,_netdev,nofail in /etc/fstab. The kernel autofs mounts on first access and silently retries on the next access if a prior mount failed — survives network races at boot, QNAP restarts, and transient NFS hiccups.

Four layered defences keep boot races visible, recoverable, and incapable of silently writing container data to local disk:

  • Pre-dockerd reachability gate: bilby/host-systemd/wait-for-qnap-nfs.service is a oneshot ordered After=network-online.target and before docker.service. It polls TCP/2049 on the QNAP for up to 180 s before declaring success. The matching docker.service.d/ drop-in Wants=+After= this unit, so dockerd's container fanout — which is what tripped the boot-time automount burst on 2026-05-30 — only starts once the QNAP is actually reachable. Best-effort: if the QNAP stays unreachable past the timeout, the gate exits 0 and dockerd starts anyway (individual NFS-bind containers fail loudly via the sentinel healthcheck below).
  • Rate-limit removed on the automount units: StartLimitIntervalSec=0 + StartLimitBurst=0 drop-ins on both mnt-pouch.automount and mnt-jump.automount disable systemd's default 5-attempt-per-10-s cap. Without this, a future burst pattern can put the automount unit in mount-start-limit-hit / failed state, where systemd will never retry it automatically (the 2026-05-30 mode: /mnt/jump stayed failed for ~14 h, manual reset-failed required).
  • Tripwire: the bare /mnt/pouch and /mnt/jump dirs have chattr +i set. With NFS unmounted, Docker's auto-create of bind-source subdirs fails loudly at container start; with NFS mounted, the immutable bit is irrelevant (NFS overlays the bare dir).
  • Sentinel-marker healthchecks: every NFS-bind-source path has a .podhaus-share-mounted file on the QNAP side. Container healthchecks check for the marker via [ -e ... ]; absence means the bind landed on a bare stub and the container goes red. See stack conventions → NFS-bind healthcheck pattern.

Install / reinstall the host-systemd defences idempotently with sudo ./bilby/host-systemd/install.sh. Full incident records: 2026-05-30 postmortem (the pre-dockerd gate + rate-limit removal), 2026-05-23 postmortem (the automount + sentinel + chattr +i defences).
