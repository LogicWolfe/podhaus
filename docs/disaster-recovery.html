Disaster recovery

Runbooks for rebuilding from nothing. The repo plus 1Password plus a working internet connection should be enough to recover either host. Restic snapshots on Jump plus the OneDrive off-site mirror are the data recovery surface.

Prerequisites

Anyone executing one of these runbooks needs:

  • A working 1Password vault with the Homelab vault access and the Emergency Kit hardcopy (recovers Login).
  • A 1Password Service Account token at the repo root in a file named OP_SERVICE_ACCOUNT_TOKEN — Komodo Connect uses this for the chicken-and-egg first boot, before the Komodo Variable for it has been seeded into Komodo itself.
  • SSH access to the target host (UniFi-managed, configured separately).
  • The restic-repo-password if restoring from OneDrive (in 1P).

Fresh bilby from scratch

Assumes bilby is bootable with a base Fedora Asahi install. The package names below match the live Fedora 43 host as of 2026-08-01. Confirm them against the current Fedora and vendor repositories during a rebuild.

  1. Install the Fedora-packaged container runtime and recovery tools: 
    sudo dnf install \
  moby-engine docker-cli docker-compose \
  git curl jq restic rclone sqlite \
  firewalld nfs-utils e2fsprogs util-linux openssh-clients
    This supplies docker compose, sqlite3, mount.nfs, chattr, and firewall-cmd under their Fedora package names.
  2. Follow 1Password's current Fedora repository instructions, then install 1password-cli. Enable Docker and give the operator account access: 
    sudo dnf install 1password-cli
sudo systemctl enable --now docker
sudo usermod -aG docker "$USER"
    Log out and back in before running Docker as the operator account.
  3. Verify the minimum command surface before continuing: 
    docker compose version
for cmd in git curl jq op restic rclone sqlite3 mount mount.nfs chattr firewall-cmd ssh; do
  command -v "$cmd" || echo "missing: $cmd"
done
    Terraform is installed separately by the chezmoi Fedora package setup. MinIO CLI, GitHub CLI, Railway, and Zellij are optional operator tools.
  4. Mount Jump and Pouch from kangaroo: 
    sudo mkdir -p /mnt/jump /mnt/pouch
sudo mount -t nfs -o vers=4.1 10.0.0.25:/Jump  /mnt/jump
sudo mount -t nfs -o vers=4.1 10.0.0.25:/Pouch /mnt/pouch
  5. Clone the repo, put the service-account token at the repo root: 
    git clone <repo> ~/repos/podhaus
cd ~/repos/podhaus
echo <token> > OP_SERVICE_ACCOUNT_TOKEN
chmod 600 OP_SERVICE_ACCOUNT_TOKEN
  6. Create the dockernet external bridge if it doesn't already exist: 
    docker network create --driver bridge --subnet 172.18.0.0/16 dockernet
  7. Run ./komodo-start. This:
    • Brings up Komodo Core (Postgres, FerretDB, Core, Periphery).
    • Waits for Core to be healthy.
    • Seeds the five chicken-and-egg variables (4 ONEPASSWORD_* + PODHAUS_REPO). TZ + MEDIA_DIR live in komodo/sync/variables.toml and apply via the sync's include_variables=true.
    • Idempotently creates the podhaus ResourceSync (with include_variables=true; GetResourceSync first so re-runs are clean).
    • Runs the bootstrap double-sync: first sync registers stacks + TOML-declared vars (including komodo-op's stack def); waits for komodo-op to backfill OP__KOMODO__* secrets; second sync re-renders stack env blocks so they resolve to live secret values.
    • Stops there. komodo-start doesn't deploy stacks — that's a separate concern.
  8. In the Komodo UI: confirm Servers list shows podhaus as healthy. komodo-op should already be deployed. After the bootstrap sync registers the stack, run ./komodo-sync (or push) — Stage 2's BatchDeployStackIfChanged "*" first-deploys the stack via its (None, _) => FullDeploy arm. If somehow it isn't running, deploy it manually — it brings up the 1P→Komodo Variable sync that everything else depends on.
  9. Restore each stack's state from restic before deploying the stack. For each: 
    restic -r /mnt/jump/backups restore latest \
  --target / --include /userdata/<stack>
    (Adjust the include path so it lands at the right host location — the runbook here is per-stack; cross-reference each runbook.) Forgejo is the important two-path exception: restore its local and Jump trees from the same quiesced snapshot, then follow the Forgejo runbook before starting it.
  10. Deploy minio first so the Terraform state backend is available, then restore /var/lib/minio from the latest Backrest snapshot. The stack's own minio-init service re-asserts the terraform-state bucket with versioning idempotently (mc mb --ignore-existing + mc version enable), so the cold-start path needs no manual mcli step. Verify the bucket holds the restored podhaus.tfstate via minio.pod.haus or mcli ls local/terraform-state.
  11. Deploy caddy next: Terraform's backend is the public https://storage.pod.haus (Caddy + LE wildcard). LAN clients reach Caddy direct via UniFi split-horizon; external clients arrive via the Numbat BinaryLane rathole relay (see hosts → Numbat). Until caddy is up + has its cert, terraform cannot reach state. MINIO_DOMAIN (in minio/stack.toml) is part of the minio deploy. See Terraform for the full backend setup.
  12. Deploy every other stack from the Komodo UI in dependency order. The repo's ResourceSync has already created the stack definitions.
  13. Verify DNS (stock terraform, no wrapper, creds from the chezmoi fish env): cd terraform && terraform plan from the working directory. Should report no changes (state restored from Backrest matches the deployed Cloudflare + UniFi resources). If there's drift, stop and investigate before applying — drift here means either the restored state is stale or someone touched Cloudflare via the dashboard. See Terraform → disaster recovery.
First-boot API-key dance komodo-start currently assumes a pre-existing "Komodo API OnePassword Sync" item in 1P that matches the live Komodo DB's keys. On a true fresh install the DB has no such key yet — you have to log into Komodo UI once, mint an API key under your user, save it to that 1P item, then re-run komodo-start. Folding this into the script as an automatic first-boot path is a deferred follow-up.

Fresh kangaroo from scratch

Assumes kangaroo is QTS-installed with Container Station available.

  1. From bilby, run ./kangaroo_bootstrap. The script is idempotent and handles:
    • SSH connectivity check.
    • Renders .env and periphery.config.toml from 1P, SCPs them and the Periphery compose file to kangaroo.
    • SSHs into kangaroo and runs docker compose up -d in the destination directory.
    • Waits until Komodo Core reports the outbound Periphery connection as healthy.
    • Installs the native QNAP boot-DOM autorun.sh hook from kangaroo/host-autorun/, so Container Station's Docker engine and restart-managed containers return after reboots and upgrades.
    • Verifies that the committed outbound-mode kangaroo entry exists in komodo/sync/servers.toml.
  2. Run ./komodo-sync — Komodo Core picks up the new Server and begins polling. Verify kangaroo shows state: Ok in the Komodo UI.
  3. If repos.toml + git_provider haven't already been declared (true on a true greenfield rebuild), they're declared in komodo/sync/repos.toml and a [[git_provider]] block in kangaroo's periphery.config.toml. kangaroo_bootstrap writes the provider config; the repo block is committed in the repo.
  4. Run ./komodo-sync to deploy kangaroo's stacks: syncthing, kangaroo-backup, kangaroo-autoheal, and kangaroo-logging.
  5. Restore kangaroo's state from /share/CACHEDEV2_DATA/Jump/backups-kangaroo/ if state was lost.

Fresh Numbat from scratch

  1. If replacing a live Numbat, rename it to numbat-old.pod.haus in BinaryLane without stopping it. BinaryLane requires unique hostnames, so this is necessary before terraform apply -replace=binarylane_server.numbat can create the replacement first. Terraform then provisions the VM, both addresses, DNS, PKI, Pocket ID client, and 1Password handoffs.
  2. Run ./numbat_bootstrap with the op-unlock SSH agent active. It verifies Terraform's pinned host key, reconciles Rocky, Docker, nftables and dockernet, starts the public relay first, then starts outbound Periphery and the userspace SSH recovery plane before closing first-boot port 2222.
  3. Run the podhaus sync or push the repository. Komodo deploys numbat-pomerium, numbat-logging, and numbat-autoheal from podhaus-numbat; it adopts the already-running relay project.
  4. Verify Pocket ID login, native SSH, public TLS, Periphery, log ingestion, and a no-op Terraform plan through storage.pod.haus.

Numbat has no irreplaceable state. Pomerium's Autocert cache is persistent for normal restarts but replaceable; all long-lived keys and credentials are in Terraform state and 1Password.

Restoring from OneDrive (worst case)

If both kangaroo and bilby state are gone (theft, fire), the off-site OneDrive mirror is the recovery source.

  1. On any machine with internet, install rclone and restic.
  2. Re-do the rclone OneDrive OAuth dance (rclone config) for this restore client. After the hosts are recovered, create independent refresh-token chains for bilby and kangaroo and update the base64 snapshots in rclone-onedrive-token-bilby and rclone-onedrive-token-kangaroo.
  3. Pull both repos: 
    rclone sync onedrive:Backups/podhaus-restic           ./recovery/podhaus
rclone sync onedrive:Backups/podhaus-kangaroo-restic  ./recovery/kangaroo
  4. Pull the restic password from 1P (Emergency Kit gets you in if 1P account access is gone; the password lives at op://Homelab/restic-repo-password/credential).
  5. Browse and restore from each repo with regular restic commands: 
    restic -r ./recovery/podhaus snapshots
restic -r ./recovery/podhaus restore latest --target ./out
  6. Stage the restored files on a fresh bilby/kangaroo and run the relevant rebuild runbook above.
Emergency Kit note The 1P Emergency Kit hardcopy should carry a note that points at the restic-repo-password item — without that password, the OneDrive copy is useless.

Drill cadence

Quarterly: run a partial bilby restore (just one stack's state from a recent snapshot to a scratch path; verify checksum). Annually: pull from OneDrive end-to-end on a laptop — proves both the off-site copy and the password recovery path work.
