Disaster recovery

Runbooks for rebuilding from nothing. The repo plus 1Password plus a working internet connection should be enough to recover either host. Restic snapshots on Jump plus the OneDrive off-site mirror are the data recovery surface.

Prerequisites

Anyone executing one of these runbooks needs:

  • A working 1Password vault with the Homelab vault access and the Emergency Kit hardcopy (recovers Login).
  • A 1Password Service Account token at the repo root in a file named OP_SERVICE_ACCOUNT_TOKEN — Komodo Connect uses this for the chicken-and-egg first boot, before the Komodo Variable for it has been seeded into Komodo itself.
  • SSH access to the target host (UniFi-managed, configured separately).
  • The restic-repo-password if restoring from OneDrive (in 1P).

Fresh bilby from scratch

Assumes bilby is bootable with a base Fedora Asahi install + Docker.

  1. Install docker + docker compose. Add user to the docker group.
  2. Install host packages we know we depend on: op (1Password CLI), git, restic (for off-site restores), rclone, zellij, sqlite3. (A canonical host-package runbook is a deferred follow-up.)
  3. Mount Jump and Pouch from kangaroo: 
    sudo mkdir -p /mnt/jump /mnt/pouch
sudo mount -t nfs -o vers=4.1 10.0.0.25:/Jump  /mnt/jump
sudo mount -t nfs -o vers=4.1 10.0.0.25:/Pouch /mnt/pouch
  4. Clone the repo, put the service-account token at the repo root: 
    git clone <repo> ~/repos/podhaus
cd ~/repos/podhaus
echo <token> > OP_SERVICE_ACCOUNT_TOKEN
chmod 600 OP_SERVICE_ACCOUNT_TOKEN
  5. Create the dockernet external bridge if it doesn't already exist: 
    docker network create --driver bridge --subnet 172.18.0.0/16 dockernet
  6. Run ./komodo-start. This:
    • Brings up Komodo Core (Postgres, FerretDB, Core, Periphery).
    • Waits for Core to be healthy.
    • Seeds the seven chicken-and-egg variables (4 1P credentials, TZ, MEDIA_DIR, PODHAUS_REPO).
    • Triggers the first ResourceSync.
  7. In the Komodo UI: confirm Servers list shows podhaus as healthy. Deploy onepassword stack first — it brings up komodo-op which fills in all the other variables.
  8. Restore each stack's state from restic before deploying the stack. For each: 
    restic -r /mnt/jump/backups restore latest \
  --target / --include /userdata/<stack>
    (Adjust the include path so it lands at the right host location — the runbook here is per-stack; cross-reference each runbook.)
  9. Deploy minio first so the Terraform state backend is available, then restore /var/lib/minio from the latest Backrest snapshot. Verify the terraform-state bucket exists with the cloudflare.tfstate object via the MinIO console (minio.pod.haus) or mcli ls local/terraform-state.
  10. Deploy caddy next: Terraform's backend is the public https://storage.pod.haus (Caddy + LE wildcard). LAN clients reach Caddy direct via UniFi split-horizon; external clients arrive via the kookaburra DigitalOcean rathole relay (see hosts → kookaburra). Until caddy is up + has its cert, terraform cannot reach state. MINIO_DOMAIN (in minio/stack.toml) is part of the minio deploy. See Terraform for the full backend setup.
  11. Deploy every other stack from the Komodo UI in dependency order. The repo's ResourceSync has already created the stack definitions.
  12. Verify DNS (stock terraform, no wrapper, creds from the chezmoi fish env): cd cloudflare && terraform plan from the working directory. Should report no changes (state restored from Backrest matches the deployed Cloudflare + UniFi resources). If there's drift, stop and investigate before applying — drift here means either the restored state is stale or someone touched Cloudflare via the dashboard. See Terraform → disaster recovery.
First-boot API-key dance komodo-start currently assumes a pre-existing "Komodo API OnePassword Sync" item in 1P that matches the live Komodo DB's keys. On a true fresh install the DB has no such key yet — you have to log into Komodo UI once, mint an API key under your user, save it to that 1P item, then re-run komodo-start. Folding this into the script as an automatic first-boot path is a deferred follow-up.

Fresh kangaroo from scratch

Assumes kangaroo is QTS-installed with Container Station available.

  1. From bilby, run ./kangaroo_bootstrap. The script is idempotent and handles:
    • SSH connectivity check.
    • Renders .env and periphery.config.toml from 1P, SCPs them and the Periphery compose file to kangaroo.
    • SSHs into kangaroo and runs docker compose up -d in the destination directory.
    • Waits for Periphery's :8120 health endpoint.
    • Installs the @reboot crontab line at /etc/config/crontab on kangaroo so it survives Container Station and QTS upgrades.
    • Idempotently appends kangaroo's [[server]] entry to komodo/sync/servers.toml.
  2. Run ./komodo-sync — Komodo Core picks up the new Server and begins polling. Verify kangaroo shows state: Ok in the Komodo UI.
  3. If repos.toml + git_provider haven't already been declared (true on a true greenfield rebuild), they're declared in komodo/sync/repos.toml and a [[git_provider]] block in kangaroo's periphery.config.toml. kangaroo_bootstrap writes the provider config; the repo block is committed in the repo.
  4. Deploy kangaroo's stacks (syncthing, kangaroo/backrest, kangaroo/autoheal, kangaroo/logging) from the Komodo UI.
  5. Restore kangaroo's state from /share/CACHEDEV2_DATA/Jump/backups-kangaroo/ if state was lost.

Restoring from OneDrive (worst case)

If both kangaroo and bilby state are gone (theft, fire), the off-site OneDrive mirror is the recovery source.

  1. On any machine with internet, install rclone and restic.
  2. Re-do the rclone OneDrive OAuth dance (rclone config). Save the new OAuth blob to 1P at op://Homelab/rclone-onedrive-token/notesPlain.
  3. Pull both repos: 
    rclone sync onedrive:Backups/podhaus-restic           ./recovery/podhaus
rclone sync onedrive:Backups/podhaus-kangaroo-restic  ./recovery/kangaroo
  4. Pull the restic password from 1P (Emergency Kit gets you in if 1P account access is gone; the password lives at op://Homelab/restic-repo-password/credential).
  5. Browse and restore from each repo with regular restic commands: 
    restic -r ./recovery/podhaus snapshots
restic -r ./recovery/podhaus restore latest --target ./out
  6. Stage the restored files on a fresh bilby/kangaroo and run the relevant rebuild runbook above.
Emergency Kit note The 1P Emergency Kit hardcopy should carry a note that points at the restic-repo-password item — without that password, the OneDrive copy is useless.

Drill cadence

Quarterly: run a partial bilby restore (just one stack's state from a recent snapshot to a scratch path; verify checksum). Annually: pull from OneDrive end-to-end on a laptop — proves both the off-site copy and the password recovery path work.
