Backup & recovery

Backrest manages restic snapshots of operational state from bilby, kangaroo, bandicoot, and Pinelake. Each stateful host has its own repository. Bilby mirrors its own and Bandicoot's snapshots to its existing OneDrive repository; kangaroo mirrors its own.

Backup topology

bilby state ─────→ bilby Backrest ─────→ /mnt/jump/backups/
bandicoot state ─→ bandicoot Backrest ─→ /mnt/jump/backups-bandicoot/
                                               │
                                               │ restic copy in Bilby's Backrest hook
                                               ↓
                           /mnt/jump/backups/ ─→ OneDrive Backups/podhaus-restic/

kangaroo state ──→ kangaroo Backrest ──→ Jump backups-kangaroo/ ──→ OneDrive
pinelake state ──→ pinelake Backrest ──→ TerraMaster local repository

Each host owns a separate restic repository and plan schedule. Bandicoot's snapshots are copied with restic into Bilby's repository by Bilby's serialized Backrest hook, then flow through Bilby's existing rclone configuration and refresh-token chain. Pinelake's local repository protects operational state from accidental damage; it does not protect against loss of the TerraMaster volume and does not contain its multi-terabyte media.

Retention on every plan: 14 daily + 4 weekly + 6 monthly. Weekly prune (Sunday 04:00) and check (Sunday 05:00) on the repo.

Forgejo's plan uses start/end hooks to stop the service, snapshot both storage tiers, restart it, wait for health, and report a dedicated Gatus heartbeat. A recovery job ticks every five minutes, offset to :03 and :08 so it never runs while the snapshot has Forgejo stopped. It restarts Forgejo only when the quiesce lock is more than fifteen minutes old and no restic process is running — a healthy snapshot holds that lock for well under a minute, so anything older means Backrest died between the hooks. See the Forgejo runbook.

The backrest-state plan runs last. Its successful or unchanged-skip hook verifies Bilby's Jump sentinel and repository identity before any work. It requires a snapshot dated today for every Bandicoot plan before copying those snapshots into Bilby's repository and applying retention only to created-by:bandicoot snapshots. If that source copy fails, it still mirrors Bilby's already-verified repository to OneDrive, then returns failure. Its existing nightly heartbeat reports only after the complete copy and upload, so it proves Bilby's aggregate off-site copy and upload without hiding a Bandicoot failure.

Pinelake plans

Pinelake backs up Plex, Flood, Syncthing, Periphery, and Backrest state to /Volumes/TerraMaster/.podhaus-backups/pinelake-restic. It does not back up the media library: that data is too large for this backup tier. The repository and media share the TerraMaster failure domain, so this protects service state from loss of the Mac's internal disk but not from loss of TerraMaster. Pinelake has no rclone configuration or OneDrive integration. All schedules below use Edmonton local time.

Sky backups on Pouch

Sky's client writes an encrypted restic repository to the private sky-backups bucket at pouch.pod.haus. The dedicated RustFS instance runs on kangaroo and stores its data directly under /share/CACHEDEV1_DATA/Pouch/rustfs.

This repository is deliberately outside the fleet Backrest plans and OneDrive rclone hooks. It is already an additional backup copy, and the placement requirement is that none of it lands on Jump. Pouch loss therefore loses this repository; Sky's source data is the rebuild source. See the Pouch RustFS runbook.

Gatus has a Backup / Sky Restic Repository check. An hourly monitor lists committed snapshots/<id> objects in RustFS and requires one written within the last seven days. A normal restic backup creates a snapshot even when the source tree hasn't changed, so the check measures completed backup runs without a client callback. A new empty repository gets seven days from its config object's creation time to produce the first snapshot.

The gateway is intentionally unbacked

Numbat has the same conditional exemption. Its Pomerium Autocert cache and Docker volumes are replaceable; PKI and long-lived secrets are recoverable from Terraform state and 1Password. Rebuild is terraform apply, ansible-playbook playbooks/numbat-bootstrap.yml, then Komodo deployment. Meaningful application data landing there would reopen this decision.

This exemption is conditional, not permanent. If any meaningful state ever lands on Numbat, such as a persistent volume, local-only key/cert, or app data that is not reconstructible from terraform apply, the backup decision must be reopened and that host added to backup/ with its own plan. A future reader who finds irreplaceable gateway state with no backup should treat that as a bug, not a deliberate choice (this is also a hard rule in AGENTS.md).

Encryption

Restic repos are encrypted with a 48-character base64 password (~288 bits of entropy). The password lives at op://Homelab/restic-repo-password/credential and flows through to Backrest via komodo-op. The init container in backup/compose.shared.yaml renders config.json from the template with the password substituted, so the running config.json on disk has the password baked in — but the source of truth is 1P.

Annotate the 1P Emergency Kit

Without the restic password, the off-site OneDrive copy is useless. The 1P Emergency Kit hardcopy should have a note pointing at the restic-repo-password item.

Off-site sync

Bilby and kangaroo trigger rclone sync after a successful or unchanged-skip backrest-state snapshot. Before Bilby syncs, its hook copies the complete current Bandicoot set from its Jump repository into Bilby's repository. The upload targets are:

  • onedrive:Backups/podhaus-restic/ — Bilby's repo and copied Bandicoot snapshots.
  • onedrive:Backups/podhaus-kangaroo-restic/: kangaroo's repo.

Bilby and kangaroo use separate OAuth snapshots in 1Password. The OneDrive init layer decodes the host's snapshot and renders rclone.conf only when its named volume is empty. After that, rclone owns the live file and persists refresh-token rotation in place; an ordinary redeploy deliberately preserves it. Back up the live config before resetting that volume, then update the matching 1Password snapshot used for cold bootstrap.

Restore drill

Quarterly cadence. Three paths to verify:

  1. Local restore from bilby's repo: open Backrest UI, pick a snapshot, restore one file to /tmp/restore-test/, verify checksum matches the source.
  2. Off-site restore: on a laptop, install restic, run rclone sync onedrive:Backups/podhaus-restic /tmp/restore-from-cloud/, then restic -r /tmp/restore-from-cloud snapshots with the password from 1P. Restore one file, verify.
  3. Pinelake local restore: through Pinelake Backrest, restore one file from podhaus-pinelake to a scratch path and verify its checksum. This proves the TerraMaster repository; it is not an off-site recovery test.

Document the dates in the runbook. Last drill: 2026-04-16 against Preferences.xml from the plex plan — matched bit-for-bit.

Alerting

Two failure surfaces, both go through Gatus → Fenwick (Signal) — the default service-alert path; see Monitoring:

  • Per-plan error: Backrest's CONDITION_ANY_ERROR hook posts success=false&error=... to the Gatus push endpoint. Alerts within minutes (failure-threshold: 3).
  • Missing nightly heartbeat: the Gatus push endpoint has a 25-hour interval window — if no successful ping arrives, the dead-man's-switch fires. Catches the case where Backrest itself is down.

Each backup stack declares its heartbeat endpoint in stack.toml. Endpoint identifiers must match Gatus's generated group/name keys, including punctuation: Bandicoot uses backup_backrest-nightly-(bandicoot). The pre-commit checks compare all backup heartbeat identifiers with the external endpoints in gatus/conf/config.yaml. See Monitoring for the Gatus side.

Adding a plan for a new stack

  1. Bind-mount the stack's state directory into Backrest read-only as /userdata/<stack>/ — edit the host's overlay, backup/<host>/compose.yaml.
  2. Add a plan block to backup/<host>/config.json.tmpl with a schedule slotted into the dead-time window (04:00–05:20 AWST), the standard 14d/4w/6m retention, and paths: ["/userdata/<stack>"].
  3. ./komodo-sync + redeploy backup. Backrest's init container re-renders config.json on next start.
  4. Take a manual snapshot from the Backrest UI to verify the plan works before letting the cron run.
