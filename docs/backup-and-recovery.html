Backup & recovery

Backrest manages restic snapshots of operational state from both hosts. Each host has its own restic repository on Jump; bilby's nightly hook also mirrors both repos off-site to OneDrive via rclone.

Backup topology

bilby state                kangaroo state
    │                          │
    ↓                          ↓
bilby Backrest             kangaroo Backrest
    │                          │
    ↓                          ↓
restic repo                restic repo
/mnt/jump/backups/         /share/CACHEDEV2_DATA/Jump/backups-kangaroo/
                           (visible to bilby over NFS as /mnt/jump/backups-kangaroo)
    │                          │
    └──────────┬───────────────┘
               ↓
       bilby Backrest's
       rclone hook (CONDITION_SNAPSHOT_SUCCESS
       on the last plan of the night)
               ↓
       OneDrive
       (Backups/podhaus-restic/  + Backups/podhaus-kangaroo-restic/)

Two restic clients on one repo is supported (per-operation locking) but kangaroo gets its own repo to avoid lock coordination across the LAN, and to keep its plan schedule independent of bilby's. The off-site mirror is done from bilby's Backrest because that's where the rclone config (multi-line OAuth blob) already lives.

Retention on every plan: 14 daily + 4 weekly + 6 monthly. Weekly prune (Sunday 04:00) and check (Sunday 05:00) on the repo.

Forgejo's plan uses start/end hooks to stop the service, snapshot both storage tiers, restart it, wait for health, and report a dedicated Gatus heartbeat. A five-minute recovery job restarts Forgejo if Backrest is interrupted while the quiesce lock exists. See the Forgejo runbook.

The backrest-state plan runs last and has a CONDITION_SNAPSHOT_SUCCESS hook that fires the nightly rclone sync to OneDrive (covering both bilby's repo and kangaroo's via the read-only NFS view), and a success ping to the Gatus heartbeat.

Sky backups on Pouch

Sky's client writes an encrypted restic repository to the private sky-backups bucket at pouch.pod.haus. The dedicated MinIO instance runs on kangaroo and stores its data directly under /share/CACHEDEV1_DATA/Pouch/minio.

This repository is deliberately outside both Backrest plans and the OneDrive rclone hooks. It is already an additional backup copy, and the placement requirement is that none of it lands on Jump. Pouch loss therefore loses this repository; Sky's source data is the rebuild source. See the Pouch MinIO runbook.

Gatus has a Backup / Sky Laptop dead-man switch. The laptop reports only after a successful restic backup; seven days without a success produces a Signal alert. This complements the MinIO liveness check: a healthy S3 endpoint does not prove a recent client snapshot exists.

Kookaburra — intentionally unbacked (conditional)

kookaburra (the off-LAN DigitalOcean public-ingress relay; see hosts → kookaburra) has no backup plan by design. It is a ciphertext-only rathole passthrough — no MinIO data, no certificates, no credentials; all state lives on bilby. Disaster recovery is terraform apply, and the DigitalOcean reserved IP keeps DNS stable across a rebuild, so there is nothing recoverable to snapshot.

This exemption is conditional, not permanent. If any meaningful state ever lands on kookaburra — a persistent volume, a local key/cert, app data, anything not reconstructible from terraform apply — the backup decision must be reopened and kookaburra added to backup/ with its own plan. A future reader who finds state on kookaburra with no backup should treat that as a bug, not a deliberate choice (this is also a hard rule in AGENTS.md).

Encryption

Restic repos are encrypted with a 48-character base64 password (~288 bits of entropy). The password lives at op://Homelab/restic-repo-password/credential and flows through to Backrest via komodo-op. The init container in backup/compose.shared.yaml renders config.json from the template with the password substituted, so the running config.json on disk has the password baked in — but the source of truth is 1P.

Annotate the 1P Emergency Kit Without the restic password, the off-site OneDrive copy is useless. The 1P Emergency Kit hardcopy should have a note pointing at the restic-repo-password item.

Off-site sync

rclone OneDrive sync runs out of bilby's Backrest container, triggered by the last plan of the night via CONDITION_SNAPSHOT_SUCCESS. Two upload targets:

  • onedrive:Backups/podhaus-restic/ — bilby's repo.
  • onedrive:Backups/podhaus-kangaroo-restic/ — kangaroo's repo (read over NFS).

The rclone config is a multi-line OAuth blob stored as a Secure Note in 1P (rclone-onedrive-token / notesPlain) — multi-line values don't round-trip through Komodo env files cleanly, so an init container in the backup stack renders rclone.conf on first boot from the synced variable. Token rotation: regenerate via rclone config on a laptop, paste the new [onedrive] block into the 1P Secure Note, redeploy.

Restore drill

Quarterly cadence. Two paths to verify:

  1. Local restore from bilby's repo: open Backrest UI, pick a snapshot, restore one file to /tmp/restore-test/, verify checksum matches the source.
  2. Off-site restore: on a laptop, install restic, run rclone sync onedrive:Backups/podhaus-restic /tmp/restore-from-cloud/, then restic -r /tmp/restore-from-cloud snapshots with the password from 1P. Restore one file, verify.

Document the dates in the runbook. Last drill: 2026-04-16 against Preferences.xml from the plex plan — matched bit-for-bit.

Alerting

Two failure surfaces, both go through Gatus → Fenwick (Signal) — the default service-alert path; see Monitoring:

  • Per-plan error: Backrest's CONDITION_ANY_ERROR hook posts success=false&error=... to the Gatus push endpoint. Alerts within minutes (failure-threshold: 3).
  • Missing nightly heartbeat: the Gatus push endpoint has a 25-hour interval window — if no successful ping arrives, the dead-man's-switch fires. Catches the case where Backrest itself is down.

See Monitoring for the Gatus side.

Adding a plan for a new stack

  1. Bind-mount the stack's state directory into Backrest read-only as /userdata/<stack>/ — edit backup/compose.shared.yaml.
  2. Add a plan block to backup/<host>/config.json.tmpl with a schedule slotted into the dead-time window (04:00–05:20 AWST), the standard 14d/4w/6m retention, and paths: ["/userdata/<stack>"].
  3. ./komodo-sync + redeploy backup. Backrest's init container re-renders config.json on next start.
  4. Take a manual snapshot from the Backrest UI to verify the plan works before letting the cron run.
