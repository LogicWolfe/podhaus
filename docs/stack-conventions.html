Stack conventions

Patterns that any stack in this repo follows. Match the existing shapes and most things line up automatically — networking, secrets, backups, monitoring.

Adding a single-host stack

  1. Create <name>/compose.yaml. Join dockernet if the stack needs to be reachable from another container or Caddy.
  2. Create <name>/stack.toml with server = "podhaus", files_on_host = true, and run_directory = "/etc/komodo/repo/<name>". Do not set deploy = true — Komodo's RunSync would then auto-deploy the stack during Stage 0, which duplicates Stage 2 and breaks on transient linked-repo Periphery timeouts. RunSync is reconcile-only; Stages 1 and 2 own deployment; the pre-commit lint tools/lint-stack-toml.py rejects deploy = true on podhaus stacks. List any required variables in the environment block. If the stack has stack-private non-secret config (e.g. a service URL, a well-known port), declare it as an inline [[variable]] block in the same file — see Stack-private variables.
  3. Add any new secrets to the 1Password Homelab vault — komodo-op auto-syncs them (see Secrets).
  4. If the stack needs a protected *.pod.haus hostname, add its DNS entry to local.pod_haus_service_dns in terraform/services_pod_haus.tf, its policy route to pomerium/config.yaml, and its private-origin host to caddy/Caddyfile. Run stock Terraform from terraform/.
  5. If the stack has services with build: directives or depends_on a build service, wire the content-hash consumer pattern — see Content-hash wiring. The pre-commit lint will block the commit if anything is missing.
  6. Commit and push. The push fires podhaus-push-deploy, which pulls bilby's Komodo-managed deploy tree to origin/main and then runs the internal podhaus-deploy procedure: Stage 0 RunSync registers the new stack + any TOML-declared variables (config reconcile only — Sync Deploy no-ops because every podhaus stack omits deploy = true); Stage 1 (RunAction "podhaus-inject-content-hashes") stamps per-stack content hashes; Stage 2 BatchDeployStackIfChanged "*" first-deploys the new stack via the (None, _) => FullDeploy arm in DeployStackIfChanged, which never reads stack.config.deploy (Komodo source bin/core/src/api/execute/stack.rs:368-447). Ofelia follows the target container's Docker events and applies any new schedule labels without a scheduler restart. No manual Deploy click. For local debug iteration without pushing, ./komodo-sync (overlays the deploy tree with the local checkout, then invokes podhaus-deploy directly).

Adding a stack to a multi-host shared service

Services in this layout today: backup/, autoheal/, and logging/. Each has a compose.shared.yaml defining the cross-host contract and per-host subdirectories overlaying the host-specific bits.

  1. Create <service>/<host>/compose.yaml with the host-specific overlay (volumes, security_opt, additional services). The shared file is composed in via file_paths in stack.toml; compose's include: directive isn't used here.
  2. Create <service>/<host>/stack.toml setting server = "<host>", the per-host environment block, and file_paths listing both compose files. See file_paths ordering below — the order matters. Variable names must match the shared compose's contract; values come from host-specific 1P items.
  3. If the host needs a config template (e.g. Backrest's config.json.tmpl), put it at <service>/<host>/<template> and reference it via the per-host overlay's bind mount.
  4. Commit + push. podhaus-push-deploy pulls the deploy tree to origin/main and runs the internal podhaus-deploy procedure, which reconciles the new stack via Stage 0 (RunSync), stamps content hashes via Stage 1 (RunAction), and deploys via Stage 2 (BatchDeployStackIfChanged) — same path for files_on_host and linked_repo hosts. New stacks first-deploy via the (None, _) => FullDeploy arm in DeployStackIfChanged, which ignores stack.config.deploy entirely. See Komodo procedures.

When fixing a bug in a multi-host service, edit compose.shared.yaml (and the shared template if present) — the change applies to all hosts uniformly. Per-host overlay edits should only touch genuinely host-specific bits.

file_paths ordering

docker compose -f A -f B gives precedence to the LAST file on scalar-field conflicts (override semantics), and resolves relative build.context paths against the FIRST file's directory. Two consequences:

  • Host-first (file_paths = ["compose.yaml", "../compose.shared.yaml"]) — the default. Use when the overlay only adds fields (extra volumes, security_opt, additional services). Relative build.context in the overlay resolves against <service>/<host>/. Current users: autoheal, logging, and backup/kangaroo.
  • Shared-first (file_paths = ["../compose.shared.yaml", "compose.yaml"]) — use when the overlay needs to override a scalar field in the shared definition (e.g. backup/bilby/compose.yaml overrides the shared healthcheck with a Jump-NFS sentinel check). Relative build.context in the overlay then resolves against <service>/, not the host dir — adjust paths accordingly. Current users: backup/bilby (only).

Whichever ordering you choose, the comment in the local stack.toml should record why. The 2026-05-23 backup/bilby flip and its silent build-context breakage (re-surfaced months later when content-hash injection triggered a rebuild) is the cautionary case.

Content-hash wiring

Every podhaus stack participates in the content-hash change-detection mechanism. Stage 1 of the internal podhaus-deploy procedure computes per-stack and per-service hashes from the deploy tree's current state and injects them as env vars on each stack; compose services consume them via labels and build args so a file change actually recreates the right containers. The pre-commit lint (tools/lint-stack-content-hash.py) enforces three rules on every commit — if you're matching an existing stack's shape it'll just work, but here's the contract:

  • Every service carries a podhaus.stack-content-hash: ${STACK_CONTENT_HASH:-unset} label. Compose tracks labels in its per-service config hash, so any file change in the stack directory recreates the container.
  • Build-mode services (those with a build: directive) additionally pass their own build-context hash as a build arg: build.args.STACK_CONTENT_HASH: ${BUILD_HASH_<SELF>:-unset}, where <SELF> is the service name uppercased with non-alnum characters replaced by _ (so plex-preferences-init → BUILD_HASH_PLEX_PREFERENCES_INIT). The matching Dockerfile declares ARG STACK_CONTENT_HASH=unset + ENV STACK_CONTENT_HASH=${STACK_CONTENT_HASH} so the value busts docker's layer cache when the resolved build context changes.
  • Services that depends_on a build service carry a podhaus.depends-on-<dep>: ${BUILD_HASH_<DEP>:-unset} label per dependency. Without this, an init-image rebuild wouldn't recreate the long-running service that consumes the init's output (the depender's own stack-content-hash only tracks its stack dir, which may not include the dependency's build context — shared init-tools/ being the obvious case).

The :-unset fallback is deliberate. If the Action hasn't run yet (first deploy of a new stack, or a Stage 1 failure that didn't make it to Stage 2 — though by design Stage 1 fails the procedure so Stage 2 doesn't run at all), compose substitutes the literal string "unset" and the deploy proceeds with that as the baseline. The next push that runs Stage 1 injects real hashes; its label reconcile triggers a recreate where needed. Refusing to deploy on missing hash (:?) would break bootstrap; deploying with whatever the variable resolves to keeps first-deploy paths working.

See Komodo for the Action / procedure machinery, and the AGENTS.md "Content-hash change detection" section for the rationale around why the hash includes bind-mounted runtime paths (the "make a change → see the change" invariant beats per-stack exclusion lists).

Stack-private variables

Komodo Variables can be declared anywhere the ResourceSync sees TOML (it walks resource_path recursively). Two homes:

  • Global, fleet-wide → komodo/sync/variables.toml. Use for things every stack might reference (TZ, MEDIA_DIR).
  • Stack-private → inline [[variable]] blocks at the bottom of the stack's own stack.toml. Use for stack-specific non-secret config — sidecar URLs, well-known ports. Pattern: fenwick/stack.toml declares FENWICK_SIGNAL_*, FENWICK_ADMIN_* alongside the [[stack]] block.
[[stack]]
name = "myservice"
[stack.config]
server = "podhaus"
files_on_host = true
run_directory = "/etc/komodo/repo/myservice"
environment = """
TZ=[[TZ]]
MYSERVICE_PORT=[[MYSERVICE_PORT]]
"""

[[variable]]
name = "MYSERVICE_PORT"
value = "8080"
description = "Service port (well-known, not a secret)"

Komodo Variables are a single global namespace — collisions across declaration sites = last-applied wins. Prefix-namespace stack-private vars (e.g. FENWICK_*, PLEX_*) so they don't collide with anyone else's declarations.

Secrets do not go in [[variable]] blocks — they go in 1Password and flow through komodo-op as OP__KOMODO__* vars (see Secrets).

Customization primitives

Three blessed primitives for when an upstream image doesn't do exactly what's needed. Pick based on the nature of the customization.

Primitive When to use Example
Init container using the shared init-tools:local image One-time setup that produces an artifact before the main service starts. Tool isn't needed during runtime. Backrest envsubst (backup/) — renders config.json from template. Plex Preferences merge — overlays enforced identity attrs onto Preferences.xml.
Custom Dockerfile + Komodo build (run_build = true, auto_pull = false in stack.toml) The main service needs the customization at runtime: different binary, missing runtime tool, upstream bug fix. komodo-op arm64 build — upstream ships a mislabeled arm64 manifest that's actually amd64.
komodo-start host render True bootstrap concerns that must happen on the host before any container can read them. Komodo Core itself, chicken-and-egg credentials.

Version policy: use the current stable upstream release by default. Pulls, builds, installs, and bootstraps should take an available upgrade rather than preserving an old version for reproducibility alone. A compatibility pin is an exception that needs a concrete documented reason and should be removed when that component is next touched and verified.

init-tools shared image: All init containers across the fleet use the same locally-built image declared at init-tools/Dockerfile (alpine + gettext + python3 + curl + jq — covers config templating, Python merge scripts, and init-time API calls). Each consumer stack triggers the build inline via its init service's build: directive (Komodo's run_build = true handles this). Init service uses pull_policy: never so Komodo's auto_pull doesn't try to fetch the local-only tag. Stack.toml has run_build = true; auto_pull stays default-true so the main service still pulls upstream image updates. Add new tools to init-tools/Dockerfile rather than layering apk add at runtime in a consumer's entrypoint — the shared image is the single owner of the convention.

Mandatory with any init container: ignore_services. A one-shot init exits 0 by design, but Komodo counts an exited container toward stack health and marks the whole stack Unhealthy — a false red that trains you to ignore the Komodo signal. Every init-container stack must set ignore_services = ["<init-service>"] in [stack.config] so Komodo excludes it from the health rollup. Reference: plex/stack.toml, backup/{bilby,kangaroo}/stack.toml, flood/stack.toml. (Gatus black-box endpoint checks remain the authoritative health signal regardless — this just keeps Komodo's at-a-glance view honest too.)

Bind mounts from the repo

When a stack needs to bind-mount config or scripts from the repo, mount the containing directory — never an individual file. Stacks that need their config at a specific in-container path either point the upstream binary at the bind-mounted directory (nginx -c /conf/nginx.conf, backrest --config /conf/config.json) or use an init container to copy the file into a named volume on first boot. 

volumes:
  # Right — directory bind. Host edits propagate immediately, atomic
  # renames don't break the link to the container.
  - ${PODHAUS_REPO}/<stack>/conf:/conf:ro

PODHAUS_REPO is a fixed variable (declared in komodo/sync/variables.toml) pointing at bilby's Komodo-managed deploy tree (/etc/komodo/repos/podhaus-deploy) — a clone fed by the push webhook (pulled to origin/main) or by ./komodo-sync (overlaid with the working checkout). Every ${PODHAUS_REPO} bind in the repo is :ro except one: home-assistant's UI-editable config mount uses ${PODHAUS_CHECKOUT} instead — a host-discovered variable seeded by komodo-start pointing at bilby's live working checkout, so the UI editor's saves land somewhere committable rather than in a tree the webhook can reset at any time. See Secrets → non-secret variables and Komodo → operating models.

Never use single-file bind mounts

Compose lines like ${PODHAUS_REPO}/<stack>/config.yaml:/etc/foo/config.yaml:ro are forbidden in this repo. File-level binds pin the inode at mount time, and any tool that saves via atomic rename (vim, $EDITOR, Claude Code, the Write tool) leaves the container pointing at the now-orphaned original inode. Subsequent host edits are silently invisible to the container until it's recreated. Mount the containing directory instead.

Real incident: the docs-server's nginx.conf was originally a file bind. After editing it, the new directives didn't take effect until the container was force-recreated — exactly the silent-divergence failure mode this rule prevents. The fix was the pattern above: nginx.conf moved into docs-server/conf/, that whole directory bound at /conf/, and nginx pointed at it via command: ["nginx", "-c", "/conf/nginx.conf", "-g", "daemon off;"].

Always use absolute host paths

Komodo-managed stack run_directory paths (/etc/komodo/repo/<stack>) exist inside Periphery but not on the host. Docker daemon resolves bind mount sources from the host filesystem, so relative paths like ./conf/ resolve to non-existent host paths and Docker silently creates empty stub directories. Always ${PODHAUS_REPO}/<stack>/..., never relative paths.

Config-only commits recreate the container (since 2026-06-18) — via the Stage-1 reconcile

Directory bind mounts mean a host-side edit is visible on disk inside the container immediately — but the process running inside is already past its config-load step and won't re-read the file. And Komodo's DeployStackIfChanged is a no-op when the compose text is unchanged, so by itself a deploy pulls the new bind-mounted file but leaves the process on the cached old config.

The podhaus-inject-content-hashes action closes this. A change to any committed in-stack file (<stack>/conf*/, caddy/conf*/, alloy-conf/, <stack>/scripts/, …) changes the stack's STACK_CONTENT_HASH; the action notices the running container's podhaus.stack-content-hash label is stale and force-deploys the stack, recreating the container so the process re-reads its config. No manual step on a normal push.
  • It's a recreate (full restart), not an in-place reload. Fine for startup-read config. If you specifically want a graceful SIGHUP/reload-endpoint instead of a restart, that's still a manual choice (docker kill -s HUP <container>, caddy reload, alloy /-/reload, …).
  • Triggered only by the push procedure / komodo-sync — not a bare docker compose up -d.
  • Not covered: secret / variables.toml value changes — the content hash excludes the deploy-written .env (see Komodo / AGENTS.md content-hash note).

Removed services leave orphan containers

Komodo runs docker compose up -d without --remove-orphans. Removing a service from compose doesn't stop or delete its existing container. After deploying the compose change, inspect the stack and remove the exact orphan explicitly with docker rm -f <container>. Do the read-only inspection first; a stale container may still hold a port, volume, or old job label.

SELinux on Fedora Asahi

SELinux on bilby denies cross-label reads into bind-mounted config files by default. Two workarounds, both already in use:

  • security_opt: label:disable on the service — lifts confinement entirely. Used by gatus, ofelia, autoheal, backrest, alloy, clickstack.
  • :z or :Z on the volume — labels the source so the container can read/write. Used on plex/, flood/, paperless pgdata mount.

Kangaroo (QTS) has no SELinux, so these flags are no-ops there but stay in compose for portability.

Healthchecks and autoheal

Most stacks declare a healthcheck + labels: autoheal: "true". The host's autoheal stack restarts any running container whose healthcheck reports unhealthy — and keeps restarting it every cycle (~30 s) until it goes healthy or leaves the running set. The healthcheck's retries is the detection threshold (consecutive failed probes before unhealthy, ≈ retries × interval), not a restart cap.

Skip the healthcheck (and the autoheal label) when the image is distroless and has no shell/curl/wget to probe with, such as paperless-tika. Liveness for those services comes from a downstream service's logs surfacing the dependency failure, plus external Gatus monitoring of the public hostname.

Recovery ownership and the patient window

Recovery has narrow owners. Docker's restart policy handles a process crash. Autoheal restarts a running container that remains unhealthy past its healthcheck threshold. Komodo IfChanged recreates a stack only when its deployed content changes. On Bilby, podhaus-nfs-container-recovery.timer closes one remaining infrastructure seam: it starts a created or exited NFS-bind container only when the retained OCI error names that bind and the exact Jump/Pouch export is healthy again.

This bit the fleet on 2026-06-16: a kangaroo NFS outage (the NAS rebooting for a firmware auto-update) tripped flood's sentinel healthcheck, autoheal restart-stormed it every 30 s, and one restart — tearing down namespaces while the NFS bind hung — wedged it to exited, where autoheal (watches running) and the restart policy (suppressed) both ignored it. See postmortem.

The rule for any container that binds an NFS path: restarting it can't fix a down NFS server, and restarting repeatedly while the bind hangs is what risks the wedge. So these containers use a patient detection window — retries: 15 at interval: 60s (≈15 min) — so a transient kangaroo NFS outage (every firmware reboot drops Pouch/Jump for minutes) rides out without autoheal ever firing; one successful probe after NFS returns resets to healthy in ~60 s. autoheal is retained for genuine app hangs, which present as sustained-unhealthy past the window. Bilby's recurring recovery reuses the existing autoheal=true opt-in and always-on restart policy; it adds no recovery label and leaves ordinary operator stops alone because they have no matching retained infrastructure error. kangaroo's own autorun.sh closes its boot-race half of the seam by reconciling exited containers at boot (clearing the stale network endpoint, then docker start).

NFS-bind healthcheck pattern

Two failure modes can hit a container that binds an NFS path (Pouch /mnt/pouch or Jump /mnt/jump), and the healthcheck must distinguish them — neither ls nor grep /proc/mounts alone gets it right:

  1. NFS is mounted but stalled. Soft NFS (soft,timeo=600,retrans=5) returns EIO after the timeout — but during the stall, any filesystem probe (ls, stat, test -e) blocks until then. The healthcheck times out, Docker marks the container unhealthy, and autoheal restarts a container whose service was perfectly fine.
  2. NFS is unmounted and a bare-stub directory is shadowing the bind. Docker still creates a bind entry in /proc/mounts regardless of source state, and a bind-source dir that's "empty but exists" looks legitimate to anything that just checks for presence. The container serves traffic but reads return wrong (empty) data, writes land on local disk. This is the failure that bit the 2026-05-23 incident — see postmortem.

The defence is a positive sentinel — a file you dropped on the QNAP share itself — plus a timeout envelope to bound the stall case: 

test: ["CMD-SHELL", "timeout 10 sh -c 'wget -q -O- http://localhost:3000/ >/dev/null && [ -e /data/.podhaus-share-mounted ]'"]

[ -e ] is a stat — cheap, no directory listing, returns boolean. On a stub-shadowed bind it returns false (no sentinel) → red. On a stalled NFS it blocks → the outer timeout 10 kills the probe → red. The sentinel is invariant to permissions, locale, and subdirectory contents.

The marker file lives at .podhaus-share-mounted in every NFS bind-source path used by any container:

  • /mnt/pouch/.podhaus-share-mounted — for any bind at the Pouch root (flood, plex media).
  • /mnt/jump/.podhaus-share-mounted, /mnt/jump/paperless/.podhaus-share-mounted, /mnt/jump/backups/.podhaus-share-mounted, /mnt/jump/paperless/documents/.podhaus-share-mounted, /mnt/jump/plex-video-thumbnails/.podhaus-share-mounted (plex BIF, moved off Pouch) — Jump consumers.

When adding a stack that binds a new sub-path under Pouch or Jump, drop a marker in that path first: sudo touch /mnt/pouch/<subpath>/.podhaus-share-mounted. The marker is written to the QNAP share, so it persists across reboots and is visible to every container that binds that path. The full set is also codified in ansible/roles/nfs_binds/ (re-touched on each play run — e.g. to restore markers after a share rebuild wipes them); add new sub-paths to that list too.

Companion: the chattr +i tripwire

The healthcheck is the last line of defence — the first is the host-level tripwire. Bare /mnt/pouch and /mnt/jump have chattr +i set on their underlying btrfs dirs (applied idempotently by ansible/roles/nfs_binds/ via a non-recursive mount --bind / that reaches the bare dir under the NFS overlay). If NFS isn't mounted, Docker can't auto-create bind-source subdirs at container start (the immutable bit blocks the mkdir) — so affected stacks fail loudly at deploy rather than silently running on bare-stub binds. With NFS mounted, the bit is irrelevant (NFS supersedes the btrfs dir). See storage → NFS recovery + bare-stub defence.

Local-bind healthcheck pattern

For local NVMe binds (/var/lib/<stack>), the failure modes are much narrower — no soft-stall, no possibility of a different filesystem silently shadowing the bind. Either prove service liveness via loopback wget/curl alone, or check the mount with grep -q " /path " /proc/mounts if the volume has ever been observed to silently detach. 

test: ["CMD-SHELL", "wget -q -O- http://localhost:3000/ >/dev/null"]

Pomerium ingress

A protected *.pod.haus service needs three matching declarations:

  1. An entry in local.pod_haus_service_dns in terraform/services_pod_haus.tf, normally pointing at local.numbat_application_ipv4.
  2. A policy route in pomerium/config.yaml.
  3. A host matcher and backend in Caddy's private :4443 listener.

Podhaus services do not get Cloudflare Tunnel or Access resources. Machine endpoints must use an exact hostname or path plus an application credential. Add them to the public Caddy listener only when Pomerium cannot handle the protocol. Run Terraform from the consolidated root and deploy config through the normal Komodo push procedure.

Backups

Any stack with state worth keeping needs an entry in backup/compose.shared.yaml (bind-mount the state dir into the Backrest container as /userdata/<stack>) plus a plan in backup/<host>/config.json.tmpl. See Backup & recovery for the full pattern.

Pre-commit env-lint hook

tools/lint-stack-env.py walks every stack.toml's environment block and verifies each declared key is referenced in the corresponding compose file(s) — catches the two-place footgun where a key lands in the project .env but no service references ${KEY}, so the container gets nothing.

Install once per clone: 

ln -sf ../../tools/pre-commit .git/hooks/pre-commit
chmod +x .git/hooks/pre-commit

(or cp instead of ln -sf if you want a static copy.) Hook runs on every git commit; the lint exits non-zero on mismatch, blocking the commit with a diagnostic. Reference copy at tools/pre-commit with the same setup instructions.

Quick checklist when adding a stack

  • ☐ compose.yaml + stack.toml in <name>/
  • ☐ stack.toml omits deploy = true (Komodo's Sync Deploy auto-deploys are not used; Stage 2 of podhaus-deploy is the deploy authority — the pre-commit lint enforces this)
  • ☐ dockernet external network declared (if reachable from other containers)
  • ☐ Bind mounts use ${PODHAUS_REPO}/..., not relative paths
  • ☐ All bind mounts are directory binds, never single files (see above)
  • ☐ Every service has the podhaus.stack-content-hash label so a config-only push recreates startup-read processes through the Stage-1 reconcile
  • ☐ SELinux flag (:z or label:disable) on bilby-targeted bind mounts
  • ☐ Healthcheck + autoheal: "true" label (unless distroless image)
  • ☐ Any soft-NFS healthcheck uses the share sentinel under a bounded timeout; it never performs an unbounded directory listing
  • ☐ Secrets created in 1P, referenced via OP__KOMODO__*
  • ☐ Stack-private non-secret config declared as [[variable]] blocks at the bottom of stack.toml (rather than seeded in komodo-start)
  • ☐ Every key in the stack.toml environment block is referenced as ${KEY} in compose (pre-commit hook catches mismatches)
  • ☐ Terraform DNS + Pomerium policy + Caddy route (if protected hostname)
  • ☐ Backrest plan added (if there's state to preserve)
  • ☐ Gatus monitor added (if there's a public hostname or critical internal endpoint)
