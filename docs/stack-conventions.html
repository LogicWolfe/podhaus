Stack conventions

Patterns that any stack in this repo follows. Match the existing shapes and most things line up automatically — networking, secrets, backups, monitoring.

Adding a single-host stack

  1. Create <name>/compose.yaml. Join dockernet if the stack needs to be reachable from another container or via the Cloudflare Tunnel.
  2. Create <name>/stack.toml with server = "podhaus", files_on_host = true, deploy = true, and run_directory = "/etc/komodo/repo/<name>". List any required variables in the environment block. If the stack has stack-private non-secret config (e.g. a service URL, a well-known port), declare it as an inline [[variable]] block in the same file — see Stack-private variables.
  3. Add any new secrets to the 1Password Homelab vault — komodo-op auto-syncs them (see Secrets).
  4. If the stack needs a hostname, add an ingress rule to cloudflare-tunnel/config.yml and a CNAME in dns/dnsconfig.js. Run ./dns-push after.
  5. Commit and push. The push fires the podhaus-push-deploy procedure: Stage 0 RunSync registers the new stack + any TOML-declared variables; Stage 1 deploys it (because deploy = true + deployed_contents is None means DeployIfChangedAction::FullDeploy per Komodo v2.2.0 source). No manual Deploy click. For local debug iteration without pushing, ./komodo-sync.

Adding a stack to a multi-host shared service

Services in this layout today: backup/, autoheal/, logging/. Each has a compose.shared.yaml defining the cross-host contract and per-host subdirectories overlaying the host-specific bits.

  1. Create <service>/<host>/compose.yaml with include: [../compose.shared.yaml] and the host-specific overlay (volumes, security_opt, additional services).
  2. Create <service>/<host>/stack.toml setting server = "<host>" and the per-host environment block. Variable names must match the shared compose's contract; values come from host-specific 1P items.
  3. If the host needs a config template (e.g. Backrest's config.json.tmpl), put it at <service>/<host>/<template> and reference it via the per-host overlay's bind mount.
  4. Commit + push. The push procedure's Stage 0 syncs the new stack def, Stage 1 deploys it on bilby (if applicable), Stage 2 force-deploys linked-repo hosts.

When fixing a bug in a multi-host service, edit compose.shared.yaml (and the shared template if present) — the change applies to all hosts uniformly. Per-host overlay edits should only touch genuinely host-specific bits.

Stack-private variables

Komodo Variables can be declared anywhere the ResourceSync sees TOML (it walks resource_path recursively). Two homes:

  • Global, fleet-wide → komodo/sync/variables.toml. Use for things every stack might reference (TZ, MEDIA_DIR).
  • Stack-private → inline [[variable]] blocks at the bottom of the stack's own stack.toml. Use for stack-specific non-secret config — repo paths, sidecar URLs, well-known ports. Pattern: fenwick/stack.toml declares FENWICK_REPO, FENWICK_SIGNAL_*, FENWICK_ADMIN_* alongside the [[stack]] block.
[[stack]]
name = "myservice"
deploy = true
[stack.config]
server = "podhaus"
files_on_host = true
run_directory = "/etc/komodo/repo/myservice"
environment = """
TZ=[[TZ]]
MYSERVICE_PORT=[[MYSERVICE_PORT]]
"""

[[variable]]
name = "MYSERVICE_PORT"
value = "8080"
description = "Service port (well-known, not a secret)"

Komodo Variables are a single global namespace — collisions across declaration sites = last-applied wins. Prefix-namespace stack-private vars (e.g. FENWICK_*, PLEX_*) so they don't collide with anyone else's declarations.

Secrets do not go in [[variable]] blocks — they go in 1Password and flow through komodo-op as OP__KOMODO__* vars (see Secrets).

Customization primitives

Three blessed primitives for when an upstream image doesn't do exactly what's needed. Pick based on the nature of the customization.

Primitive When to use Example
Init container using the shared init-tools:local image One-time setup that produces an artifact before the main service starts. Tool isn't needed during runtime. Backrest envsubst (backup/) — renders config.json from template. Plex Preferences merge — overlays enforced identity attrs onto Preferences.xml.
Custom Dockerfile + Komodo build (run_build = true, auto_pull = false in stack.toml) The main service needs the customization at runtime: different binary, missing runtime tool, upstream bug fix. komodo-op arm64 build — upstream ships a mislabeled arm64 manifest that's actually amd64.
komodo-start host render True bootstrap concerns that must happen on the host before any container can read them. Komodo Core itself, chicken-and-egg credentials.

init-tools shared image: All init containers across the fleet use the same locally-built image declared at init-tools/Dockerfile (alpine + gettext + python3 + curl + jq — covers config templating, python merge scripts, and inits that hit external APIs like tailscale-cleanup's tailnet ghost pruner). Each consumer stack triggers the build inline via its init service's build: directive (Komodo's run_build = true handles this). Init service uses pull_policy: never so Komodo's auto_pull doesn't try to fetch the local-only tag. Stack.toml has run_build = true; auto_pull stays default-true so the main service still pulls upstream image updates. Add new tools to init-tools/Dockerfile rather than layering apk add at runtime in a consumer's entrypoint — the shared image is the single owner of the convention.

Mandatory with any init container: ignore_services. A one-shot init exits 0 by design, but Komodo counts an exited container toward stack health and marks the whole stack Unhealthy — a false red that trains you to ignore the Komodo signal. Every init-container stack must set ignore_services = ["<init-service>"] in [stack.config] so Komodo excludes it from the health rollup. Reference: plex/stack.toml, backup/{bilby,kangaroo}/stack.toml, flood/stack.toml, tailscale/{bilby,kookaburra}/stack.toml. (Gatus black-box endpoint checks remain the authoritative health signal regardless — this just keeps Komodo's at-a-glance view honest too.)

Bind mounts from the repo

When a stack needs to bind-mount config or scripts from the repo, mount the containing directory — never an individual file. Stacks that need their config at a specific in-container path either point the upstream binary at the bind-mounted directory (nginx -c /conf/nginx.conf, backrest --config /conf/config.json) or use an init container to copy the file into a named volume on first boot. 

volumes:
  # Right — directory bind. Host edits propagate immediately, atomic
  # renames don't break the link to the container.
  - ${PODHAUS_REPO}/<stack>/conf:/conf:ro

PODHAUS_REPO is seeded by komodo-start with the host's absolute path to the repo clone. This keeps the repo portable across hosts and environments.

Never use single-file bind mounts Compose lines like ${PODHAUS_REPO}/<stack>/config.yaml:/etc/foo/config.yaml:ro are forbidden in this repo. File-level binds pin the inode at mount time, and any tool that saves via atomic rename (vim, $EDITOR, Claude Code, the Write tool) leaves the container pointing at the now-orphaned original inode. Subsequent host edits are silently invisible to the container until it's recreated. Mount the containing directory instead.

Real incident: the docs-server's nginx.conf was originally a file bind. After editing it, the new directives didn't take effect until the container was force-recreated — exactly the silent-divergence failure mode this rule prevents. The fix was the pattern above: nginx.conf moved into docs-server/conf/, that whole directory bound at /conf/, and nginx pointed at it via command: ["nginx", "-c", "/conf/nginx.conf", "-g", "daemon off;"].
Always use absolute host paths Komodo-managed stack run_directory paths (/etc/komodo/repo/<stack>) exist inside Periphery but not on the host. Docker daemon resolves bind mount sources from the host filesystem, so relative paths like ./conf/ resolve to non-existent host paths and Docker silently creates empty stub directories. Always ${PODHAUS_REPO}/<stack>/..., never relative paths.
Config-only commits don't auto-reload running containers Directory bind mounts mean a host-side edit is visible on disk inside the container immediately — but the process running inside is already past its config-load step and won't re-read the file. The push-deploy procedure's DeployStack step runs docker compose up -d, which is a no-op when nothing in the compose config itself has changed; the container keeps running with the cached (old) config. The new content sits on disk, untouched, until the operator does one of:
  • docker compose up -d --force-recreate <service> — cleanest; new container reads new file.
  • Send the daemon a reload signal it understands (e.g. docker kill -s HUP <container> for nginx, cloudflared, ofelia, alloy with the right command flag, etc.).
  • Hit a daemon-provided reload endpoint (some tools: caddy admin API caddy reload, alloy /-/reload, etc.).
Auto-reload exceptions known in this fleet: cloudflare-tunnel re-reads config.yml on each reconnect cycle (see the dns-push section below). Most other config-bind-mount stacks (alloy, caddy, gatus) need an explicit recreate/signal. When in doubt, force-recreate.

Real incident (2026-05-22): kookaburra's logging/kookaburra/alloy-conf/config.alloy was changed to use the bilby MagicDNS FQDN, committed, push-deployed. The Periphery clone advanced (git pull succeeded), the new file was on disk inside the running alloy container, but alloy kept shipping to the old endpoint until docker compose up -d --force-recreate alloy was run by hand. Same failure class as the file-bind-mount inode trap — silent divergence between disk and running process.

SELinux on Fedora Asahi

SELinux on bilby denies cross-label reads into bind-mounted config files by default. Two workarounds, both already in use:

  • security_opt: label:disable on the service — lifts confinement entirely. Used by cloudflare-tunnel, gatus, ofelia, autoheal, backrest, alloy, clickstack.
  • :z or :Z on the volume — labels the source so the container can read/write. Used on plex/, flood/, paperless pgdata mount.

Kangaroo (QTS) has no SELinux, so these flags are no-ops there but stay in compose for portability.

Healthchecks and autoheal

Most stacks declare a healthcheck + labels: autoheal: "true". The host's autoheal stack restarts any container whose healthcheck reports unhealthy for ~3 consecutive cycles.

Skip the healthcheck (and the autoheal label) when the image is distroless and has no shell/curl/wget to probe with — pattern documented in cloudflare-tunnel, paperless-tika, and others. Liveness for those services comes from a downstream service's logs surfacing the dependency failure, plus external Gatus monitoring of the public hostname.

NFS-bind healthcheck pattern

Two failure modes can hit a container that binds an NFS path (Pouch /mnt/pouch or Jump /mnt/jump), and the healthcheck must distinguish them — neither ls nor grep /proc/mounts alone gets it right:

  1. NFS is mounted but stalled. Soft NFS (soft,timeo=600,retrans=5) returns EIO after the timeout — but during the stall, any filesystem probe (ls, stat, test -e) blocks until then. The healthcheck times out, Docker marks the container unhealthy, and autoheal restarts a container whose service was perfectly fine.
  2. NFS is unmounted and a bare-stub directory is shadowing the bind. Docker still creates a bind entry in /proc/mounts regardless of source state, and a bind-source dir that's "empty but exists" looks legitimate to anything that just checks for presence. The container serves traffic but reads return wrong (empty) data, writes land on local disk. This is the failure that bit the 2026-05-23 incident — see postmortem.

The defence is a positive sentinel — a file you dropped on the QNAP share itself — plus a timeout envelope to bound the stall case: 

test: ["CMD-SHELL", "timeout 10 sh -c 'wget -q -O- http://localhost:3000/ >/dev/null && [ -e /data/.podhaus-share-mounted ]'"]

[ -e ] is a stat — cheap, no directory listing, returns boolean. On a stub-shadowed bind it returns false (no sentinel) → red. On a stalled NFS it blocks → the outer timeout 10 kills the probe → red. The sentinel is invariant to permissions, locale, and subdirectory contents.

The marker file lives at .podhaus-share-mounted in every NFS bind-source path used by any container:

  • /mnt/pouch/.podhaus-share-mounted — for any bind at the Pouch root (flood, plex media).
  • /mnt/pouch/plex-video-thumbnails/.podhaus-share-mounted — plex BIF subdir bind.
  • /mnt/jump/.podhaus-share-mounted, /mnt/jump/paperless/.podhaus-share-mounted, /mnt/jump/backups/.podhaus-share-mounted, /mnt/jump/paperless/documents/.podhaus-share-mounted — Jump consumers.

When adding a stack that binds a new sub-path under Pouch or Jump, drop a marker in that path first: sudo touch /mnt/pouch/<subpath>/.podhaus-share-mounted. The marker is written to the QNAP share, so it persists across reboots and is visible to every container that binds that path.

Companion: the chattr +i tripwire The healthcheck is the last line of defence — the first is the host-level tripwire. Bare /mnt/pouch and /mnt/jump have chattr +i set on their underlying btrfs dirs. If NFS isn't mounted, Docker can't auto-create bind-source subdirs at container start (the immutable bit blocks the mkdir) — so affected stacks fail loudly at deploy rather than silently running on bare-stub binds. With NFS mounted, the bit is irrelevant (NFS supersedes the btrfs dir). See storage → NFS recovery + bare-stub defence.

Local-bind healthcheck pattern

For local NVMe binds (/var/lib/<stack>), the failure modes are much narrower — no soft-stall, no possibility of a different filesystem silently shadowing the bind. Either prove service liveness via loopback wget/curl alone, or check the mount with grep -q " /path " /proc/mounts if the volume has ever been observed to silently detach. 

test: ["CMD-SHELL", "wget -q -O- http://localhost:3000/ >/dev/null"]

Cloudflare Tunnel ingress

Add an entry to cloudflare-tunnel/config.yml: 

- hostname: my-service.pod.haus
  service: http://my-service:8080

The hostname must be single-label under pod.haus for the wildcard Access app to gate it (multi-label fails through). Host-network services route via http://172.18.0.1:<port> (the dockernet bridge gateway).

Add a matching CNAME in dns/dnsconfig.js: 

CNAME("my-service", TUNNEL, CF_PROXY_ON),

Then ./dns-push to apply. The cloudflare-tunnel stack picks up the new ingress rule automatically — the bind-mounted config.yml is re-read on cloudflared's next reconnect cycle (or you can docker restart cloudflare-tunnel).

Backups

Any stack with state worth keeping needs an entry in backup/compose.shared.yaml (bind-mount the state dir into the Backrest container as /userdata/<stack>) plus a plan in backup/<host>/config.json.tmpl. See Backup & recovery for the full pattern.

Pre-commit env-lint hook

tools/lint-stack-env.py walks every stack.toml's environment block and verifies each declared key is referenced in the corresponding compose file(s) — catches the two-place footgun where a key lands in the project .env but no service references ${KEY}, so the container gets nothing.

Install once per clone: 

ln -sf ../../tools/pre-commit .git/hooks/pre-commit
chmod +x .git/hooks/pre-commit

(or cp instead of ln -sf if you want a static copy.) Hook runs on every git commit; the lint exits non-zero on mismatch, blocking the commit with a diagnostic. Reference copy at tools/pre-commit with the same setup instructions.

Quick checklist when adding a stack

  • ☐ compose.yaml + stack.toml in <name>/
  • ☐ stack.toml has deploy = true (else the sync's deploy step skips this stack)
  • ☐ dockernet external network declared (if reachable from other containers)
  • ☐ Bind mounts use ${PODHAUS_REPO}/..., not relative paths
  • ☐ All bind mounts are directory binds, never single files (see above)
  • ☐ If the stack reads bind-mounted config at startup, decide how a config-only push reaches the running process: does the daemon auto-reload (cloudflared) or does it need an explicit --force-recreate / SIGHUP after deploy? (see the callout above)
  • ☐ SELinux flag (:z or label:disable) on bilby-targeted bind mounts
  • ☐ Healthcheck + autoheal: "true" label (unless distroless image)
  • ☐ Healthcheck does no filesystem I/O on a soft-NFS path (Pouch / Jump) — loopback for the service, /proc/mounts for mount presence
  • ☐ Secrets created in 1P, referenced via OP__KOMODO__*
  • ☐ Stack-private non-secret config declared as [[variable]] blocks at the bottom of stack.toml (rather than seeded in komodo-start)
  • ☐ Every key in the stack.toml environment block is referenced as ${KEY} in compose (pre-commit hook catches mismatches)
  • ☐ Cloudflare Tunnel ingress + DNS CNAME (if public hostname)
  • ☐ Backrest plan added (if there's state to preserve)
  • ☐ Gatus monitor added (if there's a public hostname or critical internal endpoint)
