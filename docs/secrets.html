Secrets & variables

One canonical secret store (1Password Homelab vault), two automatic sync paths into Komodo, one interpolation syntax in stacks ([[VAR]]). No secret is ever copy-pasted into the UI; every stack rebuild reproduces the same secret state from 1P.

The flow

1Password Homelab vault
    ↓  (komodo-op syncs vault items → Komodo Variables)
Komodo Variables (database)
    ↓  ([[VAR]] interpolation when a stack is rendered)
Stack environment (.env file on the Periphery host)
    ↓  (${VAR} interpolation in compose)
Container environment

komodo-op runs as a container in the onepassword/ stack. It polls the 1P vault every few minutes and reflects each item as a Komodo Variable named OP__KOMODO__<ITEM>__<FIELD>. Item names like "Plex Online Token" become PLEX_ONLINE_TOKEN; field labels like credential become CREDENTIAL.

Adding a new secret

  1. Create or edit a Login/Password/SecureNote/etc. item in the Homelab vault in 1Password. Use a clear, hyphenated item name — e.g. postmark-smtp, restic-repo-password.
  2. Wait ~1 minute for komodo-op to sync (or restart the onepassword stack to force it). Verify in Komodo UI → Settings → Variables that OP__KOMODO__POSTMARK_SMTP__CREDENTIAL (or equivalent) appears.
  3. Reference that synced variable name from the consumer stack's stack.toml: 
    environment = """
POSTMARK_SERVER_TOKEN=[[OP__KOMODO__POSTMARK_SMTP__CREDENTIAL]]
"""
  4. Reference ${POSTMARK_SERVER_TOKEN} in the consumer stack's compose.yaml.
Never create variables in the UI Manually-created Komodo Variables don't survive a fresh Komodo bootstrap — they're not in the 1P vault, not in komodo-start's seed list, and not in any TOML. Silently breaks the disaster-recovery path. Always go via 1P.

Delivering a var to a container is a two-place change

A stack.toml environment = """ ... """ block is rendered by Komodo into the compose project .env — project-level variables only. Docker Compose does not automatically inject project .env variables into every service's container. Each service that needs a variable must also reference it in its own compose environment: block: 

services:
  gatus:
    environment:
      CLICKHOUSE_PASSWORD: ${CLICKHOUSE_PASSWORD}

So delivering a secret or variable to a container is always a two-place change:

  1. stack.toml environment — the Komodo Variable lands in the project .env.
  2. The compose service's environment: — the project var is passed into that container.
The footgun that bit this fleet twice If you add a var to stack.toml but forget the compose-service environment: mapping, the container never receives it: ${VAR} resolves empty → silent auth or empty-value failures — even though the 1Password item, the OP__KOMODO__* Komodo Variable, and the stack.toml line are all correct. Real cases that needed the second mapping added after the fact: logging/compose.shared.yaml (CLICKSTACK_INGESTION_KEY) and gatus/compose.yaml (CLICKHOUSE_PASSWORD).

Chicken-and-egg variables

Five variables have to exist before the ResourceSync / komodo-op flow can run — they're either inputs to komodo-op itself (so it can talk to 1Password) or host-discovered (so they can't live in a checked-in TOML). komodo-start seeds these directly via the Komodo API on each invocation:

  • ONEPASSWORD_CREDENTIALS — the 1Password Connect server's credentials file.
  • ONEPASSWORD_CONNECT_TOKEN — the access token Connect uses.
  • ONEPASSWORD_API_KEY — Komodo API key used by komodo-op.
  • ONEPASSWORD_API_SECRET — Komodo API secret used by komodo-op.
  • PODHAUS_REPO — absolute path to this repo's checkout on the bootstrap host (= $PWD when komodo-start runs; host-specific, so it can't be declared in a TOML).

The OP-family four are read out of 1P using the OP_SERVICE_ACCOUNT_TOKEN on the host. After seeding, komodo-start creates the ResourceSync (include_variables = true), runs a first sync (which registers komodo-op + all other stacks + TOML-declared non-secret vars), waits for komodo-op to backfill OP__KOMODO__* secrets, then runs a second sync so each stack's environment block renders against live secret values. Everything else (TZ, MEDIA_DIR, stack-private FENWICK_*) is declarative — see the Non-secret variables section.

Non-secret variables

Non-secret variables live in TOML and apply via the ResourceSync (the podhaus sync has include_variables = true, so its [[variable]] blocks are applied on each RunSync). Two homes:

  • Global, fleet-wide → komodo/sync/variables.toml. Currently TZ=Australia/Perth and MEDIA_DIR=/mnt/pouch. Edit + push (or ./komodo-sync) to apply.
  • Stack-private → inline [[variable]] blocks in the stack's own stack.toml. Pattern in use: fenwick/stack.toml declares FENWICK_SIGNAL_*, FENWICK_ADMIN_* alongside the [[stack]] definition.

Komodo Variables are a single global namespace — collisions across declaration sites = last-applied wins. Prefix-namespace stack-private vars (FENWICK_*, PLEX_*, etc.) to avoid name clashes.

One exception that stays in komodo-start: PODHAUS_REPO. It's host-discovered (= $PWD at bootstrap time), so it can't live in a checked-in TOML — that'd be wrong on any host that clones the repo to a different path. komodo-start seeds it directly via the API; everything else (TZ, MEDIA_DIR, Fenwick config) is declarative.

Why PODHAUS_REPO matters Stacks that bind-mount repo-resident files use ${PODHAUS_REPO}/<stack>/<file> in their compose. This keeps the repo portable — clone it anywhere on a new host and the same compose files work because komodo-start auto-detects the clone path.
Removing a variable from TOML doesn't auto-delete it from Komodo The podhaus sync runs with delete: false (additive only), which is the safe default — flipping delete: true would wipe every variable not declared in the sync, including komodo-op's continuously-synced OP__KOMODO__* values. Side effect: a variable removed from variables.toml (or a deleted [[variable]] block in a stack.toml) lingers in Komodo until manually deleted via the API (DeleteVariable). Empirically verified 2026-05-22. Edit + delete-on-purpose, not edit-and-forget.

Multi-host secrets

For shared services (backup/, autoheal/, logging/) each host has its own 1P items where appropriate. The shared compose declares standardized in-container env-var names; the per-host stack.toml maps the host-specific 1P-backed variable onto that standard name.

Example: GATUS_BACKREST_PUSH_TOKEN (bilby's nightly Backrest heartbeat) and GATUS_BACKREST_KANGAROO_PUSH_TOKEN (kangaroo's) are separate items in 1P, synced as separate variables, but both reach Gatus through bearer-token validation on the same external endpoint.

komodo-op field-name slugification komodo-op turns each 1P item field into a Komodo Variable named OP__KOMODO__<ITEM>__<FIELD>, upper-snake-cased. The item title and field labels both get slugified — spaces become underscores, casing normalises. So the Tailscale OAuth Client item with fields client id and client secret produces __CLIENT_ID and __CLIENT_SECRET. When adding a new item, check what variable name appears in Komodo's ListVariables before writing the [[VAR]] reference in stack.toml.
