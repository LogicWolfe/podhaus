StreamFab publish

StreamFab (a desktop app on a Mac laptop) captures kids' shows and movies to Pouch at /mnt/pouch/Downloads, nested by streaming service. Plex doesn't see that tree. The streamfab-publish stack is a once-a-minute sweep that moves each finished capture into the Plex Kids library — Kids/TV for episodes, Kids/Movies for films — and leaves StreamFab's scratch alone. It is the StreamFab analogue of flood's publish step, but standalone and move-based (no seeding to keep, so no hardlink).

The stack

A deliberately small standalone stack — not folded into flood, because torrents and DRM captures are separate sources with separate failure domains.

  • streamfab-publish/compose.yaml — an idle python:3.12-alpine container (sleep infinity, no network, nothing to build). It exists only to host the ofelia tick. Binds ${MEDIA_DIR} at /data and the scripts dir.
  • streamfab-publish/scripts/streamfab-publish.py — the mover. Pure stdlib; logs to stdout (ofelia/Alloy capture it); single-flight via flock in /tmp. Runs as uid 1000 so moved files and created library dirs match the rest of the Pouch tree.
  • streamfab-publish/stack.toml — files_on_host, no secrets, no build.

Scheduling is the shared host-wide ofelia instance reading the container's ofelia.job-exec.streamfab-publish labels (schedule 0 * * * * *). The push procedure's Stage 3 RestartStack ofelia makes ofelia re-read the labels on deploy.

Why no "is it finished?" wait

StreamFab muxes in a scratch directory, writes the final mp4 into the Downloads tree under a numeric staging name (e.g. 30633639.mp4), then atomically renames it to its real <Show>_S01E01_<Title>.mp4 name. A non-numeric .mp4 is therefore complete by construction — so the mover needs no quiescence/size-stable wait; it only has to skip the numeric staging name (^\d+\.mp4$). This was verified by sampling the output directory at 4 Hz through a real finalize: the numeric file grows, then the final name appears at full size in a single step.

Atomicity depends on the staging-rename staying same-filesystem.

The staging file is written in the output tree (Pouch/NFS), so it holds even with StreamFab's temp dir on the Mac's local SSD — the heavy mux scratch is local, but the final rename is still NFS-internal and atomic. If the final file ever starts arriving as a growing file under its real name (a cross- filesystem copy), re-introduce a size-stable guard. Re-check with the 4 Hz monitor after any change to StreamFab's temp/output directory settings.

Routing & layout

Each tick re-walks /data/Downloads (so it clears any backlog on the first run and cheaply no-ops afterward). For every candidate .mp4 the leading streaming-service component is dropped and the rest of the path is kept verbatim:

  • TV (filename contains SxxExx) → /data/Kids/TV/<Show>/…
  • Movie (no SxxExx) → /data/Kids/Movies/<Title>/…

StreamFab is used only for kids' content here, hence both destinations live under Kids. Plex parses StreamFab's underscored names natively, so no renaming is done. Anything that doesn't fit the <Service>/<Show-or-Title>/…/<file> shape is left in place and logged rather than guessed at.

The move is an os.rename within the single Pouch filesystem — atomic and instant. If the destination already exists: identical size ⇒ a re-download, source dropped; different size ⇒ a conflict, both left for a human.

What it leaves alone

It is a publisher, not a janitor. It only moves video (.mp4, .mkv, .m4v) and never deletes anything it doesn't understand:

  • StreamFab scratch — outputTemp, mpd, picture, MetaPicture, mp4header.dat (these follow StreamFab's temp dir; on the Mac now, but stale copies may linger on the NAS).
  • YouTube/ — deliberately out of scope.
  • macOS ._ AppleDouble sidecars — skipped, and they keep emptied dirs from being pruned.

Mount safety

Like every Pouch-binding stack, the container healthchecks on the /data/.podhaus-share-mounted sentinel (with a timeout envelope and 15 retries to ride out a QNAP-firmware-reboot NFS blip). The mover also refuses to run if the sentinel is absent — without it, /data is a bare local-disk stub and a move would scatter media onto bilby's NVMe. See stack conventions.

Deploy & observe

Push to main → the podhaus-push-deploy procedure first-deploys the stack (Stage 2 FullDeploy for a new stack) and restarts ofelia (Stage 3). Confirm via the job's stdout in ofelia's container logs (moved … -> /data/Kids/TV/…) and by the files appearing in the Plex Kids library. There is no Gatus heartbeat on this job today; add one if silent-stall detection becomes worth the wiring.
