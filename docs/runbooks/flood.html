Flood + RAR pipeline

Flood (rtorrent + Flood web UI) is bilby-resident. Downloads land in /data/torrents — a Plex-invisible working tree — never directly in the library. RAR releases extract in place there, and completed media is hardlinked file-by-file into the clean /data/{TV,Movies,Kids} library. Plex therefore only ever sees complete files (the partial-file scan race is gone), and a prioritized episode publishes the moment it finishes rather than when the whole torrent does. Every config file lives in the repo and bind-mounts into the container.

Flood

jesec/rtorrent-flood upstream, locally extended via flood/Dockerfile to add libarchive-tools (provides bsdtar with permissive RAR-read + multi-volume support — the right primitive for alpine, where standalone unrar isn't packaged and the p7zip package doesn't ship the RAR codec) and python3 (runs flood-publish.py, which queries rtorrent over its SCGI socket for per-file completion and hardlinks completed media into the library). Runs as 1000:1001 so created files end up owned the same as rtorrent's. UI on port 3000, reachable at torrent.pod.haus.

Build-stack content-hash convention

flood uses a build: directive, which means changes to the Dockerfile (and any future COPY-source files) need to invalidate docker's image-layer cache. Per AGENTS.md "Content-hash change detection": flood/compose.yaml passes build.args.STACK_CONTENT_HASH: ${BUILD_HASH_FLOOD:-unset} and the Dockerfile declares ARG STACK_CONTENT_HASH=unset + ENV-from-ARG so a new value busts the cache. BUILD_HASH_FLOOD is injected per-deploy by Stage 1 of the push procedure. The running container never reads the value; it's purely a layer-cache invalidation lever.

Storage:

  • /var/lib/flood-db (local NVMe) — rtorrent session (.torrent + .libtorrent_resume + .rtorrent files for ~200 active torrents) plus the script logs and locks.
  • /data/torrents (under /mnt/pouch, mounted as /data) — the download/extract working tree: RAR pieces, scene detritus, and the working copy of extracted media.
  • /data/{TV,Movies,Kids} — the Plex library, a curated hardlink farm. A published file shares its inode with the working-tree copy, so it's a single copy on disk until the torrent is removed.

Atomic publish: redirect + hardlink

The core of the pipeline, and why Plex never sees a partial file:

  1. Redirect at add — the event.download.inserted_new redirect_dl hook in rtorrent.rc captures the destination you typed as the torrent's publishdir custom and resets the download directory to /data/torrents: d.custom.set=publishdir,$d.directory=;d.directory.set=/data/torrents;d.save_full_session=. These are inline rtorrent commands on purpose — an external helper that called back over XML-RPC from a synchronous hook would deadlock rtorrent's single event loop (it blocks waiting for the hook while the hook blocks waiting for rtorrent to answer the RPC). A startup schedule = mkdir_download_root,0,0,"execute.nothrow=mkdir,-p,/data/torrents" ensures the root exists — rtorrent won't create a download's parent dir, and a missing /data/torrents silently stalls every redirected torrent at 0 bytes despite seeds.
  2. Publish on completion — flood/scripts/flood-publish.py queries rtorrent over /tmp/rtorrent.sock (SCGI + XML-RPC, transport inlined; no third-party client). For every torrent whose base_path is under /data/torrents with a real publishdir, it hardlinks each completed media file into publishdir, preserving the release folder. A torrent-member file is complete when f.completed_chunks == f.size_chunks — keyed by f.frozen_path (the absolute path; f.path is only relative to base_path, and using it silently broke non-RAR publishing). Extracted RAR output isn't a torrent member, so it's gated on the _unpackerred marker instead. Media-only (video + subtitle extensions; .rar/.nfo/sample skipped), idempotent via inode equality, and a torrent gets a pubdone custom once fully published so steady-state ticks skip it.
  3. Two triggers, same code path — an ofelia minute tick (0 * * * * *, the steady-state driver, run as uid 1000:1001) and the event.download.finished flood_publish hook (execute.nothrow.bg, near-instant on completion). Plex's own change-detection picks the new hardlink up because flood and Plex share the /mnt/pouch client mount on bilby, so the link is a local-VFS event (this guarantee evaporates if flood ever moves off bilby).

Hardlink, not move; library paths only

A completed file is still a live torrent member, so it can't be moved out from under rtorrent — a hardlink lets rtorrent keep seeding from /data/torrents while Plex reads the library copy, single copy on disk. Set destinations to library paths (/data/TV, /data/Movies, /data/Kids) — never under /data/torrents, which the publisher logs a WARN for and skips.

RAR auto-extract

flood/scripts/rtorrent-extract.sh — invoked by rtorrent's event.download.finished hook with the torrent's exact base_path (now under /data/torrents). It extracts every RAR set under base_path, not just the first — a season-pack torrent can carry one release subfolder per episode, and the old find … | head -1 silently skipped the rest. For each set it picks the entry-point archive (modern .rar > .partNN.rar > .r00 with .rar absence), runs bsdtar -xf in place, and drops _unpackerred.<dir>.txt as the "extracted" marker. Idempotent on the marker. Success is verified by comparing the non-archive-keeper count before vs after — libarchive emits "Truncated RAR file data" and exits non-zero at the last-volume boundary even on a full extraction, so the exit code is unreliable; a failure leaves no marker for the daily safety-net to catch. Path-guarded to /data/torrents. Log at /flood-db/rtorrent-extract.log. The extracted .mkv is then hardlinked into the library by flood-publish.py (marker-gated, since it isn't a torrent member).

Cleanup: native delete + refcount

There is no event.download.erased cleanup hook. In the hardlink model the /data/torrents/<name> tree is disposable working state, so cleanup is just Flood's Remove and delete data: rtorrent deletes the whole tree (RAR pieces + the working copy of the media), and the library hardlink survives because the inode's link count stays ≥ 1.

  • Wrong torrent caught mid-download — nothing was published, so the file is link-count 1; "Remove and delete data" correctly deletes it. (This is the deliberate, no-guard behaviour.)
  • Finished + published, done seeding — "Remove and delete data" drops the working-tree link; the library copy survives via refcount.
  • "Remove" without data — leaves an orphan working-tree folder in /data/torrents, reclaimed manually (no auto-cleanup hook).
  • The safety primitive is the inode link count — a published media file is link-count ≥ 2, so a working-tree file can be reaped safely iff its link count is ≥ 2 (anything at 1 is unpublished and must not be deleted blind).

Safety net + monitoring

flood/scripts/rar-backlog.sh — daily ofelia job at 04:50 AWST, the cron-driven backstop for the whole pipeline, two checks folded into one Gatus heartbeat (torrents_rar-extraction):

  • Extraction — scans /data/torrents for folders with RAR pieces ≥ 2h old and no extracted keeper (extraction failed/never ran).
  • Publish — runs flood-publish.py --gaps, which reports completed torrents whose media never hardlinked into the library. This is the safety net for the no-delete-time-guard model: a publish gap surfaces here before you'd ever "Remove and delete data".

Healthy → success=true; any issue → success=false&error=… with a count + sample. A missing 25h ping fires the dead-man's switch (ofelia broken, flood dead, NFS unmounted).

Cross-uid log/lock ownership

flood-publish's log and single-flight lock are touched by both the ofelia tick and rtorrent's uid-1000 execute hooks. flood-init pre-owns /flood-db/flood-publish.{log,lock} as 1000:1001 (explicit paths, no shell variable — docker compose interpolates a bare $var in the command, and an earlier loop variable expanded to empty and chmod'd /flood-db itself, crash-looping flood). The publish tick also tolerates an unopenable lock rather than aborting.

Config-as-code overlays

Two bind mounts make Flood's behavior diff-able and survive volume rebuild:

  • ${PODHAUS_REPO}/flood/conf/rtorrent.rc installed onto /flood-db/.rtorrent.rc via the flood-init one-shot init container — rtorrent reads it once at startup. flood-init also creates /data/torrents-adjacent state and pre-owns the publish log/lock.
  • ${PODHAUS_REPO}/flood/scripts overlaid onto /scripts (directory bind, so host edits propagate without restart): flood-publish.py (per-file hardlink publisher + --gaps reporter), rtorrent-extract.sh (finished-hook RAR extraction), rar-backlog.sh (daily safety-net + Gatus heartbeat), and pinelake-stignore.py.

Directory bind, not file bind, for the scripts dir

File-level binds pin the inode at mount time. Any tool that saves via atomic rename (vim, $EDITOR, Claude Code) leaves the container looking at the original inode forever. A directory bind sidesteps that.

Healthcheck + recovery from NFS loss

The flood healthcheck has three parts, each defending a specific failure mode:

  1. wget -q -O- http://localhost:3000/ — Flood's Node web server is up (proves rtorrent's parent process is alive and serving).
  2. grep -q " /flood-db " /proc/mounts — the local NVMe bind is present (catches an unmounted volume after a docker volume rebuild).
  3. [ -e /data/.podhaus-share-mounted ] — the sentinel proves /data is bound to the real Pouch NFS share, not a bare local-disk stub. Without this check, a missed NFS mount would false-green via the /proc/mounts presence check (Docker creates a bind entry regardless of source state). Background: 2026-05-23 pouch/jump mount-failure postmortem.

The whole probe is wrapped in timeout 10 so a soft-NFS stall returns red rather than hanging the healthcheck process forever.

Recovery from NFS loss is a host-then-container chain — the container can't fix the host:

  1. Host re-mounts NFS. The fstab entries use x-systemd.automount, so the kernel re-mounts on next access. If the QNAP was unreachable when boot tried, the next access (a healthcheck, a container restart, a manual ls) triggers a retry. No manual intervention required for the common case.
  2. Flood's healthcheck is still red because Docker's bind captured the source at container-start (default rprivate mount propagation — the container doesn't see new submounts on the host path).
  3. Autoheal sees red and restarts the container. The new container's bind picks up the NFS-backed source → sentinel visible → green. Same chain works for plex, paperless, backrest.

Worst-case manual recovery (QNAP is up, NFS is up, but containers stayed red): docker restart flood plex paperless backrest. This is the bilby-side incident-response one-liner — covers every Pouch/Jump consumer.

Pinelake .stignore auto-sync

Tagging a torrent pinelake in Flood marks it as "I want this on the Pinelake household Mac." On completion its publish target is routed to one of Pouch's four source folders: Movies, TV, Kids, or Sports. The root-relative path is inserted as an exact rooted negation in that folder's normal .stignore, between permanent junk exclusions and the final ** deny. Pinelake's receive-only Syncthing folder then receives the selected media on its next scan.

Source of truth is rtorrent's live session state. The reconciler queries it over the container-local SCGI/XML-RPC socket and has no Flood API dependency. It emits the publishdir named custom (the library path) rather than the base_path (which points at the /data/torrents working tree), falls back to directory for grandfathered torrents, and skips the working tree itself.

  • flood/scripts/pinelake-stignore.py — filters complete=1 && "pinelake" ∈ split(custom1, ","), validates all four ignore-file contracts before writing, and reconciles insert-only entries under a single-flight lock.
  • Triggers — the rtorrent event.download.finished hook (zero-latency) and an ofelia */5min tick (catches tag-applied-after-completion).
  • Writes — atomically to /data/{Movies,TV,Kids,Sports}/.stignore, which are Bilby's views of the normal files under /mnt/pouch. The Pinelake Flood overlay sets PINELAKE_STIGNORE_SOURCE=false and never writes them.
  • Insert-only by design — untagging/deleting a torrent does not remove its line; manual removal is the user's call (see syncthing runbook).

Tag → Plex label sync

Tags do double duty: any tag you put on a torrent in Flood is also mirrored onto the matching Plex show (or movie) as a Plex Label. This drives Plex's per-managed-user content restrictions — tag a torrent indigo and the show it belongs to becomes accessible to the indigo managed user; rowan likewise. Multiple tags → multiple labels → access for multiple kids.

Generic by design. Every tag becomes a label — there is no hardcoded list. Adding a new kid or category later is zero code change: tag the torrents, then add that label to the user's allow-list in Plex. pinelake rides along as a harmless label too.

Tag casing doesn't matter. Plex matches label tags case-insensitively and keeps the canonical casing of the label that already exists. The kid labels in Plex are Indigo / Rowan / Pippin (capitalised), so a lowercase Flood tag (indigo) merges onto the existing Indigo label rather than creating a duplicate — the show ends up tagged with the exact label object the managed-user restrictions key off. The one caveat: a tag for a label that does not yet exist in Plex is created with whatever casing you typed, so first-use sets the canonical form for a brand-new category.

  • flood/scripts/plex-label-sync.py — reuses flood-publish.py's rtorrent transport + publish-path logic (loaded by path) to find each tagged torrent's published video files, looks each up in Plex by file path, and walks to the owning show/movie. Reaches host-network Plex over the dockernet gateway at 172.18.0.1:32400; the token is the same plex.tv account credential plex/ uses.
  • Triggers — the rtorrent event.download.finished hook (zero-latency) and an ofelia */5min tick. The tick is the workhorse: Plex's own library scan lags the publish, so the finish-hook pass usually finds the file not-yet-indexed and no-ops, and the tick picks it up once Plex has scanned.
  • Label granularity is the show/movie — the only level Plex's sharing label restrictions filter on. A tagged episode labels its whole show.
  • Additive-only — removing a tag never strips the label (won't fight labels set by hand in Plex). Revoke access manually.
  • Cheap at steady state — each torrent's applied tag-set is stashed in the labelsync named custom; a tick whose current tags already match skips the torrent with no Plex round-trip. Plex is contacted only when a torrent's tags actually changed. A torrent is only marked done once every published video resolves to a Plex item, so a file Plex hasn't scanned yet is retried, never silently skipped.

One-time manual Plex setup (not codeable here). Label filtering only applies when a managed user's restriction profile is set to None (a Plex Pass feature). For each kid: in Plex → Settings → Users → (kid) → set restriction profile to None, then under the shared library's restrictions add their label to "allow content tagged with the following labels." podhaus doesn't manage Plex sharing config, so this lives in Plex's account UI. Note Plex disables folder-browse for a label-restricted user — expected.

Bulk RAR-backlog cleanup tooling

rar-cleanup-scripts/ (Dockerfile + audit.py + find-unhealthy.sh) is a disposable rar-cleanup:local image (debian:trixie-slim with unrar + python3 + sqlite3) for one-off bulk cleanup runs against the media tree. Not deployed as a stack — the day-to-day pipeline above is the steady state. Kept in the repo for the rare case of a large backlog that's easier to chew through in bulk than file by file.
