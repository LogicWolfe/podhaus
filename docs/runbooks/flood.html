Flood + RAR pipeline

Flood (rtorrent + Flood web UI) is bilby-resident. The auto-extract pipeline around it — unpackerr + rtorrent-cleanup.sh + rar-backlog.sh + Gatus heartbeat — is the config-as-code answer to RAR-multi-volume torrents. Every config file involved lives in the repo and bind-mounts into the container.

Flood

jesec/rtorrent-flood image; runs as 1000:1001 so files created end up owned the same as rtorrent's RAR files. UI on port 3000, reachable at torrent.pod.haus.

Storage:

  • /var/lib/flood-db (local NVMe) — rtorrent session (~16 MB of .torrent + .libtorrent_resume + .rtorrent files for ~200 active torrents).
  • /mnt/pouch (NFS) — actual data, mounted into the container as /data.

Config-as-code overlays

Two bind mounts make Flood's behavior diff-able and survive volume rebuild:

  • ${PODHAUS_REPO}/flood/rtorrent.rc overlaid onto /flood-db/.rtorrent.rc — the live rtorrent config that used to be container-volume-only.
  • ${PODHAUS_REPO}/flood/scripts overlaid onto /scripts (directory bind, so host edits propagate without restart). Contains rtorrent-cleanup.sh and rar-backlog.sh.
Directory bind, not file bind, for the scripts dir File-level binds pin the inode at mount time. Any tool that saves via atomic rename (vim, $EDITOR, Claude Code) leaves the container looking at the original inode forever. A directory bind sidesteps that.

The RAR auto-extract pipeline

Three parts working in concert. The whole point is "extract RAR multi-volume torrents automatically and clean up the RAR pieces afterwards, but never delete the only copy of the content if extraction silently failed."

  1. unpackerr stack (unpackerr/compose.yaml) — ghcr.io/unpackerr/unpackerr:latest, runs as 1000:1001 like flood. Watches the rtorrent download dir and extracts RAR multi-volume sets to the containing directory.
  2. flood/scripts/rtorrent-cleanup.sh — invoked by rtorrent's event.download.erased hook. Deletes RAR pieces and scene detritus (.rar, .r[0-9][0-9], .partN.rar, .sfv, .srr, .srs, .nfo, sample/ proof dirs) only after verifying at least one non-RAR/non-detritus keeper file exists in the folder. Path-restricted to /data/{Movies,TV,Kids}.
  3. flood/scripts/rar-backlog.sh — daily ofelia job at 04:50 AWST. Scans for folders containing RAR pieces ≥2h old with no extracted keepers (same detection as the cleanup script's abort guard, run proactively). Pushes success=true or success=false&error=<count+sample> to Gatus's heartbeat_rar-extraction external endpoint with the bearer token.

Safety layering

unpackerr ships no healthcheck (image has no probe binary, no HTTP endpoint). The safety net is layered:

  • Extraction-presence guard in rtorrent-cleanup.sh — if unpackerr died silently, the keeper count is zero and the cleanup aborts rather than deleting the only copy.
  • restart: unless-stopped on the unpackerr container.
  • Daily Gatus heartbeat — if no successful ping arrives within 25 hours, the dead-man's-switch fires.
  • Failure ping with context — if the proactive scan finds a stuck folder, it pushes success=false with the count and a sample folder name — Gatus alerts within minutes instead of waiting for the missing heartbeat.

One-shot RAR-backlog cleanup tooling

Before the live pipeline went on, the existing 139-folder legacy RAR backlog was remediated with a disposable rar-cleanup:local image (Dockerfile at rar-cleanup-scripts/Dockerfile — debian:trixie-slim with unrar + python3 + sqlite3). All 136 cleanup actions are recorded in ~/repos/podhaus-migration-state/rar-backlog-remediation.sqlite (off-repo sidecar). The tooling stays in the repo for reuse if the pattern recurs; not deployed as a stack.
