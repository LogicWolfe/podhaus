Flood + RAR pipeline

Flood (rtorrent + Flood web UI) is bilby-resident. The auto-extract pipeline is rtorrent-native: an event.download.finished hook fires rtorrent-extract.sh with the torrent's exact base_path, the script walks that subtree at any depth and 7za-extracts in place. The previous unpackerr stack was removed in May 2026 once we found its non-recursive watcher couldn't see nested release layouts (e.g. /data/Kids/Movies/<release> or /data/TV/<Show>/Season N/<release>). Every config file lives in the repo and bind-mounts into the container.

Flood

jesec/rtorrent-flood upstream, locally extended via flood/Dockerfile to add p7zip (provides 7za for the extract hook). Built on each deploy via Compose build: .; Periphery's compose build is fast (single apk add layer over the cached upstream). Runs as 1000:1001 so files created end up owned the same as rtorrent's RAR files. UI on port 3000, reachable at torrent.pod.haus.

Storage:

  • /var/lib/flood-db (local NVMe) — rtorrent session (~16 MB of .torrent + .libtorrent_resume + .rtorrent files for ~200 active torrents).
  • /mnt/pouch (NFS) — actual data, mounted into the container as /data.

Config-as-code overlays

Two bind mounts make Flood's behavior diff-able and survive volume rebuild:

  • ${PODHAUS_REPO}/flood/rtorrent.rc overlaid onto /flood-db/.rtorrent.rc — the live rtorrent config that used to be container-volume-only.
  • ${PODHAUS_REPO}/flood/scripts overlaid onto /scripts (directory bind, so host edits propagate without restart). Contains rtorrent-extract.sh (event.download.finished hook; in-place extraction), rtorrent-cleanup.sh (event.download.erased hook; rar piece deletion), rar-backlog.sh (daily ofelia safety-net + Gatus heartbeat), and pinelake-stignore.sh.
Directory bind, not file bind, for the scripts dir File-level binds pin the inode at mount time. Any tool that saves via atomic rename (vim, $EDITOR, Claude Code) leaves the container looking at the original inode forever. A directory bind sidesteps that.

Healthcheck + recovery from NFS loss

The flood healthcheck has three parts, each defending a specific failure mode:

  1. wget -q -O- http://localhost:3000/ — Flood's Node web server is up (proves rtorrent's parent process is alive and serving).
  2. grep -q " /flood-db " /proc/mounts — the local NVMe bind is present (catches an unmounted volume after a docker volume rebuild).
  3. [ -e /data/.podhaus-share-mounted ] — the sentinel proves /data is bound to the real Pouch NFS share, not a bare local-disk stub. Without this check, a missed NFS mount would false-green via the /proc/mounts presence check (Docker creates a bind entry regardless of source state). Caught by the 2026-05-23 incident; see postmortem.

The whole probe is wrapped in timeout 10 so a soft-NFS stall returns red rather than hanging the healthcheck process forever.

Recovery from NFS loss is a host-then-container chain — the container can't fix the host:

  1. Host re-mounts NFS. The fstab entries use x-systemd.automount, so the kernel re-mounts on next access. If the QNAP was unreachable when boot tried, the next access (a healthcheck, a container restart, a manual ls) triggers a retry. No manual intervention required for the common case.
  2. Flood's healthcheck is still red because Docker's bind captured the source at container-start (default rprivate mount propagation — the container doesn't see new submounts on the host path).
  3. Autoheal sees red and restarts the container. The new container's bind picks up the NFS-backed source → sentinel visible → green. Same chain works for plex, paperless, backrest.

Worst-case manual recovery (QNAP is up, NFS is up, but containers stayed red): docker restart flood plex paperless backrest. This is the bilby-side incident-response one-liner — covers every Pouch/Jump consumer.

The RAR auto-extract pipeline

Three parts working in concert. The whole point is "extract RAR multi-volume torrents automatically and clean up the RAR pieces afterwards, but never delete the only copy of the content if extraction silently failed."

  1. flood/scripts/rtorrent-extract.sh — invoked by rtorrent's event.download.finished hook with the torrent's exact base_path. Walks the subtree at any depth for the archive entry-point (modern .rar > .partNN.rar > .r00 with .rar absence), runs 7za x in place, drops _unpackerred.<dir>.txt on success so rar-backlog won't re-flag. Idempotent on the marker. Fails loud: extraction errors leave no marker, so the daily safety-net catches it. Path-guarded to /data/{Movies,TV,Kids}. Log at /flood-db/rtorrent-extract.log.
  2. flood/scripts/rtorrent-cleanup.sh — invoked by rtorrent's event.download.erased hook. Deletes RAR pieces and scene detritus (.rar, .r[0-9][0-9], .partN.rar, .sfv, .srr, .srs, .nfo, sample/ proof dirs) only after verifying at least one non-RAR/non-detritus keeper file exists in the folder. Path-restricted to /data/{Movies,TV,Kids}.
  3. flood/scripts/rar-backlog.sh — daily ofelia job at 04:50 AWST, cron-driven safety-net. Scans for folders containing RAR pieces ≥2h old with no extracted keepers (same detection as the cleanup script's abort guard, run proactively). Pushes success=true or success=false&error=<count+sample> to Gatus's heartbeat_rar-extraction external endpoint with the bearer token. Catches anything the rtorrent-extract hook missed — rtorrent crash mid-finished, files added manually outside rtorrent, 7za extraction failures.

Safety layering

Extraction is real-time via the rtorrent event hook, defended by these layers:

  • Extraction-presence guard in rtorrent-cleanup.sh — if the extract hook hadn't run (or failed) for a folder, the keeper count is zero and the erase-cleanup aborts rather than deleting the only copy of the content.
  • Fail-loud extract — rtorrent-extract.sh only writes the _unpackerred.<dir>.txt marker on 7za success. A failure leaves no marker, so the daily scanner picks it up.
  • Daily Gatus heartbeat — if no successful ping arrives within 25 hours, the dead-man's-switch fires (catches ofelia broken, flood dead, NFS unmounted).
  • Failure ping with context — if the proactive scan finds a stuck folder, it pushes success=false with the count and a sample folder name — Gatus alerts within minutes instead of waiting for the missing heartbeat.
Why not unpackerr Until May 2026 this pipeline ran ghcr.io/unpackerr/unpackerr as a separate stack. It worked for one-level layouts like /data/Movies/<release>, but its watcher (fsnotify + radovskyb/watcher) is non-recursive: nested subdirs are invisible. Releases at /data/Kids/Movies/<release> (depth 2 under a watched root) or /data/TV/<Show>/Season N/<release> (depth 3+) slipped through, silently piled up RAR backlog, and only the rar-backlog cron found them. Listing every possible subdir in unpackerr.conf wasn't sustainable. The rtorrent hook gets the exact path from rtorrent itself — depth-agnostic by design — and replaces the whole stack with one ~70-line script + a one-line apk add in a Dockerfile.

Pinelake .stignore auto-sync

Tagging a torrent pinelake in Flood marks it as "I want this on the pinelake household Mac." On completion, its base_path is inserted as a !<rel> allow-list line into Pouch's .stignore (alphabetically into the matching !<TopLevel>/ block, case-insensitive sort to match the file's existing convention). Receive-only peers like pinelake's syncthing then pick the file up via the next folder rescan.

Source of truth is rtorrent's own session state — Flood persists tags into d.custom1 in each torrent's .torrent.rtorrent file under /flood-db. The reconciler bencode-walks the session files; no XMLRPC, no Flood API dependency.

  • flood/scripts/pinelake-stignore.sh — the reconciler. Filters complete=1 && "pinelake" ∈ split(custom1, ","), computes !${base_path#/data/}, idempotent insert with grep -Fxq dedupe and flock single-flight.
  • Triggers — two, same code path:
    • rtorrent event.download.finished hook in rtorrent.rc (zero-latency on a fresh completion).
    • ofelia */5min tick on the flood container (catches the tag-applied-after-completion case).
  • Writes — to /data/.stignore (= /mnt/pouch/.stignore on bilby, NFS-backed by kangaroo). Tempfile-then-atomic-rename in the same dir; /mnt/pouch's setgid bit preserves group ownership across the swap.
  • Insert-only by design — untagging or deleting a torrent does not remove its .stignore line. Manual removal is the user's call; this avoids the "managed vs hand-curated entries" distinction the .stignore mixes (see syncthing runbook).
  • Log — append-only at /flood-db/pinelake-stignore.log, one timestamped line per inserted entry. Quiet on no-op runs.

One-shot RAR-backlog cleanup tooling

Before the live pipeline went on, the existing 139-folder legacy RAR backlog was remediated with a disposable rar-cleanup:local image (Dockerfile at rar-cleanup-scripts/Dockerfile — debian:trixie-slim with unrar + python3 + sqlite3). All 136 cleanup actions are recorded in ~/repos/podhaus-migration-state/rar-backlog-remediation.sqlite (off-repo sidecar). The tooling stays in the repo for reuse if the pattern recurs; not deployed as a stack.
