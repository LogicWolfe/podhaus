Bugsink

Self-hosted, Sentry-protocol error tracker on bilby at bugs.pod.haus. Complements HyperDX (ClickStack), it does not replace it: HyperDX owns logs + traces + exploratory debugging; Bugsink owns exception aggregation — stack-trace fingerprinting, grouping repeats into one issue, first/last-seen, regression detection. Single-user, SQLite, three clients, one project each: fenwick (id 1), fenwick-web-agent (id 3) and brinno-downloader (id 4); Pets (id 2) is unrelated.

Fenwick's three services are wired up

The bot reports via @sentry/deno at its single recordError seam; the browser service via the Sentry Node SDK; the footage service via the Python SDK. Each has its own project and DSN. As-built detail: Wiring Fenwick.

Topology

  • Stack: bugsink/ — bilby files_on_host, two services on one named volume (bugsink-data → /data).
  • bugsink-init: root one-shot. A fresh named volume mounts root:root and shadows the image-time chown of /data; Bugsink runs as UID 14237 and can't chown its own mount, so this chown -R 14237:14237 /data and exits 0. It is in ignore_services — a deliberate exit-0 service, not a failure.
  • UI ingress: bugs.pod.haus → Numbat Pomerium → private Caddy → http://bugsink:8000, gated by the Family policy.
  • Ingest: clients send over dockernet to http://bugsink:8000 directly — never via bugs.pod.haus (that path is behind Pomerium). ALLOWED_HOSTS is set explicitly (bugs.pod.haus,bugsink,localhost,127.0.0.1) so a request with Host: bugsink is accepted while BASE_URL stays the public host for DSNs + email links — Bugsink treats the two settings independently.

Secrets

Two 1Password Homelab items, auto-synced by komodo-op:

1Password itemKomodo Variable(s)Holds
Bugsink Secret KeyOP__KOMODO__BUGSINK_SECRET_KEY__CREDENTIALDjango SECRET_KEY (64-char base64)
Bugsink Create SuperuserOP__KOMODO__BUGSINK_CREATE_SUPERUSER__USERNAME
OP__KOMODO__BUGSINK_CREATE_SUPERUSER__CREDENTIAL		superuser email / password (see below — the item splits)

The superuser item is stored split — stack.toml reconstructs it

"Bugsink Create Superuser" is stored with the email in the item's username field and the password in its credential field (kept split deliberately, for human convenience reading it in 1Password). komodo-op emits one Komodo Variable per 1Password field, so this yields two variables — __USERNAME (email) and __CREDENTIAL (password). Bugsink's CREATE_SUPERUSER env must be the full email:password (its prestart.py raises ValueError if the value has no colon), so bugsink/stack.toml rebuilds it from both: 
BUGSINK_CREATE_SUPERUSER=[[OP__KOMODO__BUGSINK_CREATE_SUPERUSER__USERNAME]]:[[OP__KOMODO__BUGSINK_CREATE_SUPERUSER__CREDENTIAL]]
Coupling to know: the reconstruction is bound to the split layout. If the 1Password item is ever flattened back to a single credential = email:password field, __USERNAME goes empty and this expression yields a leading-colon value (:email:password) — change stack.toml back to a single [[…__CREDENTIAL]] reference at the same time. (History: created single-field, deployed once green, then the item was split by hand — the next redeploy crash-looped until stack.toml was updated to reconstruct. Lesson: validate a secret-bearing stack on a redeploy, not just first deploy.) SECRET_KEY is unaffected — its item has an empty username, so it stays a single __CREDENTIAL.

CREATE_SUPERUSER only provisions the initial user; the password must contain no colon (Bugsink splits the env on the first : only). Rotating it later is a UI password change, not an env edit.

Backup

Standard pattern: bugsink_bugsink-data is mounted read-only into Backrest on bilby at /userdata/bugsink, with a daily plan (25 5 local, 14d/4w/6m retention, skipIfUnchanged) alongside the other stacks. SQLite on a Docker named volume is an accepted trade-off for one low-volume client plus the nightly snapshot; the documented escape hatch is a Postgres sidecar via DATABASE_URL if corruption is ever observed.

Push-to-deploy

No per-stack webhook. The fleet's single GitHub push webhook drives the podhaus-push-deploy Komodo Procedure (komodo/sync/procedures.toml): Stage 0 RunSync reconciles stack defs + TOML-declared variables from disk (config reconcile only); Stage 1 handles config-only and build-context hash drift; Stage 2 handles compose changes and new stacks; Ofelia follows the target container's Docker events. The wildcard covers Bugsink automatically, so adding or removing the stack needs no terraform/github.tf edit. See Komodo → auto-deploy. First push of a brand-new stack registers it via Stage 0 and deploys it via Stage 2 through the (None, _) => FullDeploy arm in DeployStackIfChanged (which doesn't read stack.config.deploy, so the stack omits deploy = true like every podhaus stack) — no manual registration or UI click.

First-run bootstrap

  1. Deploy the stack: bugsink-init chowns /data, bugsink boots, runs Django deploy checks + migrations, and provisions the superuser from CREATE_SUPERUSER. Redeploys are idempotent: prestart.py sees a user already exists and logs "Superuser not created: … already exist(s)" then continues — it never re-creates or errors on an existing instance.
  2. Browse https://bugs.pod.haus → Pomerium (Family) → Bugsink login with the superuser credentials (the "Bugsink Create Superuser" 1Password item).
  3. Create a project per client. Bugsink has no headless project-create, but the Django shell does it without the UI: docker exec bugsink bugsink-manage shell -c '…' with Project.objects.get_or_create(name=…, team=Team.objects.get(name="Bugsink"), defaults={"slug": …}); the project's dsn property gives the key and id. Rewrite the host to the LAN form below and pipe it straight into op item create so the key is never printed. This is how all three Fenwick projects were made.

Wiring Fenwick (as-built)

How the three services are wired:

  • Projects fenwick (id 1), fenwick-web-agent (id 3) and brinno-downloader (id 4), all in team Bugsink, created via bugsink-manage shell.
  • DSNs in 1Password Homelab items Bugsink Fenwick DSN, Bugsink Web Agent DSN and Bugsink Brinno DSN, LAN form http://<key>@bilby.pod.haus:8000/<id>: the Fenwick containers run on bandicoot and reach Bugsink on the port bilby publishes, by its split-horizon name. komodo-op syncs them as OP__KOMODO__BUGSINK_FENWICK_DSN__CREDENTIAL, OP__KOMODO__BUGSINK_WEB_AGENT_DSN__CREDENTIAL and OP__KOMODO__BUGSINK_BRINNO_DSN__CREDENTIAL. Provisioned via the op CLI with the podhaus service-account token (the Connect token is read-only by design).
  • fenwick reports at its single recordError seam via @sentry/deno (tracesSampleRate: 0 — HyperDX owns tracing; Bugsink is errors-only). Well-behaved tools return error text, so only real turn/handler failures and the admin_test_exception lever raise issues. An absent DSN is disabled (local/dev); a DSN that is set but unresolved (an unrendered [[OP__KOMODO__…]] placeholder, or empty) fails fast at fenwick's boot gate — a misconfigured deploy crash- loops visibly, it is never silently degraded.
  • DSN threaded through fenwick/stack.toml + compose.yaml as BUGSINK_DSN; env is not live-reload, so a fenwick redeploy applies it.
  • Cross-link — markdown-in-extra assumption was false. Bugsink renders extra with Django linebreaks (HTML-escaped, no markdown, no urlize). So the link is the raw URL string at extra.hyperdx_trace_url (copy-pasteable) plus a trace_id tag — the real cross-reference: the same id is queried in HyperDX and searchable in Bugsink. The markdown form is not emitted.

Upgrades

Image is pinned by digest off bugsink/bugsink:2 (Bugsink ships no granular semver tags; 2 is the upstream stable major channel). Upgrades are deliberate: pull the new :2, capture the digest (docker inspect --format '{{index .RepoDigests 0}}'), and bump the pin in bugsink/compose.yaml (both services share the digest). The startup bugsink-manage check --deploy + migrations gate a bad release; autoheal + the healthcheck catch a crash-loop; the backup volume enables rollback.
