Bugsink

Self-hosted, Sentry-protocol error tracker on bilby at bugs.pod.haus. Complements HyperDX (ClickStack), it does not replace it: HyperDX owns logs + traces + exploratory debugging; Bugsink owns exception aggregation — stack-trace fingerprinting, grouping repeats into one issue, first/last-seen, regression detection. Single-user, SQLite, one intended client: fenwick.

fenwick is wired up fenwick reports exceptions here (project fenwick, id 1) via @sentry/deno at its single recordError seam, verified end to end. As-built detail: Wiring fenwick.

Topology

  • Stack: bugsink/ — bilby files_on_host, two services on one named volume (bugsink-data → /data).
  • bugsink-init: root one-shot. A fresh named volume mounts root:root and shadows the image-time chown of /data; Bugsink runs as UID 14237 and can't chown its own mount, so this chown -R 14237:14237 /data and exits 0. It is in ignore_services — a deliberate exit-0 service, not a failure.
  • UI ingress: bugs.pod.haus → Cloudflare Tunnel → http://bugsink:8000, gated by the default Access chain (Homelab service-token bypass → Family allow).
  • Ingest: clients send over dockernet to http://bugsink:8000 directly — never via bugs.pod.haus (that path is behind Cloudflare Access). ALLOWED_HOSTS is set explicitly (bugs.pod.haus,bugsink,localhost,127.0.0.1) so a request with Host: bugsink is accepted while BASE_URL stays the public host for DSNs + email links — Bugsink treats the two settings independently.

Secrets

Two 1Password Homelab items, auto-synced by komodo-op:

1Password itemKomodo Variable(s)Holds
Bugsink Secret KeyOP__KOMODO__BUGSINK_SECRET_KEY__CREDENTIALDjango SECRET_KEY (64-char base64)
Bugsink Create SuperuserOP__KOMODO__BUGSINK_CREATE_SUPERUSER__USERNAME
OP__KOMODO__BUGSINK_CREATE_SUPERUSER__CREDENTIAL		superuser email / password (see below — the item splits)
The superuser item is stored split — stack.toml reconstructs it "Bugsink Create Superuser" is stored with the email in the item's username field and the password in its credential field (kept split deliberately, for human convenience reading it in 1Password). komodo-op emits one Komodo Variable per 1Password field, so this yields two variables — __USERNAME (email) and __CREDENTIAL (password). Bugsink's CREATE_SUPERUSER env must be the full email:password (its prestart.py raises ValueError if the value has no colon), so bugsink/stack.toml rebuilds it from both: 
BUGSINK_CREATE_SUPERUSER=[[OP__KOMODO__BUGSINK_CREATE_SUPERUSER__USERNAME]]:[[OP__KOMODO__BUGSINK_CREATE_SUPERUSER__CREDENTIAL]]
Coupling to know: the reconstruction is bound to the split layout. If the 1Password item is ever flattened back to a single credential = email:password field, __USERNAME goes empty and this expression yields a leading-colon value (:email:password) — change stack.toml back to a single [[…__CREDENTIAL]] reference at the same time. (History: created single-field, deployed once green, then the item was split by hand — the next redeploy crash-looped until stack.toml was updated to reconstruct. Lesson: validate a secret-bearing stack on a redeploy, not just first deploy.) SECRET_KEY is unaffected — its item has an empty username, so it stays a single __CREDENTIAL.

CREATE_SUPERUSER only provisions the initial user; the password must contain no colon (Bugsink splits the env on the first : only). Rotating it later is a UI password change, not an env edit.

Backup

Standard pattern: bugsink_bugsink-data is mounted read-only into Backrest on bilby at /userdata/bugsink, with a daily plan (25 5 local, 14d/4w/6m retention, skipIfUnchanged) alongside the other stacks. SQLite on a Docker named volume is an accepted trade-off for one low-volume client plus the nightly snapshot; the documented escape hatch is a Postgres sidecar via DATABASE_URL if corruption is ever observed.

Push-to-deploy

No per-stack webhook. The fleet's single GitHub push webhook drives the podhaus-push-deploy Komodo Procedure (komodo/sync/procedures.toml); its Stage 1 BatchDeployStackIfChanged "*" already covers bugsink — the wildcard matches every stack, so a push that changes bugsink/ redeploys only Bugsink (other unchanged bilby stacks self-skip — no churn). Nothing to register; adding/removing the stack needs no cloudflare/github.tf edit. (Bugsink was in fact the 21st stack that hit GitHub's hard 20-webhook cap and motivated the per-stack→procedure consolidation — see Komodo → auto-deploy.) First registration of a brand-new stack is still ./komodo-sync (or a manual deploy); steady-state push-to-deploy is automatic thereafter.

First-run bootstrap

  1. Deploy the stack: bugsink-init chowns /data, bugsink boots, runs Django deploy checks + migrations, and provisions the superuser from CREATE_SUPERUSER. Redeploys are idempotent: prestart.py sees a user already exists and logs "Superuser not created: … already exist(s)" then continues — it never re-creates or errors on an existing instance.
  2. Browse https://bugs.pod.haus → Cloudflare Access (Family) → Bugsink login with the superuser credentials (the "Bugsink Create Superuser" 1Password item).
  3. Create a project (e.g. fenwick) and copy its DSN — this is the only manual UI step; Bugsink has no headless project-create that fits this flow.

Wiring fenwick (as-built)

Done and verified end to end. How it is wired:

  • Project fenwick (id 1, team Bugsink) — created via bugsink-manage shell (Bugsink has no headless project-create).
  • DSN in 1Password Homelab item Bugsink Fenwick DSN, internal dockernet form http://<key>@bugsink:8000/1, synced by komodo-op as OP__KOMODO__BUGSINK_FENWICK_DSN__CREDENTIAL. Provisioned via the op CLI with the podhaus service-account token (the Connect token is read-only by design).
  • fenwick reports at its single recordError seam via @sentry/deno (tracesSampleRate: 0 — HyperDX owns tracing; Bugsink is errors-only). Well-behaved tools return error text, so only real turn/handler failures and the admin_test_exception lever raise issues. An absent or unrendered-placeholder DSN is treated as disabled, never handed to Sentry.
  • DSN threaded through fenwick/stack.toml + compose.yaml as BUGSINK_DSN; env is not live-reload, so a fenwick redeploy applies it.
  • Cross-link — markdown-in-extra assumption was false. Bugsink renders extra with Django linebreaks (HTML-escaped, no markdown, no urlize). So the link is the raw URL string at extra.hyperdx_trace_url (copy-pasteable) plus a trace_id tag — the real cross-reference: the same id is queried in HyperDX and searchable in Bugsink. The markdown form is not emitted.

Upgrades

Image is pinned by digest off bugsink/bugsink:2 (Bugsink ships no granular semver tags; 2 is the upstream stable major channel). Upgrades are deliberate: pull the new :2, capture the digest (docker inspect --format '{{index .RepoDigests 0}}'), and bump the pin in bugsink/compose.yaml (both services share the digest). The startup bugsink-manage check --deploy + migrations gate a bad release; autoheal + the healthcheck catch a crash-loop; the backup volume enables rollback.
