Music Assistant

Music Assistant (the music-assistant stack on bilby) is a media bridge: it drives AirPlay-2 / Sonos speakers and exposes them to Home Assistant as media_player entities that support announcements. Its sole job today is the doorbell chime — a UniFi Protect ring plays a sound on the living-room Bowers & Wilkins Formation, which has no first-class Home Assistant path of its own (AirPlay-2 only, no Cast/DLNA). Most of this page is the non-obvious wiring that made that work.

The doorbell is additive The chime plays on the Formation in addition to the three physical UniFi chimes (Kitchen / Garage / Studio). It does not replace them.

Topology

  • MA server — ghcr.io/music-assistant/server, network_mode: host on bilby (mandatory: it needs L2 / mDNS access to discover and stream to the Formation). Claims TCP 8095 (web UI + websocket API) and 8097 (audio streamserver). State lives in the named volume music-assistant-data → /data (provider config, players, instance id, library). No init container.
  • AirPlay provider (enabled in MA's UI) discovers the Formation and registers it as the universal player "Living Room" → surfaced in HA as media_player.living_room.
  • HA integration — the Home Assistant "Music Assistant" integration connects to the MA server and exposes its players + the music_assistant.* services. This is the link the doorbell automation rides.
  • Ingress — music.pod.haus via the music module in terraform/services_pod_haus.tf (CF tunnel + Access for off-LAN) and a Caddy vhost + split-horizon for on-LAN. See base_url ↔ Access.

The doorbell chime

Trigger → action chain, all on bilby:

  1. event.g4_doorbell_doorbell (UniFi Protect) fires on a ring.
  2. HA automation doorbell_living_room_chime (alias "Doorbell chime — living room", in /var/lib/home-assistant/automations.yaml): snapshot the player volume → media_player.volume_set to 0.6 → 0.5s settle → music_assistant.play_announcement → restore the snapshot volume.
  3. MA fetches the chime, ducks/streams it to the Formation over AirPlay, and resumes prior MA playback if any.

The chime is /var/lib/home-assistant/www/doorbell.wav (served unauthenticated at /local/doorbell.wav, which MA fetches at http://10.0.0.119:8123/local/doorbell.wav). It carries a deliberate ~0.8s of leading silence — AirPlay clips the first fraction of a second establishing the stream, so the glitch lands on silence instead of the bells — and the trailing near-silent reverb tail is trimmed off.

The Formation ignores announce_volume MA's announce_volume parameter has no audible effect on this speaker (10 / 80 / 100 all sound identical). Its base volume is controllable via media_player.volume_set (with a read-back lag — set commands take, but an immediate state read can return the stale value). That's why the automation does an explicit snapshot → set 0.6 → restore rather than passing announce_volume.

base_url ↔ Cloudflare Access

MA announces a single base_url that every client (browsers and the HA integration alike) uses for its websocket. The wrinkle: Home Assistant runs on bilby and its connection to MA is server-to-server — it carries no Cloudflare Access cookie, so if base_url resolves to the CF edge, Access blocks it (wss://music.pod.haus/ws → 302 cloudflareaccess.com, integration dead).

The resolution lets base_url = https://music.pod.haus work for everyone:

  • Off-LAN browser → public CF record → tunnel → MA (Access cookie lets it in).
  • On-LAN, IPv4 → UniFi split-horizon A record (music.pod.haus → 10.0.0.119, in terraform/dns_unifi_split_horizon.tf) → Caddy vhost (caddy/Caddyfile, real LE cert via DNS-01) → MA. No edge, no Access.
  • Home Assistant → extra_hosts in home-assistant/compose.yaml pins music.pod.haus → 10.0.0.119 IPv4-only inside the container → Caddy → MA.
Why extra_hosts and not just split-horizon music.pod.haus is a proxied Cloudflare record, so CF advertises an AAAA (IPv6) alongside the A. Dual-stack resolvers prefer the IPv6 → they reach the CF edge and bypass the split-horizon A. The clean fix would be Cloudflare's per-record ipv4_only setting, but the pod.haus zone's plan rejects it (API error 9227: "not available to this zone"). So HA — the one consumer that must never see the AAAA — gets an /etc/hosts pin (A only) via extra_hosts; nsswitch is files dns, so the pin wins. Dual-stack LAN browsers still hairpin to MA's UI via the tunnel — harmless (Access admits them), just not LAN-direct.

Firewall (AirPlay)

AirPlay playback needs the speaker to send UDP timing/control back to MA on dynamic ports; conntrack doesn't see those as RELATED, so bilby's default-drop zone killed the handshake ("Playback failed to start" after a 10s timeout). The firewall is declarative config-as-code under bilby/firewalld/ (installed by bilby/host-systemd/install.sh):

  • services/music-assistant.xml — TCP 8095 (web UI/API, needed on the LAN for the HA integration's browser OAuth redirect) + 8097 (stream).
  • zones/public.xml — a LAN-trust rich rule (accept from 10.0.0.0/24) so AirPlay's dynamic return UDP reaches MA. The home LAN is trusted; non-LAN sources still hit the filtered service list.

State & DR

MA's /data volume is in the backup set (the music-assistant plan in backup/bilby/, daily 04:35). Two pieces of this setup are runtime config, not in the repo — same config-as-code gap as every HA integration:

  • MA's base_url = https://music.pod.haus and the AirPlay provider live in MA's /data (settings) — backed up, so DR restores them.
  • The HA-side UniFi Protect + Music Assistant integrations live in /var/lib/home-assistant/.storage (UI-configured). The doorbell automation and the chime file are plain files under /var/lib/home-assistant/, which is backed up by the home-assistant plan.

On a from-scratch rebuild: restore both volumes, then re-confirm MA's base_url and the AirPlay provider, and that HA's integration reconnects (MA logs WebSocket client authenticated and media_player.living_room leaves unavailable).

Key files

  • music-assistant/{compose.yaml,stack.toml} — the MA stack (host-network, named volume, autoheal).
  • bilby/firewalld/ — declarative firewall (MA ports + LAN-trust), installed by bilby/host-systemd/install.sh.
  • caddy/Caddyfile — the music.pod.haus vhost (LAN-direct TLS front for MA).
  • terraform/services_pod_haus.tf — the music module (CF tunnel + Access); terraform/dns_unifi_split_horizon.tf — the LAN A record.
  • home-assistant/compose.yaml — the extra_hosts pin.
  • backup/bilby/{compose.yaml,config.json.tmpl} — the MA backup plan + read-only volume mount.
  • Host-side (not in repo, but backed up): /var/lib/home-assistant/automations.yaml (the chime automation) and /var/lib/home-assistant/www/doorbell.wav (the sound).
