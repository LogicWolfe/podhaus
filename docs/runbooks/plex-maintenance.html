Plex maintenance log — 2026-04-12/13

Historical record of the Plex DB rescue that drove the Phase 6 architecture pivot (NFS → local NVMe for state). Preserved because the perf numbers and the statistics_bandwidth finding still inform current monthly maintenance.

Background

Plex was running on bilby with a 44 GB SQLite database on NFS at 10.0.0.25:/Jump/plex. Client-visible 30-60 s stalls during browsing. Multiple issues uncovered in a single overnight session:

  • Wrong host timezone (America/New_York → fixed to Australia/Perth) caused butler to run during peak hours.
  • Butler + on-the-fly theme track analysis caused cascading SQLite write-lock storms.
  • Theme music DB records missing for many shows — files on disk since 2022 but DB didn't reference them.
  • Plex had crashed earlier in the day (autoheal SIGTERM during a long DB op), recovered 872 WAL frames.

The plan

Create three side-by-side copies from the original (original at /Jump/plex never touched), then benchmark.

VACUUM saga

Plex's OptimizeDatabase on the original 47 GB DB ran for 7 hours 1 minute uninterrupted on the local-db copy — Phase 1 (temp DB build) ~12 min, Phase 2 (WAL fill, 0 → 46.41 GB) ~5 hours with rate declining from 570 MB/min to 60 MB/min, Phase 3 (checkpoint replay) ~1 hour. Reclaimed a modest 3.8% (47.13 GB → 45.35 GB).

Why the first VACUUM attempt failed

Initial VACUUM at 06:07 ran for 4.5 hours, then autoheal killed Plex at 10:35 because the healthcheck timed out under the VACUUM DB lock pressure. Plex restart rolled back the transaction, losing all 4.5 hours of work. Lesson: autoheal + long DB ops is a bad combination. Belt-and-suspenders for v2: remove autoheal: "true", disable the Plex healthcheck entirely, stop the autoheal container.

The actual culprit: statistics_bandwidth

Investigation of why VACUUM only reclaimed 3.8% surfaced the real problem: 

table                  rows
statistics_bandwidth   796,867,521   ← 9.3 years of bandwidth tracking events
taggings               401,005
media_streams          130,346
metadata_items         21,402

At ~70 bytes/row including indexes, this single table accounted for ~55 GB of the 47 GB DB. Plex's internal bandwidth tracking, used only for the Status → Statistics chart in Plex Web. No UI to manage it.

Cleanup, offline via Plex's bundled SQLite (handles the custom icu_root collation):

BEGIN;
CREATE TABLE statistics_bandwidth_new (...);  -- same schema
INSERT INTO statistics_bandwidth_new
    SELECT id, account_id, device_id, timespan, at, lan, bytes
    FROM statistics_bandwidth
    WHERE at >= strftime('%s', 'now', '-30 days');
DROP TABLE statistics_bandwidth;
ALTER TABLE statistics_bandwidth_new RENAME TO statistics_bandwidth;
CREATE INDEX index_statistics_bandwidth_on_at ON ...;
CREATE INDEX index_statistics_bandwidth_on_account_id_and_timespan_and_at ON ...;
COMMIT;

796,867,521 → 3,410 rows. Followup VACUUM completed in < 60 seconds.

Lessons carried forward

  • SQLite on NFS is fragile under write contention. Plex DB moved to local NVMe permanently; "stateless bilby on NFS" replaced by "local state is the default" — see Architecture → design principles.
  • Plex has no stats pruning upstream — we own it. Monthly statistics_bandwidth cleanup runs via ofelia on the 1st of each month. See Plex → monthly stats cleanup.
  • Force refresh is destructive to user poster selections. Avoid unless necessary; reset to defaults rather than running blanket refresh.
  • Autoheal + long DB ops is a bad combination. Disable healthchecks + autoheal before any planned multi-hour DB operation.
  • Byte math beats du -sh math when chasing where the GBs are — the statistics_bandwidth row count + byte estimate is what actually located the bloat.
