Paperless

Paperless-ngx + Postgres + Redis + Tika + Gotenberg. Bilby-resident, dockernet-only access. ~1,120 documents from a one-time OneNote import; ongoing intake is email + scanner via Paperless's consume folder. Reachable externally at paperless.pod.haus.

Stack shape

Five containers in paperless/compose.yaml:

  • paperless-postgres — Postgres 16, pgdata at /var/lib/paperless-pgdata (local NVMe).
  • paperless-redis — for Celery task queue.
  • paperless-tika — text extraction. Distroless image, no healthcheck (Tika has no shell/curl); liveness comes via Paperless's own logs.
  • paperless-gotenberg — PDF rendering for office docs and emails.
  • paperless — the webserver. Data at /var/lib/paperless-data (search index, classifiers) on local NVMe; documents at /mnt/jump/paperless. Documents tree is included in the daily paperless restic plan via the /userdata/paperless/documents bind mount in backup/bilby/compose.yaml.

Access model

Paperless is reachable three ways:

  • Browser access at https://paperless.pod.haus, gated by Pomerium's Family policy and then Paperless's own login.
  • API clients use https://paperless-api.pod.haus/api/* with both X-Podhaus-Gateway-Token from the paperless_api field of the Pomerium Gateway Tokens 1Password item and their Paperless API token. Other paths return 404.
  • Internally on the dockernet bridge at http://paperless:8000. The container's PAPERLESS_ALLOWED_HOSTS=paperless.pod.haus requires the Host: header to match.
Script-side note Migration / import scripts run in throwaway python:3.13-slim containers attached to dockernet, hit http://paperless:8000 with an explicit Host: paperless.pod.haus header. Going via the browser URL would redirect to Pomerium. Anything that follows Paperless's own pagination next URLs must walk pagination by explicit page number instead.

Paperless state at a glance

  • ~1,120 documents across 3 import batches (OneNote main + extracted ZIPs + Ghostscript-repaired PDFs).
  • 149 linked canonical-page groups, 88 sibling edges via Paperless's document_link custom field.
  • 10 custom fields: onenote_page_id, onenote_canonical_page_id, onenote_page_ids_all, onenote_resource_id, onenote_asset_kind, content_sha256, import_batch, import_heuristic_version, archive_source, related_docs (documentlink).
  • ~121 tags materialized. Content tags MATCH_AUTO except unknown (MATCH_NONE — fallback bucket).
  • Default sort: by created (OneNote page frontmatter, spans 2011-2026). modified never set by import (Evernote → OneNote collapsed 96% of modifieds to 2024-01-07 — useless signal).

Known quirks

onenote_page_ids_all truncation Paperless string custom fields cap at 128 chars. Initial bulk import hit 133 PATCH failures from this. Import script now truncates to fit; the truncation is in the sidecar but not in Paperless if you re-upload via a different path.
Tika is distroless Same shape as cloudflare-tunnel — image ships no shell. Healthcheck dropped. Tika liveness is observed via the paperless container's logs (it complains loudly on Tika failures).

Email ingest

Mail sent or forwarded to the Fastmail alias paperless@pod.haus lands automatically as a searchable document. Fastmail files alias mail (including plus-addressed variants) into a Paperless folder; Paperless polls it every minute (PAPERLESS_EMAIL_TASK_CRON). Two rules split the folder by recipient address (matched server-side as an IMAP TO search, so each mail hits exactly one — the two addresses share no substring):

  • paperless@pod.haus → full-email mode (consumption_scope 2): body + attachments bundled into one document with a copy-pasteable text layer (covers the "compose a note with an inline image + typed text" use case), tagged email-ingest.
  • paperless+attachments@pod.haus → attachments-only mode (consumption_scope 1, attachment_type 1): the attached files become documents on their own (body discarded, inline images skipped), titled from the attachment filename, tagged email-attachments. Use this when you want clean per-file documents and previews rather than a rendered email.

Source mail is deleted after a successful parse (lands in Fastmail Trash; a failed parse leaves it for retry). An attachments-only mail with no real attachment is a no-op — nothing is consumed and the mail is not deleted, so it lingers in the folder rather than disappearing.

Two pieces make this work:

  • Custom image (paperless/Dockerfile): the stock Paperless image plus paperlessngx-mail-parser (toweosp), a parser that wins message/rfc822 dispatch and renders the bundled full-email document. Still uses the existing Gotenberg + Tika sidecars.
  • paperless-mail-init: a one-shot container that upserts the Fastmail mail account + both rules via the REST API on every deploy from the Komodo-injected OP__KOMODO__PAPERLESS_FASTMAIL_IMAP__* credentials. Config-as-code — a DB wipe + redeploy reproduces them with no UI step.

Credential recovery: the IMAP login lives in the 1Password Homelab item Paperless Fastmail IMAP (fields username = primary Fastmail login, not the alias; password = a revocable IMAP app-password; hostname; port), synced by komodo-op into the OP__KOMODO__PAPERLESS_FASTMAIL_IMAP__* variables above. The exact account + both rules' field values (consumption scope, attachment handling, delete-after-parse action, the email-ingest / email-attachments tags, and each rule's filter_to) are the authoritative REST upsert in paperless/scripts/mail-init.sh — edit there, not in the UI, or the next deploy reverts it.

Full-email previews lead with the header, not the content Document thumbnails are rendered from the first PDF page, and the toweosp parser prepends the From/To/Subject/Date block inline at the top of the body — so a full-email document's preview shows that metadata, not the content. Paperless exposes no setting to pick a different thumbnail page, and the header isn't a discrete page (it bleeds into page 1), so page-level reordering can't fix it either. If it ever becomes worth solving: a PAPERLESS_POST_CONSUME_SCRIPT gated on the email-ingest tag could re-render page 2 over the stored thumbnail (the hook hands it DOCUMENT_TAGS, DOCUMENT_ARCHIVE_PATH, DOCUMENT_THUMBNAIL_PATH). Caveats: it's owned tooling, it's undone if a document is reprocessed (paperless regenerates the thumbnail from page 1), and page 2 isn't reliably the body since the header bleeds inline. Forwarding the source as an attachment sidesteps it (the attachment becomes page 1, no header block).
${PODHAUS_REPO} must be surfaced paperless-mail-init bind-mounts its script via ${PODHAUS_REPO}, which is interpolated at compose-render time — so paperless/stack.toml must carry PODHAUS_REPO=[[PODHAUS_REPO]] in its environment block. Without it the path resolves to an empty prefix, Docker stubs an empty dir, and the init silently no-ops.
