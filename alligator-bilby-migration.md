**Design principles (canonical, post-pivot):**

- **Storage tier rule:** three tiers selected by what we'd hate to lose, not just by size.
  - **Local NVMe (bilby internal):** hot operational state — small (typically <5 GB per stack), fast access, backed up nightly to Jump.
  - **Jump (NAS SSD, 382 GB, dual-disk RAID):** durable storage we'd hate to lose — backup repository, log history (VL at `/mnt/jump/victoria-logs`).
  - **Pouch (NAS HDD, 29 TB, five-disk RAID):** bulk content where capacity matters more than per-drive resilience — Plex media, paperless documents, BIFs.

## Environment-specific workarounds

All reversible, all documented in the affected compose files with inline comments.

- **NAS `/Jump` squash** — kangaroo's `/Jump` export squashes all writes to uid 1000:gid 100 and denies chown, so container images that chown their data dir on startup fail to deploy against Docker NFS volumes. Originally hit by `ghcr.io/ferretdb/postgres-documentdb`, `postgres:16`, and `1password/connect-api`. Affected volumes were carved out to local storage as "temporary" exceptions — the phase 6 pivot made those carve-outs permanent via the sizing rule, so this is no longer a blocker.
- **SELinux enforcing on Fedora Asahi** — denies container access to `/var/run/docker.sock` and cross-label reads into bind-mounted config files. Applied `security_opt: label:disable` to `komodo-core`, `komodo-periphery`, `autoheal`, `backrest`, `loki`, `alloy`, `grafana`, `uptime-kuma`. Also use `:z` flag on host bind mounts that need container write access (see `plex/compose.yaml`, `flood/compose.yaml`).
- **`ghcr.io/0dragosh/komodo-op` mislabelled arm64 manifest** — upstream Dockerfile hardcodes `--platform=linux/amd64` + `GOARCH=amd64`, so the "arm64" tag is actually an amd64 image that crashes with exec format error on real aarch64. Built a local arm64 image from upstream source via `onepassword/komodo-op.Dockerfile`. Compose declares `build: { context: ., dockerfile: komodo-op.Dockerfile }` + `image: komodo-op:local-arm64`; stack.toml has `run_build = true` + `auto_pull = false` so Komodo handles the build automatically on deploy (no manual `docker build` step needed). Upstream fix deferred (noted in Deferred).
- **Multi-line 1P Secure Notes don't round-trip through Komodo env files** (truncation at the first newline) — `komodo-start` renders `rclone.conf` on the host via `op CLI` and stacks bind-mount `/etc/komodo/rclone/rclone.conf` directly. Re-run `komodo-start` to refresh after OneDrive token rotations.
- **`cloudflare/cloudflared:latest` is distroless** — no shell, no wget, no curl, no busybox, only the `cloudflared` binary. In-container healthchecks that touch `/ready` on port 20241 are structurally impossible. Dropped the healthcheck and autoheal label from `cloudflare-tunnel/compose.yaml` (commit `3bba849`). cloudflared handles its own reconnection internally; `restart: unless-stopped` handles outright crashes; external liveness will be monitored via Uptime Kuma hitting the public hostnames.
- **Komodo ResourceSync does not apply `[[variable]]` entries from variable TOML files** — see the "Known gotcha: Komodo variable seeding" section below. Fixed 2026-04-14 via commit `336b961` which adds `TZ` and `MEDIA_DIR` to `komodo-start`'s `seed_variable` loop.
- **Komodo first-boot chicken-and-egg** — `komodo-start` reads a pre-existing Komodo API key from 1P, but on a fresh DB no such key exists. Manual workaround documented in the progress log; folding into `komodo-start` as an automatic first-boot path is deferred.
- **Bind mount paths are host-relative, not periphery-relative** — Komodo-managed stack `run_directory` paths (`/etc/komodo/repo/<stack>`) exist inside periphery but not on the host. Docker daemon resolves bind mount sources from the host filesystem, so relative paths in compose (`./loki-config.yaml`) resolve to non-existent host paths and Docker silently creates empty stub dirs. Fix: use absolute host paths in any compose file that bind-mounts repo-resident files.

## Stack customization primitives — canonicalized 2026-05-01

When a stack needs something the upstream image doesn't provide, three primitives are now blessed in this repo. Pick based on the *nature* of the customization:

| Primitive | When to use | Examples |
|---|---|---|
| **Init container** in same compose, using shared `init-tools:local` image | One-time setup step that produces an artifact before the main service starts; the tool isn't needed during runtime | Backrest envsubst (`backup/`, `kangaroo/backrest/`) — renders `config.json` from template + `RESTIC_REPO_PASSWORD`. Plex Preferences merge (`plex/`) — overlays enforced identity attrs onto the existing `Preferences.xml` |
| **Custom Dockerfile + Komodo build** (`run_build = true` + `auto_pull = false` in stack.toml) | The main service needs the customization AT RUNTIME (different binary, missing runtime tool, upstream bug fix) | komodo-op arm64 build (`onepassword/komodo-op.Dockerfile`) — upstream ships a mislabeled arm64 manifest that's actually amd64 |
| **`komodo-start` host render** | True bootstrap concerns that genuinely have to happen on the host before any container can read them | Komodo Core itself, chicken-and-egg credentials, multi-line OAuth blobs (`backup/rclone.conf.tmpl` → `/etc/komodo/rclone/rclone.conf` — Komodo's env-file pipeline truncates at `\n`) |

**Init container tooling: shared `init-tools:local` image.** All init containers across the fleet use the same locally-built image declared at `init-tools/Dockerfile` (alpine + gettext + python3). Each consumer stack triggers the build inline via its init service's `build:` directive (cached after first build per Periphery). Add new tools to `init-tools/Dockerfile` as more init containers come online; the layer cache keeps rebuilds cheap. Init service uses `pull_policy: never` so Komodo's auto_pull doesn't try to fetch the local-only tag. Stack.toml has `run_build = true` so Komodo runs `docker compose build` before `up`; auto_pull stays default-true so the main service still pulls upstream image updates.

**Why init container is preferred over custom Dockerfile when both could work:** no derivative MAIN-SERVICE image to rebuild on every upstream update (Plex updates weekly, Backrest seasonally), tool isn't carried in the running container's runtime footprint, docker-native expression of "do X then start the real service", and a per-container restart-on-crash for the main service doesn't re-run init (init only runs when compose recreates, which is what you want).

**Why custom Dockerfile is right for komodo-op:** the customization (correct arm64 binary) IS what the container runs continuously. There's no "setup then run" — the custom thing IS the main service.

**komodo-start is now narrower:** as of the 2026-05-01 cleanup it boots Komodo Core, seeds the 7 chicken-and-egg variables, renders just `rclone.conf`, and triggers the first ResourceSync. The Backrest config.json render and Plex Preferences merge moved to per-stack init containers.

## Known gotcha: Komodo variable seeding for non-secret variables — FIXED 2026-04-14

**Problem:** `komodo/sync/variables.toml` declares `TZ` and `MEDIA_DIR` as `[[variable]]` entries, and Komodo's ResourceSync *reads* them as remote content — they're visible in the `remote_contents` field of `GetResourceSync`. But the sync never materialized them as live Komodo Variables: `variable_updates` in the sync result stayed empty. Stacks that reference `[[TZ]]` or `[[MEDIA_DIR]]` in their `stack.toml` environment blocks got literal unresolved `[[TZ]]` written into their `.env` files on redeploy.

**How it manifested:** At original-deploy time the variables existed (manually seeded once, long ago), so each stack's `.env` was populated correctly and the running containers all got `TZ=Australia/Perth`. Later the variables were cleared (cause unknown). Subsequent `./komodo-sync` runs rewrote the `.env` files with `TZ=[[TZ]]` literal, but docker-compose didn't recreate containers when the spec hadn't changed, so the divergence was invisible until a real redeploy. Audit 2026-04-14 found `logging`, `uptime-kuma`, and `backup` in this state.

**Fix (landed in commit `336b961`):** `komodo-start` now calls `seed_variable` for `TZ=Australia/Perth` and `MEDIA_DIR=/mnt/pouch` the same way it seeds the 1P credentials. `variables.toml` stays around as a declarative reference but is no longer the authoritative source. `seed_variable` grew an `is_secret` parameter (default `true` to preserve existing behavior; TZ and MEDIA_DIR pass `false`). Affected stacks were redeployed via Komodo API to rewrite their `.env` files with correct interpolation — no container recreation was needed because the compose specs hadn't changed and the running containers already had the correct env vars from the original deploys.

**Flood was also backfilled:** `flood/stack.toml` now references `TZ=[[TZ]]` and `flood/compose.yaml` sets `TZ: ${TZ}` in the environment block. Flood previously had no TZ env var set at all.

**Key design decisions (all embedded in the above artifacts):**

- **Reversible ETL.** Non-destructive against the OneNote export; every upload tracked in the sidecar; `paperless-wipe --batch` can undo any batch cleanly (soft-delete → Paperless Trash for 30 days).
- **Page-level canonicalization via sha256 fingerprint.** Each page's fingerprint = sha256(sorted kept-asset-shas). Two pages with identical kept content = same fingerprint = one canonical. 528/1060 canonical = 50% N-plication rate (Evernote→OneNote tag-became-section duplication).
- **Asset-level dedup across canonical groups.** When two canonical pages reference the same asset (e.g., the same PDF on two pages that have different kept md bodies), one Paperless doc backs both pages. Sidecar's `uploads` table has multiple rows pointing at the same `paperless_doc_id`. Paperless's own checksum conflict detection is a safety net — the import script catches 400-duplicate errors and records the existing doc.
- **Classifier-friendly defaults.** All content tags MATCH_AUTO so Paperless's ML classifier trains on the imported corpus. Over time, user corrections improve predictions for new scanner/email docs. `unknown` is the only MATCH_NONE content tag (it's a fallback bucket, not a concept).
- **Timestamps: `created` yes (from PDF or page frontmatter), `modified` never.** Rationale above.
- **Flat hyphenated lowercase tag namespace.** No `section:` or `notebook:` prefixes. Multi-word tags always hyphenated. Enforced by two global rules in the curation yaml.
- **Cross-linking via Paperless's native `documentlink` custom field type** — bidirectional links auto-populated by Paperless. Primary = highest-priority kind in each group (md_body > pdf > other_attachment > image > contact_sheet).
- **Archive handling = one-shot migration-time extraction.** Not future-proofed. If future zips need Paperless consumption (scanner/email with attached zip), build a watcher sidecar stack; `paperless-extract-zips.py` has the extraction logic that would run continuously.
- **Lossless contact-sheet PDFs** for image-group zips. `img2pdf` with explicit `FitMode.into` page layout preserves PNG FlateDecode + JPEG DCT. Extract originals with `pdfimages -all -png contact.pdf out/`.
- **`unknown` fallback bucket** captures any canonical page with zero other tags. 16 pages currently — manual review in Paperless UI.

### Phase 15a/16 — done 2026-05-01



**Goal:** add the QNAP NAS (`kangaroo`, 10.0.0.25, AMD GX-420MC, 16 GB RAM, QTS 5.2.9.3451 + Container Station, ext4) as a second managed server in the existing Komodo Core (running on bilby). Once landed, any stack with `server = "kangaroo"` in its `stack.toml` deploys to the QNAP transparently — first use case is Phase 16's Syncthing relocation. Designed so that pinelake (third host, future) drops in via the same pattern with no further architectural work.

**Design decisions (locked 2026-05-01):**

- **One monorepo, two operating models per Periphery host.** Bilby stays on `files_on_host = true` with the repo bind-mounted into its Periphery (active dev workflow — save and deploy, no commit roundtrip). Kangaroo and any future deploy-target host (pinelake) use Komodo's first-class `Repo` ("Linked Repo") resource: Komodo Core declares the git remote, each remote Periphery clones it into its own Komodo-managed working directory, every kangaroo-targeted stack references the Repo by name + relative path. Source of truth is unambiguously the git remote; no `kangaroo-sync` cron needed; webhook auto-deploy is available if we want it.
- **Auth model: stage 15a → 15b.** Phase 15a brings kangaroo up on the existing legacy `KOMODO_PASSKEY` shared-secret model (same as bilby today). Phase 15b is a separate, focused change that migrates *both* Peripheries to v2 noise-handshake / keypair auth. Splitting them keeps blast radius small — if the new server has a problem in 15a, we know it isn't an auth-model issue; if 15b's v2 cutover has a problem, we know it isn't a kangaroo-bring-up issue. Decided after research surfaced that v2 onboarding is more involved than expected (Periphery autogens a keypair, pubkey has to flow back into Core's per-Server config, docs are unclear on whether passkey + v2 can coexist on a single Periphery during cutover).
- **Repo layout: keep flat.** `syncthing/compose.yaml` + `syncthing/stack.toml` with `server = "kangaroo"`, sitting next to bilby-targeted stacks. ResourceSync doesn't care about subdirectories per server, the `server` field already pins targeting, and the natural pattern scales identically when pinelake joins. The one exception is `kangaroo/periphery/` itself — its compose lives on kangaroo before kangaroo is registered with Komodo, so it can't be a Komodo-managed stack and gets its own `kangaroo/` subdirectory as scaffolding.
- **No kangaroo UI touches at any point.** Periphery deploys via SSH + `docker compose up -d` against the QNAP host's Docker daemon directly — the Container Station REST API doesn't accept arbitrary compose YAML (only built-in templates by name) and the GUI flow blocks `docker.sock` mounts that Periphery needs. Container Station won't list Periphery as one of its tracked Applications; that's a deliberate tradeoff for a fully-scriptable bootstrap. Survival across CS/QTS upgrades is handled by three independent layers below.
- **CS-upgrade survival: three layers, no GUI.** (1) `@reboot` line in `/etc/config/crontab` (QTS-persistent across both CS and firmware upgrades) waits for Docker to come up then runs `docker compose up -d` from the saved compose location. (2) `restart: unless-stopped` on the Periphery container itself catches everything else. (3) Gatus monitor on `:8120` (or kangaroo's Periphery health endpoint) alerts within minutes if both fail. (1) is the active recovery, (2) is free belt-and-braces, (3) is the alarm. None require touching the QTS or CS GUI.
- **Linked Repo via HTTPS + GitHub PAT.** Komodo doesn't support SSH cloning (`RepoConfig` docs: *"Komodo does not currently support cloning repos via ssh"*) — only HTTPS with a token-bearing `git_provider` account. We reuse the existing fine-grained PAT at `op://Homelab/Homelab GitHub Personal Access Token/token` (created during Phase 14 work, scoped to all user-owned repos with Contents Write — strict superset of what Komodo's Linked Repo needs). Configured Core-side as a `[[git_provider]]` so all Linked Repos share it.
- **kangaroo has its own Backrest stack.** Mirrors the bilby pattern: `kangaroo/backrest/compose.yaml` + `kangaroo/backrest/config.json.tmpl` (Komodo-targeted with `server = "kangaroo"`), restic-backing-up to the same `/mnt/pouch/backups` repo on kangaroo's own filesystem (no NFS roundtrip from inside the container). Two restic clients on one repo is supported (per-operation locking). Same OneDrive sync target. The bilby Backrest stays exactly as-is — we don't try to NFS-mount kangaroo state onto bilby and reuse the existing instance, because that couples backup runtime to NFS health and inherits the Jump squash pain.

**Resolved by parallel research dispatch (2026-05-01):**

Onboarding is config-file-driven, not interactive UI exchange — Periphery either trusts Core on first contact (inbound mode) or uses an `onboarding_key` from Server settings UI (outbound mode). Stacks reference via `linked_repo = "<repo-name>"` + `run_directory` (relative path inside repo) + `file_paths = ["compose.yaml"]`, with `files_on_host = false`.

## Deferred (non-blocking follow-ups)

- **NFS bind-mount auto-recovery** — bilby-local Docker stacks bind-mount NFS paths (`/mnt/pouch` for plex media/BIFs, paperless docs, flood torrents; `/mnt/jump` for Victoria Logs + restic repo).
